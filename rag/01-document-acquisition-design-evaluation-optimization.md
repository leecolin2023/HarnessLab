# RAG 文档采集：如何设计、评测与持续优化？

> 本文是 RAG 工程流程的第一篇专题文章。以 Job-RAG 招聘岗位知识库为例，从业务需求出发，理解文档采集为什么必要、什么才算采集成功、如何评价采集质量，以及如何利用 AI 持续改进采集系统。
>
> 本文重点讨论采集方案的设计与评价，不展开爬虫代码实现。文档解析、切分、索引和检索将在后续专题中分别讨论。

## 一、为什么需要文档采集？直接把资料交给 AI 不行吗？

### 1. 我们究竟需要解决什么问题？

假设我们想研究 AI 就业市场，了解哪些岗位要求 RAG、Agent、模型部署等技术。

最简单的方法是什么？

打开招聘网站，搜索 RAG，找到相关岗位，复制岗位职责和任职要求，然后交给大模型分析。

例如：

> 请根据以下 20 条招聘 JD，统计企业最常要求的 RAG 相关技术。

如果只需要分析这 20 条 JD，而且资料已经完整提供，那么完全可以直接使用大模型，没有必要专门建设采集系统。

但假设我们的目标发生变化：

> 我希望长期研究 AI 岗位市场。每隔一段时间，都能分析不同企业的技术要求、岗位数量和变化趋势。

此时会遇到新的问题：

- 今天搜索到的岗位，下次还能找到吗？
- 新发布的岗位怎样进入知识库？
- 原有岗位的任职要求发生变化，能否识别？
- 同一个岗位被多个关键词搜索到，如何避免重复？
- 采集失败的岗位，如何补齐？
- 岗位从搜索结果中消失，是否意味着停止招聘？
- 我们统计的是整个招聘市场，还是仅仅搜索到的一小部分岗位？

这些问题已经不是让大模型阅读一次资料就能够解决的。

我们需要一个能够**持续获得、保存和更新外部资料**的过程。这就是文档采集（Document Ingestion / Data Acquisition）需要解决的问题。

### 2. 文档采集究竟在做什么？

文档采集可以理解为：

**根据明确的数据需求，从允许访问的来源中取得资料，同时保留其身份、来源、时间和获取状态，使后续系统能够可靠地使用这些资料。**

例如：

~~~text
招聘网站、API、文件、数据库
              ↓
        发现候选资料
              ↓
         获取原始内容
              ↓
      记录身份、来源和时间
              ↓
       检查获取是否成功
              ↓
         保存原始资料
              ↓
     交给文档解析等后续环节
~~~

采集的目的，不是尽可能多地下载文件，而是建立一个能够回答以下问题的资料集合：

- 我们需要哪些资料？
- 已经获得哪些资料？
- 哪些资料仍然缺失？
- 获得的资料是什么版本？
- 资料来自哪里，是否允许使用？
- 这些资料是否需要继续更新？

### 3. 为什么不能直接将采集和文档解析合并？

先区分两个问题：

**文档采集：我们有没有获得需要的资料？**

**文档解析：已经获得的资料，能否转换成可供后续处理的内容？**

假设我们需要一份企业招聘 JD。

采集阶段可能负责获取：招聘页面、招聘平台提供的结构化记录、可访问的原始文件，以及来源 URL、岗位 ID 和采集时间。

解析阶段才进一步处理：从网页中识别职位描述、识别岗位职责和任职要求、从 PDF 中提取文字、识别表格标题章节、将内容转换为统一结构。

现实中两个步骤可以由同一个程序连续执行，但在设计和评测时仍应区分。

否则发现某份岗位没有正文时，无法判断究竟是没有获得完整页面，还是获得了页面但解析程序没有正确提取正文。

**区分责任边界是为了独立判断质量、定位问题和优化系统，而不是要求必须开发两套服务。**

### 4. 什么时候不需要专门建设采集系统？

| 业务情况 | 更合适的做法 |
|---|---|
| 只分析用户已经上传的几份文件 | 直接读取文件 |
| 偶尔研究几十条招聘 JD | 手工收集或导出 |
| 定期分析同一批资料 | 建立文件导入与版本管理 |
| 持续跟踪新增、修改和删除 | 建立增量采集与状态同步 |
| 多个来源、长期更新、需要审计 | 建立统一的采集流程 |

**是否需要独立采集系统，取决于资料是否需要反复获得、持续更新，以及是否需要证明获得的数据足够完整和可信。**

## 二、怎样定义一个好的文档采集方案？

### 1. 什么叫“采集得好”？

常见采集结果汇报可能是：

> 本次成功采集 10,000 份文档，成功率 99%。

但这无法直接说明质量很好：

1. 目标范围内原本应该有多少文档？
2. 10,000 份是否有大量重复？
3. 获得的是不是需要的完整内容？
4. 文档是否已经过期？

如果目标范围里有 20,000 份文档，只采到 10,000 份，采集数量再大也不能说明覆盖充分。

因此：

> **好的文档采集方案，是指它能够在明确的数据范围和合法访问条件下，以可接受的成本，持续获得业务需要的资料，并能证明数据的覆盖范围、完整性、来源和更新状态。**

### 2. 第一层：范围覆盖——需要的资料有没有采到？

假设目标是：

> 广州地区要求 RAG 相关技术的 AI 工程岗位。

至少有三个不同的范围：

- **A：** 某招聘平台中包含 RAG 字符串的岗位。
- **B：** 该平台所有职责实际涉及 RAG 工程的岗位。
- **C：** 整个广州招聘市场中职责涉及 RAG 的岗位。

如果只搜索“RAG”，可能漏掉：

> 负责企业知识库建设，包括文档解析、向量检索、重排及智能问答服务。

这份 JD 没有直接写 RAG，却与 RAG 工程相关。

因此对于范围 B，单一关键词可能覆盖不足；对于范围 C，即使覆盖某个平台全部相关岗位，也不能认为覆盖整个市场。

**必须先定义采集范围，才能讨论覆盖率。**

### 3. 第二层：内容完整——找到资料等于获得资料吗？

搜索结果可能只有：

~~~text
岗位：AI 平台工程师
公司：某科技公司
薪资：25–40K
地点：广州
~~~

如果只研究薪资，这些字段可能足够。但如果要分析技术要求，必须取得职责和任职条件。

| 状态 | 实际含义 |
|---|---|
| 已发现 | 知道资料存在 |
| 已获取 | 已取得允许访问的原始内容 |
| 内容不完整 | 缺少业务必需信息 |
| 内容完整 | 已获得满足当前任务要求的内容 |
| 待核验 | 无法确认内容是否满足要求 |

“内容完整”不是网页里的所有文字一字不漏，而是**业务所需信息是否完整**。广告、导航和评论未必需要；职责、要求及限定词不能遗漏。

### 4. 第三层：来源可信——能证明资料来自哪里吗？

如果 AI 告诉我们某岗位要求三年以上 vLLM 生产部署经验，用户可能追问来自哪个页面、何时采集。

因此采集记录至少考虑：

| 信息 | 作用 |
|---|---|
| source | 资料来源 |
| source_document_id | 来源系统的唯一 ID |
| source_url | 原始地址 |
| fetched_at | 系统取得资料的时间 |
| source_updated_at | 来源声明的更新时间（如可获得） |
| content_hash | 比较内容变化 |
| acquisition_status | 获取状态与失败原因 |
| access_scope | 访问权限或使用范围 |

来源与原始记录 ID 共同决定身份。文件名、CSV 行号、搜索排名不能直接当作稳定身份。

**采集时间不等于发布时间，也不等于最后核验有效性的时间。**

### 5. 第四层：持续更新——今天采到，明天还能信吗？

企业可能把“有 RAG 项目经验者优先”改成“必须具备 RAG 项目落地经验”。

如果知识库仍保留旧版，就可能产生错误判断。

采集需要管理新增、修改、重复出现、暂时不可访问、明确删除或停止发布等状态。

网络异常、权限限制、页面变更和岗位真正关闭不能随意合并。

**无法访问不等于已经删除；搜索结果中消失也不等于岗位停止招聘。**

### 6. 功能边界怎样定义？

在让 AI 实现前，先确定输入输出契约。

**输入：** 数据来源、目标范围、允许的访问方式、必需字段、更新策略、权限和频率约束。

**输出：** 原始资料、来源信息、唯一身份、内容版本/指纹、获取状态、失败与缺失记录、运行报告。

**必须满足：**

1. 采集失败不能伪装成成功。
2. 重复运行不能无故产生重复的同源记录。
3. 内容变化不能悄悄覆盖历史而无法追溯。
4. 来源不可访问不能自动解释为资料已删除。
5. 无权限的内容不能因技术上能够访问就被采集和传播。
6. 未经验证的内容不能被标记为已核实。

这些要求与使用 Python、浏览器自动化、API 或 Agent 没有直接关系，定义的是**功能行为**。

## 三、文档采集有哪些候选方案？应该怎样选择？

### 1. 方案 A：人工收集与文件导入

例如手工下载 PDF、导出 CSV/Excel，整理后批量导入。

对于资料少、更新不频繁的场景，它简单、容易确认来源。但随着规模扩大，会出现重复操作、漏采、难追踪修改、格式不一致等问题。

关键问题是：**人工维护成本和漏采风险，是否超过自动化建设成本？**

不需要因为 AI 会写爬虫就立即放弃人工导入。

### 2. 方案 B：官方 API 或数据连接器

如果资料系统提供授权 API，可直接获取文档 ID、内容、修改时间、文件类型、权限、删除事件等。

它可能比网页抓取稳定，但仍需检查：

- API 是否包含必需字段；
- 是否存在分页或结果上限；
- 是否提供历史和删除状态；
- 额度与授权范围；
- 来源数据延迟。

**API 返回成功，不等于数据覆盖完整。** 如每次最多 100 条而未正确分页，仍会漏采。

### 3. 方案 C：网页采集

招聘与资讯网站可能没有适合当前用途的公开 API。在来源授权和访问政策允许时，可以考虑网页采集。

至少涉及两个任务：

1. **发现页面：** 根据关键词、分类、地区和时间找到候选 URL。
2. **获取页面：** 读取已发现页面的详情内容。

搜索页显示 200 条，不代表取得了 200 份完整 JD；打开 200 个详情页，也不能证明目标范围只有这些岗位。

需要注意动态加载、分页、排序上限、跨关键词重复、结构变化、限流和访问限制。

这些风险应在运行报告中体现，而不是隐藏在程序内部。

同时应遵守网站条款、robots 指令及适用的数据保护要求；robots.txt 是爬虫访问管理信号，不是全部数据使用行为的完整授权。

### 4. 方案 D：增量同步

如果资料已采过一次，是否要全量重新获取？

来源若提供修改时间或变更游标，可以优先同步增量：

~~~text
上次成功同步位置
         ↓
查询新增与修改
         ↓
获取变更内容
         ↓
比较既有版本
         ↓
写入新版本
         ↓
同步下游索引
~~~

但必须回答：**凭什么确信没有漏掉两次同步之间的修改？**

可能出现中断、时间戳精度不足、同一更新时间、分页顺序变化、来源延迟或部分成功。

因此需区分任务启动时间、发现的最新来源时间和**已成功持久化并验证的同步位置**。

可以采用重叠回扫、稳定身份去重和可重试写入；但来源不提供可靠变更信息时，不能仅靠本地时间戳保证绝不漏采。

### 5. 是否只能选一种方案？

不一定：

~~~text
人工上传文件 ──────┐
                  │
企业 API ─────────┤
                  ├── 统一采集记录与状态
网页来源 ─────────┤          ↓
                  │     原始资料与版本
数据库同步 ───────┘          ↓
                      文档解析
~~~

不同来源不必使用同一种采集技术，但**最终应提供统一的身份、来源、版本和状态信息**，以便后续解析、切分、检索复用。

## 四、怎样建立文档采集的评测体系？

### 1. 为什么不能只统计采集数量？

A 采集 1,000 条，B 采集 800 条，无法判断哪个更好。

A 可能包含 400 条重复，B 可能覆盖更多不同真实岗位；或者二者来源范围根本不同。

**采集数量是运行结果，不是质量结论。**

### 2. 怎样评价范围覆盖？

先建立独立核验的参考集合。

例如人工核对 5 个搜索结果页，实际展示了 200 条符合范围的唯一岗位，系统采到其中 180 条：

~~~text
参考集合覆盖率 = 180 / 200 = 90%
~~~

这只证明覆盖了这 5 个已核验页面中的 90%，不能宣称覆盖整个平台 90% 的 RAG 岗位。

**覆盖率必须绑定明确参考范围和观测时间。**

如果来源没有完整清单，就通过抽样审计、已知集合或多来源对照估计覆盖缺口，不要编造全市场覆盖率。

### 3. 怎样评价内容完整性？

已发现 100 条岗位，95 条取得完整 JD，3 条只有标题薪资，2 条详情失败。

针对技术要求分析，完整正文获取率为：

~~~text
完整正文获取率 = 95 / 100 = 95%
~~~

前提是已经定义“完整正文”：

- 职责是否存在；
- 任职要求是否存在；
- 限制条件是否保留；
- 正文有没有截断；
- 正文是否匹配岗位 ID。

复杂或异常样本仍需回看来源。

### 4. 怎样评价重复数据？

~~~text
关键词 RAG       → 岗位 A、B
关键词 Agent     → 岗位 A、C
关键词 LangChain → 岗位 A、D
~~~

共有 6 次岗位出现记录，但只有 4 个不同岗位 ID。

需要区分：

- **发现次数**：岗位在结果中出现多少次；
- **唯一来源岗位数**：按来源与 ID 去重；
- **疑似跨来源重复**：不同 ID 可能指向同一职位。

前两者可根据稳定身份计算；第三者需要更谨慎的人工核验。

不能因为公司和标题相同就武断合并。

重复治理不只减少数量，还要防止误删真实岗位。

### 5. 怎样评价更新质量？

假设旧版“RAG 经验优先”改成新版“必须具备 RAG 落地经验”。

合格的更新流程应：

1. 识别同一来源岗位；
2. 检测正文变化；
3. 保存新版本；
4. 保留必要的历史与来源；
5. 通知下游索引更新；
6. 避免旧索引冒充当前内容。

还需测试内容没变时是否无意义更新、仅时间变化是否错误重建、更新失败后的行为、删除状态的证据、重复处理是否产生重复版本。

### 6. 应关注哪些指标？

| 质量层次 | 主要指标 | 回答的问题 |
|---|---|---|
| 范围覆盖 | 参考集合覆盖率、漏采数量 | 应采集的资料是否获得 |
| 内容完整 | 正文获取率、字段完整率 | 业务信息是否充足 |
| 数据身份 | 唯一记录数、误合并率、漏去重率 | 是否重复或错误合并 |
| 更新质量 | 变更发现率、同步延迟、错误状态率 | 是否正确反映变化 |
| 可追溯性 | 来源字段完整率、版本可复原率 | 能否核实来源 |
| 运行成本 | 请求次数、耗时、资源、重试 | 是否经济可靠 |

指标要配合具体失败案例。正文获取率下降可能是访问失败，也可能是页面格式变化；数字本身无法定位根因。

## 五、怎样理解采集实验结果？

### 1. 规模增加是否说明方案更好？

新增 10 个关键词，岗位从 500 增加到 800，并不等于覆盖能力提高 60%。

新增结果可能是漏掉的目标岗位、无关岗位、重复、过期岗位或扩大范围后的其他技术岗位。

要看：**新增的记录中有多少真正属于目标范围，并提供此前没有的有效信息？**

### 2. 更多关键词是否更全面？

例如搜索 RAG、LangChain、向量检索、文档解析、知识库、Agent。

继续扩词常出现边际收益下降：

~~~text
第一个关键词：发现很多新岗位
第二个关键词：补充部分岗位
第三个关键词：继续补充
第四个关键词：大量重复
第五个关键词：可能只带来少量新岗位
~~~

应该测量新增关键词带来的相关唯一岗位及额外成本，特别是是否补足此前缺失的类别。

扩词可以由 AI 提出，但必须通过采集结果验证。

### 3. 为什么不能把“没有抓到”当成“已经不存在”？

昨日能打开，今日返回 403，不能证明岗位已经关闭。

同理：

- 超时不等于删除；
- 验证码不等于删除；
- 搜索页找不到不等于删除；
- 页面跳转不一定代表招聘关闭。

应区分已采集、待补采、暂时失败、待核验和有证据明确失效等状态。

**资料采集状态与招聘业务状态不是一回事。**

### 4. 为什么关注最终业务效果？

新增 30% 岗位，但多为无关岗位，不一定改善用户查询；新增 20 条关键的模型服务和 RAG 工程岗位，反而可能大幅改善特定求职研究任务。

因此要回到：**新增资料是否让系统回答更多真实问题，或使答案更加完整、准确、及时？**

但采集只对资料获取负责，最终问答还会受到解析、切分、检索和语义判断影响，不能把所有质量变化归因于采集。

## 六、发现采集问题后，应该怎样定位原因？

### 1. “没有某岗位”可能来自哪些环节？

~~~text
目标岗位
   ↓
候选发现
   ↓
详情获取
   ↓
原始资料保存
   ↓
文档解析
   ↓
数据入库
   ↓
建立检索索引
   ↓
用户查询
~~~

任何一环失败，都可能表现为“搜不到岗位”。

### 2. 怎样沿链条定位？

**第一步：是否进入发现结果？**

没有则检查关键词、来源覆盖、过滤条件、分页、动态加载与结果上限。

**第二步：详情是否成功获取？**

有 ID/URL 没正文，则检查详情请求、内容权限、访问限制及失败记录。

**第三步：原始资料是否保存？**

取得详情但没保存，可能是校验、写入、身份冲突或任务中断。

**第四步：已保存内容是否进入下游？**

原始资料存在但知识库搜不到，应继续检查解析、入库、索引或检索，此时不能再简单归因于采集。

### 3. 常见失败如何对应优化方向？

| 失败现象 | 优先调查 | 可能改进 |
|---|---|---|
| 某类岗位长期缺失 | 发现策略 | 来源、关键词或类别 |
| 搜索页有记录但采不到 | 分页与加载 | 加载与数量核对 |
| 有 URL 但正文为空 | 详情获取 | 失败分类、合规补采 |
| 同一岗位多次出现 | 身份与去重 | 稳定来源 ID |
| 原文修改后仍是旧版 | 更新同步 | 版本比较、回扫 |
| 一次失败导致历史岗位消失 | 状态管理 | 区分缺失与明确删除 |
| 不同岗位被错误合并 | 去重逻辑 | 降低自动合并、复核 |
| 原始资料存在但搜不到 | 下游处理 | 解析、索引和检索 |

**先找到第一个发生异常的环节，再针对性优化。**

### 4. 怎样把失败案例变成长期资产？

~~~text
问题：
某个 RAG 工程岗位没有进入知识库。

预期：
目标搜索范围中应包含该岗位。

实际：
采集结果中没有该岗位 ID。

调查：
1. 招聘详情在授权范围内可获取。
2. 原搜索关键词未发现该岗位。
3. 岗位使用“知识库建设”，没有写 RAG。

判断：
候选发现策略覆盖不足。

改进假设：
补充“知识库建设”相关查询表达。

验证：
比较新增目标岗位数、重复率和成本。
~~~

验证后把该问题加入回归测试。积累的是失败类型、测试案例和优化历史，不只是代码。

## 七、怎样让 AI 持续优化文档采集？

### 1. 哪些工作适合 AI？

AI 可以帮助提出资料来源、扩展关键词、编写合规适配器、比较数据、检查缺失字段、识别疑似重复、分析日志、生成报告、提出优化假设。

但采集涉及外部权限，不能为提高成功率未经授权绕过登录、验证码或访问限制。应优先选合规来源、降低访问频率、或将内容列为待补采。

**目标是可靠获得有权使用的数据，不是突破所有访问障碍。**

### 2. 怎样建立优化循环？

**第一步：定义范围。** 如指定平台广州地区 RAG、Agent、模型部署相关岗位，明确不代表整个市场。

**第二步：冻结基线。** 保存岗位清单、参考集合、来源与状态、未取得正文的记录、版本和策略。

**第三步：运行采集并形成报告。** 记录新发现、详情成功、重复、缺失、失败、更新及状态变化。

**第四步：分析根因。** 区分范围漏采、详情失败、保存失败和下游问题。

**第五步：提出可验证假设。** 如增加“推理服务”“模型托管”来补足模型部署岗位。

**第六步：对照新旧方案。** 比较新增相关岗位、已知漏采补齐、无关与重复、成本和访问合规性。

通过验证后才更新正式策略。

### 3. 为什么要保存运行记录？

“本次更新成功”不足以支持后续分析。

需要知道来源和范围、发现与成功保存数量、失败列表、内容变化、状态不确定项，以及进度是否经过持久化验证。

**一次任务结束不意味着本轮目标资料全部同步成功。** 只有达成预定发现、获取、保存和验证条件，才能确认相应同步进度。

### 4. 负责人真正需要掌握什么？

不必亲自掌握每种请求库、下载器或同步脚本，而要能够回答：

- 为什么需要这些资料？
- 采集范围是否清楚？
- 结果有没有遗漏？
- 数据能不能核实？
- 来源更新后如何保持一致？
- 失败能否恢复？
- AI 提出的改进是否提升业务价值？

这是从“写采集程序”转向“管理可靠数据获取能力”。

## 八、Job-RAG 实践：当前采集体系有什么问题，下一步如何优化？

### 1. 当前数据来自哪里？

根据 [Job-RAG 数据说明](https://github.com/leecolin2023/job-rag/blob/main/data/README.md)，项目使用预先整理的招聘 CSV 作为输入。

当前初始快照包含：

- **593 个唯一岗位 ID**；
- **592 条非空岗位描述**；
- **1 条没有实际岗位描述**。

保留岗位名称、公司、地点、薪资、正文、URL、采集时间、关键词等字段。

**593 是整理后的来源岗位 ID 数量，不是市场岗位总数。** 592 条非空正文也不代表已经逐字人工核对。

### 2. 当前采集链条是什么？

~~~text
外部招聘信息采集
        ↓
岗位搜索结果与详情获取
        ↓
数据清洗、规整与去重
        ↓
标准化 jobs.csv
        ↓
Job-RAG 导入与版本管理
        ↓
文档解析、切分与索引
        ↓
岗位检索和技术分析
~~~

Job-RAG 主要负责接收整理后的 CSV 并管理导入、版本、索引和查询，不等于已经建成完整的在线招聘网站自动采集系统。

**外部采集质量与 Job-RAG 的数据导入质量是两回事。**

### 3. 第一问题：采集范围是否明确？

过去使用过 Agent、RAG、LangChain、LangGraph、MCP、模型服务、文档解析、向量检索、Rerank 等关键词。

关键词可以帮助发现岗位，但不等于完整 AI 岗位市场。

例如“负责模型部署”的职位可能使用推理服务、模型服务平台、私有化部署、推理引擎、模型托管等表达。

关键词越多，也可能带来更多重复和无关结果。

下一轮应先确定 Job-RAG 要研究哪些类别的 AI 工程岗位、各类别通过什么来源和策略发现，再建立覆盖审计。

### 4. 第二问题：如何判断动态加载有没有漏采？

假设页面实际加载 239 条岗位卡片，但程序只读取前 50 条。程序返回了 50 条正确结构、没有报错，却明显遗漏。

因此需要区分：

- 页面实际已加载多少条；
- 程序读取多少条；
- 有多少唯一岗位 ID；
- 哪些字段缺失；
- 读取过程中页面是否变化。

~~~text
已加载页面记录覆盖率
= 成功读取的唯一目标记录数
  / 同一次页面快照中已核验的唯一目标记录数
~~~

分母只能是已核验页面快照，不能解释成整个平台覆盖率。

在授权条件下保存必要运行证据，如 ID 清单、分页位置、日志或允许保存的快照，区分页面未加载、读取遗漏和保存失败。

### 5. 第三问题：同一岗位被多个关键词发现怎么办？

使用来源岗位 ID 是合理起点。某 JD 同时通过 RAG、Agent、LangChain 被发现三次，不应在同一来源岗位表中计为三个职位。

但应保留发现关键词，因为：

**岗位 ID 用于识别身份，发现关键词用于分析采集过程。**

据此可分析关键词新增贡献、重复程度、类别缺口和边际收益。

不能把“通过 RAG 搜索发现”当成“岗位必须要求 RAG”的事实，仍需阅读 JD。

### 6. 第四问题：如何管理失败与状态？

当前 Job-RAG 已经区分获得描述、是否仍在招、最近观察和人工核验时间。

建议保留：

~~~text
来源岗位 ID
       ↓
最近一次成功取得的内容
       ↓
最近一次获取尝试及结果
       ↓
是否有更新
       ↓
当前招聘状态及核验依据
~~~

某岗位没出现在搜索结果，不能自动关闭；详情失败，也不能直接判为失效。

采集成功、内容更新、仍在招聘是三个不同事实。

### 7. 下一轮最值得做什么？

#### 第一优先级：建立采集质量基线

审计当前数据：来源 ID、URL、采集时间、空正文、同源重复、跨源疑似重复、已发现未获取的岗位。

先知道数据库有什么和缺什么，不需要立即重访所有招聘网站。

#### 第二优先级：建立已知岗位参考集合

从 RAG、Agent、模型服务等类别选择已知目标岗位，人工确认来源和相关性，检查当前发现策略能否找到。

比盲目扩展关键词更有价值。

#### 第三优先级：对关键词扩展做实验

例如：

~~~text
模型部署
推理服务
模型托管
vLLM
SGLang
MaaS
大模型私有化部署
~~~

每次对照新增唯一相关岗位、已知漏采补齐、无关比例、重复比例和成本。

不因某词听起来相关就永久加入采集规则。

#### 第四优先级：建立增量更新机制

稳定范围后考虑更新检测、失踪岗位处理、失败补采、幂等写入和可信同步进度。

优先使用正式增量接口或来源变更标记；来源不支持时设计回扫和核验。

不能仅依据任务结束时间确认完整同步。

#### 第五优先级：连接采集评测与业务评测

例如用户问：

> 统计职责或任职要求中出现 RAG 的岗位，它们还要求哪些技术？

采集改进可能补足原先遗漏的 JD，使统计基础更完整。但后续仍需条件识别、去重、统计与原文核验。

采集数量增加，不直接等于最终答案更准确。

### 8. 建议固定采集实验报告

| 报告项目 | 需要回答的问题 |
|---|---|
| 采集目标 | 补齐什么资料 |
| 来源范围 | 哪些来源、什么条件 |
| 基线数据 | 原有已核验记录 |
| 新增发现 | 新增不同目标记录 |
| 内容完整性 | 业务正文获取情况 |
| 失败情况 | 失败记录与原因 |
| 重复情况 | 重复发现与疑似重复 |
| 更新情况 | 既有记录的变化 |
| 业务价值 | 是否补齐真实缺口 |
| 最终决策 | 保留、修改或回退 |

例如：

~~~text
优化目标：
提高模型部署相关岗位覆盖。

当前问题：
部分 JD 没有直接出现“模型部署”，
但实际描述推理服务建设。

假设：
增加“推理服务”“模型托管”等表达，
能补齐当前缺失岗位。

实验：
保持来源范围和去重规则不变，
只调整发现关键词。

验证：
1. 新增相关岗位数；
2. 已知漏采补齐；
3. 无关岗位比例；
4. 重复比例；
5. 采集成本。

决策：
根据结果确定，不预先认定有效。
~~~

**从“增加更多关键词”，转向可验证的工程问题。**

## 结语：文档采集的核心不是获取更多资料

从“怎样把招聘 JD 采集到知识库”，可以进一步追问：

1. **需要哪些资料？** 范围不清，数量不能证明充分。
2. **怎样证明获得所需资料？** 不能用运行成功代替覆盖与完整。
3. **怎样保证来源和版本可信？** 保留身份、时间、状态和历史。
4. **发现漏采如何定位？** 区分发现、获取、保存与后续处理。
5. **怎样用 AI 持续改善？** 基于失败提出假设，对照验证收益。

这些方法也适用于银行制度、合同、技术文档、企业知识库和长期更新的资讯。

AI 时代，工程师不必亲自实现每一种采集工具，但必须定义需求、评价质量、识别盲区并指导持续改进。

> **文档采集真正的目标，不是尽可能多地获取数据，而是为后续知识处理建立一个范围明确、来源可信、内容完整、可持续更新的资料基础。**

只有知道知识库获得了什么、遗漏了什么、依据是什么，后续解析、切分、检索和生成的质量评测才有可靠起点。
