# RAG Embedding 与索引：如何设计、评测与持续优化？

> 本文是 RAG 工程流程的第四篇专题文章，承接《03 · RAG 文档切分》，后续衔接《05 · RAG 检索》。
>
> 本文以 Job-RAG 招聘岗位知识库为主要案例，重点讨论：什么时候需要 Embedding、什么样的向量和索引才算好、怎样建立对照实验、如何判断模型与索引的真实收益，以及如何利用 AI 持续优化。
>
> 本文不以学习某个 Embedding API、向量数据库或 HNSW 算法的代码实现为目标，而是建立能够指导模型选型、索引设计、实验验证与工程决策的能力。

## 一、为什么需要 Embedding 与索引？直接搜索原文不行吗？

### 1. 我们真正想解决什么问题？

假设 Job-RAG 已经采集、解析并切分了数百份招聘 JD。

用户提出一个问题：

> 帮我找到真正负责企业 RAG 知识库建设的工程岗位。

最简单的方法是什么？

可以直接在全部 JD 中搜索字符串 `RAG`。

例如：

~~~text
用户问题
   ↓
在岗位 JD 中搜索 RAG
   ↓
返回包含 RAG 的岗位
~~~

对于某些问题，这样做完全有效。

例如：

> 统计所有在岗位职责中明确出现字符串 vLLM 的岗位。

如果用户明确要求字面匹配，就不一定需要 Embedding。

但换一个问题：

> 哪些岗位负责企业知识库的文档接入、索引建设、检索增强问答和工程落地？

一份真实相关的 JD 可能写着：

> 负责内部知识管理平台建设，包括文档解析、检索服务、知识检索 API 及智能问答功能开发。

它没有出现 `RAG` 这个字符串，但描述的工作可能与 RAG 工程高度相关。

这时，单纯搜索 `RAG` 就可能漏掉它。

我们需要解决的新问题是：

**用户和资料使用不同的文字表达时，怎样仍然找到可能相关的内容？**

### 2. Embedding 究竟解决什么问题？

Embedding（向量表示）是一种使用模型将文本映射为数字向量的方法。

例如：

~~~text
用户问题：
“负责企业 RAG 知识库建设”
             ↓
       Embedding 模型
             ↓
        查询向量 q
~~~

另一边：

~~~text
岗位职责：
“建设文档索引、语义检索和智能问答平台”
             ↓
       Embedding 模型
             ↓
        文档向量 d
~~~

模型通过训练，使某些语义相关的文字在向量空间中具有较接近的表示。

检索系统再根据向量之间的距离或相似度寻找候选。

例如常见的余弦相似度：

\[
\operatorname{cosine}(q,d)=
\frac{q\cdot d}{\|q\|\|d\|}
\]

公式本身并不是最重要的。

需要理解的是：

**Embedding 将部分文字相关性问题转换成了可以计算的向量相似度问题。**

不过，向量相似度只是一种检索信号，不代表模型已经完成岗位业务判断。

### 3. 为什么相似度高，不意味着岗位符合要求？

看两句话：

**JD A**

> 必须具备 vLLM 生产部署经验。

**JD B**

> 有 vLLM 生产部署经验者优先。

两句话高度相似。

它们都出现了：

- vLLM；
- 生产部署；
- 经验。

但对候选人的任职门槛明显不同。

再看两个岗位：

**JD C**

> 公司提供 RAG 知识库平台，岗位主要负责销售。

**JD D**

> 岗位负责企业 RAG 系统研发与检索优化。

虽然两份 JD 都与 RAG 相关，但真正负责 RAG 开发的是 D。

因此：

> **Embedding 的主要责任是帮助发现可能相关的证据，不是直接证明业务条件成立。**

“技术相关”“岗位职责相关”“满足任职要求”是需要区分的不同判断。

### 4. 为什么还需要索引？

假设现在只有 500 个岗位，每个岗位有几个 Chunk。

即使不建设专门的近似向量索引，也可能直接计算全部向量与问题的相似度。

但如果资料逐渐增长到几十万、几百万个 Chunk，每次查询都与全部向量比较，成本和延迟可能明显增加。

这时需要研究如何组织向量，减少检索所需的计算。

索引就是为了让系统能够更高效地找到候选。

这里需要明确三个概念：

| 概念 | 主要责任 |
|---|---|
| Embedding 模型 | 把文本转换成向量 |
| 向量存储 | 保存向量及其与原文的关联 |
| 向量检索索引 | 加速寻找相近向量 |

拥有向量数据库，并不意味着已经使用了近似最近邻索引。

即使向量保存在 PostgreSQL 中，也可以进行精确距离计算。

### 5. 什么时候不需要 Embedding？

不能因为是 RAG，就默认必须建立向量索引。

| 用户任务 | 首先考虑什么 |
|---|---|
| 查找明确出现 vLLM 的 JD | 字符串匹配、全文检索 |
| 查找与 RAG 工程语义接近的岗位 | BM25、Embedding 或组合检索 |
| 查询广州且薪资下限达到 20K 的岗位 | 结构化字段过滤 |
| 统计全库出现某技术的岗位数 | 完整枚举与确定性查询 |
| 统计真正将 RAG 列为必备条件的岗位 | 完整枚举、语义判断与证据核验 |
| 阅读一份已知 JD 的具体要求 | 直接读取全文 |

这意味着，Embedding 并不应该承担所有查询任务。

**第一条设计原则：先证明普通数据库查询和关键词检索不能充分满足业务需求，再决定 Embedding 能够补充什么能力。**

## 二、怎样定义一个好的 Embedding 与索引方案？

### 1. 什么叫“好的 Embedding 模型”？

最常见的模型比较方式，是看公开排行榜。

例如某个 Embedding 模型在 MTEB 上排名较高，就认为它更适合自己的业务。

公开基准有参考价值，但并不能直接证明模型适合 Job-RAG。

因为 Job-RAG 关注的不只是一般文字语义相似，还包括：

- 技术名称；
- 岗位职责；
- 任职条件；
- 工作能力深度；
- 不同技术之间的关系；
- 中文招聘表达；
- 具体来源证据。

例如：

> 熟悉模型 API 调用。

与：

> 负责 vLLM 推理服务生产部署。

两句话都涉及大模型应用，但所需能力深度不同。

因此，我建议这样定义：

> **好的 Embedding 模型，应该在目标业务语料和真实用户问题上，以可接受的成本，提高正确证据进入候选集合的机会，并且不显著增加关键错误。**

这才是模型选型的主要依据。

### 2. 第一层：模型输入输出是否正确？

首先定义 Embedding 服务的功能边界。

**输入：**

- 待编码文本；
- 输入角色，例如 query 或 document；
- 模型及版本；
- 必要的任务指令；
- 模型支持的长度、维度等参数。

**输出：**

- 对应输入文本的数值向量；
- 向量维度；
- 调用状态；
- 必要的模型及使用量信息。

例如：

~~~text
输入：
“负责 RAG 知识库研发”

输出：
[0.12, -0.08, 0.31, ...]
~~~

实际向量通常有数百至数千维。

系统至少需要验证：

1. 每个输入是否得到对应的输出；
2. 向量维度是否符合预期；
3. 是否出现 NaN、无穷值等异常数值；
4. 批量响应是否对应正确的输入顺序或索引；
5. 查询向量与文档向量是否使用兼容的模型和表示方式；
6. 调用失败时是否被明确记录。

如果批量生成 100 个 Chunk 的向量，却把其中两个响应错位关联到其他 JD，即使 Embedding 模型非常优秀，检索结果也会错误。

因此，**输入输出正确性是模型质量评测之前的基础保证。**

### 3. 第二层：检索相关性是否改善？

假设用户问：

> 哪些岗位负责企业知识库平台建设？

已经人工确认有 10 个相关岗位。

方案 A 使用 BM25，前 20 个结果找到 7 个。

方案 B 使用 Embedding，前 20 个结果找到 9 个。

在其他条件相同且标准答案完整的前提下，B 的岗位 Recall@20 更高。

这才是能够说明 Embedding 带来收益的证据之一。

但还需要进一步检查：

- B 新增找到的是不是正确岗位？
- 有没有把公司介绍当作岗位职责？
- 有没有让一些重要岗位排名退化？
- 是否增加了大量无关候选？
- 相应的成本是多少？

不能只因为向量模型返回结果，就认为它改善了检索。

### 4. 第三层：索引是否可靠？

这里需要区分**索引质量**与**模型质量**。

即使模型已经产生正确的向量，系统也可能因为索引问题返回错误结果。

例如某岗位从：

> RAG 项目经验优先。

修改为：

> 必须具备 RAG 项目经验。

如果岗位原文已更新，但索引仍对应旧版文本，就可能出现：

~~~text
数据库中的 JD：新版
向量索引：旧版
查询结果：旧证据
~~~

这种问题不是 Embedding 模型不够聪明。

而是**索引与来源数据的版本不一致**。

因此好的索引方案至少应保证：

| 要求 | 判断标准 |
|---|---|
| 来源关联 | 向量能对应正确文档和 Chunk |
| 版本一致 | 当前向量对应当前允许检索的文本版本 |
| 索引完整 | 应索引的资料没有无故遗漏 |
| 更新可靠 | 新旧版本不会混合 |
| 失败可恢复 | 模型超时或写入失败后可以安全重试 |
| 权限正确 | 不返回用户无权访问的内容 |
| 可追溯 | 能找回命中向量对应的原文证据 |

### 5. 第四层：成本与性能是否合理？

还需要评价：

- 建立索引需要多少时间；
- 生成 Embedding 需要多少 Token 和费用；
- 新增一份文档的更新延迟；
- 查询延迟；
- 存储容量；
- 并发处理能力；
- 系统维护成本。

但应避免一个误区：

**索引更快，不代表系统更好。**

如果查询速度提高十倍，但漏掉了大量重要证据，就不一定值得采用。

工程决策应同时考虑：

**正确性、检索质量、性能、成本和维护复杂度。**

## 三、有哪些候选方案？应该怎样选择？

这一章需要把两个问题分开：

1. 使用什么方法表示文本相关性？
2. 怎样存储和搜索这些表示？

### 1. 方案 A：不使用 Embedding，采用 BM25

BM25 根据关键词的出现情况、区分度及文档长度等因素，为候选文本计算词法相关性。

它不需要生成 Embedding。

例如用户查：

> vLLM SGLang 推理引擎部署

如果 JD 明确出现这些名称，BM25 可能表现得很好。

优势包括：

- 不需要向量模型调用；
- 成本和系统依赖较低；
- 对精确技术名称有优势；
- 查询行为相对容易解释。

不足是：

- 对同义表达依赖较强；
- 没有相同关键词时可能漏掉相关内容；
- 中文词项提取和别名规则可能影响结果。

**BM25 应当被视为正式基线，而不是引入 Embedding 之前必须淘汰的旧技术。**

### 2. 方案 B：Dense Embedding + 精确向量搜索

把每个 Chunk 转成向量，并在查询时与全部符合条件的向量计算相似度。

~~~text
所有 JD Chunk
      ↓
 Embedding 模型
      ↓
保存文档向量
      │
      │      用户问题
      │          ↓
      │     查询向量
      │          ↓
      └────→ 全量相似度计算
                  ↓
             Top-K 候选
~~~

优点是：

- 有机会找到不同文字表达的相关内容；
- 实现机制相对直接；
- 不需要近似索引带来的额外召回损失；
- 容易作为其他方案的对照基线。

不足是：

- 语义相似不等于业务相关；
- 模型质量对结果影响较大；
- 数据量增大后，全量距离计算的成本可能增加；
- 模型及索引维护需要额外成本。

对于只有数千个 Chunk 的 Job-RAG，精确向量搜索完全值得保留为基线。

### 3. 方案 C：Dense Embedding + 近似向量索引

当数据规模变大时，可以考虑 ANN（Approximate Nearest Neighbor，近似最近邻）索引。

常见方法包括：

- HNSW；
- IVFFlat。

它们试图在不必穷尽计算全部向量的情况下，尽快找到相近候选。

需要理解的核心取舍是：

> **近似索引通常以部分召回风险换取查询速度或资源收益。**

例如：

使用精确向量搜索时，某个相关 Chunk 排在第 8。

使用近似索引后，它可能没有进入返回结果。

这时不是 Embedding 模型发生变化，而是搜索算法没有找到精确搜索本来会返回的候选。

所以要额外评测：

**ANN 结果与精确向量搜索结果相比，损失了多少候选？**

在 pgvector 中，精确搜索是默认能力；HNSW 和 IVFFlat 是可选的近似索引方式。官方文档也明确区分二者的速度、内存、建索引和召回取舍。

### 4. 方案 D：BM25 + Embedding 混合检索

因为词法和语义检索提供不同信号，可以同时保留两条通道。

例如：

~~~text
                   用户问题
                      ↓
               明确硬条件过滤
                      ↓
            ┌─────────┴─────────┐
            ↓                   ↓
         BM25 检索         Embedding 检索
            ↓                   ↓
         候选集合 A          候选集合 B
            └─────────┬─────────┘
                      ↓
                合并、去重、排序
                      ↓
                   候选岗位
~~~

这类方案值得测试，是因为：

- BM25 可能擅长明确技术名称；
- Embedding 可能补足不同措辞；
- 两种方法的错误并不完全相同。

但混合检索不意味着自动更好。

例如，某个语义检索通道引入大量误匹配，融合后可能反而使结果变差。

所以需要比较：

- BM25 单独使用；
- Embedding 单独使用；
- 两者组合使用。

不能仅因为两个模型互补的理论成立，就认定当前业务里的混合效果一定最佳。

### 5. 方案 E：不依靠向量解决所有任务

假设用户问：

> 统计岗位职责或任职要求中明确出现 RAG 的岗位，一共要求哪些技术？

这是一个需要明确统计范围的问题。

如果只从向量索引返回 Top-20 候选，再统计它们的技能要求，就会遗漏没有进入候选列表的岗位。

因此可能需要：

~~~text
完整岗位库
    ↓
按照明确字段和章节条件枚举
    ↓
获得符合条件的岗位集合
    ↓
读取完整 JD
    ↓
技术要求抽取与核验
    ↓
聚合统计
~~~

这里不一定需要向量检索作为核心步骤。

**Embedding 是一种信息发现方法，而不是完整枚举和精确统计的替代品。**

### 6. 应怎样决定使用哪一种方案？

| 场景 | 值得先尝试的方案 |
|---|---|
| 数据量小，技术词明确 | BM25 |
| 查询与资料经常使用不同表达 | Embedding |
| 词法和语义各有明显漏召回 | Hybrid |
| 向量规模大且精确搜索延迟不达标 | ANN |
| 需要全库完整统计 | 数据库枚举、结构化抽取 |
| 已知具体文档，需要判断条件 | 直接回读全文 |

这不是固定答案。

实际选择必须由评测验证。

## 四、怎样建立 Embedding 与索引的评测？

### 1. 为什么不能仅依靠公开模型排行榜？

假设模型 A 在公开基准上得分更高。

模型 B 的公开成绩稍低。

能否直接选择 A？

不能。

因为公开基准与当前业务之间可能存在差异：

- 查询语言不同；
- 文档长度不同；
- 相关性的定义不同；
- 技术专有名词不同；
- 用户任务不同；
- 原文结构不同。

例如 Job-RAG 中“负责模型部署”和“了解模型部署”的相关性差异，未必在通用语义检索基准中得到充分覆盖。

因此排行榜可用于筛选候选模型，但最终需要业务测试集决定。

### 2. 应该设计哪些真实问题？

建议至少覆盖以下类型。

| 问题类型 | 示例 | 主要检验 |
|---|---|---|
| 明确术语 | 哪些岗位要求 vLLM？ | 专有名词召回 |
| 同义表达 | 哪些岗位负责企业知识库建设？ | 语义召回 |
| 职责区分 | 哪些岗位真正负责模型部署？ | 证据相关性 |
| 技术深度 | 哪些岗位负责推理服务底层优化？ | 细粒度区分 |
| 条件区分 | 哪些岗位必须具备 RAG 项目经验？ | 与后续判断配合 |
| 多技术组合 | 哪些岗位要求 Python、RAG 和服务化部署？ | 多证据查询 |
| 无答案问题 | 哪些岗位明确要求某项不存在的技术？ | 无关结果控制 |

注意：

**不同类型的问题，对 Embedding 的价值不同。**

如果测试集全是从 JD 中复制的技术关键词，那么 BM25 可能天然占优。

如果只测试同义词搜索，则可能高估向量模型的相对收益。

应尽量覆盖真实用户实际会问的问题，而不是为了证明某种技术先进而设计测试。

### 3. 一条评测案例需要包含什么？

例如：

**问题**

> 哪些岗位真正负责大模型推理服务部署？

**已核验相关岗位**

岗位 A：

> 负责 vLLM 推理服务部署、模型托管及推理性能优化。

**容易误匹配的岗位**

岗位 B：

> 调用公司已有大模型 API，开发 AI 应用。

岗位 C：

> 公司提供模型推理平台，岗位主要负责销售。

**预期**

- A：直接相关；
- B：部分技术相关，但不是模型服务部署岗位；
- C：公司背景提及，不应作为目标岗位。

**证据**

保存每个判断对应的完整 JD 原文及来源。

这样才能测试模型是否在业务层面找到真正有价值的候选。

### 4. 应该用哪些指标？

| 指标 | 回答的问题 |
|---|---|
| Recall@K | 前 K 个候选覆盖多少相关岗位 |
| Evidence Hit@K | 关键证据是否进入前 K |
| nDCG@K | 高相关岗位是否排得更靠前 |
| Precision@K | 前 K 个结果中有多少相关岗位 |
| ANN Recall@K | 近似索引找回多少精确检索候选 |
| P95 查询延迟 | 绝大多数查询是否足够快 |
| 索引新鲜度 | 当前可检索索引是否对应正确版本 |
| 建索引成本 | Embedding 和索引建设的资源消耗 |

需要特别强调两件事。

**第一，标准答案不完整时，不能宣称真实 Recall。**

如果只知道一个相关岗位，就只能统计这个已知正例是否被命中。

**第二，ANN Recall 与业务 Recall 不是同一个指标。**

ANN Recall 比较的是近似索引与精确向量搜索的候选一致程度。

业务 Recall 比较的是系统结果与真实相关岗位集合。

即使 ANN 完全复现精确向量搜索，Embedding 模型本身仍然可能漏掉真正相关的岗位。

### 5. 怎样比较 Embedding 模型？

为了归因清楚，应该尽可能固定：

- 原始 JD 数据；
- 文档解析版本；
- Chunking 方案；
- 测试问题；
- 相关性标注；
- 硬条件；
- 候选数量；
- 岗位级聚合方式；
- 距离计算方法。

然后分别运行模型 A 和模型 B。

应明确记录：

- 模型名称与版本；
- 向量维度；
- 文档和查询输入方式；
- 是否添加任务指令；
- 文本长度限制；
- 服务成本；
- 实际返回结果。

不能把“模型 A + 1100 字符 Chunk”和“模型 B + 600 字符 Chunk”的结果直接解释成模型能力差异。

### 6. 怎样比较精确与近似索引？

假设选择同一个 Embedding 模型，向量已经固定。

现在比较：

- 精确向量搜索；
- HNSW；
- IVFFlat。

这里不再改变 Embedding 模型。

要分别测量：

- 相对精确搜索的候选召回；
- 查询延迟；
- 内存；
- 索引构建成本；
- 更新性能；
- 不同过滤条件下的效果。

尤其需要注意：当向量检索与城市、权限、类别等过滤条件组合时，部分 ANN 实现的执行方式可能导致返回候选不足。

因此，必须使用真实过滤条件进行测试，不能只测试没有过滤条件的纯向量搜索。

### 7. 怎样设计开发集和测试集？

建议按用户问题主题划分：

- 开发集用于模型选择、参数调整、失败分析；
- 测试集用于检验方案对未参与优化问题的表现。

如果同一个问题只是换一种说法，不应把其中一条放开发集，另一条放测试集。

如果反复根据测试集结果修改模型与索引，测试集也会逐渐失去独立验证的价值。

## 五、怎样理解实验结果？为什么模型得分高不一定更好？

### 1. 模型 A 的 Recall@20 高于模型 B，可以直接选择 A 吗？

不一定。

至少还应追问：

1. Recall 的标准答案是否完整？
2. 改善是否集中在少数问题？
3. 哪些重要问题退化了？
4. 新增候选是否确实符合职责？
5. 成本增加多少？
6. 结果是否受到 Chunking 或岗位聚合影响？

例如：

模型 A 找到了更多与 RAG 技术词相关的 JD。

但新增命中主要来自公司介绍。

那么它未必让“寻找真正负责 RAG 开发的岗位”变得更好。

### 2. 为什么向量维度越大不一定越好？

向量维度是表示空间大小的一项配置。

更高维度可能提供更多表示能力，但不能保证目标业务检索效果一定更好。

同时，更高维度可能增加：

- 存储占用；
- 网络传输；
- 距离计算；
- 索引内存需求。

因此，应在同一模型支持的有效配置范围内，比较不同维度的实际质量与成本。

还要注意：改变向量维度可能意味着文档向量必须重新生成，不能将不同维度直接混入一个统一检索空间。

### 3. 为什么 Chunking 会影响 Embedding 实验？

假设同一个岗位：

方案 A 切成 2 个 Chunk。

方案 B 切成 8 个 Chunk。

如果岗位级相关性分数取所有 Chunk 的最大值，那么 B 有更多机会产生局部高分。

这可能使 B 排名提高。

但不能据此直接认定 B 的文本表示更准确。

因为变化来自多个因素：

- 文本边界；
- 上下文信息；
- Chunk 数量；
- 分数聚合方式。

因此，Embedding 实验必须记录文档表示方式。

尤其需要避免将分块差异、模型差异和索引差异混成一个综合分数。

### 4. 为什么索引更快，也可能让最终效果变差？

假设精确搜索需要 150 毫秒。

HNSW 需要 15 毫秒。

从性能上看，HNSW 明显更快。

但如果它在关键问题上遗漏了原本进入前 20 的相关岗位，这个速度收益可能付出了不可接受的代价。

相反，如果 HNSW 几乎不损失有效候选，同时显著改善延迟，那么它可能是合理选择。

因此正确的实验问题不是：

> 哪种索引最快？

而是：

> **在业务允许的召回损失范围内，哪种索引能够提供最好的延迟和资源成本？**

### 5. 什么情况下应该保留简单方案？

例如：

- 只有几千个 Chunk；
- 精确查询已经足够快；
- 更新频率不高；
- 无需复杂分布式部署；
- BM25 已经解决大部分真实问题。

那么增加大型向量服务、ANN 索引和复杂调参，未必值得。

**技术复杂度应由已经观察到的业务瓶颈驱动，而不应该由架构流行程度驱动。**

## 六、发现检索效果不好后，怎样诊断究竟是哪一环节的问题？

### 1. 为什么搜不到岗位，不一定是 Embedding 不够好？

假设用户问：

> 哪些岗位负责推理服务部署？

系统没有找到某个已知相关岗位。

可能原因包括：

- 该 JD 没有被采集；
- 文档解析遗漏了相关职责；
- Chunking 把关键证据拆坏；
- Embedding 没有将其表示为足够相近的向量；
- 索引不存在或使用旧版本；
- ANN 没有找到该向量；
- 城市、薪资等过滤条件将岗位排除；
- 候选已找到，但岗位聚合后被挤出 Top-K；
- 后续模型错误排除了它。

这些问题不能都通过更换 Embedding 模型解决。

### 2. 怎样按顺序定位失败？

~~~text
原始 JD 是否存在？
        ↓
解析后是否保留关键内容？
        ↓
Chunk 是否包含完整证据？
        ↓
Embedding 是否成功生成？
        ↓
当前索引是否包含对应向量？
        ↓
精确向量搜索能否找到？
        ↓
ANN 或过滤是否丢失候选？
        ↓
岗位聚合后是否仍在候选内？
        ↓
后续判断是否正确？
~~~

可以按以下顺序排查：

**第一步：检查原文。** 如果原文不存在，先解决采集。

**第二步：检查解析与 Chunking。** 如果索引文本丢失关键信息，先修复上游。

**第三步：检查 Embedding 输出。** 确认生成、模型、维度和版本。

**第四步：检查精确向量搜索。** 如果精确搜索也找不到，检查模型表示、查询文本和组织方式。

**第五步：比较近似索引。** 如果精确搜索找到而 ANN 找不到，检查索引搜索和过滤。

**第六步：检查下游排序与判断。** 如果候选已找到，检查聚合、重排和语义判断。

### 3. 常见失败与改进方向

| 失败现象 | 优先检查 | 候选改进方向 |
|---|---|---|
| 不同表达的相关岗位找不到 | Embedding 与查询表示 | 模型对照、查询改写 |
| 精确技术词经常漏召回 | 词法召回 | BM25、词项处理 |
| 重要证据不在向量文本中 | 文档表示 | 解析与 Chunking |
| 向量对应错误 JD | 索引数据关联 | 输入输出校验 |
| 新版 JD 使用旧向量 | 索引版本 | 签名、更新任务 |
| 精确搜索找到，ANN 找不到 | 近似索引 | ANN 参数与过滤 |
| 只有公司介绍命中 | 证据相关性 | 章节信息、后续核验 |
| 多 Chunk 挤占岗位排名 | 结果聚合 | 岗位级聚合策略 |
| 全库统计结果遗漏 | 查询方式 | 完整枚举而非 Top-K |

**如果问题的本质是完整统计，更换 Embedding 模型可能根本没有解决正确的问题。**

### 4. 怎样记录可复现的失败案例？

~~~text
用户问题：
哪些岗位负责模型推理服务部署？

预期岗位：
岗位 A，职责包含 vLLM 推理服务部署。

实际：
向量检索 Top-20 没有岗位 A。

检查：
1. 数据库存在完整 JD。
2. Chunk 保留正确职责。
3. 向量生成成功，版本一致。
4. 精确向量搜索中 A 排名第 12。
5. HNSW 查询 Top-20 未返回 A。

初步结论：
优先调查近似索引和过滤条件，
不是立即更换 Embedding 模型。

验证：
调整索引检索配置，
比较 ANN Recall、延迟和资源成本。
~~~

## 七、怎样让 AI 持续优化 Embedding 与索引？

### 1. AI 能够承担哪些工作？

AI 可以分析真实查询、提出模型候选、编写适配器、生成测试、批量编码、比较方案、调整索引、分析失败、性能测量、生成报告。

但“帮我优化向量检索”太宽泛：AI 可能直接换模型、加维度、引入 HNSW 或改 Chunking，未必解决问题。

### 2. 怎样组织一轮有效优化？

**第一步：冻结基线。** 保存 JD、解析和切分版本、模型配置与维度、查询标注、搜索参数、指标与成本。

**第二步：分类失败。** 区分词项不匹配、语义表示不足、文本组织不合理、索引版本错误、ANN 损失、过滤错误和下游判断。

**第三步：提出可验证假设。** 例如 Embedding 可补足“知识库建设”与“RAG 工程”等不同表达。

**第四步：只改变一个主要因素。** 测模型固定 Chunk 和索引；测 HNSW 固定向量。

**第五步：运行对照。** 查看整体及分类收益、退化、延迟、成本和一致性。

**第六步：决定保留、回退或继续。** 证据不足则保留基线。

### 3. 怎样给 AI 下实验任务？

> 请基于冻结的 JD、Chunk、测试查询和人工标准答案，评价 Embedding 与索引方案。
>
> 首先检查向量维度、输入输出关联、模型与索引签名、来源版本一致性。
>
> 比较 BM25、精确向量搜索和必要时的混合检索。
>
> 若候选遗漏，沿原文、Chunk、向量、精确搜索、ANN、过滤和岗位聚合逐层定位。
>
> 每轮只修改一个主要因素。
>
> 报告岗位召回、证据召回、排名质量、改善/退化案例、成本与延迟。
>
> 标注不完整时明确使用 seed 或 pooled 受限指标，不得宣称完整 Recall。
>
> 未通过评测，不替换生产索引或模型配置。

### 4. 为什么索引更新需要单独设计？

旧版 JD：

> 有 RAG 项目经验者优先。

新版：

> 必须具备 RAG 项目开发经验。

数据库写入成功但 Embedding 暂不可用时，必须决定新资料先保存、任务登记、失败重试、旧向量是否参与、何时切换新索引。

一种可选设计：

~~~text
新 JD 版本写入
        ↓
保存来源内容
        ↓
登记待索引任务
        ↓
解析 / 分块 / Embedding
        ↓
检查任务版本仍然有效
        ↓
原子替换对应索引
        ↓
标记当前索引就绪
~~~

**已保存的新版本资料，不应该与不匹配的旧版索引混用。**

## 八、Job-RAG 实践：怎样判断当前 Embedding 与索引方案是否合理？

### 1. 当前使用什么方案？

根据 [模型服务说明](https://github.com/leecolin2023/job-rag/blob/main/job_rag/providers/README.md)、[索引模块说明](https://github.com/leecolin2023/job-rag/blob/main/job_rag/indexing/README.md)，流程为：

~~~text
标准化岗位 JD
       ↓
保存岗位原文及版本
       ↓
生成 Chunk
       ↓
可选 Embedding
       ↓
保存 Chunk、向量、版本签名
       ↓
BM25 / 可选向量检索
       ↓
按岗位归并候选
~~~

值得保留的设计：

- 不依赖 Embedding 才能保存资料；
- 无模型配置可用 BM25；
- 索引构建与数据保存分离；
- 索引具有版本与签名；
- Worker 先准备、再验证和提交，避免新旧 Chunk 部分混合。

这些解决的是正确性与可靠性，不等于语义质量最佳。

### 2. 已经验证了什么？

根据 [2026-10-25 Embedding 实验](https://github.com/leecolin2023/job-rag/blob/main/docs/recall-pilot-2026-10-25.md)：

- 使用 592 份具有正文的 JD；
- 30 条查询，15 个主题；
- 百炼 `qwen3.7-text-embedding-flash`，1024 维；
- 比较五种分块表示；
- 精确余弦检索；
- 不引入 Rerank、改写或 Hybrid。

| 方案 | 文档表示 | Chunk 数量 |
|---|---|---:|
| A | 历史分块 | 790 |
| B | 紧凑固定分块 | 790 |
| C | 章节结构化分块 | 2,443 |
| D | 章节结构化 + 条件提示 | 2,443 |
| E | D 的较小长度预算 | 2,657 |

另有完整 JD BM25 参考，注意它与向量方案的文本表示不同。

### 3. 结果意味着什么？

当时记录的种子正例 nDCG@5：

| 方案 | Dev | Test |
|---|---:|---:|
| A：历史分块 | **0.7606** | 0.7515 |
| B：紧凑固定 | 0.7330 | 0.7757 |
| C：章节结构化 | 0.7330 | **0.8914** |
| D：增加条件提示 | 0.6973 | 0.8683 |
| E：减小长度预算 | 0.6973 | 0.8683 |
| BM25 参考 | 0.7874 | 1.0000 |

**这是每个问题只有一个已知种子正例的受限指标，不是完整人工标注的 nDCG。**

不能据此断言 BM25 真实质量一定优于 Embedding，也不能宣称 C 是最佳分块。

限制包括样本少、相关岗位标注不完整、不同方案的 Chunk 数量、输入表示和岗位聚合方式不同。

但可以得出：**Embedding 效果必须通过实际业务数据验证，而不能只依据模型介绍或排行榜推断。**

### 4. 下一步是否应该更换模型？

建议先不要。

当前更优先的问题是：

- 标准答案是否充分；
- 哪些真实问题需要语义检索；
- 哪些 BM25 已足够；
- 哪些候选被错判；
- 业务是否实际受益。

没有可靠评测时不断换模型，会增加成本和变量。

### 5. 下一轮实验先做什么？

#### 第一优先级：补齐相关性和证据标注

把单种子扩展为候选池审阅，记录直接相关、部分相关、不相关、原文证据与理由；重点区分公司介绍、职责、要求与技术深度。

未穷尽时使用 seed / pooled 口径，不宣称全库 Recall。

#### 第二优先级：三组正式基线

- A：BM25；
- B：Dense Embedding + 精确向量搜索；
- C：BM25 + Dense Hybrid。

同一集比较新增的相关岗位、错误候选、受益的问题类型、延迟和成本。

#### 第三优先级：分开验证模型与文档表示

- 固定 Chunking，比 Embedding 模型；
- 固定模型，比 Chunking；
- 固定两者，比向量维度；
- 固定召回候选，比排序方法。

#### 第四优先级：比较完整 JD 与 Chunk

包括完整 JD 单向量、章节、条目，以及小片段召回后回读完整 JD。

#### 第五优先级：不急于引入 ANN

当前约数千 Chunk，精确向量检索是合适基线。出现真实性能瓶颈后，再对比 HNSW/IVFFlat 的速度、资源与召回损失。

### 6. 索引更新优先测试哪些情况？

| 场景 | 应有结果 |
|---|---|
| 相同 JD 重复导入 | 不无故重复生成向量 |
| 只更新采集时间 | 文本与签名不变时可复用 |
| 正文变化 | 旧向量不能冒充新版本 |
| 模型维度变化 | 不混用不兼容向量 |
| 模型调用失败 | 记录失败并可重试 |
| 旧任务晚于新任务完成 | 不覆盖新索引 |
| 部分 Chunk 失败 | 不标记完整就绪 |
| 岗位关闭 | 不因有向量而违规返回 |

**相关性回答找得好不好；一致性回答证据是否可信。**

### 7. 怎样形成实验报告？

| 内容 | 需要回答 |
|---|---|
| 研究问题 | 解决什么失败 |
| 对照方案 | 改变什么因素 |
| 数据快照 | 哪些岗位版本 |
| 查询样本 | 哪些问题 |
| 标注范围 | seed、pooled 或 exhaustive |
| 召回结果 | 哪些岗位被找回 |
| 排名变化 | 哪些前进或后退 |
| 证据质量 | 职责还是公司介绍 |
| 成本性能 | Token、延迟、存储 |
| 退化 | 哪些原先成功的变差 |
| 决策 | 保留、回退或继续 |

例如：

~~~text
研究问题：
Embedding 是否补足 BM25 在不同表达下的漏召回？

方案：
A：BM25
B：Dense Embedding
C：BM25 + Dense

固定：
JD、Chunking、查询、人工答案、硬条件、Top-K。

指标：
岗位 Recall@20、证据 Hit@20、nDCG@5、
分类收益与退化、延迟和费用。

分析：
哪些 BM25 找不到的岗位通过 Embedding 正确找到？

决策：
根据完整实验结果，不预设 Hybrid 最好。
~~~

---

## 结语：Embedding 与索引的核心不是向量数据库选型

最初的问题是：如何建立 RAG 向量索引？

更值得回答的是：

1. **为什么需要向量？** 普通关键词搜索存在什么真实缺口？
2. **怎样定义好坏？** 是否找到更多正确证据，而不仅相似度更高？
3. **怎样评价模型？** 用真实问题、标注和可重复实验。
4. **怎样评价索引？** 完整、版本一致、高效并可维护。
5. **怎样归因失败？** 区分表示、模型、精确搜索、ANN、过滤、下游判断。
6. **怎样让 AI 改进？** 明确目标、控制变量、分析退化、依据结果决策。

> **Embedding 的价值是提供发现语义相关内容的检索信号；索引的价值是可靠高效地组织信号，并使其对应正确来源资料。**

二者服务于业务任务，不是独立的技术目标。

AI 时代，工程师真正值得掌握的不是某个 API 参数或全部 ANN 算法实现，而是知道**什么时候需要向量、带来什么收益、如何证明收益，以及什么时候不应该使用向量检索。**
