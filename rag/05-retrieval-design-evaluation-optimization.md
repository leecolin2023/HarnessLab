# RAG 检索：如何设计、评测与持续优化？

> 本文是 RAG 工程流程的第五篇专题文章，承接《04 · Embedding 与索引》，后续衔接《06 · Rerank 重排》。
>
> 本文以 Job-RAG 招聘岗位知识库为主要案例，从真实用户问题出发，理解为什么需要检索、怎样定义检索质量、有哪些候选方案、如何建立评测、怎样诊断召回失败，以及如何让 AI 持续优化。
>
> 本文的重点不是记住 BM25、RRF 或查询改写的代码实现，而是建立一种能力：**能够判断系统是否找到了完成用户任务所需的证据，并在没有找到时准确定位原因。**

---

## 一、为什么需要 Retrieval？直接让大模型阅读知识库不行吗？

### 1. 我们究竟要解决什么问题？

假设 Job-RAG 已经收集了数百份招聘 JD，并完成解析、切分和索引。

现在用户提出：

> 帮我找几个真正负责企业 RAG 知识库研发的岗位。

最简单的方法是什么？

如果只有 10 份 JD，可以直接把所有内容提供给大模型，让它阅读并比较。

但是，当知识库包含数千、数万甚至更多文档时，每次把全部资料交给大模型，就会遇到：

- 输入内容过多，模型处理成本增加；
- 大量无关资料占用上下文；
- 用户需要的信息可能埋在许多文档中；
- 随着资料更新，需要重新组织输入；
- 难以追踪究竟依据哪条文档得出结论。

因此，我们希望在模型正式分析之前，先找出可能相关的资料。

这就是 Retrieval（检索）的主要作用。

~~~text
用户提出问题
      ↓
从知识库中寻找相关内容
      ↓
返回有限的候选证据
      ↓
大模型阅读并判断
      ↓
生成回答
~~~

Retrieval 试图解决的是：

**面对大量资料，怎样尽量找到完成当前任务所需要的内容，而不是让模型每次阅读整个知识库？**

### 2. 为什么“找到包含关键词的文档”还不够？

假设用户想找：

> 真正负责 RAG 系统研发的岗位。

我们来看四份 JD。

**岗位 A**

> 负责企业知识库平台建设，包括文档接入、检索索引、智能问答服务开发。

**岗位 B**

> 公司主营 RAG 知识库产品，岗位负责销售拓展。

**岗位 C**

> 负责基于 LangChain 的问答应用集成和接口调用。

**岗位 D**

> 负责 RAG 检索服务研发，包括召回优化、重排和质量评测。

如果简单搜索 `RAG`：

- B 会命中，因为公司介绍出现 RAG；
- D 会命中，因为岗位职责出现 RAG；
- A 可能被遗漏，因为没有直接出现 RAG；
- C 的相关程度需要结合用户的实际要求判断。

因此，搜索到关键词，不等于找到了真正相关的岗位。

这里至少有三个不同问题：

1. **候选发现**：系统能否找到可能相关的岗位？
2. **相关性排序**：系统是否把更可能相关的岗位排在前面？
3. **业务判断**：岗位究竟是否满足用户真正关心的条件？

这三个问题不能混为一谈。

Retrieval 主要承担前两个问题中的候选发现和初步排序。

最终业务判断仍然需要阅读可靠证据。

### 3. Retrieval 和 Rerank 的区别是什么？

假设当前知识库有 10,000 个文档。

Retrieval 从中找出了 50 个候选。

Rerank 再对这 50 个候选重新评价相关性，并选出最值得阅读的 5 个。

~~~text
10,000 个文档
      ↓
Retrieval
      ↓
50 个候选
      ↓
Rerank
      ↓
5 个高优先级候选
      ↓
原文核验与回答
~~~

两者的主要区别是：

| 环节 | 核心问题 | 主要风险 |
|---|---|---|
| Retrieval | 应该让哪些内容进入候选集合？ | 漏掉正确证据 |
| Rerank | 已经找到的候选，哪些应该排前面？ | 错误候选排得太高 |
| 最终判断 | 证据真正支持什么结论？ | 误读条件或生成错误 |

例如正确岗位 A 没有进入前 50 个候选。

此时无论 Reranker 多么优秀，它都无法从这 50 个候选中找出 A。

这就是 Retrieval 的关键责任：

**尽可能避免在候选阶段过早丢掉正确证据。**

当然，Retrieval 本身也有排序能力，并不是只返回一个无序集合。这里的划分是为了明确主要责任，而不是要求两者在技术上必须完全分离。

### 4. 所有问题都应该使用 Retrieval 吗？

不应该。

看看三个用户问题。

**问题 A**

> 帮我推荐几个负责 RAG 开发的岗位。

适合使用相关性检索，寻找一批值得阅读的候选。

**问题 B**

> 当前数据库中有多少份 JD 明确出现 vLLM？

这是一个确定性统计问题，应该在定义好的数据范围内完整检查，而不是只统计 Top-K。

**问题 C**

> 统计职责或任职要求出现 RAG 的全部岗位，它们还要求哪些技术。

这个问题至少包含：

1. 明确研究范围；
2. 找到所有符合字面条件的岗位；
3. 逐份分析技术要求；
4. 去重、归类与统计。

它不是一个简单的“找几个最相关文档”的任务。

如果用 Top-20 检索结果统计整个岗位库，可能得到一份看起来合理、实际却不完整的报告。

因此：

> **Retrieval 擅长寻找有限的相关候选；完整枚举和精确统计需要另外的查询机制。**

这也是 Job-RAG 必须区分 Retrieval 与 Querying 的原因。

## 二、怎样定义一个好的 Retrieval 方案？

### 1. 什么叫“检索得好”？

最简单的判断可能是：

> 用户输入一个问题，系统返回了一些看起来相关的文档。

但这不够。

假设系统返回了 10 个岗位，全部提到了 RAG。

用户可能觉得检索效果很好。

然而，知识库中还有 5 个真正负责 RAG 研发的岗位没有被找到，前 10 个结果中还有几个只是公司介绍提到 RAG。

所以不能仅凭“返回了相关内容”证明 Retrieval 做得好。

我建议这样定义：

> **好的 Retrieval 方案，是指能够在正确的数据范围内，以可接受的延迟和成本，将完成用户任务所需要的相关证据尽可能完整地纳入候选，并保持来源、条件和版本可信。**

这个定义可以拆成几个层次。

### 2. 第一层：搜索范围正确——应该搜索哪些资料？

假设用户要求：

> 广州、月薪下限至少 20K、负责 RAG 工程的岗位。

我们首先需要判断哪些条件是确定性约束。

例如：

- 城市必须是广州；
- 月薪下限不少于 20K；
- 岗位必须处于用户允许查询的状态。

这些条件可以通过数据库字段和明确规则处理。

然后再在符合条件的岗位中检索与 RAG 工程相关的内容。

但“负责 RAG 工程”本身，通常不能简单转成 `description contains "RAG"`。

因为有些岗位使用“知识库开发”“检索增强问答”“文档索引平台”等不同表达。

因此需要区分：

**硬条件：必须满足的明确约束。**

**相关性条件：希望找到的内容方向。**

这两者不能随意转换。

例如用户明确要求广州岗位，查询改写时不能将地区扩展为全国。

用户希望找 RAG 开发岗位，也不应该把 `RAG` 三个字符变成强制字面过滤，除非用户明确要求如此。

### 3. 第二层：候选覆盖——应该找到的内容有没有进入候选？

假设经过人工完整审阅，我们确认某问题有 10 个相关岗位。

系统返回前 20 个候选，其中包含 8 个。

那么：

\[
Recall@20=\frac{8}{10}=80\%
\]

这个指标回答：

> 系统有没有漏掉重要的相关岗位？

对于 Retrieval，这是一项特别重要的指标。

但必须注意，只有标准答案足够完整时，才能将它解释为实际 Recall。

如果只知道其中一个相关岗位，那么找到了这个岗位，只能证明命中了一个已知正例。

不能说召回率为 100%。

### 4. 第三层：证据覆盖——找到了岗位，是否找到了正确依据？

假设系统找到了岗位 A。

岗位 A 的 JD 中存在：

~~~text
公司介绍：
公司提供企业级 RAG 产品。

岗位职责：
负责 Java 后端接口开发。

任职要求：
有 AI 应用项目经验者优先。
~~~

如果 Retrieval 只返回了公司介绍中的 RAG 内容，就可能让后续模型误以为岗位负责 RAG 研发。

因此需要同时评价：

- 是否找到了正确岗位；
- 是否找到了正确章节；
- 是否找到了足以支持判断的证据。

这就涉及岗位级召回和证据级召回。

| 评测对象 | 问题 |
|---|---|
| 岗位级 | 相关岗位是否进入候选？ |
| 证据级 | 关键职责或任职条件是否进入候选内容？ |

对于制度问答也是一样。

找到正确制度文件，不代表找到了正确条款。

**文档命中和证据命中应当分开评价。**

### 5. 第四层：输出是否可信？

一次 Retrieval 不应该只返回：

~~~json
{
  "text": "负责 RAG 开发",
  "score": 0.92
}
~~~

因为调用方不知道：

- 来源是哪份 JD；
- 属于哪个岗位；
- 来自哪个章节；
- 是什么版本；
- 是否符合权限和状态；
- 分数是什么含义；
- 文本是否被截断。

更合理的候选输出应包含：

~~~json
{
  "job_id": "job-A",
  "source": "boss",
  "document_version": 3,
  "evidence": "负责企业 RAG 检索服务研发。",
  "section": "岗位职责",
  "retrieval_rank": 2,
  "retrieval_method": "hybrid",
  "count_kind": "bounded_candidates"
}
~~~

这仍然是教学示意，不代表 Job-RAG 必须采用这个字段结构。

重点是输出应该让调用方理解：

**这是一条有来源、有上下文、有版本的候选证据，而不是一条已经验证的业务结论。**

### 6. 第五层：成本和效率是否合理？

Retrieval 还要考虑：

- 查询延迟；
- 模型调用成本；
- 每次检索候选规模；
- 向量计算；
- 数据库资源；
- 并发能力；
- 失败恢复。

但不能简单认为越快越好。

如果只返回 Top-3，速度可能很快，但漏掉大量重要岗位。

如果返回 Top-500，覆盖可能增加，却可能导致后续模型处理成本过高。

所以一个好的方案必须回答：

> **在可接受的资源预算下，需要找回多少候选，才能支持后续任务？**

## 三、Retrieval 有哪些候选方案？应该怎样选择？

这里需要把检索看成一个完整的候选生成过程，而不仅仅是选择 BM25 或 Embedding。

### 1. 第一步：先判断用户到底需要什么类型的查询

假设用户提出四个问题：

| 用户问题 | 主要操作 |
|---|---|
| 找几个做 RAG 工程的岗位 | 相关性检索 |
| 指定岗位 A 的任职要求是什么 | 按 ID 直接读取 |
| 广州有多少岗位字面出现 RAG | 确定性完整查询 |
| 统计所有 RAG 岗位的技术能力组合 | 定义范围、完整枚举、逐份判断与汇总 |

不同任务需要不同的数据操作。

因此，Retrieval 并不是所有知识库请求的唯一入口。

对于 Agent，应先判断任务类型，再决定是否需要检索。

这一点很重要，因为某些系统的错误不是检索算法不够好，而是**从一开始就选择了错误的查询方式**。

### 2. 方案 A：BM25 词法检索

BM25 根据词项匹配、词项区分度和文本长度等信息计算相关性。

例如：

> 查找负责 vLLM、SGLang 推理引擎部署的岗位。

技术名称非常明确时，BM25 可能效果很好。

优势：

- 不需要 Embedding API；
- 对技术专有名词比较直接；
- 计算与维护成本可能较低；
- 容易建立可复现的检索基线。

不足：

- 容易受到词汇表达差异影响；
- 同义描述不一定能够匹配；
- 分词、别名与文档长度可能改变排序。

因此 BM25 值得作为长期保留的基线。

### 3. 方案 B：Embedding 语义检索

例如：

> 找建设企业内部知识问答系统的工程师岗位。

实际 JD 可能写：

> 负责知识接入、向量索引、召回策略、检索增强生成应用开发。

两者表达不同，但具有较强的语义关联。

Embedding 可以帮助找到这种不同文字表达的候选。

然而：

> 负责模型接口调用。

和：

> 负责模型推理服务部署。

也可能具有较高的主题相似性。

所以 Embedding 的作用是增加候选发现能力，不直接替代职责与条件判断。

### 4. 方案 C：Hybrid 混合检索

可以同时执行 BM25 和 Embedding。

~~~text
用户问题
   ↓
确定搜索范围
   ↓
┌───────────────────┐
↓                   ↓
BM25             Embedding
↓                   ↓
词法候选           语义候选
└─────────┬─────────┘
          ↓
      候选融合
          ↓
     去重与排序
~~~

为什么需要融合？

假设：

- BM25 擅长找到明确写了 `vLLM` 的岗位；
- Embedding 找到了没有直接写 `RAG`、但描述了知识库开发的岗位。

两个通道可能提供互补候选。

但它们的原始分数不是同一尺度。

BM25 的 8.5 分，不代表比向量余弦相似度 0.83 高十倍。

因此不能简单直接相加。

一种常见方案是 RRF（Reciprocal Rank Fusion，倒数排名融合）。

它根据不同检索列表中的排名进行融合：

\[
RRF(d)=\sum_{r \in R(d)}\frac{1}{k+\operatorname{rank}_r(d)}
\]

其中：

- \(R(d)\) 是包含候选 \(d\) 的排名列表；
- \(\operatorname{rank}_r(d)\) 是该候选在某列表中的名次；
- \(k\) 是控制排名贡献的常数，常见值为 60。

例如：

~~~text
岗位 A：
BM25 第 2
Embedding 第 5

RRF = 1/(60+2) + 1/(60+5)
    ≈ 0.0315
~~~

RRF 可以融合不同来源的排序信号。

但要注意：

**RRF 分数不是岗位符合要求的概率。**

即使某个候选同时在多个列表排前面，也不代表它一定满足用户的业务条件。

此外，RRF 本身不会创造新候选。一个岗位如果没有进入任何输入排名列表，融合也找不到它。

### 5. 方案 D：查询改写与多查询检索

用户提出：

> 找企业 RAG 系统研发岗位。

可以尝试几个不同表达：

~~~text
原始问题：
企业 RAG 系统研发

改写 1：
企业知识库平台开发

改写 2：
文档索引与智能问答系统

改写 3：
检索增强生成应用工程化
~~~

对不同问法分别检索，再合并候选。

这样做的动机是：

**一次表达可能无法覆盖用户真正关心的全部工作内容。**

但查询改写存在风险。

例如原始问题：

> 找真正负责推理服务底层部署和性能优化的岗位。

错误改写：

> 找调用大模型 API 开发智能应用的岗位。

这改变了业务含义。

所以查询改写必须满足：

- 不放宽明确硬条件；
- 不改变核心目标；
- 不将用户没有提出的要求变成必备条件；
- 保留原始问题；
- 能够记录不同改写实际找回了什么。

**查询更多，不等于检索一定更好。**

### 6. 方案 E：多步检索与 Agentic Retrieval

有些问题只需要一次检索。

有些问题则可能需要多步查找。

例如：

> 哪些岗位涉及 Agent Runtime 开发，同时要求具备模型服务部署能力？

可以先寻找：

- Agent Runtime 相关岗位；
- 模型服务部署相关岗位；

再读取候选 JD，判断两个条件是否在同一岗位中成立。

另一种情况是企业制度问答：

> 某业务在通常情况下由谁审批？特殊授权有什么例外？

系统可能需要找到：

1. 一般审批权限条款；
2. 特殊授权条款；
3. 相应的前提条件。

这类任务可能需要模型根据初次检索结果，判断是否还缺少证据，并决定是否继续检索。

~~~text
用户问题
   ↓
首次检索
   ↓
检查证据是否足够
   ├── 足够 → 进入后续判断
   └── 不足 → 明确缺失信息
                  ↓
              补充检索
                  ↓
              再次检查
~~~

但不是所有问题都值得使用 Agentic Retrieval。

例如：

> 找所有明确包含 vLLM 的岗位。

简单的字面查询可能更加可靠。

多步检索的价值应来自实际需要，而不是因为系统已经有 Agent 框架，就强制所有查询进入 Agent Loop。

### 7. 方案 F：小片段检索，父文档回读

假设一个岗位的某个 Chunk：

> 负责知识库索引建设。

这个 Chunk 可以帮助检索系统找到岗位。

但只看它，可能不知道：

- 岗位主要职责是什么；
- 是否有其他限定条件；
- 是否是实际研发工作；
- 是否只是一项加分经历。

因此可以采用：

~~~text
问题
   ↓
检索短 Chunk
   ↓
找到所属 JD
   ↓
回读完整 JD 或父级章节
   ↓
提供完整判断证据
~~~

这种方案通常被称为 Parent-Child Retrieval。

它的主要价值不是简单增加上下文长度，而是：

**通过较小的单位发现证据，同时通过较大的单位恢复判断所需的语境。**

但它同样需要评测。

如果完整 JD 直接检索和阅读已经很好，就不一定需要复杂的父子机制。

### 8. 这些方案应该全部组合吗？

不应该。

一个系统可以按需求逐步引入：

| 已观察到的问题 | 值得尝试的方案 |
|---|---|
| 精确技术词检索已经很好 | 保留 BM25 |
| 不同表达导致漏召回 | 测试 Embedding |
| 词法与语义漏召回互补 | 测试 Hybrid |
| 一个问法覆盖不足 | 测试查询改写 |
| 问题需要多个证据 | 测试多步检索 |
| 命中片段缺少上下文 | 测试父文档回读 |
| 需要全库完整统计 | 不走有界 Retrieval，改用完整查询 |

**候选方案应由真实失败案例提出，而不是预先堆叠所有检索技术。**

## 四、怎样为 Retrieval 建立评测体系？

### 1. 为什么只看 Top-5 是否相关不够？

假设某个系统返回 5 个岗位。

人工看了以后觉得：

> 这 5 个岗位都不错。

但数据库中可能还有 20 个相关岗位没有被找到。

如果只评价返回结果的相关性，就无法发现漏召回。

因此需要区分两个方面。

**覆盖：应找到的内容有没有找到？**

**排序：已经找到的内容是否足够靠前？**

Retrieval 的评测需要同时关注这两者，但候选覆盖通常应优先得到保证。

### 2. 评测问题应该从哪里来？

应从真实用户需求出发。

对于 Job-RAG，可以设置：

| 类型 | 真实问题 | 主要风险 |
|---|---|---|
| 技术名称 | 哪些岗位涉及 vLLM？ | 专有名词漏召回 |
| 同义表达 | 哪些岗位负责企业知识库建设？ | 语义表述差异 |
| 工作职责 | 哪些岗位真正负责模型服务部署？ | 公司介绍干扰 |
| 技术深度 | 哪些岗位涉及推理服务性能优化？ | 只会调用 API 的误匹配 |
| 组合条件 | 哪些岗位同时涉及 RAG 和 Agent Runtime？ | 多证据缺失 |
| 复杂条件 | 哪些岗位必须有 RAG 落地经验？ | 优先与必备混淆 |
| 无答案 | 是否存在某种明确不在语料中的岗位？ | 无依据强行匹配 |

其中最后两类问题需要注意：

检索返回相关主题并不等于最终条件成立。

对于这些案例，应把候选覆盖与最终业务判断分别标注。

### 3. 一条完整评测案例应该包含什么？

例如：

**用户问题**

> 找真正负责 vLLM 推理服务生产部署的岗位。

**直接相关的 JD**

> 负责模型服务部署与运维，使用 vLLM、SGLang 等推理引擎构建生产推理服务。

**容易混淆的 JD**

> 熟悉调用大模型 API，负责业务应用开发。

**预期相关性**

- 第一份：直接相关；
- 第二份：部分技术背景相关，但不符合主要职责；
- 其他岗位：根据原文分别判断。

**关键证据**

保存岗位职责中的对应原文。

建议一条案例至少包含：

| 字段 | 作用 |
|---|---|
| question | 用户真实问题 |
| eligible_scope | 允许搜索的岗位范围 |
| relevant_job_ids | 已核验相关岗位 |
| relevant_evidence | 原文证据 |
| relevance_grade | 相关程度 |
| exclusion_reason | 不符合的原因 |
| judgment_scope | 标注是否完整 |
| case_type | 问题类别 |

特别需要区分：

**已知正例**与**全部正例**。

只标注了一个相关岗位，不能证明数据库中不存在其他相关岗位。

### 4. 应该使用哪些指标？

#### 岗位 Recall@K

检验前 K 个候选找回多少真正相关的岗位。

如果经过完整审阅有 10 个相关岗位，Top-20 找到 8 个：

\[
Recall@20=80\%
\]

#### Evidence Hit@K

检验完成任务所需的原文证据是否进入候选。

找到岗位但只找到公司介绍，不一定是有效的证据命中。

#### Precision@K

检验前 K 个结果中多少真正相关。

它可以反映候选污染程度，但如果标注不完整，就不能直接将未标注候选当成不相关。

#### nDCG@K

如果人工给岗位标注不同相关程度，可以评价高相关岗位是否排在更靠前的位置。

#### 运行成本

记录：

- 查询延迟；
- 不同检索通道的调用次数；
- 模型费用；
- 候选数量；
- 下游需要阅读的 Token。

这些指标应该一起看。

### 5. 为什么要分开评测岗位和 Chunk？

Job-RAG 中一份 JD 可以切成多个 Chunk。

假设：

~~~text
检索结果：
1. 岗位 A / Chunk 1
2. 岗位 A / Chunk 2
3. 岗位 A / Chunk 3
4. 岗位 B / Chunk 1
5. 岗位 C / Chunk 1
~~~

如果只看 Chunk Top-5，会觉得系统返回 5 个候选。

但实际只有 3 个岗位。

因此对 Job-RAG 应同时检查：

- Chunk 级证据召回；
- 岗位级候选召回；
- 同一岗位的聚合方式；
- 候选中是否包含足够的原文。

**用户要找的是岗位，不是 Chunk。**

检索内部的计分单位和最终业务对象不能混淆。

### 6. 怎样证明 Hybrid 比单一检索更好？

设计三套方案：

- A：BM25；
- B：Embedding；
- C：BM25 + Embedding。

固定：

- JD 数据；
- Chunking；
- 测试问题；
- 硬条件；
- 候选预算；
- 岗位级聚合；
- 标注标准。

然后比较每条问题：

- A 找到了哪些独有相关岗位；
- B 找到了哪些独有相关岗位；
- C 是否成功保留两者优势；
- C 是否引入新的无关候选；
- 哪些候选因为融合被挤出 Top-K。

如果 C 在目标问题上带来稳定覆盖收益，才有理由保留 Hybrid。

### 7. 怎样证明查询改写确实有用？

需要建立一个无改写基线。

例如：

**A：只检索原始问题。**

**B：原始问题 + 两条改写。**

**C：原始问题 + 四条改写。**

同时记录：

- 每条改写新增的唯一相关岗位；
- 重复候选数量；
- 错误扩展比例；
- 硬条件是否被改变；
- 查询延迟与成本。

还要检查：

**新增查询是否真的带来新证据，还是只是把相同岗位重复找到？**

如果增加四条改写，只多找到一个低相关岗位，成本却大幅增加，就不一定值得采用。

### 8. 为什么评测要保留具体失败案例？

假设 Hybrid 的 Recall@20 从 80% 提升至 85%。

我们还需要知道：

- 改善的是同义表达还是精确技术词；
- 哪些岗位被找回；
- 哪些岗位反而丢失；
- 某些改写是否改变业务条件；
- 是否只在少数查询上有效。

因此评测报告不能只有平均分。

**每一次明显的改善或退化，都应该能够追溯到具体问题、岗位和原文证据。**

## 五、怎样理解 Retrieval 实验结果？

### 1. 返回更多候选，是否必然意味着召回更好？

一般来说，增大候选预算会给系统保留更多内容的机会。

但有两个问题。

**第一，新增内容是否真的相关？**

例如 Top-20 已经找到全部关键岗位，扩大到 Top-100 可能主要增加无关岗位。

**第二，后续模型是否有能力处理这么多候选？**

检索阶段返回更多内容，会增加后续的上下文组织、重排或模型判断成本。

因此不能无限扩大 Top-K。

真正需要研究的是：

> 在目标任务的质量要求下，候选预算应该设置为多少？

### 2. 为什么 Recall 提高，最终答案反而可能变差？

假设 Retrieval 从 20 个候选扩展到 100 个候选。

新增了几个正确岗位，同时也引入大量相似但不符合条件的 JD。

如果后续系统没有可靠地选择证据，就可能出现：

- 正确证据被无关内容稀释；
- 不符合条件的岗位被误选；
- 上下文超过预算；
- 关键条件被截断。

所以，Retrieval 的覆盖提升不一定自动转化为答案质量提升。

这不是说应该减少召回，而是说明：

**候选生成和后续证据选择需要分别设计、分别评测。**

### 3. 为什么 RRF 分数提高不等于岗位更匹配？

RRF 根据各检索列表中的排名计算融合分。

某个岗位可能因为同时出现在多个改写查询中而得到更高的融合分。

但多个改写可能具有同样的偏差。

例如：

> 公司提供 RAG 产品。

这种内容可能在“RAG”“知识库”“智能问答”等多个查询中都排得较高。

RRF 会汇总这些排名信号，却不会自动判断它属于公司介绍而不是实际岗位职责。

因此：

**多路检索的一致命中，并不等于业务语义得到核实。**

### 4. 为什么种子岗位没有命中，不一定代表检索失败？

这是 Job-RAG 现有实验中非常重要的发现。

假设某个问题的预设正例是岗位 A。

检索系统没有将 A 排进前 10，却找到了岗位 B。

岗位 B 的 JD 可能与用户问题同样相关，甚至更加符合用户目标。

如果评测只标注 A 为正例，系统找到 B 仍可能被记为失败。

这并不意味着需要篡改原始排名。

真正需要做的是：

- 保留原始实验结果；
- 审阅新发现的候选；
- 补充独立相关性标注；
- 重新计算具有明确标注范围的指标。

**不能把“没有命中预先指定的某条 JD”等同于“没有找到用户需要的答案”。**

### 5. 为什么不应该只选择综合得分最高的方案？

假设：

- BM25 在精确技术名词上表现很好；
- Embedding 在语义改写问题上更好；
- Hybrid 在部分问题上表现稳定；
- 多查询对少数复杂问题有帮助，但增加较大延迟。

这时未必需要所有查询都采用同一策略。

可以进一步研究：

> 不同任务是否适合不同的检索路线？

但引入任务路由本身也需要新的评测。

如果路由错误，可能使本来简单可靠的查询进入更差的检索方式。

所以不应因为“动态路由”听起来更先进，就认为它一定优于简单的固定策略。

## 六、发现检索失败后，怎样定位问题？

### 1. 为什么搜不到岗位，不一定是 Retrieval 算法的问题？

假设用户问：

> 哪些岗位要求 RAG 和 Agent Runtime 的开发能力？

某条真实相关岗位没有出现在结果中。

可能原因包括：

1. 采集阶段没有取得该 JD；
2. 文档解析遗漏了职责；
3. 文档切分破坏了条件关系；
4. Embedding 没有正确表示该内容；
5. 数据库索引不是当前版本；
6. 查询路由选择了错误方式；
7. 查询改写改变了原意；
8. 硬条件过滤错误；
9. 检索候选预算不足；
10. Chunk 到岗位聚合时丢失候选；
11. Rerank 将正确岗位排到后面；
12. 最终模型误判 JD。

这些问题会表现为同一个现象：

> 用户没有看到正确岗位。

但不能都归因于 Retrieval。

### 2. 怎样沿链条定位？

~~~text
原始 JD 是否存在？
        ↓
解析结果是否保留关键内容？
        ↓
Chunk 是否包含所需证据？
        ↓
索引是否正确且为当前版本？
        ↓
硬条件是否正确？
        ↓
原始问题能否找到相关 Chunk？
        ↓
不同检索通道分别找到了什么？
        ↓
融合后是否丢失候选？
        ↓
岗位级聚合是否正确？
        ↓
Rerank 是否改变排名？
        ↓
模型是否正确理解证据？
~~~

关键是保留各阶段的中间结果。

如果只记录最终返回的 5 个岗位，就无法知道正确岗位究竟在哪个环节被丢弃。

### 3. 怎样检查硬条件过滤错误？

例如用户要求：

> 广州、月薪下限至少 20K。

某岗位薪资为：

> 15–25K。

如果系统把它纳入结果，可能是薪资下限判断错误。

另一个岗位：

> 广州，20–30K。

如果被排除，可能是薪资字段解析或过滤出错。

这类问题不能靠改变 Embedding 模型解决。

因此应当将明确条件的校验与相关性检索分开。

**硬条件不满足时，语义相似度再高也不能替代用户的明确约束。**

### 4. 怎样检查查询改写是否造成漏召回？

用户原问题：

> 负责模型推理服务底层建设的岗位。

改写后：

> AI 应用开发工程师。

这扩大了范围，也改变了核心技术深度。

如果后续结果主要来自普通 AI 应用岗位，就需要检查改写过程。

应记录：

- 原始问题；
- 改写问题；
- 每条改写的独立候选；
- 新增相关岗位；
- 新增误匹配；
- 原始硬条件。

这样才能判断改写是否有效。

### 5. 怎样检查候选融合和岗位聚合？

假设 BM25 找到了正确岗位 A。

Embedding 也找到了岗位 B。

但融合后 A 不在 Top-20。

应该检查：

- A 在 BM25 中的原始排名；
- A 是否进入融合输入；
- RRF 融合参数；
- 各路候选预算；
- Chunk 是否大量重复；
- 岗位聚合是否改变排序。

不能看到 Hybrid 漏掉 A，就立即判断 BM25 或 Embedding 有问题。

**当正确证据已经存在于某个中间阶段，却在后面消失时，优先调查发生丢失的那一步。**

### 6. 常见失败与改进方向

| 失败现象 | 优先检查 | 候选改进方向 |
|---|---|---|
| 完全找不到某个 JD | 采集、入库、索引 | 修复数据链路 |
| JD 存在但证据缺失 | 解析与切分 | 恢复原文结构 |
| 技术专有名词漏召回 | BM25 与词项处理 | 词法索引、别名 |
| 不同表达漏召回 | 语义召回 | Embedding、查询改写 |
| 地区和薪资不符合 | 硬条件过滤 | 字段与规则校验 |
| 改写后业务意图偏移 | 查询改写 | 保留约束、改写验证 |
| BM25 找到、融合后丢失 | 融合与候选预算 | 分析 RRF 与截断 |
| 多个 Chunk 占据前排 | 岗位聚合 | 先聚合或调整策略 |
| 找到岗位却缺少条件证据 | 上下文回读 | 章节或全文回读 |
| Top-K 被拿来做全库统计 | 任务路由 | 完整枚举和计数 |

所有改进方向都应该是可验证的假设，而不是直接认定的根因。

### 7. 怎样记录一个真正有价值的失败案例？

~~~text
问题：
找负责企业级 RAG 全链路研发的岗位。

预期：
岗位 A，职责包含知识接入、解析、
索引、检索、服务化和智能问答。

实际：
最终候选未返回岗位 A。

排查：
1. 原始 JD 存在。
2. Chunk 保留完整职责。
3. 当前索引版本正确。
4. BM25 中 A 排名第 8。
5. Dense 中 A 排名第 14。
6. 融合后 A 排名第 12。
7. 最终只保留 Top-10。

结论：
岗位 A 已进入检索候选，
但在最终候选预算阶段被截断。

改进假设：
适当扩大进入后续判断的候选数量。

验证：
比较 Recall@10、Recall@20、
下游排序质量、延迟与成本。
~~~

这里不能因为 A 排名第 12，就直接认定应该把 Top-K 改成 20。

还需要看真实业务收益与成本。

这正是评测的作用。

## 七、怎样让 AI 持续优化 Retrieval？

### 1. AI 可以承担哪些工作？

AI 可以：

- 理解用户问题；
- 识别查询类型；
- 提出检索表达；
- 执行多查询检索；
- 比较各通道候选；
- 分析失败案例；
- 生成优化假设；
- 修改候选融合策略；
- 运行对照实验；
- 总结改善和退化。

但是，如果直接要求：

> 优化 RAG 召回率。

AI 可能：

- 增加更多查询改写；
- 把 Top-K 调得很大；
- 替换 Embedding；
- 增加混合检索；
- 修改 Chunking；
- 加入 Agent Loop。

这些操作未必解决真实失败。

甚至会让系统更复杂，更难定位问题。

### 2. 一轮优化应该怎样组织？

**第一步：冻结数据与基线。**

保存：

- JD 数据版本；
- Chunking 版本；
- 模型和索引签名；
- 测试问题；
- 硬条件；
- 相关性标注；
- 当前检索结果。

**第二步：观察真实失败。**

重点记录：

- 漏掉哪些相关岗位；
- 为什么漏掉；
- 哪个检索通道曾找到；
- 哪个阶段发生丢失。

**第三步：提出改进假设。**

例如：

> 当前 BM25 对技术词效果较好，但“企业知识库建设”类问题存在语义漏召回。引入 Embedding 通道可能补足这类问题。

**第四步：最小范围修改。**

尽量只改变一个主要因素。

例如只增加 Dense 通道，不同时修改 Chunking、RRF 和查询改写。

**第五步：运行完整回归。**

检查：

- 目标失败是否改善；
- 其他类型问题是否退化；
- Recall 和证据命中是否变化；
- 延迟与成本是否增加。

**第六步：作出决策。**

只有存在可信收益时才保留新方案。

### 3. 怎样让 AI 自主决定是否继续检索？

对于复杂问题，AI 可以在检索后检查：

> 当前是否已经获得完成任务所需的证据？

但必须明确“足够”的含义。

例如：

**问题：找三个符合条件的岗位。**

可能只需要获得若干高相关候选并完成原文核验。

**问题：比较两个指定岗位。**

已经知道岗位 ID，应直接读取全文，不需要反复搜索。

**问题：统计全部 RAG 岗位的技术要求。**

即使找到了 20 个高相关岗位，也不能据此认为统计已经完整。

因此，继续检索或停止检索的判断应当依赖任务目标：

| 任务 | 可能的停止依据 |
|---|---|
| 找几个岗位 | 已有足够经过核验的候选 |
| 指定 JD 比较 | 指定文档已完整读取 |
| 多条件制度问答 | 所有必要条件与例外已有证据 |
| 全库字面统计 | 目标范围已完整枚举 |
| 全库语义统计 | 目标范围全部判定或明确披露未完成 |

这比设置“Agent 最多检索三次”更贴近业务目标。

不过，实际运行仍应设置最大调用次数、成本和时延预算，避免无限循环。

### 4. 怎样给 AI 下达一个有效的 Retrieval 优化任务？

> 请使用当前冻结的岗位数据库、文档索引、检索配置与评测集，评价 Retrieval 的候选召回能力。
>
> 首先确认每条问题的查询类型、硬条件、目标业务对象和人工相关性标注范围。
>
> 分别运行 BM25、Dense 与 Hybrid 基线，记录各通道原始候选、融合结果及岗位级排名。
>
> 分析漏召回案例，判断问题发生在上游数据、查询表达、过滤、单路召回、融合、岗位聚合还是候选截断。
>
> 针对已确认的问题提出可验证假设，一轮只改变一个主要因素。
>
> 比较岗位 Recall@K、证据 Hit@K、nDCG@K、典型改善、退化以及成本和延迟。
>
> 标注不完整时不得将未知候选当作负例，不得将 Top-K 候选数量解释为全库总数。
>
> 不在未通过评测时替换正式检索策略。

这类指令的意义在于：

**AI 可以承担优化执行，但工程负责人必须明确目标、判断标准与不可违反的业务约束。**

## 八、Job-RAG 实践：当前 Retrieval 设计怎么样，下一步怎么优化？

### 1. Job-RAG 当前检索流程是什么？

根据当前 [Retrieval 模块说明](https://github.com/leecolin2023/job-rag/blob/main/job_rag/retrieval/README.md)，Job-RAG 的候选检索包含：

~~~text
用户问题
    ↓
识别明确的结构化条件
    ↓
筛选符合条件的岗位
    ↓
BM25 词法检索
    ↓
可选 Embedding 语义检索
    ↓
第一次 RRF：融合 Chunk 排名
    ↓
将 Chunk 聚合为岗位
    ↓
必要时执行多个改写查询
    ↓
第二次 RRF：融合岗位排名
    ↓
返回岗位候选与来源证据
    ↓
按需读取完整 JD
~~~

需要注意：

**这是当前代码所描述的检索机制，不意味着所有模型通道在所有部署环境中都已启用。**

例如 Embedding 未配置或不可用时，系统仍可以使用 BM25。

当前在线 Retrieval 也没有默认接入完整的专用 Reranker。

因此应区分代码能力、离线实验和线上实际启用状态。

### 2. 为什么当前采用两次 RRF？

第一次发生在**同一个查询内部**。

~~~text
用户查询
   ↓
BM25 Chunk 排名
Embedding Chunk 排名
   ↓
RRF 融合
   ↓
Chunk 候选
~~~

根据现有 README，两个通道各最多提供前 100 个 Chunk 参与融合，使用常见的 `k=60` 常数。

第二次发生在**多个查询之间**。

~~~text
原始问题 → 岗位排名 A
改写 1  → 岗位排名 B
改写 2  → 岗位排名 C
             ↓
         第二次 RRF
             ↓
         综合岗位排名
~~~

当前 `candidates()` 支持原始问题加最多四条额外改写，每个问法检索最多 30 个岗位，再进行岗位级融合。

这两个步骤解决的不是同一件事。

| 融合 | 对象 | 目的 |
|---|---|---|
| 第一次 RRF | BM25 和 Embedding 的 Chunk 排名 | 合并不同匹配方法 |
| 第二次 RRF | 多个查询的岗位排名 | 合并不同问题表达 |

这种设计的优势是能够把不同检索信号组织起来。

但更复杂并不等于一定更好。

下一步需要通过对照实验回答：

- 一次 RRF 是否比单一通道更好？
- 第二次 RRF 是否带来额外相关岗位？
- 是否存在重复查询造成的无意义排名强化？
- 多查询成本是否值得？

### 3. 当前岗位聚合方案有什么值得研究？

当前检索会将同一个来源岗位的多个 Chunk 合并，并根据岗位第一次出现在 Chunk 排名中的位置决定岗位顺序。

同时，每个岗位最多附带两个命中 Chunk 作为证据。

这种做法能够避免一个岗位的多个 Chunk 在最终列表中重复出现。

但它还有值得验证的问题。

假设：

**岗位 A**

有一个 Chunk 高度相关，其余内容无关。

**岗位 B**

有三个 Chunk 分别提供了相关职责、技术要求和项目经验。

如果只依据最靠前 Chunk 决定岗位顺序，可能高估 A 的单一局部匹配，而没有充分体现 B 的多方面匹配。

这不是说应该立即改成“所有 Chunk 分数求和”。

因为求和也可能让长 JD 因为 Chunk 更多而获得不合理优势。

更合理的是设计对照：

- 最佳 Chunk 排名；
- 多 Chunk 聚合；
- 先召回再阅读完整 JD；
- 基于岗位全文的二次判断。

然后比较具体问题上的结果。

**岗位聚合是一项需要独立评测的检索设计，而不是无关紧要的实现细节。**

### 4. 当前最值得关注的实验问题是什么？

根据 [Job-RAG 逐项召回审阅](https://github.com/leecolin2023/job-rag/blob/main/docs/recall-case-audit-2026-10-25.md)，此前真实 Embedding 实验包含 592 条有正文 JD 和 30 条查询。

其中有一个非常值得注意的现象。

对于问题：

> 找负责企业知识接入、检索策略和回答生成全流程建设的工程岗位。

某种章节向量方案没有把预设的种子岗位排到前面。

但它与 BM25 的 Top-1 都找到了一条高度相关的“知识库开发工程师（RAG 方向）”。

该岗位实际涉及：

- 知识接入；
- 文档解析；
- 索引；
- 检索；
- 服务化；
- 混合检索；
- Rerank；
- 引用溯源。

这说明：

**如果只检查预设种子岗位的排名，可能把找到了真正相关岗位的系统错误判为失败。**

所以当前最优先的工作不是增加检索复杂度，而是改善相关性标注。

### 5. 下一轮应该优先做什么？

#### 第一优先级：补齐完整的候选池相关性判断

将 BM25、Dense、Hybrid 等方案返回的候选合并成一个统一审阅池。

对候选逐一判断：

- 是否符合硬条件；
- 是否真正涉及目标工作；
- 属于什么相关程度；
- 是否有岗位职责证据；
- 是否只是公司背景；
- 是否满足关键技术深度。

所有标注应回到 JD 原文。

如果只完成候选池审阅，不能假装已经穷尽数据库全部相关岗位，应在指标中保留相应限定。

#### 第二优先级：建立三个基本检索基线

建议先比较：

**A：BM25**

**B：Dense Embedding**

**C：Hybrid**

固定：

- 同一批 JD；
- 同一 Chunking；
- 同一测试问题；
- 同一硬条件；
- 同一岗位聚合；
- 同一候选预算。

观察它们实际找回的相关岗位。

在这一阶段，不先加入查询改写和 Reranker。

否则无法清楚判断收益来自哪里。

#### 第三优先级：独立验证多查询的收益

在确定一个稳定的单查询基线后，再比较：

- 无改写；
- 少量改写；
- 多条改写。

重点记录：

- 原始问题找到哪些岗位；
- 每条改写新增什么岗位；
- 哪些新增岗位真正相关；
- 改写是否偏离用户目标；
- 多查询是否导致某些重要岗位排名退化。

如果多查询只在特定复杂问题上有效，可以考虑按任务类型启用，而不必让所有问题都默认改写。

#### 第四优先级：比较岗位聚合和父文档回读

重点验证：

- 当前按最佳 Chunk 排名是否合理；
- 多个 Chunk 的证据应该怎样组合；
- 小 Chunk 命中后是否需要回读完整 JD；
- 完整 JD 回读是否改善后续条件判断；
- 上下文预算是否发生浪费。

这能够把前面《03 · 文档切分》的研究与当前 Retrieval 直接联系起来。

#### 第五优先级：再考虑 Agentic Retrieval

只有当实际问题经常需要多轮检索，并且单查询或多查询仍难以提供完整证据时，才值得引入更复杂的 Agent 决策。

例如：

> 先找到涉及模型部署的岗位，再判断哪些还涉及 Agent Runtime。

或者：

> 找到一般制度条款后，继续搜索适用的例外条款。

但也要设置明确的停止条件和成本约束。

不能让 Agent 通过不断增加搜索次数来代替有效的评测与问题归因。

### 6. 如何与后面的 Rerank 研究衔接？

建议明确两轮实验。

**第一轮：Retrieval 实验**

目标是：

> 正确候选有没有进入候选集合？

固定评测集，比较：

- BM25；
- Dense；
- Hybrid；
- Query Rewrite；
- 候选预算；
- 岗位聚合。

评价岗位召回与证据覆盖。

**第二轮：Rerank 实验**

目标是：

> 在相同的候选集合中，能否把更相关的候选排在前面？

冻结 Retrieval 产生的候选集合。

再比较：

- 不重排；
- 简单规则排序；
- 专用 Reranker；
- 模型辅助排序。

评价前排质量、业务判断及成本。

这样才能避免：

> 召回范围变大和排序模型增强同时发生，最后不知道究竟是哪项改动改善了结果。

这一点也符合当前 Job-RAG 实验框架的设计方向。

### 7. 下一轮应该形成怎样的报告？

| 报告内容 | 需要回答的问题 |
|---|---|
| 研究问题 | 本轮要解决什么检索失败 |
| 测试范围 | 搜索哪些 JD、什么版本 |
| 用户问题 | 哪些真实任务 |
| 硬条件 | 是否完整保留 |
| 候选生成 | 各通道分别找到什么 |
| 相关性标注 | 判断范围是否完整 |
| 岗位召回 | 有哪些相关岗位进入候选 |
| 证据召回 | 关键职责和要求是否命中 |
| 融合变化 | 哪些候选因融合前进或丢失 |
| 失败归因 | 最早错误发生在哪里 |
| 性能成本 | 延迟、Token、模型请求 |
| 最终决策 | 保留、回退或继续验证 |

例如：

~~~text
研究问题：
多查询是否改善 Job-RAG 对
模型服务岗位的召回？

基线：
原始问题 + Hybrid。

实验：
A：不进行查询改写。
B：原问题 + 2 条改写。
C：原问题 + 4 条改写。

固定：
JD、Chunking、Embedding、
硬条件、岗位聚合、评测标准答案。

验证：
1. 相关岗位 Recall@20；
2. 关键证据 Hit@20；
3. 各改写带来的独有相关岗位；
4. 查询偏移与无关候选；
5. 延迟与费用。

决策：
按问题类别判断多查询是否有价值，
不预设查询越多越好。
~~~

这一轮最重要的不是让模型生成更丰富的检索表达。

而是验证：

**增加检索操作，究竟有没有找回以前遗漏的有效证据？**

---

## 结语：Retrieval 的核心不是把检索算法堆得越来越多

我们从一个看似简单的问题开始：

> 用户问一个问题，知识库应该怎样搜索？

但真正值得研究的是：

**第一，用户究竟需要什么操作？**

是找几个候选、读取指定文档，还是完整统计？

**第二，应该搜索哪些资料？**

怎样区分不能妥协的硬条件和需要判断的相关性条件？

**第三，怎样定义检索质量？**

是否找到了正确的岗位和原文证据，而不只是返回了许多看起来相关的片段？

**第四，怎样比较不同检索方案？**

BM25、Embedding、Hybrid、多查询和父文档回读分别带来什么收益？

**第五，发现遗漏后怎样定位问题？**

是上游数据缺失、查询表达不足、过滤错误、候选截断，还是后续排序与判断失败？

**第六，怎样利用 AI 持续改进？**

能否让 AI 根据真实失败提出可验证的假设，执行对照实验，并依据结果决定是否修改方案？

这些问题比记住某个 RRF 常数、Top-K 参数或查询改写 Prompt 更重要。

> **Retrieval 的真正目标，不是返回更多看起来相关的文档，而是在明确范围和成本约束下，为后续任务尽可能完整地找到正确、可信、可追溯的候选证据。**

这也意味着：

**检索系统是否优秀，不能只看使用了多少种算法，而要看它能否解释自己找到了什么、遗漏了什么、为什么遗漏，以及下一步应该怎样改进。**
