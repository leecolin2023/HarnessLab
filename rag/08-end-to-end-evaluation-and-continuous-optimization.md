# RAG 端到端评测与持续优化：如何证明知识库真正解决了问题？

> 本文是 RAG 工程系列的第八篇专题文章，承接前面的文档采集、解析、切分、Embedding 与索引、Retrieval、Rerank，以及上下文组织与答案生成。
>
> 前七篇分别研究 RAG 的不同工程环节。本篇换一个角度：**如果整个 RAG 系统已经运行起来，怎样证明它真正完成了用户的任务？当它失败时，怎样知道应该修改哪个环节？**
>
> 本文以 Job-RAG 招聘岗位知识库为主要案例，沿用问题驱动的学习方法，重点研究端到端任务评测、标准答案构造、失败归因、对照实验、自动评测与持续回归。不以某个 RAG 评测框架的 API 使用方法为主要目标。

---

## 一、为什么需要端到端评测？每个环节都已经评测过了，不够吗？

### 1. 我们究竟想知道 RAG 系统好不好？

假设我们已经为 Job-RAG 完成了很多工作：

- 文档采集：获得了数百份招聘 JD；
- 文档解析：保留了原文及部分章节结构；
- 文档切分：针对职责和任职要求生成 Chunk；
- Embedding：能够计算语义相似度；
- Retrieval：能够返回相关岗位；
- Rerank：能够调整候选顺序；
- 答案生成：能够根据证据输出分析。

而且每个环节都有自己的指标。

例如：

| 环节 | 看起来不错的指标 |
|---|---|
| 文档采集 | 正文获取率 99% |
| 文档解析 | 文字准确率 99% |
| Retrieval | 已知正例命中率 90% |
| Rerank | nDCG@5 提升 |
| 答案生成 | 引用编号有效率 100% |

这些指标全部不错，是否意味着用户的问题一定得到解决？

不一定。

假设用户真正想问：

> 统计岗位职责或者任职要求出现 RAG 的全部岗位，它们还有哪些技术要求？

系统可能运行了以下流程：

~~~text
用户提出统计问题
        ↓
Embedding 检索相关岗位
        ↓
返回 Top-20
        ↓
Rerank 排序
        ↓
大模型阅读这 20 个岗位
        ↓
生成一份技术要求统计报告
~~~

报告可能写得非常流畅：

> Python、LangChain、向量数据库和 Agent 是常见技术要求。

但如果数据库中实际有 80 个符合条件的岗位，而系统只分析了 20 个候选，那么整份统计报告的基础就有问题。

即使这 20 个岗位的检索排名非常准确，也不能把它们当作全部研究对象。

这说明：

**局部技术指标优秀，不代表系统完成了用户真正要求的任务。**

### 2. 为什么局部正确不一定带来整体正确？

因为 RAG 不是多个独立算法的简单相加。

前一环节的输出，会成为后一环节的输入。

例如：

~~~text
文档采集遗漏了某份 JD
        ↓
解析阶段没有机会处理
        ↓
索引中不存在对应内容
        ↓
Retrieval 不可能召回
        ↓
Rerank 不可能重新排序
        ↓
答案生成无法引用其证据
~~~

假设每个环节的某项成功率都是 95%。

如果这些成功条件相互独立，且一次任务必须同时经过全部七个环节，那么一个简化的成功率计算是：

\[
0.95^7 \approx 69.8\%
\]

这只是说明串行流程可能累积失败风险的数学示例，**不能据此估计真实 RAG 系统的任务成功率**。

现实中的错误并不独立，而且有些环节可以恢复或绕过。

但它揭示了一个重要问题：

> **不能仅根据每个模块的平均指标，推断整个系统最终完成任务的概率。**

必须实际运行完整任务。

### 3. 什么是 RAG 端到端评测？

端到端评测（End-to-End Evaluation）指的是：

**从真实用户问题出发，让系统执行必要的完整工作流程，再根据用户任务是否被正确完成来评价结果。**

例如：

**用户任务**

> 从当前岗位库中，找出所有在岗位职责或任职要求出现 RAG 的岗位，并统计这些岗位要求的其他技术。

**系统实际执行**

1. 判断这是全库统计任务；
2. 确定数据库范围；
3. 完整枚举岗位；
4. 检查职责和任职要求；
5. 抽取技术要求；
6. 保留来源证据；
7. 程序化去重和统计；
8. 生成报告。

**最终评测**

不是只问：

> 检索找到了多少相关岗位？

而是：

> 整个任务是否按照正确范围执行完毕？筛选、判断、计数、证据和报告是否正确？

这才是端到端评测。

### 4. 端到端评测是否意味着不再需要局部评测？

恰恰相反。

如果系统回答错误，仅有最终分数，我们无法知道应该修改哪里。

例如：

> 用户问题回答错误，整体得分 0.4。

这个结果无法指导工程改进。

所以应该同时保留三个层次：

| 评测层次 | 主要问题 |
|---|---|
| 端到端评测 | 用户任务最终完成了吗？ |
| 链路诊断 | 正确证据或结果在哪一步丢失？ |
| 局部评测 | 具体模块修改后是否真的改善？ |

这三者不是竞争关系。

更合理的顺序是：

**先用端到端结果发现真实问题，再通过链路诊断定位原因，最后用局部实验验证改进。**

### 5. 最终要建立什么能力？

端到端评测真正要解决的，不是如何给每次回答打一个分数。

而是形成一种可靠的改进机制：

~~~text
真实用户任务
       ↓
运行完整 RAG 系统
       ↓
判断任务是否成功
       ↓
分析失败原因
       ↓
提出改进假设
       ↓
局部对照实验
       ↓
完整回归验证
       ↓
决定保留或回退
~~~

这就是本篇文章的主线。

## 二、怎样定义 RAG 的端到端任务成功？

### 1. 为什么不能所有问题都用同一套评分标准？

来看三个问题。

**问题 A**

> 找三个真正负责 RAG 研发的岗位。

**问题 B**

> 岗位 A 的 RAG 项目经验是必备还是优先？

**问题 C**

> 统计全部符合条件岗位的技术要求。

它们的成功标准明显不同。

| 问题 | 什么叫成功？ |
|---|---|
| 找三个岗位 | 找到三个经过原文核验、符合条件的岗位 |
| 判断必备还是优先 | 正确判断条件性质并提供依据 |
| 全库统计 | 对明确范围完成全部必要检查，准确计数并披露未知 |

如果采用统一的“答案相关性”指标，系统可能在三个任务上都得到较高评分。

但实际只有前两个完成了目标。

所以第一步不是选择指标，而是：

**先区分用户究竟要求系统完成哪一种工作。**

### 2. 最基本的任务类型有哪些？

结合 Job-RAG，可以先分成五类。

| 任务类型 | 用户问题 | 成功判定重点 |
|---|---|---|
| 查找候选 | 找几个做 RAG 开发的岗位 | 相关性、条件满足、证据 |
| 指定查询 | 岗位 A 的任职要求是什么 | 原文准确、版本正确 |
| 业务判断 | RAG 经验属于必备还是优先 | 条件性质、证据支持 |
| 多文档比较 | A 与 B 哪个更偏平台研发 | 比较维度、证据完整 |
| 全库统计 | 所有 RAG 岗位要求哪些技术 | 范围完整、逐项判断、可复算 |

还需要包括：

- 无答案问题；
- 来源冲突问题；
- 资料已过期问题；
- 权限不足问题；
- 恶意文档干扰问题。

这些不是为了让评测集看起来全面，而是因为它们对应不同的真实失败风险。

### 3. 怎样为一个任务定义成功条件？

以岗位统计任务为例。

用户问：

> 统计岗位职责或者任职要求出现 RAG 的岗位，它们还要求哪些技术。

可以拆成几个独立条件。

**条件一：研究范围正确。**

例如只统计当前数据库中的岗位，而不是宣称覆盖整个招聘市场。

**条件二：岗位筛选正确。**

只纳入职责或任职要求符合定义的岗位。

**条件三：目标岗位处理完整。**

没有漏掉尚未检查的岗位。

**条件四：技术抽取正确。**

不能凭空增加技术，也不能把否定条件反向解释。

**条件五：统计正确。**

相同岗位不能重复计数，统计结果能够重新计算。

**条件六：证据可回查。**

关键数字和技术判断能够关联原文。

**条件七：结论没有超出数据范围。**

不能把当前采集样本解释成整个市场的事实。

这样才能形成可以实际验收的标准。

### 4. 是否应该给这些条件设置一个综合分数？

可以建立综合指标，但不要过早这样做。

因为某些错误具有决定性。

例如：

- 系统完整分析了 20 个岗位，却声称统计了全部 100 个岗位；
- 系统正确生成了 99 个技术标签，但有一项将“优先”误写为“必须”；
- 系统答案很完整，但引用了用户无权访问的文档。

这些问题不能简单用其他高分抵消。

建议先区分：

**必须通过的条件：**

例如数据权限、明确的任务范围、关键事实保真、统计完整性声明。

**可以比较的质量指标：**

例如排序质量、报告可读性、响应延迟、Token 成本。

对于重要任务，可以采用：

> 必要条件全部满足后，再比较质量与成本。

而不是将所有维度加权成一个总分。

### 5. 怎么避免系统过度拒答？

强调“证据不足不能乱答”，并不意味着模型越保守越好。

例如原文已经明确写着：

> RAG 项目经验属于优先条件。

如果模型回答：

> 无法确定。

也没有完成任务。

因此需要同时评价：

- 证据充分时能否正确回答；
- 证据不足时能否合理说明；
- 是否出现无依据推断；
- 是否出现不必要的拒答。

**可信的系统不是永远保守，而是知道什么时候已经有足够依据。**

## 三、怎样建立真正有价值的端到端评测集？

### 1. 为什么不能直接让 AI 生成 100 道问题？

假设 AI 从某份 JD 中读到：

> 熟悉 Python、LangChain 和向量数据库。

然后生成：

> 这份 JD 要求哪些 AI 开发技术？

再把这份 JD 指定为唯一标准答案。

这样的测试确实能够检查系统是否找回该 JD。

但它可能存在两个问题：

**第一，问题来源和标准答案高度绑定。**

系统可能因词汇重复而容易命中。

**第二，真实用户的需求并不一定是寻找这份特定 JD。**

用户可能只是想找符合某类技术方向的岗位。

如果系统找到了另一份同样相关的 JD，却没有命中预设种子，就可能被错误评价为失败。

因此：

> **评测问题应该尽量反映真实用户任务，而不能只从某份文档反推问题，再将该文档视为唯一正确答案。**

### 2. 好的评测数据应该从哪里来？

可以考虑四类来源。

**第一类：真实用户问题。**

例如实际问过的岗位检索、制度查询和统计问题。

它们最能反映产品实际用途。

**第二类：历史失败案例。**

例如之前 Job-RAG 对“统计 RAG 岗位技术要求”给出了无法使用的报告。

这类案例可以直接转化为回归测试。

**第三类：人为设计的边界案例。**

例如：

- 必备与优先；
- Python 或 Java；
- 公司背景与岗位职责；
- 不同文件的生效时间；
- 检索结果为空。

**第四类：AI 辅助生成的补充案例。**

AI 可以帮助扩展表达、制造结构变化、补齐边界类型。

但这些案例需要核验，不能直接把生成的问题和答案当作已验证事实。

### 3. 一条评测案例应该包含什么？

建议采用以下结构。

| 字段 | 作用 |
|---|---|
| case_id | 测试案例身份 |
| task_type | 任务类型 |
| user_question | 用户真实问题 |
| corpus_ref | 冻结的数据范围与版本 |
| expected_behavior | 系统应该完成什么工作 |
| required_evidence | 必需原文或数据依据 |
| expected_result | 经过核验的期望结果 |
| forbidden_behavior | 不允许出现的错误 |
| judgment_scope | 标注范围和完整性 |
| severity | 失败的业务严重程度 |

例如：

~~~yaml
case_id: job-rag-stat-001

task_type: exhaustive_analysis

user_question: >
  统计岗位职责或任职要求出现 RAG 的岗位，
  它们还要求哪些技术。

expected_behavior:
  - 确定完整数据库范围
  - 检查职责与任职要求
  - 逐份抽取技术条件
  - 保留岗位及原文证据
  - 去重并生成统计报告

forbidden_behavior:
  - 将 Top-K 当作全部岗位
  - 将公司介绍当作岗位职责
  - 将优先条件写成必备条件
  - 虚构没有计算过的统计数字
~~~

这里还没有提供具体的期望岗位数量。

这是因为真实统计结果必须基于冻结的数据和人工核验产生，不能为了填写评测表而编造。

### 4. 为什么必须冻结数据版本？

假设今天数据库有 592 条非空 JD。

明天新增了 20 条，另有 5 条内容发生变化。

如果两次实验使用不同的数据库，却直接比较结果，就可能把数据变化误认为算法改善。

因此每次正式实验至少应固定：

- 语料内容或可复原快照；
- 文档版本；
- 解析与切分配置；
- 索引签名；
- 用户问题；
- 评测标准。

这里需要区分：

**版本指纹：**

用于检查数据是否发生变化。

**真正持久化的快照：**

能够在未来重新获得完全相同的测试数据。

只有哈希或 `corpus_id` 不代表历史数据已经保存。

如果旧版本已经被覆盖，仅有哈希不能自动恢复原文。

### 5. 为什么要区分 Seed、Pooled 和 Exhaustive 标注？

这是 Job-RAG 特别需要保留的设计。

**Seed：已知种子正例。**

例如人工确认一个岗位与问题相关。

只能说明这个岗位是正例，不能推断其他岗位都不相关。

**Pooled：候选池审阅。**

把 BM25、Dense、Hybrid 等多个系统返回的候选合并，统一进行人工判断。

这能大幅改善标注质量，但仍可能漏掉没有进入候选池的相关文档。

**Exhaustive：明确范围内的穷尽判断。**

对指定数据库范围内每个候选对象完成判定。

只有满足真正的完整性要求，才能对该范围使用完整召回率等解释。

这三者不能相互冒充。

尤其不能因为：

> Seed Recall@20 = 100%。

就宣称：

> 整个数据库所有相关岗位已全部召回。

### 6. 怎样建设训练、开发和测试分组？

建议至少区分：

**开发集（Dev）**

用于研究错误、选择方案和调节参数。

**独立测试集（Test）**

用于验证没有参与调参的问题。

**固定回归集（Regression）**

收录过去出现过的严重失败，要求后续修改不能重新引入。

还可以保留一个较少查看的最终验收集。

如果同一个问题只改变几个同义词，不能把两个版本分别放进开发集和测试集，再认为它们完全独立。

同样，如果针对测试集持续调整 Prompt，测试集也会逐渐变成事实上的开发集。

### 7. 初始评测集应该有多大？

不必一开始就追求数千个案例。

对于仍处于工程探索期的 Job-RAG，可以先建立一批人工核验的真实任务。

例如：

| 任务类型 | 建议初始案例 |
|---|---:|
| 查找候选岗位 | 10 |
| 指定文档事实查询 | 5 |
| 复杂任职条件判断 | 10 |
| 多岗位比较 | 5 |
| 全库统计 | 5 |
| 无答案、冲突和版本边界 | 5 |
| 合计 | 40 |

这些数量只是初始工作安排，不是行业标准。

更重要的是每条案例是否具有：

- 真实任务目标；
- 可核验依据；
- 明确的成功条件；
- 典型错误类型。

**先有少量高质量案例，再根据失败不断扩充，通常比一次生成大量低质量题目更有效。**

## 四、怎样运行真正的端到端实验？

### 1. 一次端到端实验应该执行什么？

最直接的办法是让系统像真实用户使用时一样运行。

~~~text
读取测试问题
       ↓
调用真实业务入口
       ↓
执行任务路由
       ↓
执行检索或数据库查询
       ↓
获取完整证据
       ↓
生成答案或统计报告
       ↓
进行结果校验
       ↓
保存运行轨迹
       ↓
按标准答案评分
~~~

重点是：

**不能只测试某一个模块的函数，然后宣称整个用户任务已经通过。**

例如直接调用 Retrieval 能够成功返回岗位，不代表 Agent 能正确判断什么时候应该调用 Retrieval。

尤其对于 Job-RAG 的多工具流程，任务路由本身就是需要评测的行为。

### 2. 为什么要保存完整运行轨迹？

假设系统最终给出错误答案。

如果只保存最终文字，就很难定位问题。

因此应尽可能记录：

~~~text
用户问题
   ↓
识别的任务类型
   ↓
实际调用的工具
   ↓
工具输入与明确约束
   ↓
检索候选和排序
   ↓
实际读取的来源文档
   ↓
进入模型的上下文
   ↓
最终生成内容
   ↓
引用与结果验证
~~~

这类记录通常称为 Trace。

但要注意：

Trace 的目标是记录系统实际发生的行为，而不是要求获取模型不可访问的内部思维链。

我们需要看到的是：

- 调用了哪些工具；
- 输入了什么；
- 返回了什么；
- 选择了哪些证据；
- 产生了什么结论。

这些信息已经足够支持大部分工程诊断。

对于内部银行资料，Trace 也可能包含敏感数据，需要做好访问控制、脱敏和保留期限管理。

### 3. 为什么不能只做完整端到端实验？

假设一轮实验用了大量模型调用，最终发现任务失败。

如果缺少中间数据，我们不知道该修改哪里。

所以应结合三类实验。

**第一类：端到端实验。**

验证用户任务是否完成。

**第二类：环节对照实验。**

验证某项技术改动是否改善指定模块。

**第三类：确定性工程测试。**

验证身份、版本、引用编号、权限、分页、数据完整性等程序契约。

例如：

| 失败 | 应该采用的测试 |
|---|---|
| AI 推荐了不符合条件的岗位 | 端到端 + 原文证据评测 |
| Retrieval 漏掉已知岗位 | 检索专项 |
| Rerank 把正确岗位降到后面 | 固定候选重排实验 |
| 分页中途数据库变化 | 确定性一致性测试 |
| 引用编号指向错误 JD | 程序映射与引用测试 |

并不是所有问题都需要昂贵的模型评测。

### 4. 怎样设计一个最基本的端到端基线？

例如选择当前系统已经支持的最简单方案：

- 基础任务路由；
- BM25 检索；
- 不使用专用 Rerank；
- 必要时回读完整 JD；
- 固定生成模型；
- 基础引用检查。

在冻结评测集上运行。

之后得到一份结果：

| 案例 | 是否完成任务 | 失败位置 |
|---|---|---|
| A | 成功 | — |
| B | 失败 | 任务路由 |
| C | 失败 | 候选召回 |
| D | 成功 | — |
| E | 失败 | 条件判断 |

这只是结果表示示例，不是 Job-RAG 已经实际测得的数据。

最重要的是，基线应该固定并可重复运行。

否则每次实验结果都无法有效比较。

### 5. 为什么生成模型需要重复测试？

某些大模型输出具有随机性。

即使问题、证据和 Prompt 相同，多次执行也可能得到不同结果。

例如对于复杂条件判断：

- 第一次回答正确；
- 第二次遗漏例外；
- 第三次过度拒答。

所以，单次通过不一定能证明方案稳定。

可以对关键案例进行多次运行，记录：

- 每次是否成功；
- 失败是否集中在相同问题；
- 结果变化程度；
- 模型版本和参数。

但要注意：

**多次运行能够观察波动，不代表可以替代独立标准答案。**

### 6. 如何避免实验受缓存和环境影响？

如果实验使用缓存，需要明确：

- 缓存对应哪个模型；
- 对应哪个 Prompt；
- 对应哪个输入；
- 是否使用相同的模型参数；
- 是否使用相同候选；
- 原始文件是否发生变化。

缓存可以显著降低成本。

但错误复用缓存会使实验结果不可解释。

同样，生产环境中的模型路由、服务降级和索引更新，也可能影响结果。

因此正式报告应记录运行环境和实现版本。

## 五、应该使用哪些指标？怎样避免把评测变成数字游戏？

### 1. 端到端最重要的指标是什么？

**任务是否成功完成。**

例如：

用户要求找三个符合条件的岗位，系统最终是否给出了三个通过原文核验的岗位？

用户要求判断必备条件，系统是否正确区分了必须与优先？

用户要求完整统计，系统是否按照指定范围完成了枚举和计数？

可以定义：

\[
\text{任务成功率}
=
\frac{\text{成功完成的任务数量}}
{\text{已评测任务数量}}
\]

但不同任务的难度和价值不同。

因此不应该只报告一个整体任务成功率。

例如：

| 任务类别 | 成功率 |
|---|---|
| 简单事实查询 | 单独统计 |
| 复杂条件判断 | 单独统计 |
| 岗位推荐 | 单独统计 |
| 全库统计 | 单独统计 |

这样才知道系统擅长什么、不擅长什么。

### 2. 为什么还需要答案忠实性？

因为系统可能碰巧回答正确，但不是根据指定资料推导出来的。

例如模型凭常识回答了一项银行制度问题。

从最终答案看可能正确，但不能保证与当前制度版本一致。

因此要检查：

> 事实性断言是否得到本次使用的来源证据支持？

这就是 Faithfulness 或 Groundedness 的主要评价对象。

但它也有边界。

一份来源资料本身可能过期或错误。

忠实复述来源，不等于回答符合最新事实。

所以 Faithfulness 与 Correctness 不能混为一谈。

### 3. 为什么要关注证据覆盖？

假设问题需要三个证据：

1. 一般规则；
2. 特殊例外；
3. 生效时间。

系统只找到了前两个。

即使回答看起来很完整，也缺少决定最终结论的依据。

因此可以评价：

**完成任务所需的关键证据，有多少真正进入了模型上下文？**

这能帮助我们区分：

- Retrieval 没有找到；
- Rerank 降低排名；
- Context Assembly 删除；
- Generation 没有正确使用。

### 4. 为什么不能只看引用编号？

例如答案：

> 岗位 A 必须有三年以上 RAG 开发经验。[1]

如果 `[1]` 只写着：

> RAG 项目经验优先。

那么引用编号有效，但答案缺乏支持。

因此应评价：

- 引用是否存在；
- 引用是否指向正确文档；
- 引用是否指向正确版本；
- 引用是否真正支持结论。

不能把编号校验成功当成事实核验成功。

### 5. 全库统计应该增加哪些专项指标？

对于完整统计任务，至少需要：

| 指标 | 作用 |
|---|---|
| 范围完整性 | 是否覆盖定义的研究对象 |
| 对象处理完成率 | 所有需要处理的岗位是否处理完 |
| 条件判定正确率 | 是否正确判断纳入条件 |
| 抽取准确性 | 技术及条件关系是否正确 |
| 未知项数量 | 哪些岗位无法可靠判断 |
| 聚合一致性 | 统计是否与逐条结果一致 |
| 证据覆盖 | 每条判断能否回查原文 |

这里有一个重要原则：

**不能为了得到一个漂亮的百分比，把无法判断的岗位悄悄排除。**

例如：

~~~text
研究范围：100 条 JD

符合条件：20 条
不符合条件：70 条
无法判断：8 条
尚未处理：2 条
~~~

此时不能声称“100 条已经完成全部分析”。

即使统计了 90 条有明确结论的岗位，也应同时披露 8 条未知和 2 条未处理。

### 6. LLM-as-a-Judge 能否代替人工评测？

不能完全代替。

LLM-as-a-Judge 指利用一个模型来评价另一个模型或系统的输出。

例如：

> 给定问题、原文证据和系统回答，判断回答是否忠实于证据。

它可以提高评测效率。

但也可能发生：

- 评价标准理解偏差；
- 偏好更长的回答；
- 对某些文风产生偏好；
- 误解否定、例外或数字；
- 对同一家模型的输出产生偏向；
- 错误地将未标注候选视为不相关。

因此建议分三层使用。

**第一层：确定性规则。**

能用程序正确判断的，就不必依赖模型。

例如分页数量、引用 ID、整数统计一致性。

**第二层：模型辅助评测。**

适合判断语义是否得到支持、回答是否遗漏信息等。

**第三层：人工校准与复核。**

尤其用于严重失败、模型评判存在分歧或业务影响较大的案例。

关键不是让评测模型永远打高分。

而是：

**自动评测应当与人工核验保持足够一致，并对不一致的案例持续分析。**

### 7. 业界的 RAG 评测方法有什么值得借鉴？

可以从三个有代表性的方向理解。

**RAGAS：将 RAG 质量拆成不同维度。**

RAGAS 系列方法关注检索上下文相关性、答案忠实性和答案质量等方面，支持不同形式的自动化评价。

它的主要启示是：

> 不要把 RAG 质量缩减成一个“答案好不好”的笼统判断。

但自动评价并不意味着在所有业务中都能无需人工校准。

**ARES：将自动评测与人工标注结合。**

ARES 使用模型评判检索上下文、答案忠实性和相关性，并通过少量人工标注缓解自动评判的误差。

它的主要启示是：

> 自动评测可以扩大覆盖范围，但必须认真处理评判器本身的误差。

**RAGBench 与后续细粒度诊断研究：让指标指向具体失败。**

这类研究强调将证据相关性、使用情况、忠实性和回答完整性等维度拆开，以便定位问题。

它的主要启示是：

> 评测指标应该能指导下一次工程修改，而不仅用于制作排行榜。

这些框架是可以借鉴的方法，不应直接照搬为 Job-RAG 的全部成功标准。

## 六、端到端失败后，怎样确定应该修改哪一个环节？

### 1. 为什么最终答错，不能直接换更强的大模型？

假设用户问：

> 岗位 A 的 RAG 经验是必备还是优先？

系统回答：

> 必备。

但原文写：

> 有 RAG 项目经验者优先。

错误可能出现在不同位置：

- 原始文档采集不完整；
- 文档解析漏掉“优先”；
- Chunk 截断；
- Retrieval 找错条款；
- Rerank 排错；
- Context Assembly 丢掉限定词；
- 模型看到完整原文仍然判断错误。

如果直接更换生成模型，可能完全没有解决根因。

因此需要先进行链路诊断。

### 2. 怎样构建统一的失败归因流程？

我建议从用户任务出发，沿完整链路回查。

~~~text
任务最终失败
      ↓
任务类型是否识别正确？
      ↓
所需资料是否存在？
      ↓
解析与切分是否保留完整证据？
      ↓
Retrieval 是否找到关键证据？
      ↓
Rerank 是否保留并优先展示？
      ↓
上下文是否提供充分证据？
      ↓
生成模型是否正确使用证据？
      ↓
结果校验是否发挥作用？
~~~

实际诊断时，可以从最终结果反向寻找错误，但最终应确定：

**哪一个环节最早开始偏离完成任务所需的正确状态。**

### 3. 为什么还需要反事实实验？

有时只检查 Trace 仍然无法确定因果关系。

例如用户的问题没有回答正确，而 Retrieval 的 Top-20 中确实没有关键证据。

这说明存在检索缺失。

但如果我们把正确证据补进去，模型是否就能回答正确？

还不知道。

可以做一个反事实实验。

**原系统**

~~~text
用户问题
   ↓
原 Retrieval
   ↓
原上下文
   ↓
模型回答错误
~~~

**反事实实验**

~~~text
同一个用户问题
   ↓
人工提供已经核验的正确证据
   ↓
保持生成模型和回答要求不变
   ↓
重新生成答案
~~~

如果补入正确证据后，答案变正确，说明上游证据缺失至少是一个重要问题。

如果补入正确证据后，答案仍然错误，说明生成阶段也存在问题。

这类实验可称为 Oracle Context 对照：用经过核验的理想证据替换某一环节的输出。

但需要注意：

**反事实改善不能自动证明唯一根因。**

例如补入原文的同时增加了上下文长度、改变了排列顺序，可能还引入其他因素。

因此应尽量控制变量，结合 Trace 作出判断。

### 4. 怎样区分“找不到”和“不会用”？

这是 RAG 诊断中非常关键的区别。

**情况 A：找不到证据。**

原文存在，但 Retrieval 没有返回。

优先调查查询表达、索引、候选预算和召回策略。

**情况 B：找到了但没有送进模型。**

Retrieval 已找到，Context Assembly 将其删除。

优先调查上下文选择和 Token 预算。

**情况 C：证据已经完整送进模型，但模型误读。**

优先调查生成模型、任务约束和证据理解。

**情况 D：回答正确，但最终报告错误。**

例如程序汇总错误或引用指向错误。

优先调查结果校验与输出处理。

这四类错误都可能表现为“用户看到的答案不对”，但工程修复完全不同。

### 5. 怎样判断一次改进应该修改哪个组件？

建立一个简单的对应关系。

| 已确认的主要失败 | 优先优化 |
|---|---|
| 目标文档没有进入数据库 | 采集 |
| 原文内容或章节识别错误 | 解析 |
| 关键限定条件跨 Chunk 丢失 | 切分 |
| 词义相近的正确证据找不到 | Embedding / Retrieval |
| 正确证据已召回但排名过低 | Rerank |
| 正确证据被上下文预算排除 | Context Assembly |
| 模型完整看到证据仍误判 | Generation |
| 正确数字被错误汇总 | 确定性计算 |
| 无法确认是否完成全部任务 | 任务执行与进度管理 |
| 新旧文档版本混用 | 一致性管理 |

这里每项都是优先调查方向，而不是自动成立的解决方案。

### 6. 为什么不能一次修改所有环节？

假设某次优化同时：

- 更换 Embedding；
- 修改 Chunking；
- 加入多查询；
- 启用 Rerank；
- 调整 Prompt。

最终任务成功率提高了。

我们不知道哪一个修改有效。

更严重的是，可能：

- Embedding 带来改善；
- Chunking 带来退化；
- Rerank 又抵消部分退化。

综合结果虽然变好，却掩盖了某个组件的错误。

因此建议：

**先通过局部对照确认主要改动的效果，再运行完整端到端回归检查整体收益。**

### 7. 如何保存失败案例？

每次重要失败至少记录：

~~~text
案例 ID：
问题：
期望任务：
实际输出：

原始来源：
证据要求：
实际检索候选：
实际模型上下文：

首次观察到的异常：
初步根因：
待验证假设：

局部实验结果：
端到端回归结果：
最终是否修复：
~~~

这使失败从一次临时问题变成未来可重复使用的工程资产。

## 七、怎样建立持续评测与优化机制？

### 1. 为什么通过一次评测，不代表系统以后一直可靠？

RAG 的运行环境可能不断变化：

- 新文档加入；
- 原始文档修改；
- Embedding 模型升级；
- Chunking 规则改变；
- 检索策略修改；
- 生成模型版本更新；
- 用户提出新的问题；
- 业务制度变化。

因此，即使今天的测试全部通过，也不能保证明天表现不变。

需要建立持续评测机制。

### 2. 持续评测应该在什么时候执行？

建议至少有三个时间点。

**开发过程中**

针对已发现的失败运行局部实验。

**上线或配置变更之前**

运行完整回归集，检查是否引入退化。

**线上运行期间**

记录真实任务、用户反馈、异常、成本和延迟，从中发现新的失败类型。

~~~text
日常使用
    ↓
收集真实失败
    ↓
形成新的评测案例
    ↓
开发环境修复
    ↓
运行局部实验
    ↓
运行完整回归
    ↓
发布新版本
    ↓
持续监测
~~~

这样的机制比定期重新跑一个固定排行榜更有价值。

### 3. 怎样避免评测集越用越失真？

有两个典型问题。

**第一个：过度适配旧题。**

不断根据某 30 条问题修改 Prompt，最后模型在这 30 条上表现很好，却不能解决其他问题。

**第二个：业务发生变化。**

原来主要是简单岗位查询，后来用户大量提出全库统计问题。

旧评测集可能没有覆盖新的任务。

因此需要同时维护：

- 固定回归案例；
- 新发现的真实问题；
- 独立的测试集；
- 按业务类型分类的指标。

不能因为旧测试集全部通过，就认为系统已经成熟。

### 4. 线上应该记录哪些信号？

可以关注：

| 信号 | 作用 |
|---|---|
| 用户任务类型 | 判断真实需求分布 |
| 查询成功率 | 是否正确完成任务 |
| 工具调用失败 | 发现接口故障 |
| 证据缺失情况 | 发现检索或数据问题 |
| 引用核验失败 | 发现生成问题 |
| 数据版本冲突 | 发现一致性问题 |
| 延迟与费用 | 评估运行效率 |
| 用户纠错反馈 | 获得新的失败案例 |

这里要注意：

用户点赞、停留时间或继续提问，并不总能直接代表答案事实正确。

例如用户可能觉得一份错误报告写得很好。

所以线上反馈有价值，但不应该自动替代原文和标准答案核验。

### 5. 怎样让 AI 自动处理大量评测结果？

可以让 AI 承担重复性工作：

- 归类失败；
- 发现异常聚集；
- 比较版本差异；
- 检查引用支持；
- 生成改进候选；
- 提出新的边界测试；
- 汇总成本与质量趋势。

例如一轮有 100 个失败案例，AI 可以先分类：

~~~text
任务路由错误：12
证据缺失：25
上下文截断：18
模型条件误判：30
引用错误：10
其他：5
~~~

这是分类示例，不是实际实验结果。

随后针对最主要的错误开展专项分析。

但自动分类也可能错误，所以要保留原始运行证据并对关键样本复核。

### 6. 怎样避免评测指标被“优化作弊”？

一个容易忽略的问题是：

> 当系统开始专门为了某个评分指标优化时，可能出现指标提高但业务变差。

例如：

**为了提高引用率：**

模型给每句话都加引用，但引用未必支持结论。

**为了提高无依据回答拦截率：**

模型大量拒答，即使已有充分证据也不回答。

**为了提高 Retrieval Recall：**

无限扩大 Top-K，增加大量无关内容和成本。

**为了提高任务成功率：**

将复杂任务判为“不支持”，只保留简单任务进入统计分母。

因此，评测应该保留多个相互制约的维度。

特别要防止：

- 更改测试口径；
- 删除困难案例；
- 静默跳过失败请求；
- 修改标准答案迎合系统输出；
- 将未完成任务排除出统计；
- 只报告平均分，不报告严重退化。

**评测体系自身也需要接受审阅和版本管理。**

### 7. 怎样把质量、成本与风险结合起来？

假设两个方案：

| 维度 | 方案 A | 方案 B |
|---|---|---|
| 任务成功率 | 88% | 90% |
| 平均延迟 | 2 秒 | 12 秒 |
| 单次成本 | 较低 | 较高 |
| 关键事实错误 | 1 个 | 1 个 |

这些是假设数据。

我们不能因为 B 的成功率高 2 个百分点，就自动选择 B。

还要看：

- 改善发生在哪些任务；
- 是否属于高价值业务；
- 延迟是否可接受；
- 成本是否可持续；
- 是否增加安全风险；
- 是否发生严重错误。

对于某些场景，2 个百分点可能非常重要。

对于另一些场景，额外十秒可能让产品体验明显下降。

因此没有一个适用于所有 RAG 产品的统一加权公式。

**应根据具体任务的质量门槛、风险和用户价值作出取舍。**

## 八、Job-RAG 实践：下一步应该怎样建立真正可用的端到端评测？

### 1. 当前 Job-RAG 已经具备什么基础？

根据当前仓库中的项目文档和实验记录，Job-RAG 已经积累了不少能力。

**数据层面：**

- 有标准化岗位 CSV；
- 保留岗位来源和原始 JD；
- 具备岗位身份和版本管理；
- 支持文档切分与索引。

**检索层面：**

- 具备 BM25；
- 支持可选 Embedding；
- 已开展真实离线向量实验；
- 已设计多查询与候选融合。

**查询层面：**

- 支持确定性字面查询；
- 支持全量计数与分页；
- 具备 `snapshot_id` 和 `corpus_id` 等一致性检查；
- 可以按岗位 ID 批量回读完整 JD。

**实验层面：**

- 已有冻结数据和配置机制；
- 保存模型请求与排名；
- 区分召回与 Rerank；
- 开始进行候选审阅和失败案例分析。

这些为端到端评测提供了基础。

但需要明确：

**已有局部实验和工具接口，不等于已经验证完整用户任务能够自动、准确地执行。**

### 2. 当前已经知道哪些限制？

根据此前的真实实验记录：

- 2026 年 10 月 25 日的离线准备快照包含 592 份非空 JD；
- 曾使用 30 条查询、15 个主题进行 Embedding 召回实验；
- 评测存在单种子正例和人工相关性标注不足的问题；
- 此前有 95 条 JD 的章节无法可靠判断，保留 `unknown`；
- 完整 Rerank 付费实验曾因输入预算核验问题尚未执行；
- 生成层的基础引用编号检查不能证明每条结论受到引用原文支持。

这些是历史实验与仓库文档记录，不能自动视为实时线上状态。

但它们已经指明下一步应该重点解决什么：

**不是再增加更多模型，而是建立能够证明完整任务成功的评测与验收机制。**

### 3. 建议第一批评测哪些真实任务？

我建议优先选三类任务。

#### A 类：寻找相关岗位

例如：

> 找三个真正负责企业 RAG 知识库研发的岗位。

需要验证：

- 是否选择了正确的候选检索入口；
- 是否保留用户硬条件；
- 是否找到了足够相关的岗位；
- 是否有职责原文；
- 是否排除了明显不符合目标的岗位；
- 是否正确披露招聘状态和数据时点。

这类任务主要连接：

Retrieval → Rerank → 原文回读 → 最终推荐。

#### B 类：判断复杂任职条件

例如：

> 某岗位的 RAG 项目经验到底是必须还是优先？

需要验证：

- 是否读取正确 JD；
- 是否读取完整任职条款；
- 是否正确识别条件；
- 是否引用有效原文；
- 是否避免无依据补充。

这类任务主要连接：

原文读取 → 上下文组织 → 条件判断 → 引用验证。

#### C 类：完整统计与分析

例如：

> 统计岗位职责或者任职要求出现 RAG 的所有岗位，它们还要求哪些技术。

需要验证：

- 是否选择完整查询而非有界 Top-K；
- 是否定义数据范围；
- 是否正确识别职责与任职要求；
- 是否完整处理目标岗位；
- 是否正确抽取技术条件；
- 是否按岗位去重；
- 是否准确汇总；
- 是否有证据与未知项披露。

这类任务主要连接：

任务路由 → Querying → 完整 JD → 逐条判断 → 程序汇总 → 报告生成。

**第三类任务最能检验 Job-RAG 是否已经从“搜索知识库”进化为“完成真实资料分析工作”。**

### 4. 怎样给全库统计任务建立标准答案？

不要直接让 AI 生成一份统计报告，再拿这份报告作为 Gold Answer。

更合理的方式是：

**第一步：冻结语料。**

确定全部待分析的岗位 ID 和对应 JD 版本。

**第二步：定义目标岗位筛选规则。**

例如职责或任职要求中包含独立的 `RAG` 技术词项。

明确大小写、词边界、章节和排除条件。

**第三步：人工或经复核的流程标记目标岗位。**

对无法可靠识别章节的 JD 保留待判定状态。

**第四步：逐份记录技术要求。**

保存：

- source + job_id；
- 技术名称；
- 章节；
- 必备、优先或其他性质；
- 对应原文；
- 判断结果；
- 是否已复核。

**第五步：通过确定性程序汇总。**

例如按岗位 ID 去重，统计技术出现次数。

**第六步：复核统计报告。**

确认最终结果与逐条标注一致。

这样形成的标准答案不仅是一段文字，而是一份可以重新计算的结构化数据。

### 5. 为什么完整统计任务需要进度管理？

假设需要分析 100 份 JD。

系统处理了 60 份后模型服务超时。

如果重新运行，可能产生：

- 前 60 份重复处理；
- 已有结果被覆盖；
- 某些岗位漏处理；
- 不同批次使用不同 JD 版本；
- 报告提前生成。

因此，端到端任务不仅需要语义正确，还需要工程完成性。

建议每条岗位保留：

~~~text
岗位身份
   ↓
预期文档版本
   ↓
是否完成处理
   ↓
结构化判断结果
   ↓
原文证据
   ↓
人工复核状态
   ↓
失败与重试记录
~~~

只有当目标集合的所有对象都进入明确终态，才能决定是否生成完整统计报告。

这里的终态可以包括：

- 已完成且结果明确；
- 已处理但无法可靠判断；
- 经核验后不适用；
- 处理失败且尚未解决。

其中“处理失败”不能自动当作“不符合条件”。

### 6. 端到端任务应该怎样设置验收标准？

可以按不同任务设计验收。

| 任务 | 必须通过 | 进一步比较 |
|---|---|---|
| 找三个岗位 | 三个岗位符合明确条件，原文可核验 | 排名、速度 |
| 判断经验要求 | 必备/优先正确，引用支持 | 表达清晰度 |
| 比较两个 JD | 维度完整、没有混淆来源 | 报告可读性 |
| 全库统计 | 范围与处理状态完整、数据可复算 | 运行效率 |
| 无答案问题 | 不编造不存在的依据 | 说明是否清晰 |
| 数据版本变化 | 不混用失效结果 | 恢复速度 |

这比统一使用“回答质量 0.8 以上”更适合指导开发。

### 7. 建议怎样组织项目目录？

可以将端到端评测放在独立的任务层，而不是继续塞进 Embedding 或 Rerank 专项实验。

例如：

~~~text
experiments/
├── retrieval/
│   └── 召回实验与分析
├── rerank/
│   └── 固定候选重排实验
└── end-to-end/
    ├── cases/
    │   ├── recommendation/
    │   ├── condition-judgment/
    │   ├── comparison/
    │   └── exhaustive-analysis/
    ├── judgments/
    │   └── 人工标准与证据
    ├── runners/
    │   └── 任务执行与 Trace 采集
    ├── evaluators/
    │   └── 规则、模型与人工评测
    └── reports/
        └── 对照、失败与回归报告
~~~

这是建议结构，不是当前仓库已经存在的目录。

目录名称可以调整。

真正重要的是三个逻辑边界：

**测试案例与标准答案独立。**

**运行系统与评测系统独立。**

**端到端评测与组件专项实验独立。**

这样才能防止系统自己定义目标、自己执行、自己评分，最后宣布自己成功。

### 8. 下一轮最值得实施的实验是什么？

我建议从之前最典型的失败任务开始：

> 统计岗位职责或者任职要求出现 RAG 的岗位中，相关的技术要求是什么？

不要立刻改整个 Job-RAG 架构。

先做一条完整的端到端测试。

**第一步：冻结当前数据。**

保存语料与来源版本。

**第二步：制定人工标准。**

明确岗位纳入条件、技术抽取规则和计数单位。

**第三步：运行现有系统。**

记录：

- Agent 选了哪个工具；
- 是否进行了全库枚举；
- 实际处理多少岗位；
- 每条 JD 得到了什么判断；
- 最终数字如何产生；
- 报告引用了哪些依据。

**第四步：判断任务是否成功。**

重点检查完整性和可复算性。

**第五步：定位首个失败环节。**

如果 Agent 用 Top-K 统计全库，先修复任务路由。

如果完整枚举已经完成，但模型把“经验优先”判成“必备”，再修复语义判断。

如果逐项判断正确，但计数有误，则优先修复汇总。

**第六步：针对根因进行最小修改。**

保持其他条件固定，运行对照实验。

**第七步：重新执行完整任务。**

不仅验证局部错误消失，还要确认最终报告确实可用。

这样一次实验，就能把 RAG 的全部工程环节连接起来。

### 9. 下一轮端到端实验报告应该怎样写？

建议统一采用：

| 项目 | 要回答的问题 |
|---|---|
| 用户任务 | 用户实际想得到什么 |
| 数据范围 | 使用什么语料及版本 |
| 成功标准 | 完成任务必须满足哪些条件 |
| 标准答案 | 依据什么判断正确 |
| 运行轨迹 | 实际调用了哪些工具和模型 |
| 任务结果 | 最终完成了什么 |
| 失败分类 | 哪些环节出现问题 |
| 根因证据 | 为什么判断是这个环节 |
| 对照实验 | 修改前后有什么差异 |
| 回归结果 | 是否修复且没有引入退化 |
| 成本性能 | Token、延迟、费用 |
| 最终决策 | 保留、回退或继续优化 |

例如：

~~~text
研究问题：
Job-RAG 能否完整统计
RAG 岗位的其他技术要求？

成功标准：
1. 明确研究范围；
2. 全部目标岗位进入处理流程；
3. 技术条件判断正确；
4. 统计结果可重新计算；
5. 每项结论具备来源证据；
6. 未知与未完成情况明确披露。

实验基线：
当前 Job-RAG 业务入口。

观察：
记录任务路由、工具调用、
完整枚举、逐项处理和最终报告。

失败分析：
找到最早偏离成功条件的环节。

改进：
一次只修改一个主要原因。

验证：
同时运行局部实验与完整回归。

决策：
只有完整任务成功，
才能认为本轮优化真正有效。
~~~

## 结语：RAG 端到端评测的目标不是得到一个更高的分数

我们从一个问题开始：

> RAG 的每个环节都已经优化过，为什么最终用户仍然觉得不好用？

原因是，用户并不关心系统采用了多少种检索算法，或者某个 Embedding 模型在排行榜上表现多好。

用户真正关心的是：

**我要求系统完成的事情，它是否可靠地完成了？**

因此，需要重新理解 RAG 评测。

**第一，先定义真实用户任务。**

不要从算法指标反推业务目标。

**第二，为任务定义可核验的成功标准。**

查找、比较、条件判断和完整统计，必须采用不同的验收条件。

**第三，建立真实且独立的评测数据。**

保留冻结版本、原文证据、人工判断以及标注完整性边界。

**第四，完整运行系统，记录实际行为。**

不能只检查最终答案，也不能把单个组件测试当成完整任务成功。

**第五，发现失败后进行链路归因。**

判断究竟是资料缺失、检索遗漏、上下文不充分、模型误读，还是确定性计算错误。

**第六，通过局部对照与完整回归验证修改。**

局部指标改善只是中间证据；最终仍要确认用户任务是否更好地完成。

**第七，将真实失败不断变成新的评测案例。**

使知识库不再依靠偶然的成功演示，而是通过可重复的实验持续提高可靠性。

> **RAG 端到端评测的真正目标，不是为系统生成一个分数，而是建立一套能够证明任务是否成功、解释为什么失败、指导下一次改进，并防止旧问题再次出现的工程机制。**

这也是整个 RAG 工程系列最重要的总结。

**AI 可以帮助我们实现采集、解析、切分、索引、检索、重排与答案生成，但工程师仍然需要明确：系统究竟应该完成什么任务，怎样证明它完成了，以及怎样让它在真实使用中持续变得更可靠。**
