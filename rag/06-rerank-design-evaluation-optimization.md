# RAG Rerank 重排：如何设计、评测与持续优化？

> 本文是 RAG 工程流程的第六篇专题文章，承接《05 · RAG 检索》，后续衔接《07 · 上下文组织与答案生成》。
>
> 本文以 Job-RAG 招聘岗位知识库为主要案例，从真实业务问题出发，理解为什么需要 Rerank、它与 Retrieval 有什么区别、怎样设计重排输入、如何评价重排质量，以及如何利用 AI 持续优化。
>
> 本文不以学习某个 Rerank API 或模型调用代码为目标，而是建立一种工程判断能力：**当正确证据已经进入候选集合时，怎样可靠地把真正符合用户意图的证据排在前面，并证明这种调整确实有价值。**

---

## 一、为什么需要 Rerank？Retrieval 已经排好序了，不够吗？

### 1. 我们究竟遇到了什么问题？

假设 Job-RAG 已经完成一次检索。

用户的问题是：

> 找真正负责企业 RAG 知识库全链路研发的工程岗位。

系统通过 BM25 和 Embedding 找到 50 个候选岗位。

其中前四个是：

| 原始排名 | 岗位 | JD 主要内容 |
|---|---|---|
| 第 1 | AI 产品经理 | 公司拥有 RAG 知识库产品，负责需求和产品规划 |
| 第 2 | 大模型应用工程师 | 调用知识库 API，实现业务问答 |
| 第 3 | 知识库研发工程师 | 负责文档接入、切分、检索、重排和服务化 |
| 第 4 | AI 平台工程师 | 负责模型部署、推理服务和平台运行 |

如果用户真正想做的是 RAG 系统工程，第 3 个岗位可能比前两个更符合需求。

但为什么它没有排在前面？

因为 Retrieval 通常依据词法匹配、向量相似度或融合分数进行初步排序。

这些信号能够判断哪些文字与问题接近，却不一定能深入比较岗位的具体职责。

例如：

- “公司使用 RAG”与“岗位负责研发 RAG”；
- “调用现成知识库接口”与“开发知识库底层能力”；
- “了解向量检索”与“负责检索效果优化”。

它们在词汇或主题上很相近，但业务匹配程度不同。

这时我们就有了一个新需求：

**已经找到一批候选，能不能再仔细阅读它们，根据用户真正关心的条件重新排序？**

这就是 Rerank（重排）的主要动机。

### 2. Rerank 究竟在做什么？

可以把重排理解为：

**在已经形成的候选集合内，使用额外的相关性判断方法，重新评价每个候选与用户问题的匹配程度，并调整其顺序。**

~~~text
用户问题
    ↓
Retrieval
    ↓
50 个候选岗位
    ↓
Rerank
    ↓
重新判断每个岗位的相关程度
    ↓
重新排序
    ↓
优先阅读前 5 个岗位
~~~

Rerank 并不是重新搜索整个数据库。

它只是对已经获得的候选集合进行二次评价。

### 3. 为什么不在第一次检索时就使用更强的模型？

因为两个阶段的计算成本不同。

假设数据库有 100,000 个 Chunk。

如果每次查询都让一个较复杂的模型逐一仔细分析这 100,000 个 Chunk，计算量可能很大。

而 BM25、Embedding 等方法可以利用已经建立的索引，更快地找到一批可能相关的候选。

因此可以分成两个阶段：

**第一阶段：快速发现候选。**

优先减少遗漏。

**第二阶段：深入评价候选。**

优先提高前排结果的质量。

~~~text
大量原始资料
      ↓
较快的候选召回
      ↓
少量候选
      ↓
更深入的相关性判断
      ↓
高质量前排结果
~~~

这通常被称为两阶段检索或多阶段排序。

不过，采用两阶段架构并不是必然要求。

如果数据量很小，直接读取全部符合条件的岗位并进行语义判断，也可能更简单。

### 4. Rerank 能解决哪些问题，不能解决哪些问题？

假设某个问题有 10 条相关岗位。

Retrieval 的 Top-50 中已经包含其中 8 条。

那么 Rerank 最多只能在这 8 条已有的相关岗位之间重新排序。

它不能让另外 2 条没有进入候选的岗位凭空出现。

因此：

| 问题 | Rerank 能否解决 |
|---|---|
| 正确岗位已经找到但排名靠后 | 可能解决 |
| 公司介绍提到 RAG 的岗位排名太高 | 可能解决 |
| 仅调用 API 的岗位排在底层研发岗位前面 | 可能解决 |
| 正确岗位没有进入候选集合 | 不能直接解决 |
| JD 原文缺失 | 不能解决 |
| 薪资或城市硬条件解析错误 | 不应交由 Rerank 代替处理 |
| 要统计全库符合条件的岗位数量 | 不能用 Top-K Rerank 代替完整统计 |

所以要记住：

> **Retrieval 决定有哪些候选可以被比较；Rerank 决定这些候选应该按照什么顺序出现。**

### 5. 什么时候不需要 Rerank？

不是每一个 RAG 系统都必须使用 Reranker。

例如：

- 只有一份明确指定的制度文件，需要直接查阅；
- BM25 已经能稳定把正确证据排在前面；
- 数据库很小，可以直接读取全部候选；
- 用户要求完整的字面统计，而不是相关性排序；
- 重排模型增加的费用和延迟超过实际质量收益。

因此，在开发 Rerank 之前，应该先问：

**当前 Retrieval 的主要问题究竟是漏掉正确证据，还是已经找到正确证据、但排序不理想？**

如果是前者，应优先优化 Retrieval，而不是盲目增加 Rerank。

## 二、怎样定义一个好的 Rerank 方案？

### 1. 什么叫“重排得好”？

假设我们接入一个模型，对 50 个候选重新排序。

原来第 10 名的岗位被排到第 1。

这是否意味着重排有效？

不能直接判断。

因为重新排序本身不是目标。

真正需要判断的是：

> 新的第 1 名是否比原来的第 1 名更符合用户需求？

因此我建议这样定义：

**好的 Rerank 方案，应该在固定候选集合内，以可接受的成本，将更符合用户真实意图、具有可靠原文证据的候选排到更靠前的位置，并且不会系统性违反明确业务条件。**

这个定义至少包括三个层次。

### 2. 第一层：相关性判断是否正确？

假设用户问：

> 找负责 RAG 系统底层研发的工程岗位。

三个候选：

**岗位 A**

> 负责知识库检索引擎、召回策略、重排模型和工程服务建设。

**岗位 B**

> 负责基于现有 RAG 平台开发业务问答应用。

**岗位 C**

> 公司提供 RAG 知识库产品，岗位负责商务拓展。

它们都与 RAG 有关。

但按照用户的具体意图：

- A：直接相关；
- B：部分相关；
- C：不符合目标职责。

重排系统应该能够区分这些情况，而不只是检查字符串 `RAG` 出现多少次。

### 3. 第二层：是否保留重要业务条件？

看另一组 JD：

**岗位 A**

> 必须具备三年以上 vLLM 生产部署经验。

**岗位 B**

> 有 vLLM 部署经验者优先。

**岗位 C**

> 熟悉大模型 API 的调用与集成。

如果用户要求：

> 找明确将 vLLM 生产部署列为必备条件的岗位。

A 与 B 的主题极其相近，但只有 A 明确符合这个要求。

这说明重排判断可能需要关注：

- 技术是什么；
- 出现在什么章节；
- 属于岗位职责还是公司背景；
- 是必备条件还是加分项；
- 是否存在否定、二选一或例外；
- 是否满足用户关注的技术深度。

但这里必须强调：

**Rerank 的相关性判断不能替代所有确定性硬条件校验。**

例如城市和薪资可以由结构化规则严格判断，就不应该依靠模型相关性分数代替。

对于“必须具备”这样的语义条件，即使模型进行了重排，最终需要精确结论时仍应回读 JD 证据。

### 4. 第三层：能否解释排序依据？

假设模型将岗位 A 从第 8 名提升到第 1 名。

最好能够让系统进一步回答：

> 为什么 A 更符合用户问题？

一种合理的证据是：

> 岗位职责明确包括文档解析、检索服务、Rerank 和知识库工程化建设。

但要注意：

并不是每个专用 Rerank 模型都会输出自然语言解释。

很多模型主要返回候选索引及相关性分数。

因此需要区分：

**Rerank 分数：用于排序。**

**原文证据：用于核验。**

如果需要业务解释，可以让后续模型阅读完整 JD，并引用对应段落。

不能因为重排分数高，就编造一个看似合理的解释。

### 5. 模型输出分数是不是匹配概率？

通常不能直接这样理解。

假设某 Reranker 返回：

~~~text
岗位 A：0.91
岗位 B：0.68
岗位 C：0.14
~~~

对于这次查询，可以利用分数确定排序。

但不能未经验证就宣称：

> 岗位 A 有 91% 的概率符合要求。

不同模型的分数定义不同。

部分新模型可能专门提供经过校准的相关性分数，但能否将其用于概率解释、跨查询阈值，取决于该模型的明确保证和实际校准验证。

对于一般的 Rerank 实验，更稳妥的理解是：

**分数首先是一种排序信号，不能默认是可跨模型、跨查询比较的业务概率。**

### 6. 功能输入输出应该怎样定义？

**输入：**

- 用户原始问题；
- 固定候选集合；
- 每个候选对应的内容；
- 候选的来源 ID 与版本；
- 必要的任务评价要求；
- 输入预算和权限约束。

**输出：**

- 候选原始 ID；
- 新的排列顺序；
- 必要的相关性分数；
- 使用的模型与配置；
- 是否存在截断、遗漏或失败；
- 运行成本和延迟。

一项非常重要的要求是：

**重排结果必须能够正确对应回原始候选。**

如果模型返回的 `index` 被错误映射到另一份 JD，排序分数再准确也没有意义。

## 三、Rerank 有哪些候选方案？应该怎样选择？

### 1. 方案 A：不使用重排，保留 Retrieval 原始顺序

这是最重要的基线。

~~~text
Retrieval Top-50
       ↓
直接保留原顺序
       ↓
返回 Top-5
~~~

这个方案几乎不增加额外排序成本。

如果原始检索已经表现良好，它可能是合理选择。

建立基线后，才能回答：

> 额外增加一个重排环节，究竟带来了多少收益？

没有这个基线，就容易把整个系统的原有检索能力误认为 Rerank 的贡献。

### 2. 方案 B：使用明确规则进行重排

例如 Job-RAG 可以考虑：

- 岗位职责出现目标技术，比公司介绍出现更有参考价值；
- 明确负责研发，比仅使用现成产品更接近工程岗位；
- 同时具备多项目标职责，可以提供更多相关证据。

这些都可以转化为候选排序特征。

例如：

~~~text
问题：
找负责 RAG 系统研发的岗位。

规则：
岗位职责明确涉及 RAG 研发 → 增加优先级
仅公司介绍涉及 RAG → 不增加职责匹配分
~~~

优点：

- 规则透明；
- 成本较低；
- 容易检查具体原因；
- 不依赖额外模型。

不足：

- 需要明确规则；
- 难以覆盖复杂自然语言；
- 可能误识别“必须”“优先”等条件；
- 规则之间可能冲突。

特别需要注意：

**文档解析阶段生成的章节或条件标签，不一定已经经过人工核验。**

如果直接把这些标签当成确定事实加权，可能扩大上游解析错误。

### 3. 方案 C：使用专用 Rerank 模型

专用重排模型通常接收：

~~~text
用户问题 Query
+
候选文档 Document
~~~

然后评价它们之间的相关性。

与典型的双塔 Embedding 检索相比，某些重排架构可以在判断时联合处理问题和候选文本中的信息。

例如：

**Embedding 检索**

~~~text
Query → 查询向量
Document → 文档向量
       ↓
计算向量相似度
~~~

**交叉编码式 Rerank**

~~~text
Query + Document
         ↓
模型联合处理
         ↓
相关性分数
~~~

这种差异意味着：

重排模型可以针对当前问题，更细致地分析候选内容，而不是只依赖已经预先生成的文档向量。

但不是所有 Reranker 都必须采用相同架构；也有采用其他编码或交互方式的实现。

它的优势主要是：

- 可以利用问题与候选之间更细的关系；
- 通常不需要为全部原始语料重新建立向量索引；
- 可以直接在既有 BM25、Dense 或 Hybrid 结果上工作。

代价是：

- 需要处理每个候选；
- 候选越多，成本与延迟可能越大；
- 输入长度有限；
- 仍可能误解复杂业务条件。

### 4. 方案 D：让通用大模型进行语义排序

也可以让大模型读取用户问题与候选 JD，给出相关性评价。

例如：

> 请区分真正负责模型推理服务研发的岗位，以及仅负责调用大模型 API 的岗位，并按匹配程度排序。

它的优势是可以表达复杂的业务评价标准。

例如：

- 必须具有研发职责；
- 模型部署是核心工作，而非偶尔使用；
- 具备生产服务运维要求；
- 同时涉及推理性能优化。

但也存在风险：

- 模型可能没有严格比较全部候选；
- 可能遗漏或重复候选；
- 可能受到输入顺序影响；
- 对长 JD 的判断可能不稳定；
- 模型可能将文档中的文字误当成系统指令；
- 生成式输出还需要结构化校验。

因此，不能因为通用大模型能解释业务，就认为它一定比专用 Reranker 更准确。

需要通过对照实验决定。

### 5. 应该逐个打分，还是一次比较多个候选？

这里还有一个值得研究的问题。

**Pointwise：逐候选评分。**

对每个候选分别判断与问题的相关程度。

**Pairwise：成对比较。**

例如比较岗位 A 和岗位 B，判断谁更接近用户目标。

**Listwise：列表整体排序。**

一次给出多个候选，让模型综合比较它们的相对顺序。

这三种方式没有绝对优劣。

| 方式 | 主要优点 | 主要问题 |
|---|---|---|
| Pointwise | 相对容易独立处理和扩展 | 不同候选分数可能难校准 |
| Pairwise | 适合比较细微差异 | 成对比较次数可能较多 |
| Listwise | 可以利用候选之间的直接对照 | 受候选数量、位置和上下文长度影响 |

例如 Job-RAG 要比较 50 条 JD，Listwise 可能面临较大的输入预算。

Pairwise 也可能随着候选规模增加而产生较多比较成本。

因此不能预先认为一次把所有 JD 交给大模型排序就是最好的方案。

### 6. 重排时应该提供 Chunk，还是完整 JD？

这是非常重要的工程问题。

假设 Retrieval 命中一个 Chunk：

> 负责知识库检索系统开发。

但完整 JD 还有：

~~~text
岗位职责：
负责知识库检索系统开发。

任职要求：
有相关项目经验者优先。

其他要求：
主要承担技术售前与客户方案交流。
~~~

如果 Rerank 只阅读被命中的 Chunk，就可能将岗位误判为纯粹的检索研发岗。

而完整 JD 提供了更多业务语境。

但另一个方面：

- 完整 JD 更长；
- 包含大量无关信息；
- 模型可能被公司介绍干扰；
- 输入 Token 和费用更高；
- 长文档可能超出供应商限制。

因此可比较：

1. 只用命中 Chunk；
2. 命中 Chunk + 所属章节；
3. 岗位标题 + 完整 JD；
4. 结构化的标题、职责、要求；
5. 先识别关键证据，再提供必要上下文。

关键不是哪一种形式看起来更完整。

而是：

**哪一种候选表示能够在不丢失关键限制条件的前提下，获得最好的业务排序质量？**

### 7. 什么时候应该使用专用 Reranker？

建议先问：

- 当前前排候选的主要错误是否属于语义判断错误？
- 正确候选是否已经进入召回集合？
- 规则排序是否已经足够？
- 专用模型是否有实际改善？
- 增加的延迟与费用是否可接受？
- 是否允许向模型服务发送这类资料？

如果是企业内部金融文档，还必须考虑数据安全和私有化部署约束。

**模型的理论能力不是最终选型标准，业务评测和运行约束才是。**

## 四、怎样建立 Rerank 的评测？

### 1. 为什么必须固定 Retrieval 候选集合？

假设我们比较两种方案：

**方案 A**

BM25 Top-20，不使用 Rerank。

**方案 B**

Hybrid Top-50，使用 Rerank。

如果 B 的 Top-5 更好，能否说明 Rerank 有效？

不能。

因为 B 同时改变了：

- 召回方法；
- 候选数量；
- 候选内容；
- 是否使用重排。

我们不知道改善来自哪一项。

因此最重要的实验原则是：

> **比较 Rerank 时，必须让不同重排方案面对相同的候选集合。**

例如：

~~~text
固定问题与 JD 快照
          ↓
固定 Retrieval Top-50
          ↓
┌───────────┬───────────┬───────────┐
↓           ↓           ↓           ↓
不重排    规则排序   专用 Reranker   LLM 重排
└───────────┴───────────┴───────────┘
                      ↓
                比较最终排序
~~~

如果还要比较不同的召回方案，应将召回实验与重排实验分开。

### 2. 为什么需要人工相关性标注？

假设用户想找：

> 负责 RAG 底层研发的工程岗位。

可以给候选建立四级评价标准：

| 等级 | 含义 |
|---|---|
| 3 | 直接匹配，核心职责符合目标 |
| 2 | 相关，但不是主要目标或深度略有差异 |
| 1 | 部分相关，存在明显业务差距 |
| 0 | 不相关或不满足关键条件 |

例如：

- 研发 RAG 检索与重排服务：3；
- 负责企业知识库应用开发：2；
- 偶尔集成现成知识库 API：1；
- 公司使用 RAG，但岗位负责销售：0。

以上只是一套示意标准。

实际评测前，应根据具体任务确定等级边界，并要求标注结果能够引用 JD 原文。

不能让重排模型自己的输出充当唯一标准答案。

### 3. 怎样避免标注人员受到原始排名影响？

假设标注人员看到：

~~~text
BM25 第 1：岗位 A
BM25 第 2：岗位 B
BM25 第 3：岗位 C
~~~

他可能受到排名暗示，默认前面的更好。

更合理的做法是：

1. 汇总不同方案的候选；
2. 按岗位 ID 去重；
3. 隐藏候选来自哪个检索系统；
4. 打乱候选展示顺序；
5. 根据原文独立标注相关程度。

之后再将标注结果用于比较不同排序方案。

这可以减少原有检索排名对人工判断的影响。

### 4. Rerank 应该重点看哪些指标？

#### nDCG@K

如果有 0～3 级相关性标注，nDCG@K 可以评价：

> 高相关候选是否排得更靠前？

例如，两个系统都返回了相同的五个岗位。

系统 A 将高度相关岗位放在第 1、第 2。

系统 B 将它们放在第 4、第 5。

那么 A 通常会有更好的 nDCG。

它非常适合比较重排质量。

#### Precision@K

例如前五个岗位中，有多少达到预先定义的相关性门槛。

必须在评测前明确什么叫“相关”。

如果把等级 2 和 3 都算正例，结果就不同于只把等级 3 算正例。

#### MRR

如果任务特别关心尽快找到第一个高度相关的结果，可以关注 MRR（Mean Reciprocal Rank）。

它评价第一个符合定义的相关候选出现得有多靠前。

但对于需要多个相关证据的任务，MRR 不能替代 nDCG 或其他覆盖指标。

#### 候选覆盖上限

还需要记录 Retrieval 候选集合中包含多少相关岗位。

因为：

**Rerank 不改变固定候选集合内的相关岗位数量，只改变它们的顺序。**

如果某条问题的相关岗位根本没有进入候选，重排质量存在天然上限。

### 5. 为什么还需要比较具体岗位的升降？

假设 nDCG@5 从 0.72 提升到 0.80。

我们还需要知道：

- 哪些岗位被提升；
- 是否提升了真正的目标工程岗位；
- 哪些岗位被降低；
- 是否错误降低了某些直接相关岗位；
- 排序变化依据是什么。

例如：

**改善案例**

原第 8 的 RAG 核心研发岗，被提高到第 2。

**退化案例**

原第 1 的模型服务部署岗，被降到第 15，而前排变成了普通 AI 应用开发岗位。

平均指标可能掩盖少数重要问题的退化。

因此应记录排序变化，并对应原文解释。

### 6. 应该怎样评测输入表示？

假设我们想比较：

- 只提供命中 Chunk；
- 提供完整 JD；
- 提供章节化 JD。

这里需要注意两个不同实验。

**实验 A：比较不同的重排算法。**

应固定候选表示。

**实验 B：比较不同的候选表示。**

应固定模型和其他配置。

例如：

~~~text
同一批候选 JD
同一个 Rerank 模型

A：命中 Chunk
B：标题 + 完整 JD
C：标题 + 职责 + 任职要求

比较：
nDCG、前排岗位相关性、
关键条件误判、输入成本。
~~~

不能同时更换模型和输入表示，然后把收益全部归因于新模型。

### 7. 怎样比较延迟与质量？

模型式 Rerank 通常比简单保留 Retrieval 排名增加额外工作。

因此需要记录：

- 候选数量；
- 每份候选的输入长度；
- 请求次数；
- Token 用量；
- 模型响应时间；
- 总体 P50/P95 延迟；
- 费用；
- 错误率与超限率。

例如，重排 Top-20 已经获得明显收益，而重排 Top-100 几乎不再改善前五名，却显著增加费用。

那么 Top-20 可能更经济。

但是要注意：

减小候选数量本身也会降低可重排的候选覆盖范围。

所以比较候选规模时，应该明确这是**新的端到端策略实验**，而不是继续声称只比较同一固定候选上的排序算法。

## 五、怎样理解 Rerank 实验结果？为什么分数高不一定更好？

### 1. 为什么模型的相关性评分不能代替原文判断？

假设某个 Reranker 给出：

~~~text
岗位 A：0.94
岗位 B：0.87
岗位 C：0.12
~~~

如果岗位 A 只是公司介绍中有 RAG，岗位 B 的核心职责却是 RAG 研发，那么 A 的高分可能说明模型没有准确把握业务目标。

因此不能只看排序分数。

要看：

- 候选是否真正符合用户意图；
- 排名变化是否得到原文支持；
- 是否误解了否定、必须、优先等条件；
- 是否把技术领域相似误当成岗位职责相似。

### 2. 为什么增加招聘领域指令不一定更好？

例如给 Reranker 增加一段指令：

> 优先将岗位职责真正涉及技术研发的岗位排在前面，降低仅在公司介绍中提及技术的候选。

这看起来合理。

但它也可能出现问题。

例如用户本身在寻找产品经理或解决方案架构师。

如果重排模型始终偏好研发岗位，就可能错误地降低产品相关职位。

这说明：

**领域指令必须服从用户问题，而不能把工程师偏好变成所有任务的统一标准。**

因此应该比较：

- 默认相关性判断；
- 引入领域指令的判断；

并按不同问题类别分析收益与退化。

还需要确认具体模型是否支持自定义指令，不能假设所有 Rerank API 都能改变相关性标准。

### 3. 为什么输入截断会严重影响结论？

假设一份 JD：

~~~text
岗位标题：AI 平台工程师

公司介绍：大量背景描述……

岗位职责：负责 AI 应用开发……

任职要求：必须具备模型推理服务部署经验。
~~~

如果输入太长，系统只发送前半部分，那么关键任职要求就可能被截掉。

重排模型没有看到这句话，自然无法依据它判断。

此时：

**错误并不一定来自模型能力，而可能来自重排输入已经丢失重要证据。**

因此，应当明确：

- 发送了完整 JD 还是部分内容；
- 是否进行了截断；
- 截断发生在哪里；
- 采用什么长度预算；
- 每种方案是否使用相同输入。

尤其不能出现：

> 默认重排使用完整 JD，领域指令重排只使用截断 JD。

然后把两者的效果差异解释成指令质量差异。

### 4. 为什么不能随意将候选拆成多个批次？

假设 50 份 JD 无法放进同一个模型请求。

于是系统将其分成：

- A 组：前 25 份；
- B 组：后 25 份。

分别调用 Reranker。

如果模型的分数没有跨请求校准保证，那么：

~~~text
A 组最高分：0.85
B 组最高分：0.92
~~~

不能仅凭这两个数字就认定 B 组候选比 A 组更相关。

因为它们可能处于不同的评分上下文或尺度。

有些逐候选评分模型可以在验证评分一致性后采用批处理；有些列表式模型则特别依赖同一批候选的相对关系。

因此：

**拆批不是单纯的请求工程优化，它可能改变排序语义。**

如果原实验无法在输入限制下完成，应明确停止，调整候选预算并重新冻结实验，或者先验证可跨批比较的方案，而不是偷偷拆批后继续汇报原实验结果。

### 5. 为什么不同模型的高分不能直接比较？

不同 Reranker 的输出范围和含义可能不同。

例如：

- 某模型使用 0～1；
- 某模型使用其他相关性评分尺度；
- 某模型输出列表相对排序；
- 某模型提供专门的校准分数。

因此实验时优先比较：

**在同一套人工相关性标准下，它们实际生成了什么岗位排序。**

不要直接比较：

> 模型 A 平均分 0.91，模型 B 平均分 0.76，所以 A 更好。

平均评分尺度不同，并不能证明排序质量高低。

### 6. 什么时候应该保留不重排方案？

如果实验发现：

- 原检索的前排已经很好；
- 模型重排没有稳定提升；
- 一些关键岗位被错误降低；
- 延迟和费用明显增加；
- 复杂输入处理带来新的失败风险；

那么保留不重排完全合理。

**技术是否先进，不决定它是否应该上线。实际质量收益才是主要依据。**

## 六、发现 Rerank 效果不好后，怎样诊断？

### 1. 为什么岗位排序错误，不一定是 Rerank 模型的问题？

假设用户问：

> 找负责模型服务底层部署的岗位。

正确岗位已经进入 Retrieval Top-50，但 Rerank 后排名下降。

可能存在以下原因：

- 用户问题表达不清晰；
- 重排输入只包含一小段 Chunk；
- 关键职责被截断；
- 标题或章节信息缺失；
- 模型只判断技术主题相似；
- 模型误解了研发与调用的差异；
- 自定义领域指令改变了用户目标；
- 候选顺序映射错误；
- 请求失败后系统混用了部分结果；
- 原先的人工相关性标注不正确。

因此不能一看到重排错误，就直接要求换一个更强的模型。

### 2. 怎样沿流程定位问题？

~~~text
用户问题
    ↓
Retrieval 候选是否完整？
    ↓
候选身份和版本是否正确？
    ↓
Rerank 输入是否完整？
    ↓
模型是否读到了关键条件？
    ↓
模型返回索引是否正确？
    ↓
分数与候选是否正确关联？
    ↓
是否按预定规则重新排序？
    ↓
最终岗位与原文是否一致？
~~~

优先检查最早出现异常的环节。

例如：

**情况 A：候选中没有正确岗位。**

优先回到 Retrieval。

**情况 B：候选中有正确岗位，但送给 Reranker 的 JD 被截断。**

优先修复输入表示或预算。

**情况 C：输入完整，但模型持续偏好公司介绍。**

优先研究模型相关性判断与任务指令。

**情况 D：模型响应正确，但最终顺序错误。**

优先检查候选 ID 映射和排序代码。

### 3. 常见失败与改进方向

| 失败现象 | 优先检查 | 候选改进方向 |
|---|---|---|
| 正确岗位根本没有进入候选 | Retrieval | 召回与候选预算 |
| 排序只依据局部 Chunk | 输入表示 | 章节或全文回读 |
| 必须/优先被混淆 | 语义判断 | 原文证据与任务标准 |
| 公司介绍干扰排名 | 章节关系 | 结构信息或模型对照 |
| 长 JD 中关键条件被忽略 | 输入预算 | 完整性核查与表示设计 |
| 同一岗位被重复排序 | 候选去重 | 按稳定岗位 ID 去重 |
| 排名与模型输出不一致 | 结果映射 | 返回索引与候选校验 |
| 拆批后排名异常 | 评分尺度 | 校准或重新设计实验 |
| 重排明显变慢 | 运行成本 | 调整候选规模或选择更快方案 |
| 排序很好但最终推荐错误 | 下游判断 | 业务核验与生成 |

### 4. 怎样记录一条重排失败案例？

~~~text
用户问题：
找负责企业 RAG 底层研发的工程岗位。

固定候选：
包含岗位 A、B、C 等 50 条 JD。

预期：
岗位 A 负责索引、召回、重排与服务建设，
应比岗位 B 更相关。

重排结果：
岗位 B 排第 1；
岗位 A 排第 9。

检查：
1. Retrieval 已找到岗位 A。
2. Rerank 输入包含完整 JD。
3. 候选 ID 映射正确。
4. 岗位 B 主要负责 API 集成。
5. 模型将技术主题相似误当成职责匹配。

改进假设：
尝试增强“岗位实际职责”的评价要求。

验证：
固定候选与完整 JD，
比较默认模型和领域指令方案，
检查其他类别岗位是否退化。
~~~

一个有效的失败案例，需要能够解释：

**错误发生在哪里，为什么认为这是错误，以及怎样验证修复方案。**

## 七、怎样让 AI 持续优化 Rerank？

### 1. 哪些工作可以交给 AI？

AI 可以承担：

- 读取固定候选；
- 生成对照模型调用代码；
- 检查模型请求长度；
- 校验响应索引；
- 分类排序错误；
- 比较不同任务指令；
- 分析升降排名；
- 计算实验指标；
- 总结退化案例；
- 生成质量报告。

但是 AI 不应该自动把自己的相关性判断当作唯一标准答案。

如果同一个模型既负责重排，又独自定义所有人工标准，评测就可能失去独立性。

### 2. 一轮优化应该怎样组织？

**第一步：冻结 Retrieval 候选。**

确保不同重排方案使用相同的候选岗位 ID 和版本。

**第二步：冻结重排输入。**

例如统一使用：

> 岗位标题 + 完整 JD 原文。

保留原始章节顺序，记录是否有截断。

**第三步：建立人工相关性标注。**

对候选统一审阅，保存相关性等级、证据和理由。

**第四步：运行不重排基线。**

保留 Retrieval 原始排序。

**第五步：运行候选重排方案。**

例如规则、专用 Reranker 和允许自定义任务标准的模型方案。

**第六步：比较结果。**

检查 nDCG@5、Precision@5、MRR、典型改善、退化及成本。

**第七步：决定是否保留。**

没有可信收益时，不替换原方案。

### 3. 应该怎样控制实验变量？

假设希望验证：

> 加入招聘领域指令能否改善 Rerank？

那么需要固定：

- 召回结果；
- 候选数量；
- 岗位版本；
- 完整 JD；
- 模型；
- 候选顺序；
- 评分方式；
- 评测标准。

只改变任务指令。

如果还同时缩短 JD、替换模型、减少候选数量，结果就无法归因。

这一点与前面的 Chunking、Embedding、Retrieval 实验方法一致。

### 4. 为什么必须有明确的失败和停止行为？

假设模型服务超时或响应不完整。

系统不能：

- 把没有返回的候选默默删除；
- 将部分候选误当成完整重排结果；
- 给遗漏的候选随意补一个分数；
- 混用不同模型版本的分数；
- 宣称整轮实验成功。

在线查询可以根据业务要求选择降级到原 Retrieval 排序，同时明确标记降级。

离线严格对照实验则应记录失败，必要时停止该组实验。

**在线系统重视可用性，评测系统重视实验有效性。两者对失败的处理可以不同，但都不能掩盖实际发生的情况。**

### 5. 怎样向 AI 下达有效的 Rerank 优化任务？

> 请基于当前冻结的 Retrieval 候选集合，评价 Rerank 的排序效果。
>
> 首先检查候选 JD 的 ID、版本、文本完整性、原文顺序和输入长度。
>
> 对不同方案使用完全一致的候选集合与候选表示，比较不重排、规则排序、专用 Reranker 和需要验证的任务指令。
>
> 以独立审阅的岗位相关性等级和原文证据作为评价依据。
>
> 报告 nDCG@5、Precision@5、MRR、典型改善、退化、延迟与费用。
>
> 如果模型输入超限、响应索引不完整或候选集合变化，不得静默截断、删减或继续合并不具可比性的分数。
>
> 对每个明显失败案例，定位是输入、模型判断、映射还是下游处理问题。
>
> 未通过有效对照实验，不修改正式 Rerank 策略。

这类任务要求 AI 对可靠实验和真实业务收益负责，而不是对“成功接入模型”负责。

## 八、Job-RAG 实践：当前 Rerank 实验做到哪里，下一步怎么推进？

### 1. Job-RAG 现在是否已经上线专用 Rerank？

根据当前项目的 [模型服务设计](https://github.com/leecolin2023/job-rag/blob/main/job_rag/providers/README.md) 和 [Embedding 与 Rerank 实验设计](https://github.com/leecolin2023/job-rag/blob/main/docs/embedding-experiments.md)，需要明确区分三件事：

**第一，当前在线候选检索。**

以 BM25 为基础，可选接入 Embedding 与混合检索。

**第二，离线 Rerank 实验框架。**

已经具备独立的专用模型调用、候选输入构造、缓存、审计和实验配置等能力。

**第三，真实完整的重排对照结果。**

此前已经验证过 Rerank 小规模探针，但完整的重排实验尚未完成。

因此不能把：

> 项目支持 Rerank API。

直接理解为：

> 线上服务已经使用专用 Reranker，而且已经证明显著改善排序。

这属于不同的工程状态。

### 2. 已经建立了什么实验设计？

当前项目计划在同一候选集合上比较：

| 方案 | 含义 |
|---|---|
| none | 保留原 Retrieval 排名 |
| bm25 | 在固定候选池内执行词法排序 |
| section_rule | 使用透明的章节与条件规则 |
| qwen_default | 使用专用 Reranker 默认设置 |
| qwen_recruitment_instruction | 使用同一模型及招聘领域指令 |

其中后两项需要注意：

模型相同，不代表所有调用必然有效。

仍需检查：

- API 是否支持相关指令；
- 请求输入是否符合限制；
- 返回结果是否完整；
- 不同方案是否使用相同候选文本；
- 实际费用和延迟。

### 3. 为什么当前项目专门审计完整 JD 输入？

这是一个值得单独研究的工程问题。

根据 [2026-10-28 完整 JD 重排输入审计](https://github.com/leecolin2023/job-rag/blob/main/docs/rerank-input-audit-2026-10-28.md)，实验输入来自：

- 30 条测试查询；
- 6 种召回方案；
- 合计 180 组冻结候选；
- 每组 3～50 份 JD；
- 默认指令与招聘领域指令两种请求变体；
- 共计 360 个待发送请求变体。

重排输入统一采用：

**岗位标题 + 完整 JD 原文。**

不改变原始章节顺序，不静默截断正文。

为什么这样做？

因为如果不同方案使用的 JD 内容不一样，最终就很难判断排序质量差异来自模型，还是输入内容本身发生了变化。

例如：

**方案 A**

使用完整 JD。

**方案 B**

只使用前 1,800 字节。

如果 B 的表现更差，可能不是模型能力弱，而是关键任职要求恰好被截断。

因此必须先保证对照的输入等价。

### 4. 输入审计发现了什么？

根据当时的审计，使用 Qwen3.7 文本重排模型时，需要遵守供应商规定的单条文档、查询和整次请求的输入限制。

但这里出现了一个实际困难：

**项目没有验证与托管模型严格对应的 tokenizer。**

因此，程序使用 UTF-8 字节数和额外保留量作为保守估算依据。

要特别注意：

**UTF-8 字节数不是 Token 数。**

不能把：

> 保守预检没有通过。

直接解释为：

> 供应商实际 Token 上限已经被超过。

审计结果显示，现有完整 JD 候选在这一保守预检下，有不少请求无法通过本地准入检查。

例如当时默认指令版本中，不同召回方案每 30 组查询大约只有 7～8 组通过该保守检查。

这并不能证明模型无法处理其他请求。

但它表明：

**在输入预算尚未核实前，不能把这批请求作为已经满足实验条件的数据直接发送。**

因此项目当时选择停止完整付费实验，而不是自动截断 JD 或缩减候选。

这是正确的实验保护思路。

### 5. 为什么不能为了跑通实验，直接减少候选数量？

假设原来每组有 50 个岗位。

为了满足输入限制，突然只保留前 20 个。

这可能使真实相关岗位被排除。

此时比较结果变化的原因就不只是 Rerank 模型。

候选集合也改变了。

因此正确做法是：

**如果需要减少候选数量，就重新定义候选预算，将其作为一项明确的新实验。**

例如：

~~~text
实验 A：
固定 Retrieval Top-20
比较不同 Rerank 方案。

实验 B：
固定 Retrieval Top-50
比较不同 Rerank 方案。

再研究：
Top-20 和 Top-50 的端到端质量、延迟和成本。
~~~

不能把 A、B 的结果混在一起，宣称只是更换了重排模型。

### 6. 当前最值得补齐的是什么？

我认为不是继续增加 Rerank 模型。

而是先把以下基础条件完成。

#### 第一优先级：完成固定候选池的人工审阅

目前已有 30 条查询和多种召回方案的候选。

应按岗位 ID 汇总候选，进行独立相关性标注。

尤其关注：

- 真正负责 RAG 研发；
- 只在公司介绍中提到 RAG；
- 业务 API 集成与底层工程开发；
- 必备与优先条件；
- 技术深度是否符合问题。

当前只依赖单个种子正例，不足以对完整重排质量作出可靠判断。

#### 第二优先级：核实模型输入预算

对于完整 JD：

- 核实具体模型限制；
- 使用经过验证的 Token 计算方式，或明确承认估算边界；
- 检查最长的岗位；
- 检查最大候选集合；
- 不静默截断或删减；
- 在付费调用前发现超限风险。

如果无法按原方案满足预算，就明确调整实验设计。

#### 第三优先级：先运行不重排与规则基线

这一步不需要调用付费 Rerank 模型。

先明确：

- Retrieval 原始排名；
- 固定候选池内 BM25 排名；
- 简单章节规则排名。

有了这些结果，才能判断付费重排模型究竟要超越什么。

#### 第四优先级：运行专用 Rerank 对照

在输入与标注符合要求后，比较：

- 不重排；
- 规则排序；
- 专用 Reranker 默认模式；
- 经过确认支持的领域指令模式。

重点看：

- nDCG@5；
- Precision@5；
- MRR；
- 具体岗位升降；
- 严重误判；
- 延迟与费用。

#### 第五优先级：评价是否值得上线

如果专用 Rerank 明显改善了前排岗位质量，且延迟和成本合理，可以进一步设计在线接入。

如果收益很小，或者关键问题上反而退化，就保留原 Retrieval 排序。

不需要为了“RAG 架构完整”而强行增加 Rerank。

### 7. 应该先做模型对比，还是输入表示对比？

建议优先完成一个固定输入表示的模型对照。

原因是：

当前已有明确的完整 JD 输入策略，可以先把它作为可验证基线。

例如：

~~~text
固定输入：
岗位标题 + 完整 JD。

候选：
相同的 20 或 50 个岗位。

比较：
不重排、规则、专用 Rerank。

评价：
人工等级、nDCG、Top-5 质量。
~~~

随后再研究：

- 完整 JD；
- 命中 Chunk；
- 章节结构化 JD；
- 关键证据 + 上下文。

两轮实验不要混在一起。

但也要注意，完整 JD 只是当前适合验证的候选方案，不代表它已经被证明是最优重排输入。

### 8. 下一轮实验报告应该怎样组织？

| 报告内容 | 要回答的问题 |
|---|---|
| 研究问题 | Rerank 需要修复哪类排序错误 |
| 固定候选 | 使用什么 Retrieval 结果 |
| 输入表示 | 是完整 JD 还是 Chunk，有无截断 |
| 人工标注 | 候选相关性如何定义和核验 |
| 对照方案 | 不重排、规则、模型、指令 |
| 排名质量 | nDCG、Precision、MRR |
| 改善案例 | 哪些真正相关岗位被提高 |
| 退化案例 | 哪些重要岗位被错误降低 |
| 完整性 | 是否遗漏、重复或截断候选 |
| 成本性能 | 模型调用、Token、延迟 |
| 最终决策 | 是否启用、回退或继续验证 |

例如：

~~~text
研究问题：
专用 Reranker 能否改善
RAG 工程岗位的前排排序？

固定条件：
- 同一批候选岗位；
- 相同 JD 版本；
- 相同完整 JD 输入；
- 相同用户问题；
- 相同人工相关性标准。

对照：
A：不重排；
B：章节规则；
C：专用 Reranker。

主要指标：
- nDCG@5；
- Precision@5；
- MRR；
- 典型改善与退化；
- 模型调用成本和延迟。

重点案例：
公司介绍提到 RAG，
但实际岗位不负责 RAG 研发。

决策：
根据完整对照结果确定，
不预设 Rerank 必然提高质量。
~~~

这就把 Rerank 从“接入一个模型进行排序”，转变成“能够验证、解释和持续优化排序质量”的工程能力。

---

## 结语：Rerank 的核心不是让排名发生变化

我们最初的问题是：

> 已经有 BM25、Embedding 和 Hybrid 检索，为什么还需要 Rerank？

真正需要回答的是：

**第一，当前主要问题是不是排序质量？**

如果正确证据没有被召回，应该先改进 Retrieval。

**第二，什么才是业务上更相关的候选？**

对于 Job-RAG，“公司使用某项技术”与“岗位负责研发这项技术”有明显差异。

**第三，怎样设计可靠的重排输入？**

需要判断 Chunk、章节或完整 JD 哪种表示更合适，并确保重要条件没有被截断。

**第四，怎样证明 Rerank 真的有效？**

固定候选集合和输入表示，以独立相关性标注比较不重排、规则与模型方案。

**第五，实验结果有什么限制？**

模型分数不一定是匹配概率，跨请求分数不一定可比较，输入预算和候选截断也可能改变实验结论。

**第六，怎样利用 AI 持续改进？**

让 AI 在明确业务目标和独立评测标准下，提出优化假设、运行对照实验、解释退化，而不是仅仅增加模型复杂度。

> **Rerank 的真正价值，不是使用更复杂的模型重新排序，而是在可靠的候选集合内，把真正符合用户意图、能够提供有效证据的内容排到更值得优先阅读的位置。**

对于 AI 时代的工程师，真正需要掌握的不是某个 Rerank API 的调用方法。

而是：

**什么时候应该重排、应该根据什么重排、如何判断模型有没有真的理解业务相关性，以及什么时候不应该为重排支付额外成本。**
