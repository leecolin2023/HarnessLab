# RAG 文档切分：如何设计、评测与持续优化？

> 本文以 [Job-RAG](https://github.com/leecolin2023/job-rag) 的招聘 JD 知识库为贯穿案例。讨论重点不是如何编写某个切分函数，而是如何确定是否需要切分、怎样定义质量、通过实验判断方案优劣，并指导 AI 持续优化。
>
> 本文在 RAG 学习链条中属于 **03：文档切分**。前置环节是文档采集与解析（02），后续环节包括 Embedding/索引、检索、重排和证据生成。

## 一、为什么要切分？不切分可以吗？

### 1. 我们究竟要解决什么问题？

假设我们正在建设一个招聘岗位知识库 Job-RAG，保存了约 600 份招聘 JD（Job Description，职位描述）。

现在，用户提出一个问题：

> 帮我找到真正负责大模型推理服务部署的岗位，而不是只负责调用大模型 API 的岗位。

为了回答这个问题，系统需要从大量 JD 中找到相关岗位，并判断它们究竟在描述什么工作。

最直接的方法是：**把每份 JD 当成一个完整文档进行检索。**

~~~text
用户问题：哪些岗位负责模型部署？
         ↓
搜索所有完整 JD
         ↓
找出可能相关的岗位
         ↓
阅读 JD 并判断职责
         ↓
返回结果
~~~

这个方案没有切分步骤，完全可能有效。

因此，我们不应该一开始就讨论 Chunk 应该是 500 字还是 1000 字，而应该先回答：

**完整文档检索究竟遇到了什么问题，以至于需要引入切分？**

### 2. 完整文档检索可能遇到什么困难？

假设一份 JD 包含：

**岗位：AI 应用开发工程师**

公司介绍：

> 公司提供基于 vLLM 的大模型推理服务。

岗位职责：

> 负责业务系统开发、模型 API 接入及应用集成。

任职要求：

> 熟悉 Python 开发，有 vLLM 生产部署经验者优先。

用户想找的是“负责大模型推理部署的岗位”。

但在这份 JD 中：

- 公司介绍提到了 vLLM，不代表这个岗位负责部署；
- 岗位职责主要是 API 接入，不是模型部署；
- 任职要求中的部署经验是优先项，而不是必备项。

如果整份 JD 作为一个检索单位，系统可能因为出现了相关技术词而给出较高的相似度。尤其当整份文本只对应一个 Embedding 向量时，向量相似度本身无法直接告诉我们：究竟是公司介绍、岗位职责，还是任职要求造成了匹配。

这里的问题不是 JD 太长，而是：**用户需要找到的是文档中的特定证据，但检索系统只知道整份文档可能相关。**

### 3. 切分能够带来什么？

一种解决方案是将 JD 按不同内容拆开：

~~~text
完整 JD
  ├── 公司介绍 Chunk
  ├── 岗位职责 Chunk
  └── 任职要求 Chunk
~~~

这样，系统就有机会分别检索不同部分。

例如用户问“哪些岗位负责模型部署”，系统可以优先关注岗位职责中的相关内容，而不是仅仅因为公司介绍提到了 vLLM 就推荐岗位。

这就是切分的主要价值：**将检索单位从完整文档缩小到更容易定位具体证据的内容片段。**

不过，切分并不会自动解决招聘语义判断。即使找到了任职要求，系统仍需要区分“必须”和“优先”。

### 4. 切分会带来新的问题吗？

会。假设原文写着：

> 熟悉 Python 或 Java，满足其一即可。

如果切分后变成：

~~~text
Chunk A：熟悉 Python
Chunk B：或 Java，满足其一即可
~~~

当系统只检索到 Chunk A 时，可能错误地认为 Python 是必须掌握的技能。

切分还可能带来其他问题：

- 一份 JD 产生更多索引记录，增加处理成本；
- 某些 Chunk 过短，失去原文上下文；
- 一份岗位产生多个高相似度 Chunk，影响岗位排序；
- 原来需要联合阅读的多条条件被拆散；
- 添加的章节和条件标签可能干扰 Embedding 排序。

因此，切分不是一个只有收益、没有成本的技术。

### 5. 应该什么时候引入切分？

判断依据不应该是文档长度本身，而应该是**当前方案是否满足业务目标**。

| 观察结果 | 是否有必要切分 |
|---|---|
| 整份 JD 检索已经能够找到正确岗位，并准确理解条件 | 不一定需要 |
| 搜索经常命中公司介绍，而不是实际岗位职责 | 值得尝试章节切分 |
| 一份 JD 包含大量独立要求，需要定位具体条目 | 值得尝试条目切分 |
| 主要需求是统计所有岗位的技能要求 | 可能更需要结构化抽取 |
| 需要跨越多个章节联合判断岗位匹配度 | 应考虑保留完整 JD 供回读 |

**第一条设计原则：不要预先假设切分是必要的。先建立完整文档基线，再验证切分是否带来实际收益。**

## 二、怎样定义一个好的文档切分方案？

### 1. 什么叫“切分得好”？

一个常见误区是根据 Chunk 的外观评价质量：

- 每个 Chunk 的长度是不是接近？
- 是否按照章节组织？
- 有没有元数据？
- 是否使用了语义切分？
- Chunk 之间有没有重叠？

这些只能描述切分方案，不能证明方案有效。

例如，一套规则能够将所有 JD 切成长度非常整齐的 500 字片段，但如果它经常切断“必须”“优先”“满足其一”等条件关系，这套方案仍然可能很差。

对于 RAG：

> **好的切分方案，应当在可接受的成本下，保留原文证据及其必要语境，让检索系统更容易找到正确证据，并帮助后续系统更准确地完成任务。**

这个定义包含三个质量层次。

### 2. 第一层：功能正确性——有没有把信息切坏？

这是最基本的要求。切分系统可以改变文本的组织方式，但不应该使原文证据丢失或无法追溯。

至少需要满足：

| 要求 | 判断标准 |
|---|---|
| 信息保留 | 原文中的有效内容没有因切分而被遗漏 |
| 来源追溯 | 能根据 Chunk 找回对应原文 |
| 语义关系 | 不应无故切断决定原意的条件关系 |
| 元数据可信 | 系统生成的标签与招聘方原文明确区分 |
| 异常可处理 | 无法识别的章节保留未知状态，不强行判断 |

例如原文：

> 有 vLLM 生产部署经验者优先。

系统可以添加：

~~~text
章节：任职要求
条件性质：优先
原文：有 vLLM 生产部署经验者优先。
~~~

但必须区分：

- “有 vLLM 生产部署经验者优先”是招聘方原文；
- “条件性质：优先”是系统生成的解释标签。

当两者发生冲突时，应以原文为最终核验依据。

从系统设计角度看，Chunk 至少需要包含用于检索的文本、所属文档 ID、对应原文或原文位置、必要的章节与来源信息，以及跨片段时能恢复上下文的关联信息。

这就是 Chunking 的**输入输出契约**。不论底层使用规则、传统 NLP 还是大模型，都必须满足这些要求。

### 3. 第二层：检索有效性——正确证据能否被找到？

假设有两套方案：

- A：整份 JD 作为一个检索单位；
- B：按照章节切分。

对于问题“哪些岗位要求 vLLM 生产部署经验”，两套方案都能找到同一份岗位。

但区别在于：

- A 返回整份 JD，需要后续模型自己定位条件；
- B 直接返回任职要求中的对应条目。

那么 B 一定更好吗？不一定。

如果后续模型阅读整份 JD 已经可以稳定、准确地定位相关条件，B 的收益可能很小。反过来，如果整份 JD 包含大量无关信息，B 可能显著改善证据定位。

因此不能只检查是否找到了岗位，还应检查：**系统是否找到了足以支持判断的具体证据。**

需要区分两个问题：

1. **岗位召回**：相关岗位有没有进入候选名单？
2. **证据召回**：判断该岗位所需的原文信息有没有进入候选内容？

两者相关，但并不相同。

### 4. 第三层：业务有效性——最终结果有没有变好？

例如用户提出：

> 统计所有将 vLLM 生产部署列为必备条件的岗位。

一套切分方案可能让系统找到了大量包含 vLLM 的 Chunk，但最后仍然把“经验优先”误认为“必须具备”。

这样的切分结果即使检索指标很高，也没有完成用户真正的任务。

对于 Job-RAG：

| 用户任务 | 最终成功标准 |
|---|---|
| 查找岗位 | 不遗漏重要的相关岗位 |
| 判断任职要求 | 正确区分必须、优先、否定及替代条件 |
| 统计技能需求 | 在明确的岗位范围内正确归类、去重和计数 |

尤其需要注意，第三类任务不一定应该依靠 Top-K 检索完成。如果用户要求统计全库，系统可能需要完整枚举符合条件的 JD，再进行结构化抽取和统计。

**不能因为 RAG 能够检索，就认为所有问题都应该通过检索排序解决。**

### 5. 最后还要看成本吗？

当然。假设 A 和 B 的业务效果基本相同，但 B 的 Embedding 输入 Token 更多、索引记录更多、查询更慢、维护逻辑更复杂。

如果这些额外成本没有换来可验证的业务收益，就没有充分理由选择 B。

**先满足正确性，再比较业务效果，最后考虑成本和复杂度。** 不能用较低成本补偿严重的事实错误，也不应为了微小且不稳定的指标变化无限增加系统复杂度。

## 三、文档切分有哪些候选方案？应该怎么选择？

### 1. 方案 A：完整文档检索

~~~text
一份 JD → 一个检索单位
~~~

优势：

- 实现简单；
- 完整保留上下文；
- 不会因为切分丢失条件关系；
- 适合整体判断岗位职责与任职要求。

不足：

- 多个主题混在一起，可能影响检索定位；
- 检索到岗位后还需要进一步定位证据；
- 文档很长时，可能超出模型输入限制，或增加处理成本。

对于 Job-RAG 这种几百份 JD 的场景，完整文档检索值得成为正式基线。

### 2. 方案 B：按照章节切分

~~~text
完整 JD
  ├── 公司介绍
  ├── 岗位职责
  ├── 任职要求
  └── 加分项
~~~

优势是能够保留不同内容的用途信息。用户搜索工作职责时，可以更容易区分岗位真正负责的工作和公司经营的业务。

不足是一些 JD 没有标准章节、部分章节非常长、一些职责与要求存在跨章节联系。

因此章节切分是否更好，需要看实际 JD 的格式分布和用户问题类型。

### 3. 方案 C：按照条目进一步切分

~~~text
任职要求
  ├── 熟悉 Linux
  ├── 有 vLLM 部署经验者优先
  └── Python 或 Java 满足其一即可
~~~

优势是方便定位具体要求。

但过短条目可能缺少上下文；复杂条件可能跨越多条内容；过多 Chunk 可能增加候选碎片和索引成本。

因此需要验证一个假设：

> 相比章节切分，更细的条目切分是否真正改善了证据召回及后续判断？

不能仅凭“粒度更细”推断结果会更准确。

### 4. 方案 D：结构化信息提取

还有一种思路是不把所有任务都交给文本检索。

例如原文：

> 有 vLLM 生产部署经验者优先。

系统可以提取：

~~~text
技能：vLLM
能力：生产环境部署
要求强度：优先
原文证据：有 vLLM 生产部署经验者优先
~~~

这样用户要统计岗位技能时，就有可能使用结构化字段查询和汇总。

但需要明确：**结构化提取不是另一种简单的 Chunk 大小，而是改变了知识的组织方式。**

它的优势是适合条件过滤、分类和统计；不足是抽取可能错误，复杂 AND/OR/例外关系不易表达，新问题可能需要新字段，抽取结果仍需关联原文。

因此结构化信息不应该完全代替原文，而应作为一层可核验的事实表示，与 JD 和文本检索配合。

### 5. 有没有必要只选择一种方案？

没有。

~~~text
                     完整 JD
                        │
          ┌─────────────┼─────────────┐
          ↓             ↓             ↓
       全文索引      章节/条目索引    结构化事实
          │             │             │
          └─────────────┼─────────────┘
                        ↓
              根据任务选择查询方式
                        ↓
                 回读 JD 核验证据
~~~

例如：

- 找相近岗位，可以进行文本检索；
- 判断某岗位的整体匹配度，可以回读完整 JD；
- 统计明确技能条件，可以查询结构化事实，并核对原文；
- 查找某条原始制度规定，可以检索具体条款。

另一种值得验证的组合是**小片段用于检索、父文档用于阅读**，通常称为 Parent-Child Retrieval（父子检索）：先通过短条目命中，再读取所属章节或完整 JD。

还有 Contextual Retrieval（上下文化检索），通过为独立 Chunk 补充所属文档的简短背景，减少语境丢失。[Anthropic 的 Contextual Retrieval 研究](https://www.anthropic.com/engineering/contextual-retrieval)提供了实验案例，但其效果不能直接套用到招聘 JD。

**不是争论哪种方案理论上最先进，而是列出合理候选，用相同业务问题比较效果。**

## 四、怎样为文档切分建立评测？

### 1. 为什么不能让 AI 自己判断切得好不好？

如果要求 AI“帮我检查当前切分质量并评分”，它可能报告章节准确、长度合理、语义完整、符合最佳实践。

但这些往往只是对方案表面特征的分析。

真正需要回答的是：**使用这套方案之后，用户的问题能否得到更正确的答案？** 这必须通过测试案例验证。

### 2. 评测案例从哪里来？

应当先从真实用户任务出发，而不是从切分算法功能出发。

| 类型 | 用户问题 | 检验能力 |
|---|---|---|
| 技术搜索 | 哪些岗位需要 RAG 开发？ | 技术相关内容召回 |
| 职责判断 | 哪些岗位真正负责模型部署？ | 公司介绍与职责区分 |
| 条件判断 | vLLM 是必须还是优先？ | 条件语义保留与判断 |
| 组合条件 | 哪些岗位同时要求 Python 和模型部署？ | 多证据联合判断 |
| 全库统计 | 要求 RAG 的岗位还要求哪些技术？ | 完整枚举、归类与计数 |

评测集不能只有大量“找某项技术”的关键词搜索。否则可能把一个擅长词项匹配、但无法理解工作职责的系统评为优秀。

### 3. 一条完整的评测案例包含什么？

**用户问题**

> 哪些岗位要求必须掌握 vLLM 生产部署？

**原始 JD**

> 熟悉 Python，具有 vLLM 生产部署经验者优先。

**预期判断**

- 这份岗位提到了 vLLM 生产部署；
- 原文明确是优先条件；
- 不能将岗位归为明确必备 vLLM 部署经验的岗位。

**预期证据**

> 具有 vLLM 生产部署经验者优先。

建议每条案例至少保存：

| 字段 | 用途 |
|---|---|
| question | 用户原始问题 |
| expected_job_ids | 已核验的相关岗位 |
| evidence | 支持判断的 JD 原文 |
| expected_judgment | 预期业务判断 |
| exclusion_reason | 不符合条件的岗位为何排除 |
| case_type | 错误或能力类型 |

必须明确区分：expected_job_ids 可能只是已知正例，也可能是穷尽审阅后的完整集合。只知道一个正确岗位，不能假装已经标注完全部相关岗位。

### 4. 怎样保证案例具有代表性？

一开始可以建立几十条问题的评测集，但需要覆盖不同难度。

**常规情况**：标准章节、标准编号、单一技能要求、完整职责描述。

**复杂情况**：章节标题不规范、多行任职条件、同一技术出现在不同章节、一条条件包含多个技能。

**容易误判的情况**：“必须/优先”、“Python 或 Java”、“无需相关经验”、“公司使用 RAG/岗位负责 RAG”、“调用 API/生产部署模型”。

**边界情况**：极短 JD、超长 JD、格式混乱、近重复岗位、证据不足的问题。

这些案例不是让切分程序记住几十个例子，而是验证它有没有破坏完成真实任务需要的关键信息。

### 5. 怎样选择评测指标？

不能只用一个总分。

| 层次 | 关键指标 | 解释 |
|---|---|---|
| 切分正确性 | 原文覆盖率、来源定位准确性、关键条件关系保留率 | 有没有丢失或破坏证据 |
| 检索质量 | 岗位 Recall@K、证据 Hit@K、nDCG@K | 正确岗位和证据能否找到、排在前面 |
| 业务质量 | 判断准确率、错误必备判断率、统计结果准确性 | 最终任务是否正确 |
| 运行成本 | 索引 Token、查询耗时、存储量、模型成本 | 提升是否值得 |

几个指标需要特别理解：

**Recall@K：前 K 个结果找回多少相关对象？**

假设人工完整审阅确认某问题有 10 个相关岗位，前 20 个找到 8 个，则 Recall@20 = 8/10 = 80%。

但如果只知道其中两个正例，就只能计算这两个已知岗位的命中，不能宣称得到了全库真实 Recall。

**nDCG@K：越相关的结果是否排得越靠前？**

用户不会阅读所有候选。nDCG 可以利用人工相关性等级评价排序质量。

**证据 Hit@K：关键证据有没有进入前 K 个检索结果？**

岗位找到了，不代表找到了正确的职责或任职条件。这要单独测量。

**业务判断准确性：最终回答是否符合原文？**

要核对“优先”是否被说成“必须”、公司业务是否被当成职责、“满足其一”是否遗漏、重复岗位是否去重。

这种指标不能被向量相似度直接代替。

### 6. 谁提供标准答案？

AI 可以帮助生成候选案例、读取 JD、提出初步标注。但关键案例应该经过人工审核，或通过独立复核过程确认。

尤其“必备/优先”、“职责/公司背景”等判断必须回到 JD 原文。

还应避免把没有人工标注的候选默认当成负例。系统可能找到一个高度相关的新岗位，只是它不在最初的标准答案里。

可以汇总不同系统的候选池，再统一审阅。

最后将评测集区分为：

- **开发集**：允许分析失败和反复优化；
- **测试集**：用于验证新方案对未参与优化的问题是否有效。

同一主题的不同问法应当一起分组，避免相似问题分别进入开发集与测试集，造成虚假的泛化表现。

## 五、怎样理解实验结果？为什么指标提升不一定代表更好？

### 1. 新方案准确率提高了，可以直接采用吗？

不能。至少还要问：

1. 使用的是什么指标？
2. 标准答案是否完整？
3. 样本量是否足够？
4. 哪些问题改善，哪些退化？
5. 改善是否真的由切分方案造成？
6. 付出了多少额外成本？

例如 A 在 20 条问题中答对 16 条，B 答对 17 条。表面上 B 从 80% 提高到 85%。

但如果 B 同时将某个重要的“优先”错误判断成“必须”，可能并不值得采用。而样本只有 20 条时，单条案例就带来 5 个百分点变化，结果也未必稳定。

不能只根据平均分做决策。

### 2. 为什么要看具体失败案例？

假设 A、B 的综合得分都是 85%。

- A 技术搜索很好，但条件判断较差；
- B 技术搜索稍差，但条件判断明显更好。

如果系统主要用于关键词搜索，A 可能更适合；如果用于分析任职要求，B 可能更适合。

因此报告不能只有“nDCG@5 提高 0.03”，还应该告诉我们改善了什么、退化了什么、为什么变化、退化是否涉及关键业务风险。

**具体案例分析是连接评测数字与工程决策的重要环节。**

### 3. 为什么不能同时修改多个环节？

假设一次优化同时：

- 将 Chunk 从 1100 改成 600；
- 替换 Embedding 模型；
- 加入 Rerank；
- 修改查询改写；
- 改变岗位聚合策略。

最终 Recall@20 提高了，但不知道原因。甚至可能是 Rerank 改善前排排序，而新 Chunking 实际降低了召回。

应尽可能固定其他条件，只改变要验证的主要因素。例如，在相同 JD、模型、查询、排序规则下比较 1100 与 600 字符预算。

### 4. 为什么要区分局部提升与整体收益？

为 Chunk 添加“岗位职责”“任职要求”等提示，可能改善职责检索，也可能使 Embedding 过度关注重复的章节词，降低技术词检索的区分度。

因此应分组观察：

- 职责检索；
- 技术检索；
- 条件判断；
- 多证据判断；
- 无答案问题。

如果某优化只对一类问题有利，应考虑是否只在对应任务启用，而不是立即替换所有场景。

### 5. 什么时候认为新方案更好？

至少满足：

1. **正确性没有明显退化**：没有新的原文丢失、来源错误或严重条件误判。
2. **目标业务指标有可信收益**：改善体现在真实任务，而非仅块数或长度。
3. **收益能够解释**：知道改善的是哪类问题以及原因。
4. **收益值得成本**：模型调用、索引维护及复杂度与业务价值匹配。

差异不稳定、样本不足时，应明确“证据不足”，保留基线，不必勉强选赢家。

## 六、发现效果不好后，怎样确定应该优化哪里？

### 1. 为什么不能一遇到错误就修改 Chunking？

完整 RAG 系统涉及多环节：

~~~text
原始文档
   ↓
文档解析
   ↓
文档切分
   ↓
建立检索索引
   ↓
检索候选
   ↓
排序与证据组织
   ↓
大模型判断与回答
~~~

例如用户问“哪些岗位将 vLLM 生产部署列为必备技能”，系统错误返回了一个“vLLM 部署经验优先”的岗位。

可能原因包括：

- 切分时丢失了“优先”；
- 切分正确，但检索到的是公司介绍；
- 检索到了正确证据，但排序后没有提供给模型；
- 模型看到了证据，却误解条件；
- 前面都正确，但统计时把优先项计入必备项。

这些问题需要不同方法。

### 2. 怎样沿处理链条定位？

**第一步：原文中是否存在正确证据？**

没有证据就不应编造答案；如果有，继续检查。

**第二步：切分后的内容是否保留证据？**

如果没有，检查文档解析与切分。如果有，就不要先假定 Chunking 是根因。

**第三步：检索候选中是否出现证据？**

如果没有，检查查询表达、召回策略、索引表示、检索数量及过滤条件。

**第四步：正确证据是否进入最终判断？**

如果候选中有但模型未看到，可能是排序、证据拼接或上下文预算问题。

**第五步：模型拿到证据后是否判断正确？**

证据完整而答案错误，就检查语义判断、条件逻辑和业务规则。

> **优先调查最早发生可观察异常的环节，而不是直接修改最终出现错误的组件。**

### 3. 常见失败如何对应优化方向？

| 失败现象 | 首先检查 | 候选优化方向 |
|---|---|---|
| 关键原文内容丢失 | 解析与切分 | 调整边界、保留原文及续片关系 |
| Chunk 缺乏上下文 | 切分与检索表示 | 父级上下文、父子检索 |
| 有相关 JD 但找不到 | 召回 | BM25、Embedding、查询改写 |
| 找到岗位但排名较低 | 排序与聚合 | Rerank、岗位聚合策略 |
| 公司介绍误当职责 | 证据定位与判断 | 章节识别、证据核验 |
| 优先误判为必须 | 条件解释 | 原文复核、判断规则、结构化抽取 |
| 统计遗漏或重复 | 枚举与统计 | 完整查询、岗位去重、事实校验 |

“候选优化方向”只是需要验证的假设，不是确定答案。

例如 Chunk 缺乏上下文，可以尝试父子检索；但如果完整 JD 直接检索已获得同样效果，就未必需要更复杂的父子索引。

### 4. 怎样把失败变成知识资产？

不能只记录“这个问题回答错了”。

更好的记录方式：

~~~text
问题：哪些岗位必须掌握 vLLM？
预期：排除仅将 vLLM 列为优先项的岗位。
实际：错误包含某岗位。

已核实：
1. 原文包含“优先”。
2. Chunk 保留“优先”。
3. 检索结果包含正确原文。
4. 最终判断仍解释为必备。

结论：
优先调查条件判断环节，而不是 Chunking。

后续：
新增条件判断回归案例。
~~~

每次失败都产生两项资产：经过归因的工程问题，以及防止再次犯错的回归测试。

## 七、怎样让 AI 持续优化系统？

### 1. AI 时代工程负责人应该负责什么？

AI 已经可以承担大量实现工作：

- 生成候选切分方案；
- 修改代码；
- 运行测试；
- 调用 Embedding 模型；
- 比较实验；
- 汇总失败；
- 提出优化建议。

但如果只是说“帮我优化 Chunking，让效果更好”，AI 可能增加规则、引入语义切分、调整长度、添加元数据、重写模块，复杂度增加了，却没有证明价值。

因此负责人首先要给出：**目标、约束和评价方法**。

### 2. 一轮完整优化应是什么样？

**第一步：冻结当前基线。**

保存原始测试数据、方案与参数、检索和判断结果、指标、成本。

**第二步：分析失败案例。**

区分切分、检索、后续判断的问题及暂时无法归因的问题。必要时重放相同中间输入隔离问题。

**第三步：提出改进假设。**

例如：“当前部分 Chunk 缺少父级章节信息，导致职责类问题检索下降；尝试补充章节上下文，对照证据召回。”

这不是直接要求加上下文，而是提出一个可证伪的假设。

**第四步：实现最小改动。**

只修改与假设有关的部分，不同时换长度、Embedding、Rerank 和 Prompt。

**第五步：运行完整回归。**

观察原来失败的问题是否改善、原来正确的问题是否退化、业务指标和成本如何变化、结果是否稳定。

**第六步：决定保留还是回退。**

收益明确且成本可接受才考虑替换；效果不明显则保留基线、记录结果，避免重复走弯路。

### 3. 怎样将优化任务交给 AI？

可以使用固定任务描述：

> 请基于当前冻结的测试集评测现有 Chunking。
>
> 先检查功能正确性，再比较岗位召回、证据召回和最终任务判断。
>
> 对失败案例分类，定位可能的问题环节。
>
> 针对证据充分的主要问题提出改进假设，每轮只改变一个主要因素。
>
> 在相同条件下对照新旧方案，报告改善、退化和成本变化。
>
> 不根据单一指标选择方案。证据不足时明确说明，保留原基线。
>
> 未通过评测之前，不替换生产配置或原有索引。

这与“把 Chunking 实现得更先进”不同：前者要求对业务结果负责，后者只要求做技术改造。

### 4. 为什么仍需要理解一定的技术原理？

AI 可能建议“当前准确率不高，把 Chunk 从 1100 缩到 300”。

如果知道：

- 小 Chunk 可能改善局部定位；
- 也可能破坏跨句上下文；
- 更多 Chunk 可能改变岗位聚合排名；
- 最终效果还取决于召回和排序；

就能追问：**现有失败案例证明 Chunk 过大是主要原因了吗？**

缺少证据，就不应直接修改参数。

AI 时代不需要负责人掌握每个算法的实现，但需要理解到足以解释系统行为、提出假设、判断实验结果的程度。

## 八、Job-RAG 实践：如何评价当前方案，下一步应该怎么做？

### 1. 当前采用什么切分方案？

根据 [Job-RAG Chunking README](https://github.com/leecolin2023/job-rag/blob/main/job_rag/chunking/README.md)，默认使用 section_typed：

~~~text
完整 JD
   ↓
识别章节
   ↓
识别条目
   ↓
识别条件性质
   ↓
必要时拆分超长条目
   ↓
合并相邻且符合条件的短片段
   ↓
添加检索上下文
   ↓
保存 Chunk 与原文位置
~~~

其考虑包括：

- 不让公司介绍与任职要求无差别混合；
- 尽可能保留完整招聘条件；
- 区分必备、优先、混合等条件性质；
- 控制 Chunk 长度；
- 保留原文定位能力。

这些设计逻辑上合理，**但合理不等于已经证明效果最好**。

### 2. 已经做过哪些真实实验？

根据 [2026-10-25 Embedding 召回实验](https://github.com/leecolin2023/job-rag/blob/main/docs/recall-pilot-2026-10-25.md)，项目使用 592 份非空 JD 和 30 条查询，对五种文档表示进行了比较。

实验固定相同 Qwen Embedding 服务及主要检索条件；该轮没有 Rerank 或 Hybrid。

| 方案 | 主要区别 | Chunk 数量 |
|---|---|---:|
| A：legacy_1100 | 原始固定/段落分块 | 790 |
| B：fixed_compact_1100 | 原边界，缩减头部 | 790 |
| C：section_compact_1100 | 章节/条目结构化 | 2,443 |
| D：section_typed_1100 | C 加条件性质提示 | 2,443 |
| E：section_typed_600 | D 缩小字符预算 | 2,657 |

注意：A 的预算主要约束正文，完整索引文本不一定与其他方案等长，不能将所有方案视为严格单因素对照。

### 3. 实验结果是什么？

| 方案 | Dev seed nDCG@5 | Test seed nDCG@5 |
|---|---:|---:|
| A：原始分块 | **0.7606** | 0.7515 |
| B：紧凑分块 | 0.7330 | 0.7757 |
| C：章节结构化 | 0.7330 | **0.8914** |
| D：增加条件提示 | 0.6973 | 0.8683 |
| E：缩小字符预算 | 0.6973 | 0.8683 |

这里的指标基于每个问题唯一已知种子岗位的排名，**不能直接解释为完整人工相关性标注下的 nDCG**。

Dev 为 14 条查询，Test 为 16 条，规模较小。

可以得到四个观察：

**观察一：结构化分块在 Test 上表现更好，但 Dev 未稳定领先。**

C 相比 A，在 Test 中提高了种子岗位排名质量；Dev 中 A 反而更好。因此不能证明 C 普遍最优。

**观察二：增加条件提示没有带来稳定收益。**

C 到 D 加入条件性质提示，但这两个集合的汇总指标均下降。“保留条件标签用于判断”和“将标签文字加入 Embedding”是两回事。

**观察三：将 1100 缩为 600 未显示明显收益。**

D 与 E 的汇总指标相同。这只能说明当前实验中缩短预算未改善相关汇总指标，不能证明 1100 是最优长度。

**观察四：BM25 仍值得保留。**

该轮 BM25 对种子岗位的排名很强，但查询包含许多明确技术词，且使用的输入表示与向量方案不同。它是有价值的参考基线，不是词法检索普遍优于语义检索的证据。

### 4. 为什么还不能决定最佳方案？

有两个关键限制。

**第一，正例标注不完整。**

每条查询主要标注一个已知相关岗位。但数据库中可能有多个同样符合需求的岗位。系统检索到一个相关的新岗位，却可能无法得到正例评分。

**第二，尚未充分覆盖最终业务判断。**

需要验证：

- 正确原文证据是否进入候选；
- “必须/优先”是否正确区分；
- 公司业务是否误认为职责；
- 多个技能条件是否正确组合；
- 全库统计是否遗漏或重复。

已有实验证明项目具备对照能力，但不足以裁决最佳架构。

### 5. 下一步如何优化？

建议按顺序推进。

#### 第一优先级：补齐评测标准答案

**先不要重写 Chunking。**

使用当前候选审阅数据补全不同方案检索出来的相关岗位和证据判断。

现有实验准备了 2,470 项 query/job 候选判断，其中 301 项优先审阅。

先完成高优先级审阅，再扩大范围。重点确认：

- 哪些岗位真正相关；
- 相关程度如何；
- 哪句原文是证据；
- 容易混淆的条件是什么；
- 哪些岗位应排除。

同时补充无答案、否定条件、二选一关系等专项案例。

#### 第二优先级：加入完整 JD 检索基线

当前五套方案都属于不同程度的分块或文本表示。

下一轮值得加入：

> **一份 JD 对应一个完整检索单位。**

要回答：对于当前几百份招聘 JD，切分是否真的优于完整文档检索？

应固定 Embedding 模型、查询、过滤条件及主要排序规则，同时观察岗位召回、证据可定位性、业务判断、Token 成本及延迟。

如果完整 JD 已达到相近效果，应重新评估复杂分块的必要性。

#### 第三优先级：分析结构化方案具体的改善与退化

已有实验中：

- 部分 Harness 查询在结构化后种子岗位明显提前；
- 部分营销 Agent 查询却退化；
- 有些 RAG 查询没命中种子，但前排实际出现了相关岗位。

应追查究竟是切分边界、上下文信息、Chunk 数量，还是岗位聚合改变了排名。

尤其当前实验对同一个岗位的多个 Chunk 取**最高相似度**作为岗位分数。Chunk 更多的岗位可能有更多获得局部高分的机会，因此排名提高不一定意味着语义理解更好。

#### 第四优先级：验证面向不同任务的组合方案

在前三项完成后再考虑：

- 如果小 Chunk 缺上下文：尝试短条目命中后回读父级章节或完整 JD；
- 如果章节有帮助但提示文本干扰 Embedding：将章节保留为元数据而非写入索引文本；
- 如果技术统计经常出错：建立技能、能力深度、要求强度与原文证据的结构化关联；
- 如果多 Chunk 影响岗位排名：比较不同的岗位级聚合方法。

每一种方案都应对应真实失败案例，不要因为技术流行而自动引入。

### 6. 如何判断下一轮优化是否成功？

建议固定实验报告结构：

| 报告内容 | 应回答的问题 |
|---|---|
| 优化目标 | 本轮要解决什么失败？ |
| 修改内容 | 相比基线改变了什么？ |
| 测试范围 | 哪些 JD、查询和标准答案？ |
| 整体指标 | 哪些指标提升或下降？ |
| 改善案例 | 哪些问题被解决？ |
| 退化案例 | 哪些原本正确的问题变差？ |
| 失败归因 | 为什么产生这些结果？ |
| 性能成本 | 额外消耗多少资源？ |
| 最终决策 | 保留、回退，还是继续实验？ |

例如：

~~~text
优化目标：
改善职责类问题的证据召回。

假设：
当前部分 Chunk 缺少父级章节信息。

实验方案：
保持切分边界不变，仅调整检索上下文表示。

实验结果：
- 职责类证据召回：待测试
- 其他问题排名变化：待测试
- 最终判断准确性：待测试
- Token 成本变化：待测试

决策：
根据实验结果确定，不预先认定新方案更优。
~~~

**实验结果必须先于方案结论。不能先决定采用某方案，再让 AI 找数据证明它合理。**

---

## 结语：真正需要掌握的不是某一种切分算法

我们从一个看似简单的问题开始：

> 一份文档应该切成多大的 Chunk？

但更重要的问题是：

1. **为什么需要这个功能？** 不切分是否已经满足需求？
2. **什么叫这个功能做得好？** 保留原文、找到证据，还是完成业务任务？
3. **怎样知道当前方案有多好？** 有没有真实问题、可信答案、可复现实验？
4. **发现问题后如何优化？** 能否判断错误发生在哪个环节？
5. **如何利用 AI 持续改进？** 能否让 AI 基于目标提出假设、执行实验，再据结果取舍？

这些问题远远超出文档切分。

研究 Retrieval、Agent Runtime、模型推理服务、MCP 工具，甚至企业 AI 平台时，都可以使用同一套方法。

在 AI 已经能够承担大量实现工作的情况下，工程师不一定要亲自掌握每个算法的代码细节。

但应逐渐建立另一种能力：

> **能够定义系统应该具备什么能力，建立判断系统好坏的标准，通过真实运行结果定位问题，并指导 AI 持续改进。**

技术原理依然重要，但应服务于理解系统行为、分析因果关系和作出工程决策。

最终我们学习文档切分，不是为了记住某个字符预算或某段代码，而是为了学会：

**面对 AI 能够生成无数种实现方案的问题，如何依据证据，判断哪一种方案真正值得采用。**
