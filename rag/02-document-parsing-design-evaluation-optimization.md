# RAG 文档解析：如何设计、评测与持续优化？

> 本文是 RAG 工程流程的第二篇专题文章，承接《01 · RAG 文档采集》，后续衔接《03 · RAG 文档切分》。
>
> 本文以 Job-RAG 招聘岗位知识库为主要案例，同时引入金融财报、企业制度和复杂 PDF 文档。重点讨论如何定义解析质量、比较候选方案、建立评测、定位失败，以及利用 AI 持续优化，而不是介绍某个 OCR 或文档解析框架的具体代码实现。

## 一、为什么需要文档解析？直接把文件交给大模型不行吗？

### 1. 我们究竟要解决什么问题？

假设我们已经收集了一批招聘信息，包括：

- 从招聘平台导出的 CSV；
- 招聘网页的 HTML；
- 企业发布的 PDF 招聘公告；
- Word 格式的岗位说明书。

现在希望让 Job-RAG 回答：

> 统计岗位职责或任职要求中出现 RAG 的岗位，它们还要求哪些技术？

最简单的方法是什么？

直接把文件交给支持文件读取的大模型，让它理解内容。

对于少量、结构简单的资料，这种方法完全可能有效。

如果只有 10 份 PDF，而且每份都很短，模型能够直接阅读并回答，我们没有必要先开发复杂的解析系统。

但如果有数千份文件，需要长期更新、重复查询和精确核对，就会出现新的问题：

- PDF 里的文字是否都被读出来了？
- 两栏排版是否被按照正确顺序阅读？
- 表格中的数值是否对应正确的行和列？
- 标题是否与所属段落建立联系？
- 某段文字是否来自页眉、脚注还是正文？
- 图片中的重要信息有没有遗漏？
- 以后能否根据模型给出的答案定位到文件中的原始位置？

这些问题不能仅靠“模型成功输出了一段文字”证明已经解决。

我们需要一个能够将不同格式资料转换为**可信、可处理、可追溯的内容表示**的过程。

这就是文档解析（Document Parsing）要解决的问题。

### 2. 文档解析究竟在做什么？

文档解析可以理解为：

**从已经获得的原始文档中，识别其内容、阅读顺序和组织结构，并转换为后续系统能够使用和核验的表示。**

例如：

~~~text
PDF / Word / HTML / 图片
            ↓
       识别文件内容
            ↓
      提取文字及其他元素
            ↓
   恢复阅读顺序和文档结构
            ↓
     保存内容与来源位置
            ↓
       形成解析结果
            ↓
    文档切分 / 检索 / 分析
~~~

这里面其实包含三个不同层次：

**第一层：文字有没有正确提取？**

例如 PDF 中写着：

> 熟悉 Python 或 Java，满足其一即可。

解析结果是否完整保留这句话？

**第二层：内容之间的结构关系有没有保留？**

例如这句话属于“任职要求”，而不是“公司介绍”。

解析结果能否体现这个关系？

**第三层：后续系统能不能利用解析结果正确理解业务？**

例如模型能否判断：

> Python 和 Java 是二选一，而不是必须同时掌握。

这三个层次相互关联，但不是同一个问题。

文档解析主要负责前两个层次，并为第三层提供可靠输入。

### 3. 为什么文字提取正确还不够？

假设有一份金融财务报表：

| 指标 | 2025 年 | 2024 年 |
|---|---:|---:|
| 营业收入 | 1,000 | 800 |
| 净利润 | 120 | 100 |

一个文档解析工具提取出的文字是：

~~~text
营业收入
净利润
2025 年
2024 年
1,000
800
120
100
~~~

从文字识别角度看，所有内容都正确。

但如果后续系统不知道哪个数值对应哪个指标和年份，就无法可靠回答：

> 2025 年净利润是多少？

这说明：

**解析不仅要保留文字，还要保留文字之间决定其含义的结构关系。**

同样的问题也出现在：

- 多层标题；
- 两栏或多栏正文；
- 多级编号；
- 跨页表格；
- 合并单元格；
- 图片与图注；
- 正文与脚注。

### 4. 文档解析与文档切分有什么区别？

假设一份 JD 包含：

~~~text
岗位职责
1. 负责 RAG 知识库开发。
2. 负责模型服务接口建设。

任职要求
1. 必须熟悉 Python。
2. 有 vLLM 部署经验者优先。
~~~

文档解析应该回答：

- 哪些文字是岗位职责？
- 哪些文字是任职要求？
- 编号条目怎样组织？
- 每条内容位于原始文件哪里？

文档切分则进一步回答：

- 每条职责是否独立参加检索？
- 是否需要把相邻条目合并？
- 每个 Chunk 应该包含多少上下文？
- 检索时是否附加章节标题？

因此，两者不是简单的“先按标题切，再按长度切”。

更准确的关系是：

**文档解析恢复原始资料的内容与结构；文档切分根据检索目标决定如何使用这些结构。**

解析阶段不应该因为某个 Chunk 长度预算，就提前破坏文档原有结构。

### 5. 什么时候不需要独立的文档解析环节？

取决于输入资料已经具备怎样的结构。

| 输入资料 | 可能的处理方式 |
|---|---|
| 简单 TXT | 直接读取文本 |
| 结构明确的 JSON | 根据 Schema 读取字段 |
| 已规范化的招聘 CSV | CSV 解析、字段校验 |
| HTML 网页 | 识别主要内容与文档元素 |
| 原生 Word | 读取段落、表格和标题结构 |
| 可选中文本 PDF | 提取文本，并判断布局是否正确 |
| 扫描版 PDF | OCR 及必要的版面恢复 |
| 复杂财报、合同、手册 | 可能需要布局分析、表格恢复和专项验证 |

这里最重要的判断是：

**已有资料能否以足够可靠的方式满足后续任务，而不是是否存在一个独立的解析程序。**

## 二、怎样定义一个好的文档解析方案？

### 1. 什么叫“解析得好”？

假设某个解析工具报告：

> OCR 文字识别准确率达到 99%。

这是否意味着它适合金融财报 RAG？

不一定。

假设一份财报中有 10,000 个字符，只识别错了 10 个。

如果错误主要发生在无关页脚，对业务影响可能很小。

但如果其中一个错误是：

~~~text
原文：净利润 120
解析：净利润 1,200
~~~

那么即使整体字符准确率很高，财务分析也可能发生严重错误。

所以解析质量不能只根据文字识别率判断。

我建议将它定义为：

> **好的文档解析方案，是指能够以可接受的成本，将原始资料转换为内容准确、结构关系可信、来源可追溯的表示，并支持后续业务任务正确使用这些信息。**

可以从三个层次进行评价。

### 2. 第一层：内容正确性——原文有没有被正确保留？

最基础的要求包括：

| 要求 | 判断标准 |
|---|---|
| 内容覆盖 | 业务相关文字是否遗漏 |
| 文字准确 | 是否存在识别、替换或添加错误 |
| 数值准确 | 金额、日期、百分比等是否正确 |
| 原文保真 | 是否发生无依据改写 |
| 缺失透明 | 无法识别时是否标注，而不是编造 |

例如原文写：

> 无需具备 RAG 开发经验。

解析结果不应变成：

> 具备 RAG 开发经验。

因为一个“无”字，就足以改变招聘要求。

对于金融文档，“100 万元”与“100 元”、“2025 年”与“2024 年”，也可能产生完全不同的结果。

因此，除了整体字符准确率，还需要关注**关键业务信息的准确性**。

### 3. 第二层：结构正确性——内容关系有没有恢复？

假设一份制度包含：

~~~text
第三章 授信审批

第十二条 审批权限
原则上由总行审批。

第十三条 特殊授权
符合以下条件之一的，可以授权分行审批：
（一）……
（二）……
~~~

如果解析结果保留了所有文字，却打乱了条款之间的关系，就可能使后续模型误读审批规则。

因此需要保留：

- 标题及层级；
- 段落所属章节；
- 列表及嵌套关系；
- 表格的行列对应关系；
- 正确阅读顺序；
- 页眉、页脚和脚注的角色；
- 图片与正文或图注的关联。

不是所有文档都需要上述全部能力，但必须根据实际任务明确哪些关系不可丢失。

特别是表格。

假设：

| 指标 | 本期 | 上期 |
|---|---:|---:|
| 营业收入 | 1,000 | 800 |
| 净利润 | 120 | 100 |

解析方案至少要能够支持：

> 净利润 → 本期 → 120

不能只是返回“净利润、本期、120”这三个孤立字符串。

### 4. 第三层：证据可追溯——能不能回到原文？

假设模型回答：

> 该岗位要求具备三年以上 RAG 项目经验。

用户希望检查这句话是否准确。

如果解析系统只保存一份重新生成的 Markdown，但没有保留来源位置，就可能无法直接定位原始文件中的依据。

因此建议解析输出保留：

- 来源文档 ID；
- 原始文件版本；
- 元素 ID；
- 元素类型；
- 原始内容；
- 在文档中的位置；
- 所属标题或父级结构；
- 解析方式与版本；
- 必要的置信度或异常标记。

对于 PDF，位置可以是页码与页面坐标。

对于 HTML，可以是 DOM 路径、原文片段或其他稳定定位信息。

对于 Word，可以使用段落、表格或其他文档结构标识。

对于 CSV，可以保留来源记录 ID、字段名称及对应文本。

**不是所有格式都必须使用同一种位置表示。**

但系统应能够回答：

> 这段解析结果究竟对应原始资料中的哪里？

### 5. 应该定义怎样的输入输出契约？

**输入：**

- 原始文档；
- 文件类型；
- 来源文档 ID 与版本；
- 业务所需的内容类型；
- 访问与处理约束。

**输出：**

- 文档的主要内容；
- 标题、段落、表格等结构元素；
- 元素之间的层级和顺序；
- 与原文件的定位关系；
- 解析状态和必要的异常信息。

例如，一份解析结果可以抽象成：

~~~json
{
  "document_id": "example-jd-001",
  "elements": [
    {
      "element_id": "e1",
      "type": "heading",
      "text": "任职要求"
    },
    {
      "element_id": "e2",
      "type": "list_item",
      "parent_id": "e1",
      "text": "有 vLLM 部署经验者优先。",
      "source_location": {
        "page": 2
      }
    }
  ]
}
~~~

这是教学示意，不是规定所有系统都必须采用这个 Schema。

解析结果可以同时提供方便阅读的 Markdown 与结构化元素表示。

但要注意：

**Markdown 适合展示，不一定能完整表达复杂表格、空间位置和所有结构关系。**

不能因为 Markdown 看起来整齐，就认定所有信息已经正确保留。

### 6. 哪些行为应该明确禁止？

至少应避免：

1. 没有依据地补全文字；
2. 将不确定识别结果当成确定事实；
3. 随意调整数值、单位和日期；
4. 将标题与正文错误关联而不记录来源；
5. 在格式转换时静默丢弃表格或图片；
6. 将模型生成的解释冒充原文；
7. 解析部分失败，却将整份文件标记为完整成功。

这里有一个重要原则：

**解析失败可以被接受，但无法察觉的错误解析更危险。**

## 三、文档解析有哪些候选方案？应该怎样选择？

### 1. 方案 A：直接读取原生结构

对于 DOCX、HTML、CSV、JSON 等资料，可以先利用原有文件结构读取内容。

例如 Word 中可能已经保存了：

- 段落；
- 标题样式；
- 表格；
- 列表；
- 文档属性。

HTML 中则存在：

- 标题标签；
- 段落元素；
- 列表；
- 表格；
- 页面结构。

优势是成本低、速度快，并且可能直接取得源文件中的结构信息。

但需要注意：

**文件具备结构，不代表这个结构一定正确反映作者的实际意图。**

例如 Word 作者可能没有使用标题样式，只是把一行文字设置为加粗。

HTML 页面也可能主要通过 CSS 控制视觉布局，而没有清晰的语义标签。

因此仍需要判断直接读取的结构是否满足要求。

### 2. 方案 B：文字提取与 OCR

PDF 需要特别注意：它主要描述页面呈现方式，并不总是具备完整的逻辑阅读结构。

一些 PDF 可以直接提取文字；扫描版 PDF 则可能只包含页面图像。

对于扫描文档，通常需要 OCR（光学字符识别），把图片中的文字转换成机器可处理的文本。

优势是让原本不可直接检索的扫描内容变得可搜索。

但 OCR 本身不保证：

- 多栏阅读顺序正确；
- 表格行列关系完整；
- 标题层级准确；
- 数值没有识别错误；
- 文本与图片关系已经建立。

因此：

**OCR 是文档解析的重要能力，但不等于完整的文档理解。**

### 3. 方案 C：布局感知解析

如果文档结构比较复杂，就可能需要识别页面布局。

例如：

~~~text
PDF 页面
 ├── 文档标题
 ├── 一级标题
 ├── 正文段落
 ├── 双栏内容
 ├── 表格
 │    ├── 表头
 │    ├── 数据行
 │    └── 合并单元格
 ├── 图片
 └── 页脚
~~~

布局感知解析试图恢复这些元素及其关系，而不是只按页面坐标抽取文字。

这种能力对以下资料尤其有价值：

- 财务报表；
- 研究报告；
- 企业制度；
- 复杂说明书；
- 多栏 PDF；
- 包含大量表格的技术文档。

例如 Microsoft Document Intelligence 的布局分析能力可以输出段落、表格、页面、图像、章节等结构元素，并支持 Markdown 表示。

但它是否比简单文本提取更好，仍然需要针对实际资料测试。

### 4. 方案 D：视觉语言模型解析

随着多模态模型能力增强，还可以让视觉语言模型（VLM）直接阅读文档页面图像，生成文本和结构化结果。

例如让模型识别一页财报中的表格，再输出对应的行列关系。

它的优势在于能综合利用视觉布局和语义信息，适合部分传统规则难以处理的复杂页面。

但也存在新的风险：

- 模型可能漏读；
- 可能无依据补充文字；
- 相近数字可能被误识别；
- 表格位置可能对应错误；
- 输出具有不确定性；
- 成本和延迟可能更高。

对于需要严格原文保真的场景，尤其不能把“模型生成的文本很通顺”当成解析正确的证明。

### 5. 方案 E：直接让多模态模型完成最终任务

还有一种需要认真考虑的方案：

**不提前把所有文档统一解析成文本，而是在用户需要时，让多模态模型直接阅读原始文档。**

例如用户上传一份只有几页的财务报表，直接要求模型分析特定指标。

这种方案可能比建设完整的离线解析流水线更简单。

但它也有局限：

- 相同文档可能被反复处理；
- 跨大量文档的检索和统计不方便；
- 来源定位和结果复用可能较困难；
- 运行成本可能更高；
- 仍需要验证视觉读取和业务判断是否正确。

因此，不能预先认定“先解析再检索”总是最佳方案。

**是否需要独立解析产物，同样应根据文档规模、复用需求、查询频率和实际质量决定。**

### 6. 能不能按照文档特点动态选择方案？

可以，而且这通常比所有文件统一调用最复杂模型更值得研究。

例如：

~~~text
输入文档
   ↓
检查文件类型与内容特征
   ↓
是否已有可靠结构化内容？
   ├── 是 → 直接读取原生结构
   └── 否
        ↓
   是否存在可提取文本？
        ├── 是 → 文本提取与布局核验
        └── 否 → OCR
                    ↓
           是否存在复杂结构？
                    ├── 否 → 保存结果
                    └── 是 → 布局解析或视觉模型
~~~

这只是候选路由，不代表所有可选中文本 PDF 都适合简单提取。

有些 PDF 虽然能提取文字，但存在严重的阅读顺序和表格问题。

因此真正应该采用的原则是：

> **优先使用能够满足质量要求的低成本方案；当证据表明它不足时，再使用更复杂的解析能力。**

这样的方案需要经过实际评测，而不是仅凭文件扩展名决定。

## 四、怎样建立文档解析的评测体系？

### 1. 为什么不能只让大模型给解析结果打分？

假设我们把一份 PDF 交给两个工具。

方案 A 输出一份排版普通的文本。

方案 B 输出一份标题清晰、表格漂亮、格式规范的 Markdown。

如果让大模型直接评价可读性，它可能更喜欢 B。

但 B 可能把财务报表中的“120”错误改成“1,200”。

因此，解析评测不能只评价格式是否美观、文本是否流畅、结构是否整齐。

真正需要比较的是：

**解析结果与原始文档实际内容、结构和业务含义是否一致。**

### 2. 应该从哪些真实任务构造测试案例？

| 类型 | 测试材料 | 重点 |
|---|---|---|
| 基础文本 | 简单 JD、操作说明 | 内容有没有遗漏 |
| 阅读顺序 | 双栏报告、跨页正文 | 顺序是否正确 |
| 标题结构 | 制度、招聘公告 | 标题与段落关系 |
| 表格结构 | 财报、额度表 | 表头、行列、合并单元格 |
| 复杂内容 | 扫描件、图片、混合 PDF | OCR、视觉及异常处理 |

还应加入：

- PDF 有文本层但提取顺序错误；
- Word 用加粗而不是标题样式；
- 跨页表格；
- 中英文混排；
- 页眉页脚重复；
- 部分页面损坏；
- 字体编码异常；
- 来源文件缺页；
- 图片中的重要信息无法识别。

这些案例应对应真实失败风险，而不是单纯追求格式种类多。

### 3. 一条标准评测案例需要包含什么？

以财务报表为例。

**原始文件**

某企业 2025 年财务报表 PDF，第 5 页包含：

| 项目 | 本期金额 | 上期金额 |
|---|---:|---:|
| 营业收入 | 1,000 | 800 |
| 净利润 | 120 | 100 |

**预期解析结果**

~~~text
表格：利润表
行：净利润
列：本期金额
值：120
来源：第 5 页对应单元格
~~~

**容易出现的错误**

- 将 120 识别为 1,200；
- 将本期与上期颠倒；
- 将净利润与营业收入对应错位；
- 遗漏表头；
- 表格被拆散后无法恢复；
- 无法定位数据来源。

**后续业务验证问题**

> 本期净利润是多少？

正确答案是 120，而不是 100 或 1,200。

这里应该分别记录两个结果：

1. 解析出的表格结构是否正确；
2. 后续模型是否能够依据该结构正确回答。

只有这样，才能避免将后续模型的判断错误全部归因于文档解析。

### 4. 如何评价文字提取质量？

可以使用字符错误率（CER）、词错误率（WER）等指标。

例如标准文本有 100 个字符，解析时发生一定数量的替换、删除和插入，就可以通过编辑距离计算 CER。

但相同的错误数量，可能对应完全不同的业务风险：标点识别错误、金额数量级错误、否定词缺失。

因此应增加**关键字段或关键事实的准确性检查**。

财报重点核验金额、单位、年份、科目；JD 重点核验技能名称、年限、条件强度和否定表达。

### 5. 如何评价阅读顺序？

假设原始页面是双栏布局：

~~~text
左栏第 1 段        右栏第 1 段
左栏第 2 段        右栏第 2 段
左栏第 3 段        右栏第 3 段
~~~

正确阅读顺序可能是：

~~~text
左栏 1 → 左栏 2 → 左栏 3
→ 右栏 1 → 右栏 2 → 右栏 3
~~~

但解析器可能按纵向坐标输出：

~~~text
左栏 1 → 右栏 1
→ 左栏 2 → 右栏 2
→ 左栏 3 → 右栏 3
~~~

文字都存在，结果却被打乱。

可以人工标注关键段落的正确先后关系，检查解析结果中这些关系是否成立。先针对关键的双栏、脚注和跨页场景建立测试即可，不一定要给所有元素标注完整顺序。

### 6. 如何评价标题和表格结构？

标题应检查：是否识别、层级是否正确、段落归属是否正确、列表是否归属正确条款。

表格应检查：行列是否完整、表头与数据是否对应、合并单元格是否正确、跨页能否衔接、数值单位是否准确。

**行列关系本身就是需要验证的数据。**

### 7. 最终建议采用哪些指标？

| 评测层次 | 主要指标 | 作用 |
|---|---|---|
| 内容 | 字符错误率、内容覆盖率、关键字段准确率 | 文字与数据保真 |
| 顺序 | 关键元素阅读顺序正确率 | 内容顺序 |
| 结构 | 标题层级、段落归属、表格关系正确率 | 结构恢复 |
| 追溯 | 原文位置定位成功率 | 原文复核 |
| 业务 | 基于固定解析结果的任务正确率 | 支持业务 |
| 运行 | 成功率、耗时、成本、异常率 | 工程可用性 |

如果比较两个解析器，应固定后续切分、检索和判断方式，尽量隔离解析差异。还应保留失败样本，而非仅报告平均分。

## 五、怎样理解实验结果？为什么更先进的解析模型不一定更好？

### 1. OCR 准确率提高，就能直接替换吗？

不能。

新方案可能降低字符错误率，却使处理时间增加三倍，且复杂表格仍存在行列错位。

对于纯文字制度有价值，对于财报分析可能仍不足以满足要求。

**需要的是文字正确、结构正确，还是特定数据关系正确？** 不同任务要求不同。

### 2. 为什么整体指标可能掩盖关键问题？

| 文档类别 | 方案 A | 方案 B |
|---|---|---|
| 普通文本 | 较好 | 相近 |
| 双栏 PDF | 一般 | 较好 |
| 简单表格 | 较好 | 相近 |
| 复杂财报 | 关键数字更准确 | 偶尔数值错误 |

如果简单文本占大多数，B 的平均质量可能更高。但如果主要任务是财报分析，复杂财报的数值错误就不能被简单文档的成功掩盖。

应按文档类别和业务风险分组，严重数值错误或错误条件判断可设置单独上线约束。

### 3. 为什么不能同时修改解析和切分？

假设同时替换 OCR、引入布局解析、改变 Markdown、Chunk 从 1100 改成 600、加入 Rerank。

业务指标提高却无法归因。可能解析提升、切分反而破坏表格；也可能解析没改善，只是 Rerank 排名更好。

应固定原文和后续处理，先比较解析结果，再验证下游收益。

### 4. 为什么不只比较工具名称？

规则、OCR、布局分析和 VLM 各有适用场景。

应比较哪些文档更准确、错误是否可检测、内容是否遗漏、能否回溯原文、是否满足隐私部署要求、成本与时长。

银行内部资料尤其要考虑允许的部署环境和数据传输方式；云端模型再强，如果无法合规发送，就不是可用方案。

### 5. 何时采用新方案？

建议同时满足：

1. 关键内容与结构正确性达标；
2. 目标任务有可信收益；
3. 严重错误没有增加；
4. 原文证据可追溯；
5. 成本和安全约束可接受。

证据不足时保留原方案，扩充评测，而不是勉强选赢家。

## 六、发现解析结果不好后，怎样确定应该优化哪里？

### 1. 最终答案错误，不一定是 OCR 错误

用户问某财报 2025 年净利润，系统答 100，原文是 120。

可能是 OCR 识别错数字、表格行列错位、切分丢失表头、检索返回上期数据、模型选错值。

同一表现需要不同优化。

### 2. 怎样逐层反查？

~~~text
原始文档
    ↓
文字提取是否正确？
    ↓
阅读顺序是否正确？
    ↓
标题与表格结构是否正确？
    ↓
解析结果是否完整保存？
    ↓
切分后是否保留所需关系？
    ↓
检索是否提供正确证据？
    ↓
最终模型是否判断正确？
~~~

应从原文开始，找到**最早能够观察到错误的环节**：

- 文字已错：优先检查 OCR / 文本提取；
- 文字正确、表格错位：检查布局和表格恢复；
- 解析正确、片段缺表头：检查切分和证据组织；
- 证据完整、模型选错列：检查语义判断或规则。

### 3. 常见失败与改进方向

| 失败现象 | 优先检查 | 候选改进 |
|---|---|---|
| 部分文字缺失 | 文字提取 | 文件读取、OCR、异常页 |
| 数值识别错误 | OCR | 数值专项校验 |
| 双栏正文交错 | 阅读顺序 | 布局解析 |
| 标题归属错误 | 结构恢复 | 标题层级 |
| 表格行列错位 | 表格恢复 | 结构解析与单元格校验 |
| 页脚混入正文 | 元素角色 | 页眉页脚分类 |
| 图片内容遗漏 | 多模态元素 | 视觉解析 |
| 无法定位证据 | 来源映射 | 原文位置、元素 ID |
| 解析正确但答案错 | 下游 | 切分、检索或生成 |

以上都是需验证的假设，不是自动适用的方案。

### 4. 怎样记录失败案例？

~~~text
文档：某企业 2025 年财报，第 5 页
预期：净利润本期金额 120
实际：解析结果标为 100

检查：
1. OCR 提取数字正确。
2. “本期/上期”表头识别正确。
3. 表格恢复时列对应错误。

结论：
表格结构解析问题，不是 OCR 错误。

假设：
使用更可靠的表格结构恢复。

验证：
比较复杂表格单元格对应准确性，
同时检查其他表格是否退化。
~~~

经复核的失败案例应加入回归测试。

## 七、怎样让 AI 持续优化文档解析？

### 1. 哪些工作可以交给 AI？

AI 可以分析文件类型、选择候选方案、实现适配器、对比原文、发现遗漏、分类失败、提出假设、跑对照实验、生成报告。

但不能让同一个 AI 自己生成标准答案，再仅凭自评宣布成功。财报金额、制度条款和招聘条件需要独立核验依据。

### 2. 一轮优化如何组织？

1. **冻结评测资料**：原始文件、人工核验关键内容、结构和测试问题。
2. **运行基线**：记录文字、结构、定位、任务正确性、成本和耗时。
3. **分类失败**：文本缺失、OCR、顺序、标题、表格、位置、后续判断。
4. **提出假设**：如只对检测到双栏的 PDF 启用布局解析。
5. **最小改动**：避免同时替换所有工具和检索算法。
6. **回归决定**：比较改善、退化、成本及安全约束。

### 3. 如何给 AI 下任务？

> 请基于冻结的文档解析评测集，分别检查文字准确性、阅读顺序、标题层级、表格关系、原文定位和最终任务质量。
>
> 对失败案例分类，找到最早的错误环节。
>
> 针对主要失败类型提出可验证假设，每轮尽量只改变一个主要因素。
>
> 在相同条件下对照新旧方案，报告改善、退化、成本和数据安全影响。
>
> 证据不足时保留不确定状态，不得无依据补全文字或数据。
>
> 未通过评测，不替换正式配置。

### 4. 何时人工介入？

不必逐页检查所有文档，但金额、日期、关键编号异常、表格结构不确定、页面明显缺失、解析结果冲突，以及影响重要结论的证据，应考虑复核。

复核结果继续沉淀为测试案例，减少未来重复人工工作。

## 八、Job-RAG 实践：当前解析方案有什么问题，下一步如何优化？

### 1. 当前是否实现完整文档解析？

根据 [Job-RAG 数据说明](https://github.com/leecolin2023/job-rag/blob/main/data/README.md)，项目主要接收整理好的 jobs.csv，初始快照有 593 条不同岗位 ID、592 条非空岗位描述、1 条未取得实际描述。

外部流程已完成部分获取和正文提取，项目不必重新从 PDF 或网页提取全部文字。

当前主要解析工作包括 CSV 读取、正文保真、字段校验、部分章节识别、编号条目识别和原文定位。

这不意味着已具备完整 PDF、Word、HTML、扫描件和复杂表格布局解析。

**当前项目从较规范文本输入开始，而不是已经解决所有企业文档解析问题。**

### 2. 哪些设计值得保留？

**原文保真。**

“有 vLLM 部署经验者优先”不能被无依据改写成“需要具备 vLLM 部署能力”。

**来源定位。**

当前分块结果保留 source_start、source_end、raw_text 等信息。这些是 JD 原始字符串中的位置，而非 PDF 坐标，可帮助核验系统添加的标签。

**未知状态。**

章节识别主要使用规则，无法可靠分类时保留 unknown，避免强行猜测。

### 3. 当前值得研究的问题

根据 [Job-RAG Embedding 实验说明](https://github.com/leecolin2023/job-rag/blob/main/docs/embedding-experiments.md)，此前一次数据准备中有 **95 条岗位无法可靠判断章节，保留 unknown**。

这不直接证明解析差。需要先问：

- 原文本身有没有明确章节？
- 是否使用了特殊标题？
- 是否将职责和要求写在同一段？
- 是否存在换行或编号问题？
- 是否只是规则覆盖不足？

如果原文无清晰结构，保留 unknown 可能正确；若章节清楚但规则未覆盖，则值得优化。

**不要直接要求 AI 把 95 条 unknown 全部识别出来，先审阅其原因。**

### 4. 如何建立解析评测？

| 类型 | 测试目标 |
|---|---|
| 标准 JD | 识别职责和要求 |
| 特殊标题 | 处理工作内容、岗位条件等变体 |
| 无标题 JD | 保留内容、不编造章节 |
| 混合段落 | 不混淆职责与要求 |
| 多级编号 | 保留条目和父级 |
| 复杂条件 | 保留必须、优先、或、无需 |
| 异常格式 | 换行、空白和非标准列表 |

人工基于 JD 原文标注标准答案，不能直接以现有规则输出当成真值。

### 5. 比较哪几种方案？

**A：保守规则解析。** 低成本、稳定、可解释。

**B：规则 + AI 疑难处理。** 规则无法可靠分类时才调用模型。

**C：模型直接识别结构。** 读取完整 JD，识别职责、要求、加分项并标注原文依据。

在同一批 JD 上比较章节识别、unknown 合理性、错误归类、条件保留、原文定位和成本。

**unknown 越少不意味着越好。** 如果靠强行猜测将 unknown 降为零，却引入错误标签，反而更差。

### 6. 现在要不要引入复杂 PDF 解析？

对当前 CSV 输入，没有充分证据表明必须立即引入。

将来扩展企业文档知识库时，可分别测试：

- 银行制度：标题、条款、例外；
- 财务报表：金额、科目、年份、表格；
- 银行流水：交易、金额、日期和字段关系；
- 技术文档：标题、代码、表格和引用；
- 招聘 JD：职责、条件与限定词。

这些材料可以有统一解析接口，但不一定共用相同策略。

### 7. 下一轮如何推进？

1. 审阅现有 unknown：区分合理未知与规则遗漏。
2. 建立独立标准答案：人工标记代表性 JD 的章节、条目与条件。
3. 比较规则与模型辅助：不预设模型必然更好。
4. 衔接切分实验：先测解析，再测对证据检索的影响。
5. 按真实需求扩展格式：需要 PDF、Word、表格时再建设专项能力。

### 8. 实验报告如何写？

| 内容 | 问题 |
|---|---|
| 解析目标 | 解决哪类文档问题 |
| 原始样本 | 使用哪些真实文件 |
| 基线 | 现在结果如何 |
| 错误分类 | 内容或结构哪里错 |
| 改进假设 | 为什么新方法可能有效 |
| 新方案 | 哪些错误被修复 |
| 退化 | 哪些原本正确的文档变差 |
| 原文追溯 | 能否回到原文 |
| 成本 | 额外资源消耗 |
| 决策 | 保留、回退或继续 |

示例：

~~~text
目标：提高非标准 JD 的章节识别准确性。

问题：部分 JD 无法区分职责与任职要求。

调查：
需区分原文无标题和规则漏识别。

假设：
对规则无法识别的文档使用模型辅助解析。

方法：
固定人工标注样本，对照规则与模型。

验证：
1. 章节识别准确性；
2. 错误归类；
3. unknown 合理性；
4. 来源定位；
5. 模型成本。

决策：
不以 unknown 减少作为唯一目标。
~~~

## 结语：文档解析的价值不是把文件变成 Markdown

最初的问题是：怎样将 PDF、Word、HTML 转换成大模型可读内容？

更重要的是：

1. **内容是否正确保留？** 数值、日期、单位、限制条件不能无依据改变。
2. **结构关系是否恢复？** 标题、条目、表格和阅读顺序影响原意。
3. **能否回查原文？** 否则难以区分事实和处理错误。
4. **怎样证明有效？** 使用真实文件、独立标准答案与任务验证。
5. **失败后如何优化？** 定位最早异常，让 AI 对照实验并依据结果取舍。

文档解析不仅是 OCR 或 Markdown 转换，而是连接原始资料和知识系统的关键能力。

> **文档解析的真正目标，是让原始资料中的内容、结构及其证据关系，以可信、可核验、可复用的形式进入知识系统。**

AI 时代，工程师不必以掌握每种 PDF 库为终点，而应能够判断什么解析结果足以支撑业务、如何证明可靠、不可靠时改进哪里。
