# 什么是模型服务平台，为什么需要？

## 一、模型已经能运行，为什么还需要模型服务？

一套文档识别程序，可以直接在自身进程中加载 OCR 模型，读取图片并得到文字、坐标和置信度：

```text
文档 → 预处理 → OCR 模型 → 识别结果 → 业务处理
```

当请求量稳定、计算资源充足时，这种方式就能完成任务。

**第一次变化：大量文档集中到达。** 文档识别从偶尔执行的函数调用，变成持续占用 CPU、GPU 或 NPU 的计算负载。如果通过增加业务进程扩容，每个进程可能需要分别加载模型，增加内存或显存占用；业务处理和模型推理也只能一起扩缩容。继续采用进程内调用并非不可行，但必须自行解决实例复用、任务排队、资源限制和故障恢复。

**第二次变化：业务程序与模型需要分别维护。** 例如，业务程序频繁调整页面与流程，识别模型却需要较长的加载时间；或者识别模型升级后，需要单独验证效果与耗时，而不希望同步发布整个业务系统。这时，可以把模型作为独立的长期运行服务：

```text
业务程序 → 文档识别 API → 常驻 OCR 模型实例 → 识别结果
```

业务程序负责提交文档和使用结果；模型服务负责加载、承接请求、限制并发、报告就绪状态、处理推理故障。两者可以按不同的负载和发布周期管理。

**独立模型服务不是必经步骤。** 如果进程内调用已经满足容量、可靠性和维护需求，没有必要为了增加一层 API 而拆分服务。

## 二、从模型服务到模型服务平台

现在企业除了 OCR，还使用大语言模型、Embedding 和 Reranker。假设它们分属不同业务系统，却共享有限的 GPU/NPU 资源。

每个服务能管理自身的请求队列，却无法只凭自身负载决定：哪个模型应常驻、哪个应用优先使用算力、资源如何在不同服务间分配，以及如何统一处理发布、权限和容量风险。

于是出现两类跨服务的工作：

- **服务与资源管理**：登记部署的模型及版本，分配计算资源，协调扩缩容，监控容量，组织升级和回滚。
- **统一访问治理**：让不同应用经过身份认证、授权、路由、限流和用量审计后访问模型服务。

把这些责任集中管理，就形成了**模型服务平台的能力范围**。平台不是“一个更大的模型”，也不只是“给推理服务前面加一个 API”。它关注企业如何管理一组长期运行的模型能力。

平台可以由现有容器与运维设施、推理服务、模型网关以及少量集成能力共同组成；不要求重新开发一套完整产品。

## 三、大语言模型带来了哪些特殊运行约束？

并发、鉴权、监控和升级不是模型服务独有的问题。与普通后端服务相比，大模型推理的特殊性主要在于**模型权重、计算设备、显存/内存以及每次请求的实际计算量会共同决定容量**。

一轮 LLM 推理通常涉及输入 Token 处理、Prefill（处理输入上下文）、Decode（逐步生成），具体排队与调度顺序因实现而异。

- **长输入**：增加输入处理计算量，并可能带来更高的首 Token 延迟。
- **长输出或长时间推理**：Decode 持续消耗计算资源，一个请求可能运行较长时间。
- **并发和上下文长度**：多个请求的 KV Cache 占用内存或显存；不能只看请求数判断服务容量。
- **调度与过载**：推理服务需要决定哪些请求同时执行、等待、取消或拒绝，避免资源耗尽拖垮全部请求。

因此，即使只有一个 Agent 应用、一个自行部署的推理模型，也需要解决模型加载、请求调度、容量监控及故障恢复。**这证明需要可靠的模型 Serving，不等于必须另建统一平台。**

## 四、模型服务平台在 AI Infra 中的位置

AI Infra（人工智能基础设施）覆盖从计算资源到模型推理和服务交付的能力。把一个企业 AI 应用向下追踪，可以看到五个不同的工程层次：

```text
┌────────────────────────────────────────────────────────┐
│ AI 应用层                                                │
│ Agent · RAG · 金融 AI 应用 · 智能办公                     │
└──────────────────────────┬─────────────────────────────┘
                           │
┌──────────────────────────▼─────────────────────────────┐
│ Agent Runtime / Agent Platform                          │
│ Agent Loop · Tool Calling · Session · Skills · 任务编排   │
└──────────────────────────┬─────────────────────────────┘
                           │ 模型 API
╔══════════════════════════▼═════════════════════════════╗
║ Model Platform / 模型服务层                              ║
║ 模型发布 · Serving · 模型网关 · 路由 · 鉴权 · 监控 · 治理     ║
╚══════════════════════════╤═════════════════════════════╝
                           │
┌──────────────────────────▼─────────────────────────────┐
│ 推理引擎层                                               │
│ vLLM · SGLang · TensorRT-LLM · KV Cache · 推理调度         │
└──────────────────────────┬─────────────────────────────┘
                           │
┌──────────────────────────▼─────────────────────────────┐
│ 算力基础设施层                                           │
│ GPU/NPU · CUDA/驱动 · Kubernetes · MIG · 虚拟化 · 算力池   │
└────────────────────────────────────────────────────────┘
```

这张图描述的是**职责与依赖关系**：普通文档识别、Embedding 或 RAG 服务可以直接调用模型 API，并不必先经过 Agent Runtime；一个 AI 产品也可以同时包含多个层次的能力。

各层主要回答不同问题：

| 层次 | 核心问题 | 主要工程工作 |
| --- | --- | --- |
| AI 应用 | 模型怎样解决业务任务？ | 业务规则、RAG、文档处理、用户交互、结果验收 |
| Agent Runtime / Platform | 多轮模型判断怎样变成可控制的行动？ | 工具执行、上下文、会话、任务状态、权限、编排与反馈 |
| **Model Platform** | **多个应用怎样稳定、安全、可治理地使用模型？** | **模型部署与发布、Serving 管理、统一 API、网关、容量与运行治理** |
| 推理引擎 | 一次或多次模型计算怎样高效执行？ | Prefill/Decode、批处理、KV Cache、调度与推理优化 |
| 算力基础设施 | 计算设备怎样提供并分配给模型服务？ | GPU/NPU、驱动与 CUDA、容器调度、设备隔离、资源池 |

其中模型平台处于**应用及 Agent 运行环境与推理引擎之间**：向上交付可调用、可治理的模型能力；向下部署和管理推理服务，使用已有算力资源。

模型平台不必亲自实现 CUDA 算子、KV Cache 算法或 GPU 虚拟化，但需要理解其容量与性能边界，才能正确配置部署、制定限流策略并诊断问题。

## 五、模型服务平台具体做什么工作？

设想银行或一家 AI 应用公司，要在自己的计算资源上部署 Qwen，供制度检索 Agent、知识问答与其他应用调用。

从「获得模型」到「长期提供服务」，平台团队面对的是一套持续运行的工程工作。

### 1. 部署并提供模型推理服务

选择模型版本、推理引擎、运行参数及计算资源，使用 Docker、Kubernetes 或现有部署系统启动服务。

- 使用 **vLLM / SGLang** 等引擎加载模型，配置上下文长度、并发和显存相关参数；
- 管理模型权重、配置、运行镜像、实例与依赖版本；
- 检查模型是否真正完成加载、能够接收推理请求，而不只是进程已经启动；
- 根据业务负载管理副本、扩缩容、服务重启和故障恢复。

vLLM / SGLang 负责实现具体推理执行和请求调度，模型平台负责**使用、配置、部署和持续管理这些能力**。只有当团队承担推理引擎研发时，才进一步修改调度器、注意力机制或 GPU 内核。

### 2. 对外提供统一模型 API

不同模型和推理服务可能具有不同接口与参数。平台通过统一入口，让应用能够稳定调用模型。

- 向业务系统提供 **OpenAI-compatible API** 或明确约定的内部接口；
- 规范模型名称、请求与响应格式、流式输出、错误码、超时及取消行为；
- 为 LLM、OCR、Embedding、Reranker 等不同能力定义适合各自任务的接口；
- 在更换模型或引擎时，尽量保持上层调用契约稳定。

「OpenAI-compatible」表示采用某种兼容接口格式，并不保证不同服务对所有端点、Tool Calling、结构化输出及流式事件具有完全相同的实现；这些差异需要做兼容性测试。

### 3. 建设模型网关和访问治理

当多个应用共同调用模型时，平台需要控制谁能够访问、如何路由以及可以消耗多少资源。

- **认证与授权**：识别调用方，并限定可访问的模型和操作；
- **模型路由与负载分担**：按模型名称、版本、实例可用性和策略选择目标服务；
- **限流与配额**：按照请求量、Token 用量或资源策略限制消费，处理超限与过载；
- **审计与计量**：记录应用、模型版本、调用量、Token 用量、耗时和失败情况，支持统计与成本归集；
- **可用性治理**：识别不可用实例，按接口语义决定拒绝、重试或切换，避免不受控的重复调用。

网关可由现有 API Gateway、代理或专门的 AI Gateway 实现；平台团队不必为每项功能重新编写一套网关。

### 4. 管理性能、算力容量和运行状态

模型服务即使持续返回成功，也可能因为排队或资源竞争而变慢。平台需要知道请求耗时发生在哪一段、资源是否足够，以及是否应该调整运行策略。

| 观察内容 | 代表性指标或证据 | 支持的判断 |
| --- | --- | --- |
| 服务可用性 | 请求成功率、错误率、就绪状态、超时 | 服务是否能正常接收与完成调用 |
| 延迟 | 端到端耗时、TTFT（首 Token 延迟）、TPOT（输出 Token 间隔）、P95 | 慢在等待、输入处理还是生成过程 |
| 吞吐 | 请求数、输入/输出 Token 吞吐、并发数 | 当前配置能处理多少工作量 |
| 资源与队列 | GPU/NPU 利用率、显存、KV Cache、排队长度、OOM | 容量瓶颈及资源争用出现在哪里 |
| 业务质量 | OCR 识别指标、固定样本集上的输出正确性、格式合规性 | 接口成功是否仍能满足业务要求 |

这些指标的具体可用性取决于推理引擎、网关和监控实现。例如，平台可依据队列及显存指标调整实例数、路由或限流，但单纯增加实例不一定能解决独占 GPU、显存不足或计算效率瓶颈。

性能治理既包括故障排查，也包括**正常运行中的流量波动、资源争用、性能退化和输出质量变化**。

### 5. 管理模型版本、升级与可靠性

- 维护模型及服务版本、部署配置、运行环境和调用方兼容关系；
- 新版本发布前验证接口兼容性、性能和代表性任务结果；
- 按需灰度发布、观察新旧版本差异，出现问题时回滚；
- 为重启、取消、超时和服务不可用定义清楚的处理方式；
- 对有合规要求的场景，落实敏感数据处理、访问日志保护和必要的输入/输出内容安全策略。

例如，Qwen 新版本可能接口仍然返回 HTTP 200，但相同业务输入的输出格式、时延或结果质量发生变化。因此发布验收不能只检查「模型能够响应」。

### 6. 一次业务调用与平台管理如何配合？

```text
                       控制面：模型注册、部署、版本、资源、策略
                                        │
                                        ▼
Agent / RAG / 业务应用
        │  模型名称、身份、输入
        ▼
统一模型 API / Gateway ── 认证、授权、限流、路由、审计
        │
        ▼
Qwen 推理服务实例 ──────── vLLM / SGLang 处理推理请求
        │                            │
        │                            ▼
        │                     GPU / NPU 计算资源
        ▼
模型输出返回业务应用
        │
        └── 调用日志、延迟、吞吐、错误与资源指标 → 监控与治理
```

**数据面**负责实际请求的接收、路由、推理和返回；**控制面**负责模型与服务的部署配置、版本、资源配额及治理策略。数据面的运行指标又会反馈到控制面的容量与发布决策。

由此可见，模型服务平台的工作远不止「持续接收、处理并返回模型请求」，而是对**模型服务从部署、交付、访问到生产运行的完整生命周期**负责。

## 六、不同类型企业如何承担模型服务工作？

同样是模型服务岗位，技术职责的深度与企业提供的产品有关。

| 企业类型 | 模型服务相关工作的重点 |
| --- | --- |
| **AI 基础设施厂商**（云厂商、智算平台、虚拟化厂商等） | 将算力分配、Serving、模型网关、多租户和服务治理做成可交付的平台产品 |
| **大模型厂商** | 提供模型服务，并可能深入推理引擎、分布式计算、显存与 Token 吞吐优化 |
| **AI 应用企业**（银行、证券、交易所、AI 应用公司、一般企业） | 根据自身业务需要部署或接入模型，建设统一 API、网关、监控、版本管理并支持 Agent/RAG 等应用 |

这三类并非完全互斥。同一家企业可能同时研发模型、销售平台并开发应用。小型团队通常由后端或 AI 工程师兼任模型服务工作，不构成另一种技术类别。

决定岗位内容的还有**模型运行责任**：

- 只调用外部模型 API：主要承担模型接入、网关、权限、成本和服务质量治理；
- 自行部署开源模型：增加推理引擎部署、计算资源、容量、性能与故障处理；
- 向客户销售模型平台：增加多客户、多租户、异构硬件和产品化运维要求；
- 自研推理引擎：进一步深入计算内核、缓存、调度和分布式推理。

## 七、什么条件下需要独立平台？

| 实际场景 | 主要需求 | 适当的建设方式 |
| --- | --- | --- |
| 单个文档识别程序，负载稳定、资源独占 | 完成推理并保证基本可靠性 | 进程内模型或轻量独立服务 |
| 单个应用自行部署 LLM，请求长且并发波动明显 | 模型加载、调度、容量与故障恢复 | 成熟 Serving + 必要的运维监控 |
| 一个应用与其他模型任务共享稀缺 GPU/NPU | 统一资源分配、模型版本与容量管理 | 引入跨服务资源和生命周期治理 |
| 多个团队调用多种模型，有不同权限与额度 | 授权、路由、限流、审计与成本核算 | 统一 Gateway 和模型管理能力 |
| 多个应用使用成熟托管模型服务，现有网关已满足要求 | 统一访问与调用治理 | 复用现有体系，可能无需自建推理平台 |

对比两个容易误判的情形：

- **只有一个应用也可能需要统一治理**：它使用自行部署的模型，并与其他模型任务争用有限算力；服务之间的资源分配无法只靠各自排队解决。
- **有很多应用也不一定需要自建平台**：它们直接使用外部托管模型，且既有网关已满足身份、路由、限流和审计要求。

判断的关键是：**企业实际承担哪些模型运行责任、资源是否需要跨服务协调、故障风险有多大，以及现有组件是否已覆盖这些责任。**

## 八、模型服务平台与 Agent Runtime 的分工

模型服务平台负责**模型请求的部署、执行、交付与运行治理**；Agent Runtime 负责**如何围绕任务目标多次调用模型、选择工具、获取环境反馈并推进任务**。

```text
Agent Runtime：目标 → 模型判断 → 工具执行 → 环境反馈 → 再判断
                           ↓ ↑
模型服务平台：         模型 API → 推理调度 → 模型输出
```

模型成功生成文本，不代表 Agent 已经完成任务。例如，模型可能正确提出“查询制度”，但工具未执行、证据不完整或报告未通过核对。反过来，Agent Loop 也不会自动解决 GPU 显存压力、模型发布或请求限流。
