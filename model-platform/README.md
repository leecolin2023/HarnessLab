# 什么是模型服务平台，为什么需要？

## 一、从文档识别开始

一套文档识别程序需要把扫描件、图片或 PDF 页面转换为文字和位置信息。最直接的做法，是在程序中加载 OCR 模型，调用识别函数，取得结果：

```text
文档 → 预处理 → OCR 模型推理 → 文字、坐标、置信度
```

当业务量不大、模型独占计算资源时，这条链路已经能满足需求。

问题在于，**模型能完成识别，不等于模型能够稳定承担生产流量**：

- **集中处理**：同时收到大量文档，推理任务如何排队、并发和限流？CPU、GPU 或 NPU 不够时怎么办？
- **服务可用性**：程序已启动但模型尚未加载完成，调用方如何知道可以开始识别？推理失败后怎样恢复？
- **模型变更**：升级识别模型后，输出字段、准确率或耗时发生变化，如何验证新版本并回滚？
- **多应用复用**：多个系统需要同一种识别能力时，如何避免各自部署模型、重复占用资源和维护不同接口？
- **生产定位**：识别变慢或结果异常时，如何判断问题出在输入、模型、资源还是服务接口？

这些工作与 OCR 算法本身不同：OCR 模型负责识别，**模型服务负责把识别能力持续、可靠地提供给调用方**。

## 二、大语言模型为什么更依赖推理服务？

一个企业应用即使只使用一个大语言模型，也需要处理不同于普通业务接口的资源问题。

```text
请求进入 → Tokenize → 排队与调度 → Prefill → Decode → 流式返回
```

- **Prefill** 处理输入上下文并建立计算所需的中间状态；长输入会影响首 Token 延迟。
- **Decode** 逐步生成新 Token。长输出或推理型模型的长时间生成，会持续消耗计算资源。
- **KV Cache** 保存注意力计算所需的历史中间状态；并发请求和长上下文会增加显存压力。
- **Batching 与调度** 决定多个请求如何共享计算资源，以及等待、取消和过载如何处理。

因此，只有一个 Agent 应用，也可能遇到长请求挤占资源、队列积压、显存不足、请求取消和服务重启等问题。它需要可控的推理服务；是否进一步建设统一平台，取决于资源共享、管理要求和现有服务能力。

## 三、模型服务平台到底管理什么？

| 层次 | 职责 | 典型机制 |
| --- | --- | --- |
| **模型（Model）** | 完成识别、生成、向量编码等计算 | OCR、LLM、VLM、Embedding、Reranker |
| **推理引擎（Inference Engine）** | 在给定硬件上执行与优化模型计算 | 权重加载、KV Cache、Batching、GPU 调度 |
| **模型服务（Model Serving）** | 对外提供持续可调用的推理能力 | API、并发控制、流式响应、就绪检查、错误处理 |
| **模型网关（Model Gateway）** | 治理调用方对模型服务的访问 | 身份认证、授权、路由、限流、计量、审计 |
| **模型服务平台（Model Service Platform）** | 管理模型服务的资源和生命周期 | 部署发布、资源分配、版本、容量、监控、升级与回滚 |

例如，vLLM、SGLang 主要服务于推理执行和 Serving；API Gateway 负责访问治理；模型部署与资源管理可以由既有容器平台、运维系统或专用模型平台承担。它们的功能可能重叠，不必按表格逐层部署五套产品。

## 四、一次推理请求和日常平台管理如何衔接？

```text
业务应用 / Agent
    ↓
身份认证、授权、限流、模型路由
    ↓
推理服务接收请求、排队与调度
    ↓
模型执行 → 返回识别结果或生成内容
    ↓
记录调用、耗时、资源消耗与错误
```

**数据面**处理每次请求：接收、校验、路由、调度、推理与返回。

**控制面**管理服务生命周期：决定模型版本部署到哪里、分配多少计算资源、何时扩缩容以及怎样升级和回滚。一次模型发布改变的是控制面的配置，后续请求由数据面执行。

认证、授权、配额也是不同的控制点：API Key 可以证明调用凭证有效；授权决定调用者能用哪些模型；配额和限流约束资源使用。只有一把共享密钥，无法实现按应用区分权限和用量。

## 五、什么时候需要模型服务平台？

| 实际条件 | 建设方式 |
| --- | --- |
| 单个程序、轻量模型、资源独占、负载简单 | 进程内推理或轻量独立服务 |
| 单个应用使用 LLM，存在并发、长上下文、故障恢复要求 | 成熟推理服务 + 必要的监控、访问控制与部署管理 |
| 多应用或多模型共享 GPU/NPU，资源有限 | 统一资源分配、模型发布、路由、容量监控与使用治理 |
| 多团队使用，需独立权限、版本灰度、审计与成本核算 | 统一模型网关和服务生命周期管理 |

决定建设程度的不是服务器数量或应用数量本身，而是**资源是否需要协调、服务是否需要独立维护、故障影响多大，以及管理需求能否由现有组件承担**。

例如，企业只有一个应用，却与其他模型共享稀缺算力时，仍然需要统一资源治理；反过来，即使有多个应用，现有推理服务和网关如果已经满足需求，也没有必要重新开发一个平台。

## 六、模型服务平台与 Agent Runtime 的分工

模型服务平台解决的是：**一次模型请求如何被执行、交付和治理**。

Agent Runtime 解决的是：**模型请求之间如何决定行动、执行工具、观察反馈、保存任务状态并继续完成目标**。

```text
Agent Runtime：目标 → 模型判断 → 工具执行 → 环境反馈 → 下一轮
                           ↕
模型服务平台：        模型 API → 推理调度 → 模型输出
```

模型 API 返回成功，只能说明一次推理调用完成；Agent 是否完成任务，还取决于工具执行、外部状态及结果校验。模型服务的 GPU 调度、限流和版本管理，也不会由 Agent Loop 自动解决。
