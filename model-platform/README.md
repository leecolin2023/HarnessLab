# 什么是模型服务平台，为什么需要？

> HarnessLab / Model Platform · 定位初稿 V0.1 · 2026-10-21  
> 本文先回答“为什么需要”，不预设要自研一套平台，也不将候选工具当成已验证能力。

## 一、先从一个模型已经能跑的场景说起

假设银行财报系统需要识别客户上传的报表。最简单的实现，是在业务程序里安装 OCR 库，加载模型，调用推理函数，再把识别结果交给后续科目匹配和数据校验代码。

如果只有一个调用方、资源充足、负载简单，这种方案**完全可以成立**。不必因为用到了 AI，就先建设独立模型平台。

但把条件稍微改变，问题就出现了：

- 月底大量文件集中上传时，谁控制 OCR 能使用多少 CPU/GPU？是否会影响其他模型？
- 模型升级后识别结果发生变化，谁维护版本、验证兼容、决定回滚？
- 模型已启动却尚未加载好权重，业务系统如何得知它尚不能提供服务？
- 调用失败、排队过久或资源耗尽时，谁负责监控、限流、定位与恢复？
- 后来合同审核、影像归档也要使用 OCR，是否每个系统都安装并维护一份模型？

这时产生了一类不同于“如何识别图片”的工作：**如何长期、稳定、可控地向业务系统提供模型能力**。这就是模型服务工程要解决的问题。

## 二、换成大语言模型，为什么问题更明显？

再假设企业只部署**一个推理模型，为一个 Agent 应用服务**。哪怕算力暂时够用，模型仍不是一个“输入字符串就立即返回”的普通函数。

一轮推理通常经历：接收请求 → Tokenize → 排队与调度 → Prefill（处理输入）→ Decode（逐步生成）→ 流式返回或结束。在过程中，服务要管理模型权重、KV Cache、并发请求以及内存/显存。

尤其面对长上下文、长时间生成或推理型（CoT）模型：

1. 一个请求可能持续较长时间，并长期占用部分计算与 KV Cache 资源；
2. 多个请求到来时，需要决定如何批处理、排队、调度以及何时拒绝过载请求；
3. 请求取消、客户端断开、模型 OOM、进程重启或版本切换，都要求定义清楚的失败语义；
4. 业务上还需要知道模型版本、请求耗时、首 Token 延迟、生成速度及失败原因。

**这些责任不因为只有一个应用就消失。** 但它们首先证明的是“需要生产级模型服务能力”，并不自动证明“必须再自建一套大型、独立的模型服务平台”。成熟推理服务和现有运维体系，可能已经足够覆盖需求。

## 三、把几个容易混淆的概念分开

| 概念 | 主要回答什么问题 | 典型内容 |
| --- | --- | --- |
| 模型（Model） | 模型能计算什么？ | LLM、OCR、VLM、Embedding、Reranker 的权重与算法 |
| 推理引擎（Inference Engine） | 如何高效运行一次或一批推理？ | 模型加载、GPU 内核、KV Cache、Batching、调度 |
| 模型服务（Model Serving） | 如何持续对外提供可调用的模型能力？ | API、并发、流式输出、健康检查、错误处理、部署 |
| 模型网关（Model Gateway） | 多个调用方怎样统一访问和治理？ | 身份认证、授权、路由、限流、审计、用量统计 |
| 模型服务平台（Model Service Platform） | 企业如何统一管理模型服务的全生命周期与资源？ | 模型发布、资源分配、版本管理、容量、监控、升级与回滚 |

这些是**职责边界**，不是规定必须采购或部署五个独立产品。一套软件可能同时承担多项职责。

其中，“模型服务能力”和“独立模型服务平台”尤其不能混同：前者是生产运行必须有人负责的事情，后者只是组织这些事情的一种实现形态。

## 四、一轮业务调用究竟发生了什么？

以企业内网 Agent 向私有大模型请求推理为例：

`Agent / 业务应用 → 身份与访问检查 → 模型路由 → 推理服务排队调度 → 模型生成 → 流式响应 → 指标与日志`

这条链至少有两类不同职责：

**请求处理（数据面）**：校验调用、选择可用服务、安排推理、返回 Token 或报错。这发生在每次调用过程中。

**资源与生命周期管理（控制面）**：决定哪些模型版本部署到哪些机器、分配多少资源、如何滚动升级、观察容量和处理故障。这是持续性的管理工作。

控制面、数据面是理解职责的方式，不意味着必须把它们做成两个独立系统。

例如，API Key 认证只回答“凭证是否有效”；授权回答“它能访问哪些模型”；限流与额度回答“它可消耗多少资源”。`sk-` 不是所有 API Key 的通用标准，也不能用一把共享密钥替代企业完整的身份与权限体系。

## 五、到底什么时候需要“平台”？

应分成三个层次判断，而不是先给出“必须上平台”的结论：

| 场景 | 合理的起点 |
| --- | --- |
| 单程序、小模型、资源独占，运行要求简单 | 应用进程内调用或轻量独立服务 |
| 单个 LLM / CoT 模型，要求稳定并发、API、恢复和部署治理 | 复用成熟 Serving 引擎 + 最小运维、监控和访问控制 |
| 多模型、多应用、共享稀缺 GPU/NPU，需要统一发布、路由、审计、容量与权限 | 引入统一模型管理与网关能力；评估现有平台能否承担 |

注意：即使企业只有几台服务器，共享资源冲突、性能瓶颈和服务升级仍可能是真实问题；规模小不意味着不用治理。但也不能将“必须有人管理”偷换成“必须自行开发新平台”。

更精确的判断是：

> **只要模型需要承担生产任务，就需要与生产要求相适应的模型服务能力；是否独立建设模型服务平台，取决于实际约束及已有组件能否满足。**

## 六、模型服务平台与 Agent Runtime 的边界

模型服务平台主要保证：**模型请求能否以可预期的资源、接口、时延和可靠性执行。**

Agent Runtime 主要保证：**模型在一次次推理之间如何选择行动、调用工具、获得环境反馈、管理任务状态并继续推进目标。**

模型服务平台可能成功返回了全部 Token，但 Agent 仍可能调用错工具、遗漏证据、没有完成业务任务。反过来，Agent 设计合理，也无法替代 GPU 调度、模型部署和推理服务故障处理。

两者应通过清晰的模型 API 契约连接，而不混为同一运行时。

## 七、HarnessLab 在这里研究什么？

研究重点不是自己训练模型或重新实现 vLLM / SGLang，而是回答：

- 一次推理请求从 API 进入后，如何被调度、执行和返回？瓶颈出现在哪一段？
- 如何判断算力不足、上下文过长、KV Cache 压力、队列积压和网关限流？
- 单应用、单模型、多应用、多模型三种情况，治理责任有何不同？
- 怎样比较现成推理引擎与平台组件的原生能力、缺口及维护成本？
- 怎样通过部署日志、成功吞吐、TTFT、TPOT、P95、GPU 占用、故障与回滚实验验证结论？

后续再选择 PaddleOCR、vLLM、SGLang 或网关产品做实验；**候选工具列表不等于完成部署，文档结论不等于实测结论**。
