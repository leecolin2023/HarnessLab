# 什么是模型服务平台，为什么需要？

## 一、模型已经能运行，为什么还需要模型服务？

一套文档识别程序，可以直接在自身进程中加载 OCR 模型，读取图片并得到文字、坐标和置信度：

```text
文档 → 预处理 → OCR 模型 → 识别结果 → 业务处理
```

当请求量稳定、计算资源充足时，这种方式就能完成任务。

**第一次变化：大量文档集中到达。** 文档识别从偶尔执行的函数调用，变成持续占用 CPU、GPU 或 NPU 的计算负载。如果通过增加业务进程扩容，每个进程可能需要分别加载模型，增加内存或显存占用；业务处理和模型推理也只能一起扩缩容。继续采用进程内调用并非不可行，但必须自行解决实例复用、任务排队、资源限制和故障恢复。

**第二次变化：业务程序与模型需要分别维护。** 例如，业务程序频繁调整页面与流程，识别模型却需要较长的加载时间；或者识别模型升级后，需要单独验证效果与耗时，而不希望同步发布整个业务系统。这时，可以把模型作为独立的长期运行服务：

```text
业务程序 → 文档识别 API → 常驻 OCR 模型实例 → 识别结果
```

业务程序负责提交文档和使用结果；模型服务负责加载、承接请求、限制并发、报告就绪状态、处理推理故障。两者可以按不同的负载和发布周期管理。

**独立模型服务不是必经步骤。** 如果进程内调用已经满足容量、可靠性和维护需求，没有必要为了增加一层 API 而拆分服务。

## 二、从模型服务到模型服务平台

现在企业除了 OCR，还使用大语言模型、Embedding 和 Reranker。假设它们分属不同业务系统，却共享有限的 GPU/NPU 资源。

每个服务能管理自身的请求队列，却无法只凭自身负载决定：哪个模型应常驻、哪个应用优先使用算力、资源如何在不同服务间分配，以及如何统一处理发布、权限和容量风险。

于是出现两类跨服务的工作：

- **服务与资源管理**：登记部署的模型及版本，分配计算资源，协调扩缩容，监控容量，组织升级和回滚。
- **统一访问治理**：让不同应用经过身份认证、授权、路由、限流和用量审计后访问模型服务。

把这些责任集中管理，就形成了**模型服务平台的能力范围**。平台不是“一个更大的模型”，也不只是“给推理服务前面加一个 API”。它关注企业如何管理一组长期运行的模型能力。

平台可以由现有容器与运维设施、推理服务、模型网关以及少量集成能力共同组成；不要求重新开发一套完整产品。

## 三、大语言模型带来了哪些特殊运行约束？

并发、鉴权、监控和升级不是模型服务独有的问题。与普通后端服务相比，大模型推理的特殊性主要在于**模型权重、计算设备、显存/内存以及每次请求的实际计算量会共同决定容量**。

一轮 LLM 推理通常涉及输入 Token 处理、Prefill（处理输入上下文）、Decode（逐步生成），具体排队与调度顺序因实现而异。

- **长输入**：增加输入处理计算量，并可能带来更高的首 Token 延迟。
- **长输出或长时间推理**：Decode 持续消耗计算资源，一个请求可能运行较长时间。
- **并发和上下文长度**：多个请求的 KV Cache 占用内存或显存；不能只看请求数判断服务容量。
- **调度与过载**：推理服务需要决定哪些请求同时执行、等待、取消或拒绝，避免资源耗尽拖垮全部请求。

因此，即使只有一个 Agent 应用、一个自行部署的推理模型，也需要解决模型加载、请求调度、容量监控及故障恢复。**这证明需要可靠的模型 Serving，不等于必须另建统一平台。**

## 四、模型服务平台究竟负责什么？

沿一次请求和模型生命周期，可以区分五种职责：

| 概念 | 负责什么 | 代表性机制 |
| --- | --- | --- |
| **模型（Model）** | 计算什么结果 | OCR、LLM、Embedding、Reranker |
| **推理引擎（Inference Engine）** | 怎样执行、优化模型计算 | 权重加载、KV Cache、批处理、调度 |
| **模型服务（Model Serving）** | 怎样持续接收、处理并返回模型请求 | API、并发控制、就绪检查、流式响应、错误处理 |
| **模型网关（Model Gateway）** | 哪些应用能够访问哪些模型、如何控制调用 | 身份认证、授权、路由、限流、计量、审计 |
| **模型服务平台（Model Service Platform）** | 模型服务如何部署、分配资源和持续维护 | 发布、版本、容量、监控、扩缩容、回滚 |

以 vLLM、SGLang 为例，它们覆盖推理执行及部分 Serving 能力；模型网关承担跨应用访问治理；模型生命周期和算力分配也可以复用企业现有基础设施。上表区分的是责任，并不是要求部署五套产品。

一次典型调用与背后的管理关系如下：

```text
控制面：发布模型版本、指定资源配额、配置服务与路由规则
                                  ↓
数据面：业务应用 → 访问控制/路由 → 推理服务 → 模型输出
                                             ↓
                                  调用指标、资源与错误反馈
```

控制面决定模型和资源如何配置；数据面按当前配置处理请求，并把运行反馈提供给管理环节。

## 五、什么条件下需要独立平台？

| 实际场景 | 主要需求 | 适当的建设方式 |
| --- | --- | --- |
| 单个文档识别程序，负载稳定、资源独占 | 完成推理并保证基本可靠性 | 进程内模型或轻量独立服务 |
| 单个应用自行部署 LLM，请求长且并发波动明显 | 模型加载、调度、容量与故障恢复 | 成熟 Serving + 必要的运维监控 |
| 一个应用与其他模型任务共享稀缺 GPU/NPU | 统一资源分配、模型版本与容量管理 | 引入跨服务资源和生命周期治理 |
| 多个团队调用多种模型，有不同权限与额度 | 授权、路由、限流、审计与成本核算 | 统一 Gateway 和模型管理能力 |
| 多个应用使用成熟托管模型服务，现有网关已满足要求 | 统一访问与调用治理 | 复用现有体系，可能无需自建推理平台 |

对比两个容易误判的情形：

- **只有一个应用也可能需要统一治理**：它使用自行部署的模型，并与其他模型任务争用有限算力；服务之间的资源分配无法只靠各自排队解决。
- **有很多应用也不一定需要自建平台**：它们直接使用外部托管模型，且既有网关已满足身份、路由、限流和审计要求。

判断的关键是：**企业实际承担哪些模型运行责任、资源是否需要跨服务协调、故障风险有多大，以及现有组件是否已覆盖这些责任。**

## 六、模型服务平台与 Agent Runtime 的分工

模型服务平台负责**一次模型请求如何被执行、交付和治理**；Agent Runtime 负责**如何围绕任务目标多次调用模型、选择工具、获取环境反馈并推进任务**。

```text
Agent Runtime：目标 → 模型判断 → 工具执行 → 环境反馈 → 再判断
                           ↓ ↑
模型服务平台：         模型 API → 推理调度 → 模型输出
```

模型成功生成文本，不代表 Agent 已经完成任务。例如，模型可能正确提出“查询制度”，但工具未执行、证据不完整或报告未通过核对。反过来，Agent Loop 也不会自动解决 GPU 显存压力、模型发布或请求限流。
