# vLLM 为什么能让同一张 GPU 处理更多请求？

## 一、模型能生成文字，为什么一接入多用户就变慢？

假设一个开发者把开源大语言模型加载到 GPU，用 Python 调用模型生成文字，再封装成 HTTP 接口。只有一个用户时，程序能够正常回复；多个用户同时提问后，后到的请求开始等待。

这里有两个不同的问题：

1. **单个请求算得快不快**：用户输入多长、模型每秒能够生成多少 Token？
2. **同一时间能处理多少请求**：有限的显存和计算资源，怎样分配给不同长度、随时到达的请求？

简单地把推理函数封装成 HTTP 服务，并没有自动解决第二个问题。特别是朴素的逐请求执行方式，无法充分利用 GPU 的并行计算能力；而一味增加并发，又可能很快耗尽显存。

**vLLM 是面向大语言模型推理的执行与 Serving 系统。** 它通过 KV Cache 管理、请求调度、批处理和其他推理优化，让有限的 GPU 资源承载更多有效工作。这里说的“更多请求”主要指在给定延迟约束下提高吞吐或可承载并发，不能直接理解为任何单条请求都会快几倍。

这也是它在 AI Infra 中的位置：

```text
Agent / RAG / 业务应用
         ↓  模型 API
模型网关 / Model Platform（鉴权、路由、配额、部署、监控）
         ↓
vLLM Serving（请求接入、调度、KV Cache 管理、推理执行）
         ↓
GPU / NPU 计算资源
```

vLLM 可以直接暴露兼容 OpenAI 风格的 API，但它不自动包办企业层面的全部身份权限、跨模型资源管理和发布治理。

## 二、为什么生成一个 Token 还需要保存前面所有 Token 的信息？

自回归语言模型先处理用户输入，再逐步产生输出：

```text
输入 Prompt → Prefill → 第 1 个输出 Token
                             ↓
                         Decode 第 2 个
                             ↓
                         Decode 第 3 个 → ...
```

在 Transformer 的注意力计算中，当前 Token 的 Query（Q）需要与此前 Token 的 Key（K）比较，并利用对应 Value（V）汇总上下文信息。K、V 是模型内部计算出的向量，并不是“文字本身”和“词语含义”的简单数据库字段。

如果每生成一个新 Token 都重新计算全部历史 Token 的 K、V，会发生大量重复运算。因此推理时通常保存历史的 **KV Cache**，新的一步只补充新位置的 K、V，并复用此前缓存。

代价是显存。对采用普通全量 KV 缓存的注意力模型，可用一个近似关系说明：

```text
KV Cache 字节数
≈ 2（K 和 V）× 层数 × KV Head 数 × 每个 Head 的维度
  × 缓存 Token 数 × 每个元素的字节数
```

例如原始 Llama 2 13B 一类采用 40 层、40 个 KV Head、Head Dimension 128、FP16 缓存的配置，**2048 个 Token 对应约 1.56 GiB（1.68 GB）KV Cache**。这只是特定架构的计算示例；采用 GQA/MQA、滑动窗口注意力、不同精度或混合缓存设计的模型，消耗会不同。

模型权重已经占用大量显存，剩余空间又要容纳多个请求不断增长的 KV Cache。因此，**缓存如何分配，直接限制了同一 GPU 能同时承载多少序列**。

## 三、PagedAttention：显存没有用完，为什么仍装不下新请求？

设想一种简单的内存管理方式：为了容纳可能增长到 2048 Token 的请求，提前为每个请求预留连续的 KV Cache 空间。

如果请求最终只用了很短的序列，预留空间没有真正存入数据；而若分配和回收造成不连续的空洞，还可能出现“总空闲量足够，却无法找到满足连续分配要求的区域”。

**PagedAttention 的思路是：不要要求一条序列的 KV Cache 在物理显存里连续摆放，而是按固定大小的块管理。**

假设每个块容纳 4 个 Token，一条请求目前拥有 7 个 Token：

```text
逻辑顺序：
Token   1 2 3 4 | 5 6 7 _
逻辑块    B0    |   B1

块表映射：
B0 → 物理块 #8      B1 → 物理块 #2

物理显存池（示意）：
[#0 空闲] [#1 其他请求] [#2 本请求 B1] ... [#8 本请求 B0]
```

这条请求只需两个块，最后一个块剩一个空位。下一步生成新 Token，先利用尚未填满的块；再增长时才领取新的块。注意力计算通过块表找到分散存放的 K、V。

这样带来三个直接结果：

- **按需增长**：不需要为未知的最终输出长度提前占满整个最大窗口。
- **减少碎片和预留浪费**：不要求序列 KV 在显存中连续；典型浪费主要集中在每条序列末尾的未满块。
- **统一分配和回收**：请求结束后，块可重新进入可用集合；满足缓存条件的已计算块还可能被后续请求复用。

PagedAttention 最初提出时，主要贡献就是改变 KV Cache 的内存管理方式。**它并没有减少模型每个输出 Token 所必需的全部计算，也无法创造额外显存**；它通过提高缓存利用效率，为调度器留下容纳更多并发序列的空间。

## 四、前缀缓存：两个请求为什么能复用同一段计算？

假设企业所有制度问答都使用相同的长系统提示词，后面才跟用户的不同问题：

```text
请求 A：固定系统提示词 + 问题 A
请求 B：固定系统提示词 + 问题 B
```

两条输入有相同前缀。第一次请求已计算出该前缀的 KV Cache 后，如果相应块仍在缓存中，后续请求可以命中并复用，无须重复执行那部分 Prefill 计算。

vLLM 的自动前缀缓存主要依据**实际 Token 前缀和块的哈希**识别可复用内容，而不是判断两段文字在语义上“差不多”。对话模板、模型相关配置以及多租户隔离等条件也会影响缓存键与复用策略。

从机制上看，前缀缓存与 PagedAttention 解决的是不同问题：

| 机制 | 优先解决的问题 | 最直接的收益 |
| --- | --- | --- |
| PagedAttention | 一条序列的 KV Cache 如何高效存放与增长 | 减少显存浪费，支持更多活跃序列 |
| Prefix Caching | 多个请求为何重复计算完全相同的开头 | 减少重复 Prefill 计算和缓存占用 |
| Continuous Batching | 多个长短不同的请求怎样共享计算轮次 | 提高推理过程中的 GPU 利用率和吞吐 |

如果所有请求的开头都不同，前缀缓存可能几乎没有效果；如果 KV Cache 已接近容量上限，缓存块也可能被回收或驱逐。提示词“固定部分在前、变化部分在后”能创造命中机会，但性能提升仍依赖真实工作负载。

## 五、Continuous Batching：为什么不等一批请求全部结束？

GPU 擅长并行处理计算。逐条执行请求，会让多个可并行的推理工作无法一起利用计算资源。

于是可以把请求组成一个批次。但朴素的静态批处理存在新的问题：请求 A 生成 20 个 Token 就结束，请求 B 却要生成 500 个 Token。如果批次一直固定到全部请求完成，已结束的 A 所占位置不能立即让给新请求，资源可能闲置。

**Continuous Batching（连续批处理）让调度器在推理迭代边界动态更新参与执行的请求集合。**

下面是教学示意，并非真实 GPU 运行 Trace：

```text
时刻 1：A、B 开始生成
时刻 2：A、B 继续，C 到达并等待
时刻 3：A 已结束 → 释放相关资源
时刻 4：B 与 C 进入后续执行轮次
时刻 5：B 结束，C 继续
```

实际一次迭代可能处理不同数量和类型的 Token，不能简单理解为“每个请求永远恰好生成一个 Token 才能调度”。本质是**根据请求当前进度、可用 KV 块和调度预算动态组织执行**。

PagedAttention 和连续批处理因此是相互支撑的：前者让多个正在增长的序列更高效地占用显存，后者让新请求更及时地利用释放出来的执行机会。单独解决一个问题，并不自动解决另一个。

## 六、Chunked Prefill：为什么长输入可能卡住别人的输出？

Prefill 负责处理输入 Prompt；Decode 负责逐步生成后续 Token。两者的计算特征不同。

假设正在运行的多个请求每隔一段时间就要生成下一 Token，此时新来一个特别长的 Prompt。若它的 Prefill 长时间占用执行资源，其他请求的 Decode 就可能被延后，用户看到的现象是：**已有回答没有失败，却突然停止流式输出一段时间。**

Chunked Prefill 把长输入分成若干段，在调度预算内与其他请求的 Decode 工作穿插执行。vLLM V1 在支持的场景下可优先安排待执行的 Decode，再使用剩余 Token 预算处理 Prefill。

关键参数 `max_num_batched_tokens` 限制一次调度迭代可处理的 Token 预算：

- 较小的预算，可能降低长 Prefill 对已有 Decode 的干扰，有利于 Token 间延迟（ITL）。
- 较大的预算，可能让长输入更快完成 Prefill，有利于首 Token 延迟（TTFT）或吞吐。

这是工作负载相关的取舍，不存在适用于所有模型和硬件的统一最佳数值。

## 七、量化与多卡并行分别解决什么问题？

前面的机制让**已经放得下的模型更有效率地服务请求**；如果模型权重本身就装不进显卡，必须先解决模型放置问题。

**量化**通过使用更低精度的数值表示，减少模型权重或 KV Cache 的存储开销。例如将权重的每个数值从 FP16 的 2 字节改为适合的 8-bit 表示，原始元素存储量理论上约减半，但真实部署还包括缩放因子、未量化算子、运行时缓存等开销。推理速度和输出质量也取决于硬件、量化方案及内核，不能保证量化必然更快或无精度影响。

**张量并行（Tensor Parallelism）**把一层内部的部分计算和权重拆到多 GPU，降低单卡权重压力，但层内可能发生跨卡通信。

**流水线并行（Pipeline Parallelism）**把不同网络层分布到不同设备，减少某些层内通信需求，但存在流水线阶段交接、气泡和端到端时延约束。

还有 CPU Offload 等方法能用主机内存换取显存空间，但可能引入数据搬运开销。以上策略主要用于模型能否部署以及总体成本性能优化，与 KV Cache 的分块管理不是同一层问题。

## 八、从一次 API 请求看 vLLM 内部如何协作

在 vLLM V1 的典型在线 Serving 架构里，可观察到三个主要执行角色：

```text
客户端
  │ OpenAI-compatible 请求
  ▼
API Server
  ├─ HTTP 接口、请求校验与输入处理 / Tokenization
  └─ 流式输出与响应
        │
        ▼
Engine Core
  ├─ Scheduler：决定本轮执行哪些请求与 Token
  ├─ KV Cache Manager：查询前缀、分配与管理缓存块
  └─ 协调模型执行
        │
        ▼
GPU Worker / Model Runner
  ├─ 加载模型权重
  ├─ 在 GPU 上执行 Prefill / Decode
  └─ 产生模型计算结果
        │
        ▼
Engine Core 更新请求进度 → 下一轮 / 完成
        │
        ▼
API Server 返回输出
```

一轮请求先进入 API Server，完成必要输入处理；Engine Core 的调度器决定可安排的工作并申请 KV 块；GPU Worker 完成模型前向计算；结果返回后，未完成的请求进入后续迭代，结束的请求释放相应占用。若启用了前缀缓存，符合条件的 KV 块可以继续留在缓存中等待复用。

对于多 GPU，Worker、Engine Core 和协调进程的数量会随张量并行、流水线并行、数据并行的配置变化。上图描述典型职责，不能当作所有版本、后端和分布式架构的固定进程数。

## 九、生产运行正常返回，为什么仍可能越跑越慢？

理解执行链后，观察到“请求变慢”时，就不应该直接推断“GPU 算力不足”。

| 生产现象 | 可能的不同机制 | 首先需要区分的证据 |
| --- | --- | --- |
| 响应变慢，但错误率没有升高 | 排队变长；或 Prefill/Decode 本身变慢 | Queue Time、TTFT、ITL、输入/输出 Token 长度 |
| KV Cache 占用很高，等待请求增加 | 活跃序列过多、上下文增长、KV 块供应受限 | KV 使用率、等待数、抢占次数、请求长度分布 |
| 大量请求共享提示词，但首字仍很慢 | 前缀实际不一致、块未命中或命中后瓶颈仍在其他环节 | Prefix Cache 命中量、Prefill Time、排队耗时 |
| 新来长 Prompt 后，已有流式回答卡顿 | 长 Prefill 与 Decode 争用调度预算 | 长输入占比、迭代 Token、ITL 与调度配置 |
| 吞吐提高，个别用户反而等待更久 | 批处理增强总体利用率，但排队或尾延迟恶化 | 总 Token/s、并发、P95/P99、TTFT/ITL |

vLLM 提供 Prometheus `/metrics` 指标，例如 `vllm:num_requests_waiting`、`vllm:num_requests_running`、`vllm:kv_cache_usage_perc`、`vllm:num_preemptions`、`vllm:time_to_first_token_seconds` 和 `vllm:inter_token_latency_seconds`。指标名称和细节需要以部署版本为准。

当 KV Cache 紧张并发生抢占时，部分请求可能需要以后重新计算；抢占能维持调度运行，却可能增加时延。可能的处理包括调整请求并发预算、上下文上限、KV Cache 容量或模型部署方式，而不是遇到抢占就一律提高显存利用率。

特别注意 `gpu_memory_utilization`：它表示 **vLLM 模型执行器可使用的设备内存比例**，不是“显存的这一比例全部用来创建 KV Cache 池”。模型权重、执行缓存和其他占用都在容量考虑范围内；实际 KV Cache 空间由运行配置与内存分析结果决定。

## 十、“同一张 GPU 多扛几倍请求”到底怎样验证？

vLLM 的 PagedAttention 论文发表于 **2023 年**。论文报告：在其所测试的模型、负载和基线下，vLLM 在相同延迟水平上取得约 **2–4 倍吞吐提升**。这不是对今天所有模型、GPU、框架版本或请求形态的普遍保证。

实际比较必须先确定**在什么条件下称为更好**。一项可复现的实验应固定模型及精度、GPU、输入输出长度分布和请求到达模式，比较不同 Serving 策略下的：

- **吞吐**：完成请求数/秒和输出 Token/秒；
- **时延**：TTFT、ITL、端到端延迟的中位数与 P95；
- **容量**：运行/等待请求数、KV Cache 使用率、抢占次数；
- **业务约束**：错误率、超时比例，以及实际可接受的延迟目标。

最好设置两种有区分力的负载：

1. **前缀基本不重复**：主要观察 KV Cache 管理、批处理和调度策略。
2. **多个请求共享长前缀**：在其他条件尽量一致时，观察自动前缀缓存产生了多少计算复用。

只有在可比较条件下满足时延和错误率约束，吞吐提升才意味着“同一张 GPU 可以有效服务更多请求”；仅仅把并发数调高、让所有人都排队更久，并不是 Serving 性能提高。
