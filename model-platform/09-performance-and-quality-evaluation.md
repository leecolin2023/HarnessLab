# 09 · 性能与质量评测：吞吐增加了，为什么业务体验可能反而更差？

> **学习目标**：理解 TTFT、TPOT、P50/P95、吞吐、并发、排队与错误率的统计口径，学会为 Qwen、DeepSeek 和 OCR 分别定义有效负载；知道怎样将性能指标与模型回答正确性、文档结构质量及服务成本共同用于验收。
>
> **贯穿对照**：Qwen3-4B 单实例 Serving → Qwen3.8-27B 的 TP/副本 → DeepSeek V4 Flash 八卡 MoE → PaddleOCR-VL-1.5 文档 Pipeline。我们共享评测方法，但**不假定所有模型适用同一个性能指标**。
>
> **关联路线**：[阶段 3—11](./LEARNING_PATH.md)。[05](./05-single-instance-concurrency-scheduling.md) 已解释调度机制，[06](./06-moe-and-multi-device-inference.md) 解释多卡；本篇专门研究怎样形成可靠的对比证据，后续用于 [10 · 发布与回滚](./10-release-rollback-resource-governance.md)。
>
> **边界**：公式和表格中的数字如未注明实际来源，均为教学示例或测试设计，不代表 HarnessLab 已完成的 GPU/NPU 性能测试。

## 一、某次基准显示输出 Token/s 提高 30%，能直接说模型服务更好了吗？

一个同事告诉我们：

> “调大 Batch 后，输出 Token 吞吐提升 30%。”

这听起来像是非常明确的性能改进。但我们必须继续问：

- 是单请求，还是 20 个并发请求？
- 输入是 100 Token 还是 20K Token？
- 输出长度和完成请求数相同吗？
- TTFT 与 P95 是否发生恶化？
- 有没有因 OOM、超时被丢弃的请求？
- 改变了量化精度后，业务回答质量是否退化？

例如，系统把 100 个请求排成更大的批次，总吞吐可能提高，但等待较久的短请求反而更慢。服务资源利用率提高，不等于用户满意度一定提高。

所以合理的评测顺序是：

**先确定目标业务负载与质量要求，再选择指标，最后解释不同配置造成的资源与延迟变化。**

## 二、一次文本生成的时间究竟由哪些部分组成？

对一个流式文本请求，可以画出时间线：

~~~text
客户端发出请求
       ↓ 网络/代理/鉴权
网关进入后端并排队
       ↓
Prefill 与首个输出 Token
       ↓              ← TTFT 到此结束
Decode Token 2、3、4...
       ↓
最后一个 Token / 完成事件
       ↓ 网络传回客户端
~~~

最常见的指标：

**TTFT（Time to First Token）**：客户端/服务观察的请求开始到首个可用 Token 之间的耗时。它通常包含排队与 Prefill；不同系统是否包含网络往返要明确说明。

**TPOT（Time per Output Token）**：常用定义是首 Token 之后，每个后续 Token 平均耗时。一种近似计算为：

\[
TPOT=\frac{T_{\mathrm{finish}}-T_{\mathrm{first}}}{N_{\mathrm{output}}-1}
\]

只有输出至少两个 Token 时，这一式子才有意义。不同测量工具的 TPOT 定义可能不同，有些还使用相邻 Token 的时间间隔或分位数，不能混算。

**端到端时延（E2E）**：请求开始到完整响应完成的总时间，应该清楚是否包含队列、网络和客户端后处理。

**ITL（Inter-Token Latency）**：相邻输出 Token 之间的实际时间差，可以用于观察生成过程中是否出现明显卡顿。

以上指标回答不同体验问题：TTFT 决定“多久开始看到答案”，TPOT/ITL 决定“答案继续出现是否流畅”，E2E 决定“多久得到完整结果”。

## 三、P50、P95 和平均值为什么能给出不同结论？

假设十次请求中，九次都在 2 秒左右完成，一次因为长上下文等待 30 秒。平均值会被异常请求拉长，但同时也很难说明**最慢的那一部分用户到底等了多久**。

P50 是中位数附近的延迟，P95 是约 95% 观测值不高于的延迟阈值。实际分位数计算还有不同插值方法，样本过少时 P95 特别不稳定。

因此：

- P50 代表典型用户请求；
- P95/P99 帮助暴露排队、长请求与尾部异常；
- 平均值在计算资源消耗与总体耗时方面仍有价值；
- **错误率与超时率必须同时报告**，不能把超时请求直接从时延样本里删掉。

如果方案 B 比 A 的成功请求 P95 更低，却因为过载拒绝了大量请求，这不是一个可以直接宣布的整体改善。

还需要为延迟指定观察边界：网关入口、Serving 后端，还是用户浏览器。不同边界都正确，却不能互相替代。

## 四、吞吐、并发与请求到达速率之间是什么关系？

这里有三个常被混淆的数字：

- **并发（Concurrency）**：某时刻同时处于服务流程中的请求数；
- **到达速率（Arrival Rate）**：每秒有多少新请求到达；
- **吞吐（Throughput）**：系统每秒真正完成多少请求或处理多少 Token。

如果请求到达速度长期超过系统可持续处理速度，队列就会增长。即使 GPU/NPU 利用率很高，新的请求也要等越来越久。

可以使用 Little's Law 建立直觉：

\[
L=\lambda W
\]

在稳定、满足相应条件的系统中，平均在途请求数 L、平均完成速率 λ 和平均停留时间 W 之间存在这样的关系。

这不是用来预测任何真实系统性能的万能公式；它帮助理解为什么**队列变长、停留时间就可能上升**。

还要区分：

| 吞吐指标 | 含义 | 容易误用的地方 |
| --- | --- | --- |
| 请求/秒 | 每秒完成几个请求 | 不考虑输入/输出长度 |
| 输出 Token/秒 | 每秒产生多少 Token | 输入 Prefill 负载可能完全不同 |
| 输入 Token/秒 | 每秒处理多少 Prompt Token | 长 Prompt 会改变调度与缓存 |
| 合格任务/小时 | 每小时完成多少通过验收的业务任务 | 必须结合 Checker 和失败重试 |
| 文档页/秒 | OCR Pipeline 的处理量 | 不考虑页面复杂度时容易失真 |

只提供其中一个数字，通常不足以比较两套不同模型服务。

## 五、Qwen 小模型、27B 与 DeepSeek 怎样做可比的压测？

我们不应把三个模型强行固定到同一种 TP 配置，因为硬件要求不同；但可以固定**业务负载与验收条件**。

先建立三类文本请求：

1. 短输入短输出：简单 JD 分类；
2. 长输入短输出：完整 JD/多段合同的条件抽取；
3. 长输入长输出：需要解释与报告草稿。

对每类请求保存输入、Token 数、输出上限、模型版本、模板与采样参数，并进行必要的质量核查。

### 对比什么？

**同模型配置对照**：例如 Qwen3.8-27B W8A8 TP=2 与 TP=4。同一权重和负载下，比较每卡 HBM、请求 P95、吞吐和错误。

**相同总卡数对照**：例如 TP=4 单实例，与 TP=2 两副本。在公平的总体资源预算中比较整体请求吞吐与尾延迟。

**跨模型能力对照**：Qwen3.8-27B 与 DeepSeek V4 Flash 对同一业务问题进行质量与成本比较。但由于模型能力和设备拓扑不同，不能把绝对 Token/s 差异误称为“TP 比 EP 更优秀”。

### 为什么还要有固定到达率？

如果基准工具使用“发出 N 个请求，完成后立即再发”的闭环负载，系统慢下来时新请求的实际到达率也会下降。它可能掩盖真实的队列积压。

对接近生产的容量问题，还应使用固定到达率或明确的到达分布进行实验，观察 SLO 违约和排队。

但简单单并发基准仍有用：它是理解最小延迟与模型加载正确性的基础，不必一上来就模拟几百用户。

## 六、OCR 为什么不能按“每秒输出 Token”验收？

OCR 文档解析不是单一 Token 生成问题。

一份 30 页 PDF 可能包含图片渲染、版面分析、视觉推理、表格重组和后处理。即使其中的 VLM 推理 Token/s 非常高，如果页面渲染慢或跨页表格被破坏，文档服务仍可能不合格。

OCR 至少需要分别报告：

| 层次 | 负载与性能 | 质量要求 |
| --- | --- | --- |
| 页面 | 每页像素、DPI、复杂度、页级延迟 | 文字 CER/WER、区域定位 |
| 表格 | 单元格、合并表头、跨页数量 | 行列结构与数值对应 |
| 文档 | 页数分布、整文档 P50/P95、吞吐 | 页面覆盖、阅读顺序、跨页一致性 |
| 后处理 | CPU 时间、内存和队列 | Markdown/JSON 结构与证据定位 |
| 业务字段 | 单文件有效字段数、复核量 | 金额、日期、主体与原文一致 |

例如一份报告里所有数字都被识别为正确字符，但“金额”和“币种”对应到了错误行，它在业务上仍可能是严重错误。

所以 OCR 质量不能只靠整体文字编辑距离表述，也不能只看高性能 Serving 端点的成功率。

## 七、怎样避免“基准数据越测越好看”的错觉？

一次压测可能受到许多条件影响：

- 模型权重已经预热、编译缓存已生成；
- 输入反复使用同一前缀，Prefix Cache 命中率大幅上升；
- 不同批次的 Context 长度和生成上限不一致；
- 只统计成功请求，遗漏了失败和取消；
- 不同版本更改了 Chat Template 或 EOS；
- 后端 GPU/NPU 同时运行其他模型；
- 时延口径从客户端变成服务端而未记录。

因此需要在实验 Manifest 中固定：

~~~yaml
# 教学用运行清单
dataset_revision: "<脱敏压测输入版本>"
model_revision: "<固定权重与量化版本>"
engine_version: "<vLLM / vLLM-Ascend 版本>"
device: "<具体设备与节点>"
topology: "<TP/EP/副本及互联>"
input_distribution: "<短/中/长请求比例>"
output_limit: "<最大输出设置>"
arrival_pattern: "<并发/到达率>"
warmup_policy: "<预热方式>"
cache_policy: "<是否刻意制造前缀命中>"
measurement_boundary: "<客户端 / Gateway / Serving>"
quality_gate: "<固定文本/OCR 质量条件>"
~~~

如果要研究缓存收益，就应明确设计“相同前缀”和“不同前缀”两组负载。否则在重复相同 Prompt 的基准里测到很好的 TTFT，未必能代表真实多租户工作负载。

## 八、最终如何决定“通过上线前评测”？

可以定义一个多维度的发布门槛，而不是只选最大 Token/s：

**功能门槛**：预期 API、模型权重、流式输出、工具调用/JSON（仅在支持时）正常。

**质量门槛**：固定任务集分类与证据要求通过，OCR 的文字、结构和字段误差可接受。

**性能门槛**：在真实代表性的请求分布和指定吞吐/到达率下，P95/TTFT/TPOT 满足目标，错误与超时可控。

**资源门槛**：每卡 HBM、CPU、队列和通信开销有余量；服务故障后能够恢复。

**成本门槛**：在质量合格条件下，比较每份真正合格业务任务的计算成本，而非只有裸 Token 价格。

如果真实目标未定义，这些都只是待确认条件，不能编造“P95 必须小于 X 秒”的统一行业标准。

对于一个银行内部文档解析服务，重要的可能是正确性与可回查；对高并发在线聊天，TTFT 和稳定吞吐权重可能更高。指标排序来自**业务契约**，不是硬件宣传。

**评测的作用不是给模型打一张漂亮成绩单，而是解释选定配置在什么负载、质量和成本条件下可以持续交付。**
