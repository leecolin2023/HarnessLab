# 11 · 端到端业务调用与工程决策：一份文档为什么需要多个模型，又为什么不必全部调用？

> **学习目标**：把权重、Serving、并发、多卡、OCR、Gateway、质量评测和发布治理串成一个可追踪的业务闭环；理解业务 Workflow、Model Platform 与 Agent Runtime 各自拥有的控制权，能够用结果决定哪些模型值得常驻、哪些调用应该被删除。
>
> **贯穿任务**：用户提交一份脱敏的扫描版岗位 JD，要求识别技术条件，区分 required、preferred、mixed 与 unspecified，并提供可回查原文。纯文本 JD 作为对照路径，避免默认 OCR 参与所有请求。
>
> **可用模型**：Qwen3-0.6B / 4B 负责低成本服务实验，Qwen3.8-27B 承担 Dense 中大型推理，DeepSeek-V4-Flash-0731 研究大型 MoE，PaddleOCR-VL-1.5 处理文档解析。**这些是可选择的能力，不是规定每项业务必须执行的串行步骤。**
>
> **学习路线位置**：[阶段 12](./LEARNING_PATH.md)，是 [03—10 系列](./README.md) 的总结性业务设计。本文的流程、任务 ID 和运行数据都是教学示例；HarnessLab 目前没有完成对应生产服务，不能声称已经获得真实延迟、准确率或资源节省。

## 一、四类模型已经部署，为什么最终业务仍可能做不好？

假设团队能够展示：

- Qwen 小模型能够 Chat Completion；
- Qwen3.8-27B 能够在多卡上稳定流式生成；
- DeepSeek V4 Flash 八卡 MoE 能够回答复杂问题；
- PaddleOCR-VL 能输出 Markdown 和表格。

这证明各个模型服务具备一定能力，但业务用户真正要的是：

> “我提交这份扫描 JD，系统能正确说明哪些技术是必备、哪些属于加分，并告诉我判断的原文依据。”

这里还要回答：

1. PDF 是否真正被正确还原？表格行列有没有错？
2. 条件表达是否足够简单，普通规则能不能直接处理？
3. 是否需要小模型、27B，还是更大的 DeepSeek？
4. 模型输出是否有对应页码、位置和原文证据？
5. 某个后端失败后，系统会明确返回未完成，还是继续生成看似完整的错误报告？
6. 一份通过验收的结果究竟耗费多少资源？

所以，端到端设计不是把四种模型全部接成一条直线，而是**根据输入类型、难度和实际效果，选择最小且满足质量要求的执行路径**。

## 二、一份文档进入系统之前，谁先决定它是否需要 OCR？

假设用户可能提交两种输入：

**A：** 已有结构化文本的 JD。

**B：** 扫描版 PDF，文字还嵌在页面图片中。

如果对 A 也先转换成图片再做 OCR，不仅增加延迟，还可能把原本准确的文字引入识别错误。

因此第一步应该由确定性的输入适配程序判断：

~~~text
业务请求
   ↓
检查用户身份、数据权限与文件类型
   ↓
是否已有可信且完整的可用文本？
   ├── 是：直接进入文本清洗、字段定位
   └── 否：调用 PaddleOCR-VL Pipeline
               ↓
          页面、结构、表格、来源定位
   ↓
统一为带证据位置的文档数据结构
~~~

这不是强制依靠 LLM 决定是否做 OCR。文件类型、已有文本层、页面质量以及业务字段是否缺失，可以先交给程序检测。

但“PDF 有文本层”不一定代表文本层完整正确；对扫描混合 PDF 可能需要按页判断或抽样校验。

**输入适配的目标是减少不必要的模型调用，同时不要牺牲必要的文档证据。**

## 三、OCR 结果为什么不能直接交给 DeepSeek 生成报告？

PaddleOCR-VL-1.5 可能输出文字、版面区域和表格结构。如果原始 JD 是：

~~~text
职位职责：负责 RAG 知识库服务。
任职要求：
  Python：必须
  Milvus：经验优先
~~~

解析时如果表格对应关系被错位，后续语言模型即使严格依据输入，也可能得出错误判断。

因此 OCR 输出至少应转换为一份明确的数据契约：

~~~json
{
  "document_id":"doc-001",
  "pipeline_version":"PaddleOCR-VL-1.5",
  "pages":[
    {
      "page_no":1,
      "blocks":[
        {"block_id":"b1","text":"负责 RAG 知识库服务","bbox":[10,20,300,60]},
        {"block_id":"b2","text":"有 Milvus 使用经验者优先","bbox":[10,70,320,110]}
      ]
    }
  ],
  "parsing_status":"completed"
}
~~~

这是教学用数据结构，坐标和内容并非实际 PDF 识别结果。

在进入语言模型之前，程序应先确认页面数、关键字段、表格结构是否满足任务最低要求。若表格缺行或某页识别失败，应明确标记，不能继续假定输入完全可信。

下游输出还需保留 `document_id / page_no / block_id`，否则模型生成一段很好的解释，也无法回答“原始证据在哪里”。

## 四、Qwen 小模型、27B 和 DeepSeek，应该如何设计选择性路由？

从业务角度看，三者不必按模型参数从小到大逐个执行。

可以先把任务拆成几类：

| 任务类型 | 合理的首轮方案 | 为什么 |
| --- | --- | --- |
| 明确固定字段或正则规则 | 普通程序 | 稳定、便宜且可回查 |
| 简单文本标签、低风险辅助整理 | 小 Qwen（需要验证收益） | 低成本、低资源需求 |
| 长 JD、多条件组合、较复杂抽取 | Qwen3.8-27B 作为对照 | 中大型 Dense，质量与资源容易形成可测基线 |
| 多轮解释、复杂限制和高难样本 | DeepSeek V4 Flash 候选 | 有能力尝试更复杂判断，但需量化真实质量收益 |
| 扫描页、复杂表格和版面 | OCR Pipeline | 解决输入数据恢复，而非抽象文本推理 |

从架构上看：

~~~text
文档解析与规则校验
           ↓
     任务难度/风险判断
           ↓
     ┌──────┼────────┐
     ↓      ↓        ↓
    规则   Qwen4B   Qwen27B
                      ↓
            必要时升级 DeepSeek
     └──────┼────────┘
           ↓
       统一业务 Checker
~~~

这里“升级”不一定意味着必须先运行 27B 再运行 DeepSeek：如果系统事先知道某类难题需要 DeepSeek，可以直接选它；只有不确定时，才可能采用先低成本尝试再升级的策略。

也不能凭模型参数量断言 DeepSeek 一定更准确。**模型路由条件必须由真实的任务评测、置信证据、错误成本和资源预算支持。**

## 五、模型服务平台与 Agent Runtime 的职责怎样划分？

这是整个 HarnessLab 两条学习路线的交汇点。

### Model Platform 负责模型服务本身

- 哪个逻辑模型名对应真实权重；
- 模型部署在哪个设备、使用什么推理引擎；
- 请求能否被授权、限流、路由、审计；
- 服务是否就绪，当前延迟、吞吐和资源状态如何；
- 升级、灰度与回滚怎样进行。

### 业务 Workflow 负责业务工作的固定边界

- 输入是什么文档、具有哪些权限；
- OCR 是否通过，哪些页面待复核；
- 哪些条件可以由程序直接判断；
- 结果是否符合任务验收、需要局部重试或人工确认。

### Agent Runtime 只在需要动态行动时出现

例如模型需要根据上一轮工具结果动态回查某条 JD、选择另外一份内部资料、组织多轮说明时，可以借助 Agent Runtime 的 Loop、工具、Context 和 State。

但如果任务始终是“解析文档 → 提取字段 → 校验报告”，固定 Workflow 可能已足够。**不应为了证明 Model Platform 存在价值，强行把每一份文档都改造成多 Agent 系统。**

~~~text
业务任务 / Workflow / 可选 Agent Runtime
                 ↓
模型 Gateway（认证、路由、限流、版本）
                 ↓
Qwen / DeepSeek / OCR 真实 Serving
                 ↓
GPU/NPU + 实例资源 + 监控与发布
~~~

每层都可使用成熟框架，不要求我们重写底层引擎和 Agent Harness。

## 六、如果结果错误，应该先改模型还是先找第一次偏差？

假设报告错误地把“Milvus 经验优先”写成必备。

不能立即说 Qwen 太小，应该改用 DeepSeek。更好的排查方法是：

~~~text
源文档里是否准确写着“经验优先”？
          ↓
OCR 是否保持这几个字与所在表格列？
          ↓
模型输入 Context 是否包含正确原文？
          ↓
业务标签定义是否说明“优先”的含义？
          ↓
模型是否仍将 preferred 错判为 required？
          ↓
Checker 为什么没能阻止最终交付？
~~~

每一步都有不同的最小修正：

- OCR 错行 → 修正文档解析/表格结构；
- 原文未传给模型 → 修改输入组织；
- 标注口径不清 → 明确标签定义；
- 原文清楚但模型持续错分 → 优化选择、Prompt 或局部复核；
- 结构化结果正确但报告错误 → 修正汇总与验收。

**只有在证据指向模型能力不足时，换更大模型才是有依据的优化。**

这一方法和 [Agent Runtime 10 · 端到端评测](../agent-runtime/10-end-to-end-evaluation-and-optimization.md) 完全一致，但本篇更关注模型部署、路由、成本与服务接口的责任。

## 七、怎么保留真正能解释一次业务结果的追踪？

同一业务任务可能调用 OCR、Qwen27B 和 DeepSeek，不同模型的日志没有天然关联。

建议建立：

~~~text
task_id：业务任务
   └── document_id + 文件哈希 / 已授权来源
        └── page / block / field 的证据标识
             ├── OCR 请求 ID → pipeline revision → 后端实例
             ├── 文本模型请求 ID → 真实权重与模板版本
             ├── 是否升级到其他模型及其原因
             └── Checker 结论 → 最终报告产物
~~~

每次请求至少关联：

- 业务任务和模型 Gateway 的请求 ID；
- 逻辑模型名与实际部署版本；
- 输入类型、Token 长度或文档页数；
- TTFT/整任务延迟、错误和重试；
- 输出结构与证据位置；
- 是否通过业务验收；
- 费用或设备时长的可信统计。

默认记录必要的结构数据和摘要；原始机密文档、完整 Prompt 或密钥不应在未经批准的情况下外发或长期留存。

同时不要把“模型调用返回 200”当作任务完成。只有 Checker 确认报告中的技术条件、页码与原文匹配，才能按业务标准交付。

## 八、端到端演示应该怎样设计，才不会只是一个花哨的 Demo？

选择一组固定脱敏文件：

1. 一条纯文本 JD，验证跳过 OCR；
2. 一份单页扫描 JD，验证 OCR 与文本模型衔接；
3. 一份含合并表格的多页文档，验证结构和跨页；
4. 一份写着“经验优先”“不要求”的难例，验证语义判断；
5. 一份解析部分失败的文档，验证部分结果和错误交付。

把每一项都定义成可检查的标准答案，比较几条方案：

| 方案 | 目的 | 需要观察什么 |
| --- | --- | --- |
| 程序规则基线 | 判断哪些步骤根本不需要模型 | 正确率、覆盖与低成本 |
| OCR + 小 Qwen | 看低成本模型能解决哪些简单条件 | 误判、延迟、OCR 影响 |
| OCR + Qwen27B | 建立中大型 Dense 的质量与成本基线 | 复杂条件、Token/HBM、端到端耗时 |
| OCR + DeepSeek | 检查大型 MoE 是否有足够增益 | 难例修复、资源占用、成本 |
| 条件路由 | 判断“按难度升级”是否真的更经济 | 每份合格结果的模型调用与总开销 |

**不能只挑 DeepSeek 回答最好看的三条样例，就宣布模型路由成功。** 还需要同样样本、相同文档解析版本、业务正确性、失败率与置信条件。

如果实验没有访问昇腾八卡，则可先通过已标记的托管 API 做语义试验，**但不能把托管 API 的输出等同于私有化模型的延迟、吞吐与量化质量**。

## 九、工程上什么时候应该增加平台复杂度，什么时候应该删掉一项模型调用？

完成实验后，可能得到这些观察：

- 纯文本输入完全不需要 OCR；
- 一部分字段由程序准确判断，不必使用 Qwen；
- 简单分类 Qwen4B 已足够，27B 只增加延迟；
- 某些困难条件由 Qwen27B 和 DeepSeek 的结果差距很小；
- 大量错误来自 OCR 表格错位，增加更强文本模型也没有改善；
- DeepSeek 对极少数难例确实有明显收益，但不值得让全部任务都占用八卡。

这些才是模型服务平台应该支持**按能力、风险与负载选择模型**的原因。

优化目标可以描述为：

> 在满足预先确定的质量、安全和响应时间要求前提下，让每项合格任务使用尽可能少且可解释的资源。

它不是“所有请求都用最便宜模型”，也不是“模型越多平台越高级”。

**整个路线最终要建立的，是能够独立判断：这项业务需要什么模型能力、如何部署、如何路由、为什么性能受限、怎样验证结果，以及什么时候应该保留或删除一个服务环节。**

## 十、从完整系列回头看，应该形成什么知识体系？

~~~text
03 工件与环境：究竟运行什么权重、在哪执行？
         ↓
04 模型 API：怎样让一次推理变成可持续的服务？
         ↓
05 单实例调度：请求增加时怎样分享计算和缓存？
         ↓
06 Dense / MoE 多卡：权重、TP、EP、DP 和通信如何分配？
         ↓
07 OCR Serving：如何交付带结构与证据的文档解析能力？
         ↓
08 Gateway：业务怎样安全访问不同模型与能力？
         ↓
09 评测：哪些质量、时延、容量与成本指标可信？
         ↓
10 发布治理：合格版本怎样上线、回滚和长期运行？
         ↓
11 端到端：哪些调用真正改善了业务结果？
~~~

这是一条从**权重和执行环境**到**推理服务与资源治理**，最终回到**真实业务交付**的学习链。

同一个案例贯穿所有环节，但不意味着技术之间永远有固定先后调用顺序。正确的工程判断，是**理解每项技术解决了哪一个限制，并根据运行证据决定是否采用**。

到这里，Model Platform 03—11 的理论主线完成；后续可以按 [学习路线](./LEARNING_PATH.md) 逐项建设 Qwen、Qwen27B、DeepSeek、OCR 和 Gateway 的真正实验，而不必把教学示例当成已部署系统。
