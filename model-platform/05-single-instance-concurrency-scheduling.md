# 05 · 单实例并发与推理调度：请求越来越多，为什么 GPU/NPU 忙了却更慢？

> **学习目标**：从单请求的 Prefill/Decode 出发理解请求队列、Continuous Batching、KV/状态缓存、PagedAttention、Chunked Prefill 和 Prefix Cache 如何协作；学会在固定负载下判断是等待、计算、缓存还是资源限制导致延迟变化。
>
> **贯穿实验**：固定一套 Qwen3-4B Serving 和脱敏 JD 输入，从一个请求逐步增至多个请求。后续用相同方法观察 Qwen3.8-27B，但不直接将小模型的参数设置复制到 27B 或 DeepSeek MoE。
>
> **前后关系**：[01 · vLLM 推理原理](./01-vllm-inference-serving.md) 已解释 KV Cache 等机制的基本原理；[04 · 模型 API](./04-local-inference-to-model-api.md) 已建立常驻服务。本篇重点是**这些机制在多个同时到达的请求中如何共同工作**，并为 [09 · 性能评测](./09-performance-and-quality-evaluation.md) 提供可复核的指标。
>
> **事实边界**：所有数值与调度轨迹均为说明机制的示意，实际吞吐、时延和参数支持以固定版本及硬件上的运行证据为准。

## 一、单个用户五秒能得到答案，十个用户一起调用还能五秒吗？

假设只有一个请求：

~~~text
Q1：输入 500 Token → Prefill → 生成 200 Token → 完成
~~~

我们测到的时延包括启动等待、输入处理、逐 Token 生成和网络传输。

现在同一秒来十个请求，模型权重不会自动复制十份，而是十个请求需要**分享同一个实例的计算、显存和调度机会**。

如果朴素地每次只处理一个请求，其余请求只能排队；如果所有请求都无约束地一起执行，GPU/NPU 的动态缓存与工作区又可能被耗尽。

这就产生了 Serving 层必须解决的矛盾：

**尽可能让计算设备保持有用工作，同时不要让某个超长请求拖垮别人的响应时间或消耗全部缓存。**

注意“并发请求数”不是能力本身。真正关心的是**在规定 P95、错误率和质量要求内，单位时间能够完成多少请求或 Token**。

## 二、为什么同样是 Token，Prefill 和 Decode 的运行性质不同？

自回归语言模型一次生成通常分成两个主要阶段：

~~~text
用户输入 Token ── Prefill：处理当前 Prompt
                             ↓
                       得到首个输出 Token
                             ↓
                    Decode：逐步生成后续 Token
~~~

Prefill 处理整段输入，通常具有更强的并行计算机会；Decode 每步向已有上下文追加少量新 Token，反复读取权重与历史缓存，性能特点与 Prefill 不同。

因此这几类负载并不等价：

| 负载 | 主要压力 | 容易观察到的现象 |
| --- | --- | --- |
| 100 输入 / 20 输出 Token | 较轻计算、请求调度开销 | 短任务吞吐 |
| 20,000 输入 / 20 输出 Token | 长 Prompt 的 Prefill、上下文状态 | TTFT 与资源峰值 |
| 100 输入 / 2,000 输出 Token | 长 Decode、多轮调度 | 完成时间、输出吞吐 |
| 20,000 输入 / 2,000 输出 Token | Prefill + 长期占用运行状态 | 缓存容量、排队与尾延迟 |

这里的数字只是对照输入类型，不是实际硬件的性能数据。

如果只用极短 Prompt 测一个并发值，就不能把它直接宣传为“20K Context 下的系统可承载并发”。

## 三、Continuous Batching 为什么能减少“等最慢请求结束”的浪费？

传统静态批处理把一批请求放在一起，往往要等该批完成才释放机会。但生成请求的输出长度差异很大：Q1 输出 20 Token，Q2 输出 1,000 Token。

如果只能等整批生成完成，新请求会被一个长输出拖住。

Continuous Batching 的要点是：**每个调度周期都能考虑哪些请求继续、哪些已经完成、是否接纳新请求**。

~~~text
调度轮次 1：Q1 + Q2 共同执行
调度轮次 2：Q1 + Q2 继续
Q1 完成 → 释放其活动序列资源
调度轮次 3：Q2 继续，Q3 可以获得执行机会
~~~

这里“每轮”是教学抽象；真实引擎还有 Preemption、Prefill/Decode 混合、批次 Token 预算和设备执行等更复杂的实现。

这样改善的是**调度粒度和计算利用**，不是把每个 Token 的计算量突然变成零。多个请求仍然竞争有限的显存和计算资源。

相关原理可对照 [01 · vLLM 推理服务机制](./01-vllm-inference-serving.md)。

## 四、为什么显存看上去还没满，却接纳不了新请求？

每个正在生成的序列都要保存运行时状态。对普通全注意力模型，主要是每层的 KV Cache；对 Qwen3.8-27B 这样的混合注意力模型，还有不同于普通 KV 的状态管理。

如果每个请求按“最大上下文长度”一次性预留全部 KV Cache，大多数短请求用不完，却会占据大量空间。

PagedAttention 的核心思想是**用逻辑块到物理块的映射来管理缓存**：

~~~text
请求 Q1：逻辑块 A、B、C
                  ↓
               映射表
                  ↓
实际物理块： 17、4、26（无需连续存放）
~~~

随着序列增长分配新块，完成后归还块，可以降低大块连续预留和碎片浪费。

但是：

- 它不能消除真实 Token 状态占用；
- 块仍有最后一块的内部浪费；
- 运行时仍需为计算图、其他状态和权重留出空间；
- 对混合/线性注意力模型不能机械套用“全部层都为 KV”的统一公式。

**PagedAttention 改善缓存分配方式；它不是无限扩展上下文或并发的许可证。**

## 五、长 Prompt 为什么会拖慢其他正在输出的请求？

现在有两个用户：

- Q1 正在 Decode，每一小步产生新 Token；
- Q2 突然提交 30K Token 的长输入，需要较大的 Prefill。

如果调度器直接把 Q2 整个 Prefill 作为一个大计算阶段，Q1 的后续 Token 可能需要更久才能得到服务。

Chunked Prefill 将长 Prompt 的 Prefill 拆成较小块，使调度器能够在不同工作之间安排执行机会。

~~~text
没有拆块：
Q1 Decode → Q2 很长 Prefill → Q1 Decode（中间等待较长）

分块后：
Q1 Decode → Q2 Prefill 块1 → Q1 Decode → Q2 块2 → ...
~~~

这里的简图不代表特定 vLLM 版本严格固定采用交替顺序；实际优先级取决于调度器和批次预算。

它改变了**长输入与已有 Decode 的竞争方式**，可能改善某些请求的尾延迟，但也可能增加调度开销或降低特定负载吞吐。因此要用长短输入混合的固定工作负载来验证，而不是“开关打开就一定更好”。

## 六、两个请求共享相同 System Prompt，为什么仍可能重复做 Prefill？

假设多个 JD 分类请求都使用同一份系统规则：

~~~text
系统规则：区分 required / preferred / unspecified
           +
每条 JD 的原文不同
~~~

如果它们的**实际 Token 前缀完全一致**，推理引擎在符合实现条件时可以重用已经计算并保留的前缀缓存。

Automatic Prefix Caching 的收益主要是减少重复 Prefill。它不会缓存“最终答案”，也不会因为两个问题语义相似就必然命中。

不命中的原因可能包括：

- Chat Template 或特殊 Token 不同；
- 前缀 Token 不完全相同；
- 缓存块已经被回收；
- 缓存功能未启用或不适用于当前路径；
- 不同引擎、实例或模型版本不能共享同一份有效缓存。

因此，要测**缓存命中 Token、TTFT 变化和缓存资源占用**，而不是仅通过“第二次比第一次快”推断原因，因为权重加载、系统预热和设备状态也可能改变耗时。

另外，跨租户的缓存隔离与信息安全要由实际引擎/平台确认，不能仅凭“共享系统 Prompt”就默认所有用户可以无界复用内部状态。

## 七、调整 `max-num-seqs`、批次 Token 或 Context，分别在控制什么？

同一个实例内，常见限制与调度参数负责的资源不同。

| 调整方向 | 主要影响 | 可能的副作用 |
| --- | --- | --- |
| 活跃序列上限（如 `max-num-seqs`） | 同时允许多少序列参与调度 | 太大使缓存/工作区紧张；太小造成排队 |
| 批次 Token 预算（如 `max-num-batched-tokens`） | 单轮允许处理多少 Token | 影响 Prefill/Decode 组合与吞吐、尾延迟 |
| 最大上下文长度 | 每个请求可拥有多长的输入/历史 | 影响状态容量和极端请求风险 |
| Prefix Cache | 减少重复前缀 Prefill | 占用缓存、命中依赖真实输入与策略 |
| 可用显存比例 | 权重以外可给执行器和缓存的预算 | 配置过激可能 OOM，未必提高有效吞吐 |
| 到达速率/网关队列 | 系统入口接受多少工作 | 如果不做背压，延迟与失败率会上升 |

这些参数**不是同一个“性能旋钮”**。调大序列上限不会自动增加 HBM；提高批次预算不会让请求数无限增长；减少 Context 可能降低内存占用，却也可能截断真实业务所需证据。

vLLM 参数和实现的默认值会变化，应以当前版本命令行帮助与 [官方 Serving/调度文档](https://docs.vllm.ai/) 为准。

## 八、怎样设计一次真正能解释调度行为的实验？

先固定 Qwen3-4B 的准确权重、引擎版本、设备、模板与生成参数。准备三种脱敏负载：短输入短输出、长输入短输出、短输入长输出。

逐次改变一个条件：

1. **到达速率**：固定输入分布，增加每秒请求数，观察队列何时增长。
2. **请求混合**：加入少量长输入，观察短请求 TTFT 与 P95 是否变化。
3. **缓存命中**：相同系统前缀重复请求与随机前缀对照。
4. **批次约束**：比较同版本支持的调度设置，保留资源和错误记录。
5. **取消与过载**：停止长请求，看缓存与排队恢复是否符合预期。

每次至少记录：实际输入/输出 Token、吞吐、TTFT、TPOT、完成时间 P50/P95、等待与运行请求数、KV 或其他状态缓存占用、HBM 峰值和失败数。

一个最简单的观察逻辑是：

~~~text
吞吐上升 + P95 在目标内  → 容量利用可能改善
吞吐上升 + P95 大幅恶化 → 吞吐/延迟权衡，不能只报吞吐
队列持续增加           → 入口到达速率超过稳定服务能力
HBM 接近约束并出现 OOM   → 缓存/工作区或并发预算需要核查
~~~

这些是分析方向，不是单凭某项图表即可确定根因；还需要结合真实引擎指标和运行轨迹。

### 为什么不直接在 27B 上做全部试验？

Qwen3-4B 成本低、迭代快，适合先学会构造负载与理解指标。随后再把**同一套实验方法**迁移到 Qwen3.8-27B，比较 Dense 大模型的 HBM、TP 和缓存机制；不能把不同模型的绝对性能数字直接视为调度算法差异。

本篇最重要的判断是：**提高单实例并发能力不是某一个开关，而是围绕 Prefill、Decode、缓存、调度和入口负载建立可测的资源分配方法。**

下一篇 [06 · MoE 与多卡推理](./06-moe-and-multi-device-inference.md) 将把 Qwen27B 的 Dense 多卡当成对照，研究 DeepSeek 大型 MoE 为什么多出了专家分布与通信难题。
