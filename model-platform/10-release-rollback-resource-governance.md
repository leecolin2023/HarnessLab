# 10 · 发布、回滚与资源治理：模型已经能运行，为什么还不能直接交给所有业务使用？

> **学习目标**：理解模型服务的发布单、版本固定、就绪与健康、流量切换、失败回滚、资源配额、鉴权、审计和成本归因；知道大型模型更新为什么不能等同于普通代码热更新。
>
> **贯穿场景**：同一模型平台已有 Qwen3.8-27B、DeepSeek-V4-Flash-0731 和 PaddleOCR-VL-1.5。现在要替换其中一款模型的权重、量化格式或引擎版本，但必须保证其他应用的服务质量不会因为升级突然失控。
>
> **承接关系**：[09 · 性能与质量评测](./09-performance-and-quality-evaluation.md) 回答“新版本是否更好”；本篇回答“怎样让经过验收的版本真正被发布、限制影响范围并在失败时撤回”。
>
> **事实边界**：以下发布流程和字段是可复用的工程设计；当前 HarnessLab 没有完成实际生产灰度、资源调度或灾备演练。对不同昇腾/英伟达硬件，是否支持热加载或多版本并存需由具体后端和资源条件决定。

## 一、模型已经加载、接口返回 200，为什么不直接切流量？

设想 Qwen3.8-27B 的新版本权重已经加载成功，`/v1/chat/completions` 返回一句正常中文。

但业务方接下来发现：

- 原有 Tool Calling 格式变了；
- 输入 10K Token 的请求 P95 明显上升；
- W8A8 改造后某些金额字段开始错分；
- OCR Pipeline 更新后合并单元格丢失；
- 两个服务争夺同一组 HBM，导致彼此 OOM。

**“进程可用”只证明它能够执行某种工作，不证明它满足真实业务的接口、质量、容量与安全要求。**

因此，发布前必须用 [09](./09-performance-and-quality-evaluation.md) 建立的固定负载和业务样本验收；发布之后也要监控实际流量，并在结果不合格时快速回退。

## 二、模型服务一次发布，究竟发布了哪些东西？

普通业务程序发布常以一个镜像版本为单位。模型服务的运行结果却由多个工件共同决定：

~~~text
模型权重与量化工件
       +
Tokenizer / Chat Template / 生成参数
       +
推理引擎与 CUDA/CANN/驱动
       +
TP/EP/DP、Context、Cache 与批次参数
       +
GPU/NPU 节点与设备拓扑
       +
Gateway 注册、路由与权限
       ↓
最终用户真正调用到的模型服务版本
~~~

例如只更换模型的量化权重，不改 HTTP URL，可能仍造成输出质量和吞吐变化；只升级 vLLM-Ascend 而不更换权重，也可能改变调度、兼容性和计算峰值。

所以发布单应记录**工件+运行环境+服务配置+API 契约**，不能只写“Qwen27B 已升级”。

教学示例：

~~~yaml
# 发布单 Schema 示例，不是已有生产配置
release_id: qwen27b-r2
model:
  logical_name: qwen-27b
  artifact: Qwen/Qwen3.8-27B
  revision: "<实际 revision>"
  quantization: w8a8
runtime:
  engine: vllm-ascend
  version: "<经验证的版本>"
  driver_cann: "<固定依赖组合>"
  topology: "TP=2; 2 replicas only if capacity permits"
api_contract:
  chat_streaming: verified
  structured_output: "<测试后填写>"
validation:
  quality_suite: "<固定测试集>"
  performance_report: "<对应结果>"
  rollback_target: qwen27b-r1
status: planned
~~~

发布单里未完成的项应保持未验证，不能把 `verified` 写成礼貌性的默认值。

## 三、为什么模型“健康”至少有三个不同意思？

在发布流程中很容易只做一个 HTTP 健康检查，但健康度具有不同层次。

**存活（Liveness）**：进程还在、事件循环可能还能够响应。

**就绪（Readiness）**：权重加载、设备初始化与必要依赖已经完成，可以实际处理符合契约的请求。

**业务健康（Quality/SLO）**：在真实负载中，延迟、错误率、输出质量和容量仍满足承诺。

例如大型 MoE 进程启动后，可能仍在加载权重或建立通信组；这个时候端口存在，不代表能够接受正式流量。

再如 OCR Gateway 可以返回健康，但底层 Triton 与 VLM 其中一个尚未就绪。官方 [PaddleOCR 高性能 Serving](https://github.com/PaddlePaddle/PaddleOCR/blob/main/deploy/paddleocr_vl_docker/hps/README.md) 也区分存活探测与验证相关服务状态的就绪探测。

所以路由要以**真实就绪状态**为依据，不能只判断 TCP 端口是否能连接。

## 四、灰度发布为什么不是“把 10% 的请求随机送过去”这么简单？

对于两份输出完全兼容的后端副本，逐渐增加新版本流量是自然的做法。

但模型服务存在几个特殊条件：

- **权重常驻开销大**：新旧大型模型能否同时放进 HBM？
- **模型行为会变化**：相同 Prompt 可能产生不同内容，是否有质量回归标准？
- **流式请求较长**：切换过程中已建立的请求应保持绑定原实例。
- **上下文和工具格式可能变化**：不能只测 `hello` 就让业务全部切换。
- **模型路由会影响成本**：新版本 Token/s 高未必降低每个合格任务的成本。

对于 Qwen3.8-27B 两副本部署，如果有空余容量，可以先让一个副本运行新配置，经过固定回归和部分受控流量观察再扩容。

但 DeepSeek 0731 可能占用一整组八卡。如果企业只有一组可用资源，**就没有免费同时运行新旧两套全尺寸服务的条件**。这时可以采用离线回放、受控维护窗口、预留备用节点或明确的回退策略，但不能声称已实现真正无中断灰度。

**灰度的前提是有真实可用的隔离资源和观察机制，不是写上 Canary 百分比就自动成立。**

## 五、切换失败了，怎样才算可回滚？

假设新版 DeepSeek 已经成功运行，但长上下文请求不断出现错误。

回滚不是简单修改模型名称。它至少需要：

1. 保留上一版的权重、量化工件、镜像和启动配置；
2. 知道 Gateway 的旧别名映射和后端地址；
3. 确认旧版运行环境仍与当前驱动、NPU 兼容；
4. 对新请求停止路由到问题版本；
5. 让已开始的流式请求按预先约定完成或返回中断；
6. 恢复旧版，验证就绪与关键业务样本；
7. 记录这次事故涉及哪些请求、版本和结果。

如果升级同时迁移了不可逆的数据 Schema 或修改了外部副作用，回滚模型权重并不自动回滚业务数据。因此模型服务变更与业务数据迁移最好分开治理，必要时定义受控补偿。

**可回滚性必须提前验证**。若旧版镜像已删除、Token 模板不再兼容或 NPU 驱动已不可逆更新，临时写一句“回滚至上一版本”并不能完成恢复。

## 六、为什么资源治理不仅仅是按模型分配卡？

假设有限的 NPU 资源上同时运行 Qwen27B 和 DeepSeek，OCR 也需要部分计算能力。

即使每个模型都能单独启动，一起运行时仍可能发生：

- HBM 竞争与 OOM；
- 多卡通信和设备互联争用；
- 共享 CPU/内存与文件缓存争用；
- 网络出口和模型下载占用带宽；
- 高频业务占满请求队列，其他业务长期等待；
- 大模型长期空闲但仍独占多卡资源。

因此需要区分**静态部署资源**和**动态请求配额**。

| 控制对象 | 需要决定什么 |
| --- | --- |
| 设备与实例 | 哪些 GPU/NPU 卡给哪个实例，是否允许共置 |
| 模型权重驻留 | 哪些模型常驻、哪些需要排队或按需启动 |
| 请求队列 | 租户配额、优先级、最大等待与过载拒绝 |
| Token / 页数预算 | 不同请求的真实计算量与收费口径 |
| 故障域 | 一个八卡实例失败是否影响其他服务 |
| 成本 | 每类模型消耗多少设备时长、请求和业务任务 |

例如“模型 A 空闲就把它的设备让给模型 B”看起来简单，但释放和重新加载大权重有启动时间与状态代价。若没有足够的模型缓存、调度能力和重启预算，动态迁移可能比保持常驻更昂贵。

需要根据真实负载研究：是提高已有实例利用率，还是增加副本；是分时共享，还是长期独占。不能凭设备利用率一个百分比得出最佳配置。

## 七、日志与审计为什么不能“越详细越好”？

为了定位问题，确实需要请求 ID、用户/业务身份、逻辑模型名、真实后端版本、耗时、Token/页数、错误和重试信息。

但如果把每次 Prompt、OCR 原图、合同全文、API Key 都发送到外部监控平台，模型服务本身反而成为数据泄露通道。

合理的默认记录可以是：

~~~json
{
  "request_id":"req-example-001",
  "application_id":"document-analysis",
  "model_alias":"qwen-27b",
  "release_id":"qwen27b-r2",
  "status":"completed",
  "prompt_tokens":1800,
  "output_tokens":210,
  "latency_ms":3200,
  "content_recorded":false
}
~~~

这些数字只是**字段示例，不是实际运行数据**。

敏感原文只在真正需要调查并获授权时采集，且应经过脱敏、加密、访问控制与期限管理。不要为了将来某次调试，把所有完整请求体默认永久保存。

另外，成功率不能只看 HTTP 200：OCR 返回部分页面、模型流中途断开或生成结果格式不合格，都可能需要独立的业务状态。

## 八、怎样建立一个最小但完整的发布演练？

在测试环境先使用 Qwen 小模型或 Mock Serving，保证不会影响真实业务。

**步骤 1：固定旧版。** 保留工件/配置与一组脱敏接口、质量、性能样本。

**步骤 2：部署候选新版。** 检查权重身份、就绪、GPU/NPU 资源、API 和质量。

**步骤 3：逐步切流量。** 在确实存在两个可用实例时，按受控比例路由；否则使用离线回放或维护窗口验证。

**步骤 4：故障注入。** 让新版本模拟超时、不可就绪或格式退化，确认监控能发现并阻止继续扩大影响。

**步骤 5：执行回滚。** 恢复注册表、后端与路由，重新验证旧版的固定样本。

**步骤 6：形成复盘。** 记录哪个条件触发回滚、影响范围、恢复时间、有没有请求结果未知或业务任务需要补偿。

完成一次演练后，才有依据讨论更复杂的自动灰度、弹性扩缩容和版本仓库。

**本篇核心结论：模型服务平台的发布对象不只是权重，而是一组能被调用、测量、授权、隔离和恢复的运行契约。** 没有质量与容量验收的版本切换，不算工程上完成发布。
