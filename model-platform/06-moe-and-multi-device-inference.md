# 06 · MoE 与多卡推理：Qwen 27B 已经会 TP，DeepSeek 为什么还需要 EP？

> **学习目标**：先用 Qwen3.8-27B 的 Dense 多卡服务理解 TP、DP/副本与权重/显存预算，再研究 DeepSeek-V4-Flash-0731 的 MoE 专家路由、EP、通信代价和容量。能够解释为什么“总参数多”和“每 Token 激活参数少”可以同时成立，以及多卡配置怎样影响延迟和吞吐。
>
> **贯穿实验**：在可用昇腾 910B4/A2 八卡节点上，先以 Qwen3.8-27B 的 W8A8 TP=2/4 与多副本形成受控对照，再评估 DeepSeek V4 Flash-0731 W8A8 的官方参考路径。若没有 NPU 实机权限，只完成兼容与容量推导，不将文档参数冒充部署实测。
>
> **前后关系**：[02 · 模型服务容量规划](./02-model-serving-capacity-planning.md) 讲为什么不能单靠参数量选卡，[05 · 并发调度](./05-single-instance-concurrency-scheduling.md) 讲一台实例内部怎样承接请求。本篇研究**权重和计算需要跨设备分配时，模型结构如何改变分配与通信问题**。

## 一、Qwen3.8-27B 的两卡方案与 DeepSeek 的八卡方案，是同一种扩容吗？

设想已经完成 Qwen3.8-27B 的基础部署：两张昇腾卡构成一个模型实例，共同处理同一请求。

我们还想把 DeepSeek V4 Flash 部署在八张卡上。最直觉的想法是：27B 用两卡，284B 用八卡，只是参数更多。

但实际区别更深：

**Qwen3.8-27B 在本轮对照中是 Dense 模型**，主要研究同一模型的权重与计算怎样分摊；**DeepSeek-V4-Flash 是 MoE**，会依据 Token 选择专家，要求理解专家放在哪张卡、不同请求怎样访问这些专家。

两者都可能使用 Tensor Parallel，MoE 却额外引入**专家路由、跨设备 Token 调度、All-to-All 通信和负载不均衡**。

因此学习顺序应是：

~~~text
Qwen3.8-27B：权重放得下吗？TP=2/4 怎样分片？加副本划算吗？
       ↓
DeepSeek V4 Flash：权重仍要完整部署，但每个 Token 只激活部分专家
       ↓
专家分片到设备后，Token 如何被送到对应专家？
       ↓
TP / EP / DP 在同一服务里怎样组合、通信与扩容？
~~~

## 二、为什么 MoE 的 13B 激活参数不能按 13B 小模型部署？

按照官方已公开的 DeepSeek V4 Flash 规格，模型总参数约 **284B**，每 Token 参与前向计算的激活参数约 **13B**。这里是两个不同的计量对象：

- **总参数**：要能提供整个模型推理服务，通常需要让全部相应专家权重可被调度访问，涉及全量权重的存储/驻留与设备分布；
- **激活参数**：对某个 Token，路由器只选择部分专家参与计算，有助于降低每 Token 的实际计算量。

一个最小示意：

~~~text
假设 MoE 层有很多专家 E1、E2、...、En
某 Token 的 Router 选择 E3 和 E8
      ↓
只执行这些被选中的专家
      ↓
其他专家没有参与该 Token 的专家计算
~~~

这个例子没有声称 DeepSeek 具体每层选几个专家；实际专家数、共享专家与路由方式应查准确权重架构。

“没有参与这次 Token 的计算”并不等于专家权重可以在请求到来时凭空消失。若要快速处理任意 Token 的路由结果，服务仍然需要在设备内存或设计好的存储层为权重提供可访问性。

所以不能估算：

~~~text
错误：13B 激活参数 × 1 字节 ≈ 13GB → 单卡就能跑
正确：全部相关权重的量化存储和分片
      + Attention/Router/共享层等实际精度
      + 运行缓存、计算工作区、跨卡通信
      → 再核对目标设备与软件支持
~~~

W8A8 是量化方案，不意味着每个模块绝对只占 1 字节/参数；额外缩放信息、保留高精度张量和执行缓存仍需计算。

## 三、先看 Dense：TP 与部署两个副本究竟有什么区别？

以 **Qwen3.8-27B** 为基准，假设官方权重/框架支持 TP=2、TP=4 两种配置。

### TP：同一个请求，由多张卡共同计算

Tensor Parallel 将同一层的部分矩阵或相关计算分配到不同设备。每张卡只持有相应分片，但**处理同一 Token 时，需要配合完成一次模型前向**。

~~~text
Qwen27B 单实例 / TP=4
  请求 A
     ↓
  NPU0 + NPU1 + NPU2 + NPU3 共同执行
     ↓
  汇合必要结果并继续下一层
~~~

它有助于分担权重和计算，但会产生设备之间的通信和同步。

**TP=4 不一定比 TP=2 延迟更低。** 如果模型在两卡已能完成计算，增加卡数可能减少单卡负载，也可能增加跨卡通信损耗。必须用相同请求负载实测。

### DP / 两个副本：不同请求分给不同完整实例

例如同样四张卡：

~~~text
副本 A（TP=2）：NPU0、NPU1 → 请求 1、3、5
副本 B（TP=2）：NPU2、NPU3 → 请求 2、4、6
~~~

每个副本运行完整模型（内部按 TP 分片），不同请求可以被路由到不同实例。

它的优势主要是**总请求吞吐、隔离和故障域**，但不能让单个请求自动用上四张卡的计算力。

| 使用四张卡 | 一个实例 TP=4 | 两个实例，各 TP=2 |
| --- | --- | --- |
| 权重 | 四卡分担一个模型 | 两份模型实例，各自两卡分片 |
| 请求 | 一个实例内调度多个请求 | 两个实例可独立处理请求 |
| 单请求延迟 | 可能受计算分片与通信影响 | 每请求按 TP=2 性能执行 |
| 总吞吐 | 取决于大 TP 的计算、缓存和调度 | 可能因多副本而改善，但权重重复占用 |
| 故障 | 一个实例失败影响其全部请求 | 单个副本故障可能由另一个副本承接部分流量 |

这就是为什么容量规划必须先分清：“**一个模型实例需要几张卡**”和“**业务总共需要几个实例**”。

## 四、MoE 中的 EP 又把什么分到不同卡上？

Expert Parallel（专家并行）侧重将不同专家放在不同设备或设备组上。

举一个跨设备路由的教学过程：

~~~text
请求产生若干 Token
          ↓
Router 判断每个 Token 要访问哪些专家
          ↓
Token / 中间激活被发送到拥有对应专家的设备
          ↓
设备本地执行专家计算
          ↓
结果汇合，进入后续层
~~~

对于某个 Token，可能需要访问不同设备上的专家，因此执行过程中会发生跨设备数据交换。实际引擎如何安排专家所有权、发送什么形状的张量、使用什么通信算子，取决于实现。

与 TP 的关键差别：

- **TP**：拆分一层的矩阵计算，多个设备协作处理同一层；
- **EP**：把不同专家分配到设备，Token 依据路由选择专家执行；
- **DP**：复制一个完整模型执行组，将不同请求分配给不同副本；
- **PP（Pipeline Parallel）**：按层/阶段分割模型，在设备组之间依次传递中间结果。

它们不是“从四个选项中只选一个”。某些推理框架允许多个并行维度组合，实际组合则必须受模型结构、设备互联、版本和框架支持限制。

### 为什么还会出现专家负载不均衡？

如果一批 Token 更常选中某些专家，那些专家所在设备可能比其他设备忙。

即使卡数和总算力看似够用，单个热点专家也可能成为关键路径。于是才有专家负载均衡、专家复制、路由调整或专家布局优化等问题。

但这些优化可能增加权重驻留或通信，不能只凭“让专家更均匀”就保证吞吐改善。

## 五、通信为什么有时比算力更难？

在 Dense TP 中，不同卡需要对中间计算结果做必要的集合通信；在 MoE EP 中，可能还要把 Token 的激活分发给相应专家并收集结果。

设备互联的带宽、延迟、拓扑和通信实现因此直接影响模型执行。

假设设备能快速计算，但每层都在等待通信：

~~~text
NPU 计算完成 → 等待跨卡交换 → 下一阶段计算
                    ↑
             网络/互联成为关键路径
~~~

此时增加更多设备不一定有效；如果只是扩展同一 TP 或 EP 组，通信量和同步边界可能随之增加。

需要同时观察：

1. 模型加载后的每卡 HBM 是否均衡；
2. 实际计算利用率是否持续偏低；
3. HCCL/通信日志是否存在异常、重试或等待；
4. 批处理大小变化是否改变通信与计算的比例；
5. 同样总卡数下的 TP/EP/副本方案哪个符合延迟与吞吐要求。

不要简单把“某张卡利用率低”直接诊断成专家路由失衡；它也可能等待其他算子、Prefill/Decode 阶段、同步或队列。

## 六、为什么不能把 Qwen 的 KV Cache 公式直接照搬给 DeepSeek V4？

模型架构也影响运行时状态。

普通全注意力模型容易用“层数 × KV 头数 × 维度 × 序列长度 × 精度”等因子近似缓存量。但 **Qwen3.8-27B 有混合注意力结构**，不能把其所有层都视为传统全量 KV；DeepSeek V4 也有自己的混合注意力与压缩状态机制。

因此估算时要拆分：

~~~text
模型权重驻留
    + 对应注意力/状态机制的序列缓存
    + Prefill/Decode 计算工作区
    + 通信和并行执行缓冲
    + 框架/设备保留
    = 需要实测验证的峰值资源需求
~~~

不能因为宣传支持很长上下文，就直接在首轮八卡实验设置最大理论长度。长上下文会改变排队、状态占用和请求吞吐，必须从可验证的短上下文开始逐步增大。

## 七、昇腾 A2 上的 DeepSeek 0731 应该怎么逐步验证？

参考 [vLLM-Ascend DeepSeek V4 Flash 官方指南](https://docs.vllm.ai/projects/ascend/en/main/tutorials/models/DeepSeek-V4-Flash.html)，先固定 **`DeepSeek-V4-Flash-0731-w8a8`** 工件、对应镜像、CANN、设备映射和引擎版本。官方给出了 Atlas 800I A2 八卡的参考环境，但**它不是任何 910B4 节点已经通过的实测证明**。

按以下顺序推进：

**第一关：环境与权重。** 核对驱动、设备、量化权重、模型结构、推理后端、通信与内存预算。

**第二关：基本正确性。** 真正完成模型加载，非流式与流式请求均可生成，且错误、停止原因和精度状态可解释。

**第三关：固定负载。** 分别使用短输入短输出、长输入短输出和长 Decode 请求记录 TTFT、TPOT、P95、吞吐、每卡 HBM、设备状态与通信错误。

**第四关：配置对照。** 只在官方支持的组合中比较并行、上下文、缓存和量化参数；单次优先改变一个变量。能够区分“加载失败”“加载成功但慢”“接口正常但质量不通过”。

**第五关：生产取舍。** 如果一个实例占满八卡，需要判断是否确实能满足业务请求量；若需要副本或高可用，容量规划就不再是“八卡能启动”这么简单。

在没有上述数据时，合理结论是**可研究的官方参考路径已确认，实际硬件容量与业务表现待测试**。

## 八、同样是 8 卡，怎样判断 Qwen 多副本与 DeepSeek 单实例谁更有价值？

这不能仅靠模型参数或峰值 Token/s 决定。

选择一批固定的脱敏业务问题，包括明确的字段提取、较复杂的条件判断和需要证据解释的难例。

分别记录：

| 对照维度 | Qwen3.8-27B W8A8 TP=2 × 多副本 | DeepSeek V4 Flash W8A8 参考八卡实例 |
| --- | --- | --- |
| 模型能力 | 固定质量集验证 | 使用同一业务标准验证 |
| 设备占用 | 多实例重复权重 | 大型 MoE 完整部署 |
| 单请求延迟 | 依赖 TP=2 和负载 | 依赖 MoE 路由、并行和通信 |
| 请求总吞吐 | 多副本可独立调度 | 在大型单实例中批处理 |
| 故障域 | 副本可独立失败与恢复 | 实例故障影响整个服务 |
| 成本 | 设备时长与合格任务数 | 设备时长与合格任务数 |

这张表不是暗示同样八卡下哪个一定更快、质量一定更好；它规定了**怎样才能公平比较**。

尤其要关注“每份合格报告的设备时间”，而不是为了更高模型能力让所有简单分类请求都占用大型 MoE。

**本篇的核心结论是：TP 解决一个实例怎样分担计算，DP/副本解决如何分担请求，EP 解决专家怎样跨设备分布；只有理解对应模型结构和通信，才可能合理配置多卡。**
