# 如何根据模型和业务需求确定 AI 推理服务器的加速卡数量？

**——以 Qwen3.8-27B 和昇腾 910B4（单卡 64GB）为例，推导需要多少张 AI 加速卡**

## 一、为什么不能直接根据模型参数量确定卡数？

假设银行计划部署 Qwen3.8-27B，为财务报表分析、合同核验和制度问答等业务系统提供推理服务。

已经确定采用昇腾 Ascend 910B4，每张卡拥有 64GB HBM 显存。

现在需要回答：

- 部署 Qwen3.8-27B，需要一张卡还是两张卡？
- 如果需要支持 64K 或 128K 长上下文，是否要增加卡数？
- 如果有几十个用户同时调用，应该继续增加模型使用的卡数，还是部署更多模型实例？
- 怎样根据这些要求，计算整套服务需要多少张卡？

最容易想到的办法是根据参数量计算权重大小。

Qwen3.8-27B 约有 270 亿参数，采用 BF16 时，权重理论存储量约为：

\[
27\times10^9\times2=54\text{ GB}
\]

而每张昇腾 910B4 标称拥有 64GB HBM。

这里的 54GB 是按十进制字节计算的理论权重大小，约合 50.3GiB。硬件标称容量和软件报告的容量可能使用不同单位，实际比较前必须统一口径。

是不是一张卡就够了？

不能这样判断。

首先，54GB 只是权重的理论大小，运行模型还需要额外显存。

其次，即使模型能够放进一张卡，也不代表它能在规定时间内完成业务请求。

最后，模型采用什么精度、使用什么推理框架，以及框架是否支持单卡执行，都会影响最终卡数。

因此，容量规划应当依次回答三个问题：

**第一，显存是否足够？**

确定一个模型实例需要多少显存，判断一张 64GB 卡能否容纳。

**第二，软件是否支持？**

确认模型结构、量化权重及推理框架是否支持在相应卡数上运行。

**第三，性能是否足够？**

在模型能够运行的基础上，测试指定卡数下的延迟和吞吐量，判断是否满足业务负载。

这三个问题都解决之后，才能确定服务器需要多少张卡。

---

## 二、第一步：了解模型的基本规格

### 1. 去哪里查模型参数？

建议优先参考三个来源。

**模型官方仓库**

https://huggingface.co/Qwen/Qwen3.8-27B

了解模型参数量、架构、上下文、权重精度和使用方法。

**模型配置文件**

https://huggingface.co/Qwen/Qwen3.8-27B/blob/main/config.json

了解网络结构、层数及相关计算参数。

**昇腾推理框架适配文档**

https://docs.vllm.ai/projects/ascend/en/latest/tutorials/models/Qwen3.8-27B.html

了解模型在昇腾上的适配情况、支持的权重版本、张量并行配置和已验证的部署环境。

需要注意，模型官方规格告诉我们模型本身具备什么能力，不一定直接给出所需服务器的最小配置。

而推理框架的部署文档，通常只能保证其列出的特定硬件和软件组合已得到相应验证，不能直接把结论推广到所有显存容量相同的设备。

### 2. Qwen3.8-27B 的主要规格

| 指标 | 模型参数 | 对容量规划的意义 |
|---|---|---|
| 参数量 | 27B | 影响权重规模及计算量 |
| 模型类型 | Dense 稠密模型 | 主要模型参数参与推理 |
| 语言模型层数 | 64 | 影响计算及运行状态 |
| 模型结构 | 混合注意力 | 影响长上下文资源需求 |
| 原生上下文 | 262,144 Token | 模型支持的序列长度 |
| 模态 | 文本、图像、视频 | 决定请求类型 |
| 推理模式 | 支持不同思考等级 | 影响生成负载 |

有三个参数尤其重要。

**参数量决定基础权重需求。**

27B 意味着需要存储和计算数百亿个参数。

**模型架构影响实际计算与显存。**

Qwen3.8-27B 采用混合注意力架构。在 64 层中，48 层采用 Gated DeltaNet，16 层采用完整注意力。

因此，不能简单把传统 27B Transformer 的全部运行时显存公式套用到这个模型上。

**上下文长度决定潜在请求规模。**

模型原生支持 256K Token，但实际部署时，可以根据业务需要使用 16K、32K、64K 或其他上下文配置。

支持的模型最大长度，不等于每个模型服务实例都必须按最大长度分配资源。

## 三、第二步：确定模型采用什么精度

模型参数量不变，但使用不同数值精度时，权重占用可能明显不同。

### 1. 计算权重大小

基本公式：

\[
M_{\text{weights}}=P\times B
\]

其中：

- \(P\)：参数数量。
- \(B\)：每个参数占用的字节数。

对于 Qwen3.8-27B：

| 精度 | 理论权重大小 |
|---|---:|
| FP32 | 108GB |
| BF16 / FP16 | 54GB |
| INT8 | 27GB |
| INT4 | 13.5GB |

这些是理论值。

实际模型可能有额外参数、未量化模块及量化元数据，不能直接将理论值等同于加载到 HBM 后的实际占用。

### 2. 结合单卡 64GB 判断 BF16

假设采用 BF16。

权重理论占用约 54GB。

而一张昇腾 910B4 标称具有 64GB HBM。

为了演示预算计算，先**把标称 64GB 按十进制 GB 处理**，并暂以 85% 作为模型推理的显存预算比例：

\[
64\times0.85=54.4\text{ GB}
\]

按照这个**十进制 GB 的教学假设**，单卡显存目标预算为 54.4GB；只有模型和硬件容量的单位一致，这样比较才有意义。

要特别区分 GB 和 GiB：

- **1GB = 10⁹ 字节；1GiB = 2³⁰ 字节。** 理论权重 54GB 约合 50.3GiB。
- 如果设备实际可用容量报告为 **64GiB**，85% 对应的是 **54.4GiB（约 58.4GB）**，不能直接写成 54.4GB。
- 官方仓库的模型文件大小、模型加载后的 HBM 占用和设备实际可用 HBM，并非同一个指标。

Qwen3.8-27B 的 BF16 理论权重约为 54GB，已经占用单卡相当大的空间；而运行服务还需要为缓存、计算工作区与框架留出资源。

因此可以先作出一个审慎的工程判断：

**单张标称 64GB HBM 的 910B4 不宜直接作为 BF16 生产服务的优先方案；具体能否加载以及是否具备可靠余量，还需要按实际容量和运行峰值验证。**

如果必须使用 BF16，就应该优先评估多卡模型并行。

### 3. W8A8 是否可以减少卡数？

如果采用 W8A8 量化，主要量化权重可以使用 8 位表示。

纯 8 位参数的理论空间约为 27GB。

这与 BF16 的 54GB 相比，约减少一半。

因此，从权重显存的角度看，W8A8 有可能使 27B 模型在单张 64GB NPU 上运行。

但这里有两个限制。

第一，实际 W8A8 权重中可能仍有高精度模块和量化元数据，加载后的真实占用需要测量。

第二，需要确认目标 NPU、推理引擎及量化权重能够支持 TP=1，即单卡运行。

因此，我们只能先得出：

**W8A8 在显存容量上具备单卡候选条件，但不能仅凭 27GB 理论值就认定单卡方案可用。**

这里讨论的是昇腾适配的 INT8/W8A8 权重，不应直接把 Qwen 官方 FP8 权重与之等同。

## 四、第三步：根据实际显存需求判断需要几张卡

这是容量规划中第一个真正决定卡数的环节。

### 1. 单卡显存不仅需要存储权重

大模型运行时的 HBM 消耗，主要可以分为：

\[
\begin{aligned}
M_{\text{total}}=\;&M_{\text{weights}}\\
&+M_{\text{runtime}}\\
&+M_{\text{workspace}}\\
&+M_{\text{framework}}
\end{aligned}
\]

其中：

- `weights`：模型权重。
- `runtime`：请求执行期间需要保存的数据和状态。
- `workspace`：中间计算工作空间。
- `framework`：推理框架及底层运行环境开销。

运行时显存之所以会变化，是因为请求进入模型后还要保存推理状态。模型先在 **Prefill** 阶段处理输入 Token，再在 **Decode** 阶段逐步生成 Token。对于完整注意力层，推理服务通常使用 **KV Cache** 保存已处理 Token 的 Key、Value，避免在生成下一个 Token 时重复计算全部历史内容；保存的上下文越长，这类缓存通常就越大。

Qwen3.8-27B 的 64 个语言模型层中，16 层采用完整注意力、48 层采用 Gated DeltaNet。后者采用不同的状态更新与保存机制，因此不能把传统“所有层都是完整注意力”的 KV Cache 显存公式直接套用到整个模型。

同时处理多个请求时，活跃请求还需要分别维护相应状态。上下文变长或同时活跃请求增多，都会改变运行时资源需求；具体占用则取决于模型结构、缓存精度、推理引擎的状态管理和并行配置。

权重相对固定，其他部分则可能随着输入长度、请求数量和运行配置发生变化。

因此，模型服务的显存需求，不能简单用参数量乘以字节数得出。

### 2. 先确定单卡资源预算

沿用上一节的教学假设：**单卡按十进制 64GB 计量，以 85% 为初步显存预算比例**。实际部署时应先读取容量字节数、统一 GB/GiB 单位，再代入计算：

\[
M_{\text{budget}}=64\times0.85=54.4\text{ GB}
\]

这意味着我们希望每张 910B4 上的推理资源使用量，处于约 54.4GB 的预算内。

85% 是初步测试假设，不是昇腾的固定限制，也不代表进程的实际显存使用量始终严格停留在 85%。在 vLLM-Ascend 中，还需要结合引擎的显存分配方式、模型预热峰值、KV Cache 容量及安全余量判断。以下 34GB、12GB 和 24GB 继续采用统一的十进制单位，仅为教学演算。

### 3. 用 W8A8 做一次示例测算

假设模型在某个经过验证的 W8A8 软件环境中，实际权重及基础常驻开销为 34GB。

这是为了演示计算方法而设定的假设，并非 Qwen3.8-27B 在 910B4 上的实测值。

如果预计某项业务的请求运行时数据和其他工作空间还需要 12GB：

\[
34+12=46\text{ GB}
\]

46GB 小于 54.4GB。

从显存容量角度看，单卡满足预算。

但如果业务要求更长上下文和更高并发，使额外运行时需求上升至 24GB：

\[
34+24=58\text{ GB}
\]

58GB 大于 54.4GB。

这就超出了我们设置的单卡目标预算。

此时需要考虑减少服务上下文和活跃请求规模，或者通过模型并行使用多张卡。

这两个示例说明：

**同一个模型、同一种精度、同一张 GPU，可能因为业务负载不同，产生不同的最小卡数需求。**

### 4. 如果显存不够，怎样通过多卡解决？

假设 BF16 模型需要的权重和运行时资源已经超过一张卡。

可以采用 Tensor Parallelism（张量并行，TP），把模型的部分参数与计算拆分到多张 NPU。

例如，TP=2 表示使用两张卡共同运行一个模型实例。

概念上可以理解为：

| 配置 | 每卡 HBM | 总物理 HBM | 权重理论均分参考 |
|---|---:|---:|---:|
| TP=1 | 64GB | 64GB | BF16 约 54GB/卡 |
| TP=2 | 64GB | 128GB | BF16 约 27GB/卡 |
| TP=4 | 64GB | 256GB | BF16 约 13.5GB/卡 |

表中的权重均分只是理想化计算。

实际并不是全部模型参数和运行时数据都严格按照卡数平均分配。部分模块可能复制、部分数据需要通信，NPU 之间还存在集体通信及运行时开销。

因此，不能直接认为两张 64GB 卡就拥有一块可以自由使用的 128GB 大显存。

真正需要验证的是：

**当采用 TP=2 或 TP=4 时，每张卡的最大实际 HBM 占用是否低于单卡可用预算。**

### 5. 显存估算能否直接得到最小卡数？

可以先得到粗略候选，再通过软件验证修正。

例如：

\[
N_{\text{memory}}
\approx
\left\lceil
\frac{M_{\text{estimated}}}
{M_{\text{budget per card}}}
\right\rceil
\]

但这个简化公式只有在资源可以近似分摊时才有参考价值。

对于存在复制数据、非均匀分片、通信缓冲区和固定运行时开销的部署，不能直接把它当成精确计算公式。

更合理的做法，是根据权重估算先选择 TP=1、TP=2 或 TP=4 等候选配置，然后实测每张卡的显存使用和模型初始化情况。

## 五、第四步：确认推理框架实际支持几卡运行

这一环节不能省略。

因为理论上可以放进显存，不代表软件就支持这种部署方式。

### 1. 为什么软件兼容性也会影响卡数？

假设 W8A8 权重在单卡上只需要约 34GB 常驻资源。

从显存来看，64GB HBM 似乎足够。

但如果当前 vLLM-Ascend 版本中，这个模型的相关算子、量化内核或模型执行路径只在 TP=2 下完成验证，那么单卡仍然不能直接视为可用方案。

也就是说：

**有时候使用两张卡，不是因为一张卡的显存一定不够，而是因为当前软件实现和验证范围决定了应优先采用多卡部署。**

### 2. 官方针对 Qwen3.8-27B 给出了什么方案？

vLLM-Ascend 官方文档提供了 Qwen3.8-27B 在 Atlas 800 A2 等昇腾平台上的部署方法。

其中，针对 Atlas 800 A2 的 W8A8 示例使用：

```bash
--tensor-parallel-size 2
```

并配合：

```bash
--quantization ascend
```

以及相应的上下文和并发参数。

文档还提供了 TP=4 的相关部署路径。

但需要注意：

这些示例来自对应昇腾服务器和软件版本的验证环境，不代表任意由两张 910B4 组成的服务器，都可以不经拓扑和通信验证就获得完全相同的结果。

同样，官方使用 TP=2，也不能在数学上证明 TP=1 永远不可行。

它说明的是：**对于当前参考部署，TP=2 是有明确文档依据的起点；TP=1 仍需针对具体版本单独确认。**

### 3. 最小卡数应怎样确定？

此时需要综合两个条件。

**条件 A：显存要求。**

至少多少张卡才能容纳模型及目标请求负载？

**条件 B：软件要求。**

当前模型、权重和推理引擎支持怎样的张量并行配置？

可以把最终候选集合定义为：

\[
\mathcal{N}_{\text{candidate}}
=
\mathcal{N}_{\text{memory}}
\cap
\mathcal{N}_{\text{supported}}
\]

也就是说，从软件支持的卡数组合中，选择能够满足显存要求的候选，再进行性能测试。

对于当前 Qwen3.8-27B W8A8 与 Atlas 800 A2 的参考部署，**TP=2 是比未经验证的 TP=1 更有依据的首轮测试方案**。

但还需要根据服务器 NPU 互联、CANN、vLLM-Ascend 和模型版本，确认实际部署条件。

## 六、第五步：显存够用以后，怎样判断性能需要几张卡？

这一步解决另一个容易混淆的问题：

假设两张 910B4 已经能够运行 Qwen3.8-27B，而且显存还有余量。

是否说明两张卡足以满足全部业务？

不一定。

因为业务还存在延迟和吞吐量要求。

### 1. 先统计真实业务负载

以财务报表智能分析为例，假设通过真实请求采样，得到以下需求：

| 指标 | 示例业务负载 |
|---|---|
| 输入 Token P50 | 4,000 |
| 输入 Token P95 | 16,000 |
| 输出 Token P95 | 2,000 |
| 服务上下文配置 | 32K |
| 高峰请求到达速率 | 2 次/秒 |
| P95 完整响应时间目标 | 20 秒 |
| 请求类型 | 主要为文本分析 |

这些数字是为了说明容量规划方法而构造的业务假设，不是服务器实测数据。

有了这些指标后，才能设计有意义的压测。

### 2. 首先测试 TP=2 的模型实例

假设使用两张 910B4，组成一个 TP=2 模型实例。

测试时应关注：

- TTFT：首 Token 延迟。
- TPOT：后续 Token 生成耗时。
- 请求吞吐量：每秒完成多少请求。
- 输出吞吐量：每秒生成多少 Token。
- P95 完整响应时间。
- 每张 NPU 的显存峰值。
- 错误率和资源稳定性。

如果测试结果已经满足高峰请求速率和 P95 延迟目标，那么从业务性能来看，就没有必要为了提高模型并行度而增加更多卡。

如果不满足，需要进一步判断究竟是单次计算慢、请求排队严重，还是显存限制了可同时处理的请求。

不同原因对应不同扩容方式。

### 3. TP=4 是否一定比 TP=2 更好？

不一定。

TP=4 把一个模型实例的计算进一步分配到四张卡。

这可能改善单实例的资源容量和某些计算环节的速度，但也会增加跨 NPU 通信。

对于某些请求规模，TP=4 可能带来性能收益。

对于另一些场景，增加并行度的通信成本可能抵消一部分收益。

因此，不能简单认为：

> 两张卡生成 40 Token/s，四张卡就一定生成 80 Token/s。

这需要通过相同输入输出条件下的实际测试进行比较。

## 七、第六步：增加卡数，到底应该使用模型并行还是多副本？

这是完整容量规划中最重要的架构决策之一。

假设已经有四张 910B4。

至少存在两种不同的部署方案。

### 方案 A：四张卡共同运行一个模型

采用：

```text
TP = 4
模型实例数 = 1
总卡数 = 4
```

四张卡共同执行同一份模型。

这种方式通常优先用于：

- 单实例显存需求较高。
- 需要更大的单实例资源容量。
- 单请求计算性能需要进一步优化。
- 软件实现适合 TP=4。

### 方案 B：两张卡运行一个模型，部署两个副本

采用：

```text
TP = 2
模型实例数 = 2
总卡数 = 4
```

每两张卡组成一个独立模型实例。

两个实例都能够接收业务请求，前面可以通过网关或负载均衡分发流量。

这种方式通常优先用于：

- TP=2 已经满足单请求性能。
- 主要瓶颈是请求量和排队。
- 需要提高整体服务吞吐量。
- 需要一定程度的实例级故障隔离。

### 两种方案有何不同？

| 对比 | TP=4，单实例 | TP=2，双实例 |
|---|---|---|
| 总卡数 | 4 | 4 |
| 模型实例数 | 1 | 2 |
| 每实例卡数 | 4 | 2 |
| 单实例可用资源 | 更多 | 相对较少 |
| 单请求速度 | 可能改善，需实测 | 维持 TP=2 的能力 |
| 整体请求吞吐 | 取决于并行效率 | 更适合横向扩展的候选 |
| 故障隔离 | 单实例故障影响整个服务 | 两实例可互为一定程度的冗余 |

因此：

**如果单个请求性能或资源容量不够，优先考虑增大 TP；如果单实例性能已经达标，但请求量太大，优先考虑增加实例副本。**

不过，这不是绝对规则。

最终仍要比较两种方案在相同总卡数下的吞吐量、P95 延迟、显存以及稳定性。

---

## 八、第七步：怎样计算整个业务最终需要多少张卡？

现在我们可以建立一个更完整的容量规划公式。

\[
\boxed{
N_{\text{total}}
=
N_{\text{cards per instance}}
\times
N_{\text{instances}}
}
\]

其中：

\(N_{\text{cards per instance}}\) 表示每个模型实例使用多少张 910B4。

它由模型显存、软件兼容性和单实例性能共同决定。

\(N_{\text{instances}}\) 表示需要部署多少个独立实例。

它由高峰流量、实例吞吐能力、响应时间要求及冗余需求决定。

### 1. 首先确定每个实例需要多少张卡

假设实测结果表明：

- TP=1：当前软件组合没有完成兼容性验证。
- TP=2：模型成功运行，32K 上下文满足要求。
- TP=4：能够运行，但目标业务下单实例性能收益不明显。

那么可以初步选择：

\[
N_{\text{cards per instance}}=2
\]

这是一个假设性的测试结论，不是本文已经获得的 910B4 实测结果。

### 2. 再确定需要多少模型实例

假设 TP=2 模型实例在满足 P95 延迟要求时，能够持续处理每秒 0.7 个请求。

业务高峰要求处理每秒 2 个请求。

那么仅按吞吐量计算：

\[
N_{\text{instances}}
=
\left\lceil\frac{2}{0.7}\right\rceil
=3
\]

如果每个实例使用两张卡：

\[
N_{\text{total}}=2\times3=6
\]

得到的初步结果是 6 张 910B4。

但这是基于假设吞吐量进行的计算演示，并不是 Qwen3.8-27B 的实际性能结论。

而且这里还没有额外考虑冗余、故障后的流量承接和业务增长余量。

实际配置还需要进行整体压测，确认多个实例在目标到达速率下仍然能够达到 P95 响应时间要求。

### 3. 如果要求实例故障后业务仍正常运行怎么办？

还需要把可用性纳入计算。

例如，三个 TP=2 模型实例可以满足正常高峰负载，但其中一个实例故障后，剩余两个实例能否继续满足性能目标？

如果不能，就需要增加实例冗余或者降低故障期间的服务目标。

因此，生产容量规划不只是满足正常状态下的业务流量，还需要定义允许的故障场景。

对于多卡模型并行，一个实例内部任何关键 NPU 或通信链路出现故障，都可能影响整个模型实例。因此，实例冗余不能由单个 TP 组内的多卡直接替代。

## 九、将整个判断过程整理成决策流程

现在，我们可以形成一套实际可执行的决策流程。

<escape>
业务需求与目标模型
        │
        ▼
确定模型精度（BF16 / W8A8）
        │
        ▼
估算权重和运行时显存
        │
        ▼
单张 64GB HBM 能否承载？
        ├── 否 → 评估 TP=2 / TP=4
        └── 是 → 验证 TP=1 的软件兼容性
        │
        ▼
选择已支持且显存充足的卡数组合
        │
        ▼
压测单实例性能
        │
        ▼
达到单请求延迟要求吗？
        ├── 否 → 比较更高 TP 和推理优化
        └── 是 → 进入吞吐容量评估
        │
        ▼
能够承载业务高峰流量吗？
        ├── 否 → 增加独立模型实例
        └── 是 → 评估余量和冗余
        │
        ▼
得到最终卡数
</escape>

需要强调，这不是简单地从 TP=1、TP=2、TP=4 一直往上增加卡数。

每一步都必须明确增加卡数的目的。

如果只是权重显存不足，重点是模型分片与量化。

如果单请求计算慢，重点是并行效率和计算性能。

如果请求排队严重，重点是实例吞吐量与横向扩展。

如果需要高可用，重点是独立实例和故障隔离。

这些问题虽然都可能通过增加 NPU 数量解决，但对应的最佳架构未必相同。

## 十、回到 Qwen3.8-27B：目前可以得出什么结论？

我们已经知道以下条件：

| 项目 | 当前结论 |
|---|---|
| 目标模型 | Qwen3.8-27B |
| 单卡硬件 | 昇腾 910B4 |
| 单卡显存 | 标称 64GB HBM；计算需统一 GB/GiB 口径 |
| BF16 权重 | 理论约 54GB |
| W8A8 权重 | 主要参数理论约 27GB，实际需验证 |
| 原生上下文 | 256K |
| 昇腾 W8A8 官方参考部署 | Atlas 800 A2 上提供 TP=2 示例 |
| 单卡 TP=1 | 仍需核对具体软件版本和算子支持 |
| TP=2 性能 | 待实测 |
| TP=4 性能 | 待实测 |
| 最大业务并发 | 待业务负载与压测确定 |

由此可以形成明确的下一步判断。

**第一，不建议将 BF16 单卡作为主要方案。**

权重已占用单卡容量的较大比例，还需要为运行状态和工作区保留空间；实际余量须以设备报告和推理服务测量结果确认。

**第二，W8A8 具有较好的权重资源优势。**

但不能只根据 27GB 理论值认定单卡可以稳定部署。

**第三，优先评估 TP=2 的实际部署方案。**

这是目前更有官方适配依据的起点，尤其应核对 Atlas 800 A2 参考部署与实际 910B4 服务器的硬件连接、通信和软件环境是否一致。

**第四，以业务需求决定是否继续采用 TP=4。**

如果 TP=2 的显存、上下文容量或单实例延迟不能满足要求，再评估 TP=4。

**第五，如果 TP=2 已满足单请求要求，但高峰吞吐不足，应优先比较部署多个 TP=2 副本的方案。**

例如，四张卡应当组成一个 TP=4 模型，还是两个 TP=2 模型实例，取决于实际性能测试，而不是单纯比较卡数。

因此，我们现在不能直接宣布 Qwen3.8-27B 最终需要两张、四张还是八张 910B4。

但已经能够明确卡数应该怎样推导出来。

## 十一、总结：决定卡数的不是模型大小，而是完整的服务要求

本篇文章围绕一个确定条件展开：

**每张昇腾 910B4 标称具有 64GB HBM，我们要在统一容量单位、理解运行时资源的基础上，确定 Qwen3.8-27B 需要多少张卡。**

完整的判断过程是：

**第一步：通过模型参数与权重精度，得到基础显存需求。**

**第二步：结合上下文长度、运行时资源与并发需求，判断单个模型实例需要多少 HBM。**

**第三步：确认当前推理框架、量化模型和 NPU 硬件实际支持的张量并行配置。**

**第四步：在可运行的卡数组合上进行性能测试，判断单实例能否达到业务响应时间要求。**

**第五步：根据高峰请求量和单实例实际吞吐能力，确定需要部署多少模型实例。**

**第六步：考虑故障冗余和业务增长，形成最终服务器配置。**

由此得到两个关键公式。

首先，单个模型实例需要多少张卡，要结合显存、兼容性和性能共同确定：

\[
N_{\text{TP}}
=
f(\text{模型、精度、显存、软件、单实例性能})
\]

然后，整个业务需要多少张卡：

\[
\boxed{
N_{\text{total}}
=
N_{\text{TP}}\times N_{\text{instances}}
}
\]

这里的实例数，需要通过业务请求速率、实测吞吐量、响应目标和冗余要求确定。

**模型权重决定能否装下；软件实现决定能否运行；单实例性能决定每个模型需要几张卡；业务吞吐与可靠性要求决定最终需要部署多少个模型实例。**

这才是从模型和业务需求推导服务器配置的完整过程。

完成容量规划之后，才能进入后续的模型下载、环境安装、模型加载、推理执行和 HTTP 服务部署。
