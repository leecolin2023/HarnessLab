# 什么是 Agent，为什么需要 Agent Runtime？

> **学习入口**：本篇保留为 Agent / Runtime 基础原理文章。完整学习路线见 [Agent Runtime 学习路线](./LEARNING_PATH.md)，job-agent 项目解读见 [job-agent 项目架构与核心代码解读](./job-agent/01-project-architecture-and-code.md)。运行代码、Docker、测试和 CI 已迁入独立的 [job-agent 工程仓库](https://github.com/leecolin2023/job-agent)。

## 一、为什么需要 Agent？

### 1. 大语言模型已经能够回答问题，为什么还需要 Agent？

假设我们正在开发一个银行制度审查工具。

用户提出一个问题：

> 授信业务的审批权限是如何规定的？

我们可以先从知识库检索相关制度，再把检索结果交给大语言模型，让它生成回答。

~~~text
用户提出问题
    ↓
检索相关制度
    ↓
大语言模型阅读资料
    ↓
生成回答
~~~

如果用户只是想了解某项制度，这样的系统可能已经足够。

但现在，用户提出了一个不同的要求：

> 检查现行授信管理制度，找出不同制度之间可能存在的规定冲突，并生成一份附有原文依据的审查报告。

这不再是一个简单的知识问答，而是一项需要实际完成的工作任务。

系统不仅要理解制度，还需要找到相关文件、检查修订关系、比较具体条款、核对依据，最后形成审查报告。

**用户希望获得的不再只是一段回答，而是一项工作已经完成的结果。**

### 2. 为什么不能直接让大模型一次完成这项任务？

最直接的办法，是把制度文件全部提供给大模型，让它一次性分析并生成报告。

如果资料数量少、证据齐全，任务又比较简单，这种方式可能奏效。

但真实的制度审查往往没有这么直接。

例如，模型阅读制度 A 后，发现它引用了制度 B；读取制度 B 后，又发现 B 已经由制度 C 修订。

此时，系统需要继续寻找制度 C，并检查其生效日期和适用范围。

问题在于，我们无法保证任务开始时就已经提供了全部必要资料，也不一定能够预先确定完整的执行步骤。

仅仅让模型生成一段文字，还不足以完成这些实际操作。

当然，传统程序也可以完成工作任务。如果检索、判断和处理规则都已经明确，固定工作流通常更合适。

但对于执行过程中需要不断理解新信息、判断下一步行动的任务，我们希望模型能够参与整个执行过程。

### 3. 我们真正希望 Agent 做到什么？

我们希望用户只需要提出目标：

> 检查授信制度冲突，并生成审查报告。

系统就能够围绕这个目标，开展必要的工作：

~~~text
用户提出工作目标
        ↓
理解需要完成什么
        ↓
开展实际工作
        ↓
根据结果继续推进
        ↓
完成任务并交付成果
~~~

这里最重要的变化是：

**从利用模型回答问题，扩展为利用模型推动一项真实工作任务的完成。**

模型不再仅仅负责生成最终答案，而是参与任务执行过程中的判断，并通过外部工具与真实环境交互。

这正是引入 Agent 的重要动机。

接下来要解决的问题是：为了让 Agent 真正完成一项工作，我们需要让它具备哪些能力？

## 二、为了完成工作任务，Agent 需要具备哪些能力？

上一章提出了一个目标：用户不只想得到回答，还希望 Agent 能够围绕目标开展工作。接下来先不考虑多 Agent、复杂规划或审批系统，而是从**最基本的执行过程**开始：一个 Agent 怎样从用户提出的目标出发，完成一次真实操作，并决定接下来做什么？

### 1. 最基本的能力：模型决策 → 工具执行 → 反馈 → 继续或结束

假设用户提出：

> 查一下制度 B 是否已经被其他制度修订，并告诉我依据。

用户给出的是目标，没有逐一告诉系统要调用什么工具、拿到结果后怎样判断。

**第一步：模型决策——现在应该做什么？**

模型收到用户目标、当前已知信息和可以使用的工具说明，判断下一步行动。

如果只有制度名称，没有文档内容，它可能选择先调用搜索工具：

~~~json
{
  "name": "search_policy",
  "arguments": {"query": "制度 B 修订"}
}
~~~

这个调用请求表示模型希望执行的操作。模型并没有亲自访问制度库；它只产生了行动意图。

**第二步：工具执行——把决策变成实际操作。**

Agent 的运行程序接收调用请求，找到对应工具，将参数交给工具执行，然后接收执行结果。

例如，`search_policy` 实际查询了制度库，返回：

~~~json
{
  "status": "success",
  "documents": [
    {"id": "C", "title": "关于修订制度 B 的通知"}
  ]
}
~~~

这一步不能由模型“描述自己完成了检索”来替代。**工具必须真的执行，才算与外部环境发生了交互。**

**第三步：反馈——让模型知道刚才发生了什么。**

执行结果返回后，运行程序把相关信息提供给模型。

模型原来只知道“需要核实 B 是否被修订”，现在知道“搜索到了制度 C”。这项新信息会改变下一步的判断。

模型可能继续调用 `read_document` 读取 C，检查其修订范围和生效日期。它也可能发现没有找到足够证据，需要再次检索。

因此，**反馈不是把日志保存起来就结束，而是让真实结果进入后续决策过程。**

**第四步：继续或结束——本轮工作还需要进行吗？**

如果检索结果不足以回答问题，模型可以继续提出工具调用；如果已经取得足够资料，则可以生成回答。

这里存在两条基本路径：

- **继续**：模型提出新的工具调用，程序再次执行并反馈。
- **结束**：模型生成最终答复，运行程序结束这次任务或当前轮次。

如果工具失败、模型调用报错、用户取消或达到执行限制，运行程序还需要以相应状态中断，而不是无限循环。

到这里，我们已经得到最小的**工具调用式 Agent 工作过程**：

~~~text
用户提出目标
     ↓
准备当前信息与可用工具
     ↓
  ┌─→ 模型决策 ─────────→ 生成最终回答 ─→ 结束
  │       │
  │       │ 请求工具
  │       ↓
  │    工具执行
  │       ↓
  │    返回反馈
  │       ↓
  └── 基于新信息继续判断

发生错误、取消或达到运行限制时，也可能中断。
~~~

这张图中最重要的不是步骤数量，而是：**下一次行动可以依据上一次操作取得的新信息而改变。** 模型有时可以直接回答，不一定每次都调用工具；有时需要多轮调用工具，才能完成同一个目标。

### 2. 为什么这就形成了 Agent Loop？

传统固定程序可以事先写好“先查 A，再查 B，最后输出”；而在上面的例子中，下一步取决于实际检索到了什么。

运行程序需要反复完成：

1. 准备当前上下文和可用工具。
2. 调用模型，让模型生成回答或工具调用。
3. 如果存在工具调用，执行并收集返回结果。
4. 将结果加入可供下一次决策使用的信息。
5. 继续下一次模型调用，或根据模型响应及运行限制结束。

这个反复运行的过程就是 **Agent Loop**。

~~~python
# 只为解释机制的伪代码，不是某个 SDK 的完整实现
while True:
    response = call_model(context, tools)

    if response.has_tool_calls:
        results = execute_tools(response.tool_calls)
        context = append_tool_results(context, results)
        continue

    if response.has_final_answer:
        return response.final_answer

    if response.failed_or_stopped:
        return handle_termination(response)
~~~

这段代码说明两件事：

- **模型**决定是否请求执行操作、选择什么操作。
- **运行程序**负责调用模型、调度工具、收集反馈，并维持循环的运行。

它们相互配合，但不是同一个东西。模型输出工具请求，不等于工具已经执行；模型输出最终回答，也不自动证明业务目标已经正确完成。

**这就是 Agent 最基本的执行能力。** 对于比较简单、可以通过少量工具调用完成的任务，理解这条循环已经足够。下一章再专门讨论组织循环的程序层为什么叫 Agent Runtime。

### 3. 任务变复杂之后，还需要增加什么能力？

现在把目标改成：

> 检查现行授信管理制度，找出不同制度之间可能存在的规定冲突，并生成附有原文依据的审查报告。

这项任务不只需要查找一个文件，还可能涉及几十份制度、多个修订版本、跨文件比较和报告交付。

**基本 Agent Loop 仍然是执行基础，但仅靠反复“模型决策—工具执行—反馈”，不一定足以可靠地组织整个工作。** 因而可以根据任务需要增加下列机制。

#### 3.1 显式任务规划：把工作目标分解为可管理的步骤

对于复杂任务，如果始终只决定“下一步做什么”，系统可能反复检索、遗漏某类制度，或者不知道已经完成了哪些部分。

这时可以先形成一份明确的任务计划：

~~~text
目标：生成制度冲突审查报告

1. 明确审查范围
2. 收集现行制度及修订关系
3. 识别需要比较的条款
4. 逐项检查可能的冲突
5. 核对原文证据和有效版本
6. 生成报告并检查完整性
~~~

**显式规划**让系统有一个可以检查、跟踪和调整的工作安排。计划可以由模型生成，也可以由业务程序提供固定骨架，或者由独立的 Planner 组件管理。

注意区别：模型直接选择“先查制度 B”属于基本循环中的**行动决策**；模型另外生成、保存并维护一份多步骤任务计划，才属于这里讨论的**显式规划机制**。

#### 3.2 计划修订：执行过程中发现新情况，怎样改变原计划？

假设计划原本安排比较制度 A 和 B，但读取 B 后发现它已由 C 修订。

最基本的 Agent Loop 可以让模型下一步先去读取 C；但如果任务涉及几十个依赖步骤，仅改变一次工具调用还不够。

系统可能需要更新原计划：

~~~text
原计划：比较制度 A 与制度 B
    ↓
发现：B 已由 C 修订
    ↓
修订计划：先核实 C 的生效与适用范围
    ↓
更新待检查对象：A 与现行有效条款
    ↓
继续执行
~~~

因此，**基于反馈选择下一步**是基本能力；**维护整份计划及其依赖关系、完成状态和修订记录**是复杂任务中的增强能力。

#### 3.3 业务结果验证：怎样知道真的完成了用户目标？

基本循环中，模型可以生成最终回答，Runtime 也可以记录本轮已经正常结束。但**运行结束不等于任务完成**。

例如报告文件已经生成，却可能遗漏修订版本、引用了无效制度，或者把不同适用范围的规定误判为冲突。

这时需要在交付前设置独立检查：

- 文件是否真实存在，格式是否符合要求；
- 每项结论能否定位到有效制度原文；
- 计划中的审查范围是否得到覆盖；
- 对证据不足或争议较大的判断，是否需要人工复核。

验证可以由规则程序、另一次模型调用、专门的 Checker 或人工完成。未通过时，可以给 Agent 提供具体错误，让它修正相应部分。

因此需要区分：**模型生成答案、工具执行成功、业务验收通过**是三个不同层次的结果。

#### 3.4 人工审批与权限控制：Agent 能决定，不代表可以擅自操作

读取制度和修改正式制度不是同一风险等级。

例如，Agent 在审查过程中认为需要修改某项制度。它可以**提出修改建议**，但不应直接拥有修改正式制度的全部权限。

~~~text
模型请求修改制度
       ↓
工具权限与参数检查
       ↓
需要审批？
   ├── 是 → 人工审核 → 允许 / 拒绝
   └── 否 → 执行已授权操作
       ↓
记录操作结果并反馈给 Agent
~~~

人工审批主要用于具有较高风险或不可逆副作用的动作；只读任务不一定需要逐项审批。权限限制应由可靠的执行环境、工具策略和业务系统实施，不能只依靠提示词要求模型“不要越权”。

更长的任务还可能需要持久状态、Checkpoint、超时与重试、成本预算、多个 Agent 分工等机制。这些能力会在后面的章节按需展开。

### 4. 基本执行循环与复杂任务增强机制是什么关系？

现在可以把整个系统理解为**执行核心加上按需增强的控制层**：

~~~text
                      用户工作目标
                           ↓
              ┌──────────────────────┐
              │ 复杂任务控制（按需）  │
              │ 显式规划 / 计划修订  │
              │ 业务验证 / 人工审批  │
              └──────────┬───────────┘
                         ↓
            ┌────────────────────────┐
            │     基本 Agent Loop    │
            │                        │
            │ 模型决策 → 工具执行     │
            │       ↑       ↓        │
            │    继续判断 ← 反馈      │
            │       ↓                │
            │   回答 / 结束 / 中断   │
            └────────────────────────┘
                         ↓
                   结果与运行记录
~~~

这里的“控制层”只是便于理解的逻辑分层，不要求所有系统都部署成两个独立服务。有的项目将规划和校验写在应用代码里，有的框架以插件或工具提供，有的简单任务完全不需要这些扩展。

**所以应该先理解最基本的 Agent Loop，再根据任务为什么无法可靠完成，逐步引入规划、计划修订、业务验证和人工审批。** 这才是从最小 Agent 走向复杂工作型 Agent 的自然演进过程。

> **代码对照**：[job-agent 当前的基本执行循环由哪些组件提供，哪些复杂任务机制尚未实现？](./job-agent/01-project-architecture-and-code.md) 项目解读会沿着上述两层结构分别分析，避免把“SDK 提供了 Agent Loop”直接写成“应用已经拥有规划和业务验证能力”。

## 三、什么是 Agent Runtime？

### 1. 为什么有了 Agent Loop，还需要 Runtime？

在刚才的 Agent Loop 中，我们已经看到：

模型需要被调用，工具调用请求需要被接收，工具需要真正执行，执行结果又需要交给下一轮模型。

那么：

谁负责调用模型？

谁负责接收和执行工具请求？

谁负责把执行结果送回模型？

谁负责判断是否继续运行？

这些工作需要一个实际的程序层进行组织。

这个程序层就是 Agent Runtime。

**Agent Runtime 是负责组织模型调用、工具执行、环境反馈及必要的会话状态，使 Agent Loop 得以持续运行的执行层。它提供执行循环，并不自动保证具有显式任务规划、业务验证或任务成功判定。**

### 2. Runtime 实际做了什么？

仍然以制度审查为例。

当模型决定读取制度 B 时，Runtime 需要：

1. 接收模型输出的 read_document 工具调用请求。
2. 检查工具是否存在、参数是否合法、当前操作是否获得授权。
3. 调用实际的文件读取工具。
4. 接收工具返回的文件内容或错误信息。
5. 更新任务记录，并为下一轮模型推理准备必要信息。
6. 依据模型响应与控制策略继续调用模型，或者暂停、取消或结束当前运行；业务目标是否完成需另行判断。

于是，模型和工具能够形成连续的执行过程。

最小的 Agent Runtime 可以只是一个循环：

~~~python
state = initialize_task(user_request)

while not state.finished:
    context = build_context(state)

    response = call_model(context, tools)

    if response.has_tool_calls:
        results = execute_authorized_tools(
            response.tool_calls
        )
        state = update_state(state, results)

    elif response.has_final_answer:
        state = handle_final_answer(state, response)
~~~

这是简化的伪代码，实际运行还需要处理执行失败、超时和终止条件。

它表达了 Runtime 的核心职责：

**负责让模型能够反复决策，让工具调用真正执行，让执行结果能够影响下一轮判断。**

### 3. Agent 与 Agent Runtime 有什么区别？

Agent 是由模型、工具和运行控制等机制共同构成的任务系统。

Agent Runtime 则强调使这个系统持续运行的执行机制。

模型可以负责理解目标、规划任务和选择行动。

工具负责与文件、数据库或业务系统交互。

Runtime 负责连接模型和工具，协调执行过程，并管理任务状态。

因此，Agent 和 Runtime 不一定是两个独立的软件服务。

最简单的 Agent 可以通过几十行循环代码运行；复杂的 Agent 则可能使用专门的 Runtime 框架。

## 四、为什么任务变长之后，还需要管理 Context 和 State？

前面介绍的最小 Agent Runtime 已经能够完成简单任务。

但如果制度审查涉及数百份文件、几十轮工具调用，就会遇到一个问题：

**每次调用模型，都需要把之前所有信息重新输入吗？**

### 1. 什么是 Context？

Context 是当前一次模型调用时，模型能够看到的信息。

例如：

~~~text
任务目标：
检查授信制度冲突。

当前进度：
已检查制度 A、B。

主要发现：
B 已由 C 修订。

下一步问题：
制度 C 是否适用于目标机构？
~~~

模型需要这些信息，才能判断下一步应该做什么。

但它不一定需要重新读取前面所有文件的完整内容。

如果每轮都带上全部历史，随着任务持续执行，上下文会越来越长，增加模型调用成本，并可能超过上下文窗口的限制。

因此，Runtime 需要为每轮模型调用组织必要的信息。

### 2. 什么是 State？

假设我们不再把所有信息放入当前 Context，那么之前的任务进度保存在哪里？

这就需要 State。

State 是系统维护的任务状态，例如：

~~~text
task_id: review_001

目标：
检查授信制度冲突

已检查：
- 制度 A
- 制度 B

待检查：
- 制度 C

已发现问题：
- 制度 B 已失效

任务状态：
running
~~~

State 可以保存已经完成的动作、待处理事项、收集到的证据及其存储位置等。

Runtime 根据 State 和外部资料，为当前模型调用组织 Context。

~~~text
            State
        （保存任务状态）
               ↓
       提取当前必要信息
               ↓
            Context
               ↓
           模型推理
               ↓
           工具执行
               ↓
          更新 State
~~~

可以简单理解为：

**State 保存任务进行到了哪里；Context 决定本轮模型需要看到什么。**

二者可能重叠，但并不相同。

### 3. Session 又是什么？

假设同一个用户同时发起两个审查任务：

一个检查授信审批制度，另一个检查贷后管理制度。

两项任务使用相同的模型和工具，但必须保留各自独立的历史与进度。

Session 通常用于组织一条连续交互的上下文。

不同框架还可能使用 Thread、Run、Task 等概念区分会话、任务和具体执行过程。

这些名称并不完全统一，重点是理解：Runtime 需要能够识别不同任务，并找到它们对应的状态与历史信息。

---

## 五、Agent 执行中断后，怎样继续工作？

假设 Agent 已经检查了 80 份制度，服务却突然重启。

如果进度只保存在程序内存中，就可能丢失此前完成的工作。

因此，长任务还需要考虑状态持久化与恢复。

### 1. 什么是 Checkpoint？

Checkpoint 是在任务执行过程中保存的可恢复检查点。

例如：

~~~text
Checkpoint 1：
完成制度 A 审查

Checkpoint 2：
确认制度 B 已被修订

Checkpoint 3：
准备核对制度 C 的适用范围
~~~

当服务重启时，具备相应恢复协议的应用或 Runtime 可以根据检查点恢复对应状态。**但 Session 日志持久化、Runtime 内部持久化屏障和可从某个业务步骤继续运行的 Checkpoint 并不等价**；能恢复哪些内容，要看实际保存了什么，以及外部副作用是否得到处理。

### 2. 恢复后能不能直接重试？

不一定。

例如，Agent 已经成功向业务系统写入审查报告，但服务在记录成功状态之前崩溃。

如果恢复后直接重试，可能造成重复提交。

因此：

- 对于只读检索，通常较容易重试。
- 对于修改文件、更新数据库、发送邮件等有副作用的操作，需要确认此前是否已经执行。
- 必要时使用幂等控制或补偿机制，避免重复操作造成问题。

**Checkpoint 解决的是如何恢复任务进度；幂等和补偿机制解决的是如何安全处理已经发生的外部操作。**

---

## 六、Agent 可以自主执行任务，为什么还需要权限与安全控制？

Agent 可以根据任务目标选择工具，但不代表它可以随意使用所有工具。

假设制度审查系统提供：

~~~text
search_policy    检索制度
read_document    读取制度
write_report     生成报告
update_policy    修改正式制度
send_email       发送邮件
~~~

读取制度与修改正式制度显然具有不同风险。

即使模型认为应该调用 update_policy，**实际执行前也必须经过有效的权限判断与必要的人工审批**。这些控制可以由 Runtime 插件、业务系统或外部执行环境共同承担，不能假定任何默认 Profile 都自动具备完整授权机制。

~~~text
模型提出工具调用
        ↓
检查工具与参数
        ↓
检查用户权限
        ↓
必要时人工确认
        ↓
执行实际操作
        ↓
记录执行结果
~~~

对于文件系统、命令执行或网络访问，还可以使用沙箱限制 Agent 的活动范围。

同时，Agent 读取到的外部文件和工具结果只是任务数据，不能自动成为更高优先级的系统指令。

**让 Agent 具备自主行动能力，不等于把全部执行权限交给模型。**

**执行环境和授权机制必须确保行动发生在经过授权的范围之内。** Runtime 可以参与强制控制，但是否真正执行授权检查，取决于具体工具、插件、策略及外部业务系统的配置。

---

## 七、如何让 Agent 的结果更可靠？

第二章已经说明，复杂工作需要根据业务目标验证结果；但这类验证**不能仅凭 Agent Loop 正常结束来推定已经实现**。

在真实系统中，还需要进一步区分：

**工具执行成功，不等于业务任务成功。**

例如，报告生成工具返回：

~~~json
{
  "status": "success",
  "file": "review_report.docx"
}
~~~

这只能证明文件生成操作成功。

报告引用的制度是否有效、条款是否准确、结论是否成立，还需要进一步核实。

因此，可以组合不同层次的检查机制。

### 1. 确定性检查

例如：

- 报告文件是否生成；
- 引用的文件编号是否存在；
- 条款能否定位到原文；
- 报告是否符合规定格式。

这些检查适合由程序完成。

### 2. 语义判断

例如：

两项制度是否真正存在冲突，还是只是适用机构、业务范围或生效时间不同？

这可能需要模型进行进一步分析。

对于无法可靠自动判定的高风险结论，仍然需要人工复核。

### 3. 验证反馈

如果校验发现问题，可以将结果重新提供给 Agent，让它补充查证或修复报告。

这实际上是在 Agent Loop 中加入一项验证机制。

同时，Runtime 需要设置最大执行步数、超时、成本预算等边界，防止 Agent 因不断尝试修正而陷入无效循环。

无法确认的任务可以暂停或交由人工处理，不必强行要求模型给出确定结论。

---

## 八、什么时候应该使用 Agent？

理解 Agent 的能力之后，还需要判断哪些工作真正适合它。

### 1. 任务步骤完全确定：使用传统程序或工作流

例如：

~~~text
上传财务报表
    ↓
OCR 识别
    ↓
字段提取
    ↓
科目映射
    ↓
公式计算
    ↓
生成报告
~~~

如果步骤和处理规则已经明确，就没有必要让模型反复决定下一步。

其中仍然可以使用大模型，但总体流程由程序控制。

### 2. 一次检索即可回答：使用普通 RAG

例如，用户询问某项授信业务的审批权限。

系统检索制度条款，再让模型生成回答。

如果资料完整，这种固定检索与生成流程即可满足要求。

### 3. 需要动态追查资料：考虑使用 Agent

例如，检查制度冲突时，系统需要根据新发现的文件引用、修订记录和适用范围，动态决定下一步查询。

这种任务更适合让模型在执行过程中进行决策。

### 4. 能不能只在部分步骤使用 Agent？

可以。

例如：

~~~text
固定流程：确定审查范围
        ↓
Agent：动态追查制度关系
        ↓
固定流程：整理证据
        ↓
模型：分析制度冲突
        ↓
固定流程：校验并生成报告
        ↓
必要时人工复核
~~~

对于能够明确规定的步骤，继续使用传统程序。

对于需要根据新信息作出语义判断的步骤，再考虑引入 Agent。

**Agent 不是为了替代所有工作流，而是为了处理那些难以完全预先确定执行路径的工作。**

---

## 九、回到最初的问题

我们最开始希望做的，是让大语言模型不再局限于回答问题，而是能够完成一项真实工作任务。

从最小 Agent Loop 开始，系统需要让模型能够基于当前信息选择行动，让工具执行并把结果反馈给下一轮；模型也可以直接回答而不调用工具。

当任务变得复杂时，再按需增加显式计划、计划修订、业务结果验证、人工审核和任务恢复等能力。它们可以与 Agent Loop 配合，但**不应被理解为每个 Runtime 默认具备且每轮必经的五个步骤**。

而 Agent Runtime 负责组织这个循环，让模型决策、工具执行、执行反馈和任务状态更新真正发生。

随着任务执行时间增长，Runtime 又需要进一步处理上下文管理、状态持久化、中断恢复、权限控制和结果验证等问题。

因此，整个演进过程可以概括为：

**从回答问题到完成工作任务，我们引入 Agent；为了让 Agent 持续决策和行动，我们需要 Agent Loop；为了让这个循环真正运行起来，我们需要 Agent Runtime；为了让任务长期可靠执行，我们还需要上下文、状态、恢复、权限与验证等工程机制。**
