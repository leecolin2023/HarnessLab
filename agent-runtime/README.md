# 什么是 Agent，为什么需要 Agent Runtime？

> **学习入口**：本篇保留为 Agent / Runtime 基础原理文章。完整学习路线见 [Agent Runtime 学习路线](./LEARNING_PATH.md)，job-agent 项目解读见 [job-agent 项目架构与核心代码解读](./job-agent/01-project-architecture-and-code.md)。运行代码、Docker、测试和 CI 已迁入独立的 [job-agent 工程仓库](https://github.com/leecolin2023/job-agent)。

## 一、为什么需要 Agent？

### 1. 大语言模型已经能够回答问题，为什么还需要 Agent？

假设我们正在开发一个银行制度审查工具。

用户提出一个问题：

> 授信业务的审批权限是如何规定的？

我们可以先从知识库检索相关制度，再把检索结果交给大语言模型，让它生成回答。

~~~text
用户提出问题
    ↓
检索相关制度
    ↓
大语言模型阅读资料
    ↓
生成回答
~~~

如果用户只是想了解某项制度，这样的系统可能已经足够。

但现在，用户提出了一个不同的要求：

> 检查现行授信管理制度，找出不同制度之间可能存在的规定冲突，并生成一份附有原文依据的审查报告。

这不再是一个简单的知识问答，而是一项需要实际完成的工作任务。

系统不仅要理解制度，还需要找到相关文件、检查修订关系、比较具体条款、核对依据，最后形成审查报告。

**用户希望获得的不再只是一段回答，而是一项工作已经完成的结果。**

### 2. 为什么不能直接让大模型一次完成这项任务？

最直接的办法，是把制度文件全部提供给大模型，让它一次性分析并生成报告。

如果资料数量少、证据齐全，任务又比较简单，这种方式可能奏效。

但真实的制度审查往往没有这么直接。

例如，模型阅读制度 A 后，发现它引用了制度 B；读取制度 B 后，又发现 B 已经由制度 C 修订。

此时，系统需要继续寻找制度 C，并检查其生效日期和适用范围。

问题在于，我们无法保证任务开始时就已经提供了全部必要资料，也不一定能够预先确定完整的执行步骤。

仅仅让模型生成一段文字，还不足以完成这些实际操作。

当然，传统程序也可以完成工作任务。如果检索、判断和处理规则都已经明确，固定工作流通常更合适。

但对于执行过程中需要不断理解新信息、判断下一步行动的任务，我们希望模型能够参与整个执行过程。

### 3. 我们真正希望 Agent 做到什么？

我们希望用户只需要提出目标：

> 检查授信制度冲突，并生成审查报告。

系统就能够围绕这个目标，开展必要的工作：

~~~text
用户提出工作目标
        ↓
理解需要完成什么
        ↓
开展实际工作
        ↓
根据结果继续推进
        ↓
完成任务并交付成果
~~~

这里最重要的变化是：

**从利用模型回答问题，扩展为利用模型推动一项真实工作任务的完成。**

模型不再仅仅负责生成最终答案，而是参与任务执行过程中的判断，并通过外部工具与真实环境交互。

这正是引入 Agent 的重要动机。

接下来要解决的问题是：为了让 Agent 真正完成一项工作，我们需要让它具备哪些能力？

## 二、为了完成工作任务，Agent 需要具备哪些能力？

上一章说，希望 Agent 不只回答问题，还能够推进实际工作。但这里必须先澄清一个容易产生误解的地方：

**“完成复杂工作时可能需要的能力”不等于“每个 Agent Runtime 默认实现的功能”。**

例如，最简单的 Agent 可以在一次模型调用中直接给出答案，也可以调用一个工具后再回答。它未必需要写出计划、拆分多个子任务，更不代表已经具备独立的业务结果审核器。

为理解一个成熟的工作型 Agent，我们仍然从五个问题出发，但会明确区分：哪些是基本循环中的环节，哪些是为复杂任务按需添加的机制。

### 1. 任务规划：只有工作目标，Agent 应该从哪里开始？

假设用户要求：

> 检查现行授信管理制度，找出可能冲突的规定，并生成一份附原文依据的报告。

对于这样的任务，系统可能需要先确定检查范围、收集相关制度、查找修订关系、比较条款，最后组织报告。

~~~text
目标：完成授信制度冲突审查
    ↓
确定审查范围
    ↓
收集制度与修订版本
    ↓
比较具体条款
    ↓
组织并核对报告
~~~

这是一份可能有用的**任务计划**，但它不一定是 Agent 执行前必须创建的产物。

这里至少有三种不同的做法：

| 做法 | 运行时发生什么 | 有没有明确的计划产物 |
| --- | --- | --- |
| **直接执行** | 模型根据任务直接选择第一个行动；后续根据结果决定下一步 | 不一定有 |
| **模型生成计划** | 模型先输出步骤清单，再依照清单推进，必要时修改 | 有文本计划，但未必有执行约束 |
| **专门规划机制** | 使用 Plan Mode、规划工具或应用层 Planner；计划可能需要审核、存储和状态管理 | 有相应协议或结构，但仍需核查是否真正执行 |

**规划的本质是把目标转化为可执行的工作安排；Agent Loop 本身并不要求每个任务先经过一个独立的 Planner。**

尤其要区分“模型内部可能进行了思考”和“系统实现了可观察的规划机制”。后者通常能够找到计划产生、保存、修改、执行或审批的证据。只看到一次工具调用，不能推断存在 Planner。

对应的现有项目：[job-agent 采用 `sdk-minimal`，提示词已经明确要求依次查看目录；项目没有实现 Planner，也未启用专门的 Plan Mode。](./job-agent/01-project-architecture-and-code.md#1-任务规划当前没有独立实现) 它可以帮助我们观察最小执行循环，但还不能证明复杂任务规划能力。

### 2. 行动决策：面对当前情况，下一步具体做什么？

假设制度 A 引用了制度 B，读取 B 后又发现制度 C 已经修订 B。

此时下一步应当从“比较 A 与 B”改为“先核实 C”。对于动态任务，我们希望模型根据**目标、当前信息、可用工具**选择下一个动作，而不是始终执行一段固定脚本。

~~~text
用户目标 + 已有信息 + 工具描述
               ↓
          模型本轮决策
             /    \
       直接回答   请求调用工具
                    ↓
                 工具执行
~~~

在常见的工具调用式 Agent Loop 中，模型生成回答或工具调用意图，Runtime 负责承接它。这是基础循环的核心能力。

但有两点不能混淆：

- Bash 脚本里的 `case` 分支、程序预先写定的步骤，不等于 Agent 自主决定下一步。
- 模型具备在多种工具中作选择的机会，不代表我们已经观察到它确实正确地做出了选择。需要实际模型请求和 Session Trace 来确认。

### 3. 工具执行：模型决定读取文件后，谁让操作发生？

模型可以提出类似下面的工具调用意图：

~~~json
{"name": "read_document", "arguments": {"document_id": "B"}}
~~~

但这条消息本身并不会读取文件。需要 Runtime 中的工具执行器接收调用、找到相应工具、执行操作并返回结果。

因此至少存在两个不同的行为：

1. **模型选择工具**：生成工具名及参数。
2. **执行器运行工具**：在真实环境操作文件、数据库或网络服务，返回结果或错误。

这也是 Agent Runtime 的基础职责之一。

在 job-agent 中，Python 入口并没有编写 `read_document`；它选择 DeepSeek Harness 的 `sdk-minimal` Profile，其中已配置 Linux 下的 Bash 工具。需要注意，**`cwd` 是工作目录，不是权限边界**；是否允许实际读取或修改由执行环境的权限与策略决定。

### 4. 反馈调整：工具执行后，Agent 怎样决定是否改变做法？

工具调用之后，Runtime 通常把工具结果写入历史，并将必要信息交给下一轮模型。这样模型**有机会**基于实际结果重新决策。

例如：

~~~json
{"status": "success", "content": "制度 B 已由制度 C 修订"}
~~~

下一轮模型可能决定先读取 C；读取失败时，也可能换一种搜索方式。

但**“反馈被送回模型”与“模型已经正确调整计划”不是同一件事**：

- **反馈通道**是 Runtime 负责提供的机制。
- **调整行为**是模型或业务控制器基于反馈做出的决策。
- **调整是否有效**需要具体任务的真实执行记录和验证结果。

在一个只要求执行 `pwd` 和 `ls` 的实验中，即使出现两次工具调用，也未必发生了需要改变目标或计划的情形，因此不能声称已经验证复杂任务的“自主反思和纠错”。

### 5. 结果验证：怎样知道工作真的完成，而不是只结束了运行？

生成一份制度审查报告，并不等于报告的结论正确。我们可能还需要检查引用是否存在、制度版本是否有效、条款是否确有冲突。

这里应区分三个层次：

| 层次 | 检查什么 | 谁负责 |
| --- | --- | --- |
| **运行层结束** | 模型是否结束本轮、是否因错误/取消/限制而停止 | Runtime 的 Turn/Step 生命周期 |
| **操作层成功** | 工具是否返回成功、目标文件是否存在 | 工具执行器、应用检查 |
| **业务层验证** | 证据是否可靠、结论是否符合任务要求、有没有遗漏 | 应用校验逻辑、评估器或人工 |

这三者可以独立变化。例如一个 Runtime 完整结束的 Agent，仍可能输出错误结论；一次 Shell 成功运行，也不表示已经完成制度审查。

**结果验证对高质量任务交付非常重要，但不是最小 Agent Loop 必然自带的审核步骤。** 对简单任务可能直接结束，对复杂任务则需要按业务定义独立的验证标准，并在失败时修复或转人工。

当前 job-agent 的 `finish_reason` 检查，只属于“运行层状态判断”；`session_report.py` 统计日志事件类型，也不构成业务验证。

### 6. 五种能力如何组合？先看最小循环，再按需增强

现在我们可以把它们分成两层，而不是误以为它们每次都必须顺序出现。

**第一层：最小工具调用式 Agent Loop**

~~~text
接收任务
   ↓
准备当前上下文与可用工具
   ↓
调用模型，生成回答或工具调用意图
   ├── 生成最终回答 ──────────────→ 结束当前运行
   └── 请求工具 ──→ 执行工具 ──→ 记录结果
                       ↑            │
                       └── 下一轮模型调用 ←┘
~~~

工具可以调用多次，也可以一次都不调用。Runtime 还必须处理取消、错误、资源限制与状态持久化等实际问题。**基础循环保证有执行与反馈的机制，并不保证模型每次都做对。**

**第二层：按任务复杂度补充的工作机制**

- **任务规划**：在直接行动之前生成计划，或在执行过程中维护和修订计划。
- **反馈调整策略**：当工具失败或新信息出现时，规定什么时候重新检索、重试或转向其他步骤。
- **任务验证**：在允许结束前检查产物、证据与业务目标，必要时修正或交由人工审核。
- **Workflow、多 Agent、Checkpoint、权限审批等**：只有遇到明确需求才额外增加。

所以，如果在某个项目中没有看到 `Planner`、`Checker`，不一定说明那个项目没有 Agent Runtime；更可能说明它**尚未实现复杂任务的规划和验证层**。

> 对照阅读：[job-agent 如何对应这五种能力，以及哪些当前没有实现](./job-agent/01-project-architecture-and-code.md#三按照五种能力对照现有代码哪些存在哪些没有)。

## 三、什么是 Agent Runtime？

### 1. 为什么有了 Agent Loop，还需要 Runtime？

在刚才的 Agent Loop 中，我们已经看到：

模型需要被调用，工具调用请求需要被接收，工具需要真正执行，执行结果又需要交给下一轮模型。

那么：

谁负责调用模型？

谁负责接收和执行工具请求？

谁负责把执行结果送回模型？

谁负责判断是否继续运行？

这些工作需要一个实际的程序层进行组织。

这个程序层就是 Agent Runtime。

**Agent Runtime 是负责组织模型调用、工具执行、环境反馈及必要的会话状态，使 Agent Loop 得以持续运行的执行层。它提供执行循环，并不自动保证具有显式任务规划、业务验证或任务成功判定。**

### 2. Runtime 实际做了什么？

仍然以制度审查为例。

当模型决定读取制度 B 时，Runtime 需要：

1. 接收模型输出的 read_document 工具调用请求。
2. 检查工具是否存在、参数是否合法、当前操作是否获得授权。
3. 调用实际的文件读取工具。
4. 接收工具返回的文件内容或错误信息。
5. 更新任务记录，并为下一轮模型推理准备必要信息。
6. 依据模型响应与控制策略继续调用模型，或者暂停、取消或结束当前运行；业务目标是否完成需另行判断。

于是，模型和工具能够形成连续的执行过程。

最小的 Agent Runtime 可以只是一个循环：

~~~python
state = initialize_task(user_request)

while not state.finished:
    context = build_context(state)

    response = call_model(context, tools)

    if response.has_tool_calls:
        results = execute_authorized_tools(
            response.tool_calls
        )
        state = update_state(state, results)

    elif response.has_final_answer:
        state = handle_final_answer(state, response)
~~~

这是简化的伪代码，实际运行还需要处理执行失败、超时和终止条件。

它表达了 Runtime 的核心职责：

**负责让模型能够反复决策，让工具调用真正执行，让执行结果能够影响下一轮判断。**

### 3. Agent 与 Agent Runtime 有什么区别？

Agent 是由模型、工具和运行控制等机制共同构成的任务系统。

Agent Runtime 则强调使这个系统持续运行的执行机制。

模型可以负责理解目标、规划任务和选择行动。

工具负责与文件、数据库或业务系统交互。

Runtime 负责连接模型和工具，协调执行过程，并管理任务状态。

因此，Agent 和 Runtime 不一定是两个独立的软件服务。

最简单的 Agent 可以通过几十行循环代码运行；复杂的 Agent 则可能使用专门的 Runtime 框架。

## 四、为什么任务变长之后，还需要管理 Context 和 State？

前面介绍的最小 Agent Runtime 已经能够完成简单任务。

但如果制度审查涉及数百份文件、几十轮工具调用，就会遇到一个问题：

**每次调用模型，都需要把之前所有信息重新输入吗？**

### 1. 什么是 Context？

Context 是当前一次模型调用时，模型能够看到的信息。

例如：

~~~text
任务目标：
检查授信制度冲突。

当前进度：
已检查制度 A、B。

主要发现：
B 已由 C 修订。

下一步问题：
制度 C 是否适用于目标机构？
~~~

模型需要这些信息，才能判断下一步应该做什么。

但它不一定需要重新读取前面所有文件的完整内容。

如果每轮都带上全部历史，随着任务持续执行，上下文会越来越长，增加模型调用成本，并可能超过上下文窗口的限制。

因此，Runtime 需要为每轮模型调用组织必要的信息。

### 2. 什么是 State？

假设我们不再把所有信息放入当前 Context，那么之前的任务进度保存在哪里？

这就需要 State。

State 是系统维护的任务状态，例如：

~~~text
task_id: review_001

目标：
检查授信制度冲突

已检查：
- 制度 A
- 制度 B

待检查：
- 制度 C

已发现问题：
- 制度 B 已失效

任务状态：
running
~~~

State 可以保存已经完成的动作、待处理事项、收集到的证据及其存储位置等。

Runtime 根据 State 和外部资料，为当前模型调用组织 Context。

~~~text
            State
        （保存任务状态）
               ↓
       提取当前必要信息
               ↓
            Context
               ↓
           模型推理
               ↓
           工具执行
               ↓
          更新 State
~~~

可以简单理解为：

**State 保存任务进行到了哪里；Context 决定本轮模型需要看到什么。**

二者可能重叠，但并不相同。

### 3. Session 又是什么？

假设同一个用户同时发起两个审查任务：

一个检查授信审批制度，另一个检查贷后管理制度。

两项任务使用相同的模型和工具，但必须保留各自独立的历史与进度。

Session 通常用于组织一条连续交互的上下文。

不同框架还可能使用 Thread、Run、Task 等概念区分会话、任务和具体执行过程。

这些名称并不完全统一，重点是理解：Runtime 需要能够识别不同任务，并找到它们对应的状态与历史信息。

## 五、Agent 执行中断后，怎样继续工作？

假设 Agent 已经检查了 80 份制度，服务却突然重启。

如果进度只保存在程序内存中，就可能丢失此前完成的工作。

因此，长任务还需要考虑状态持久化与恢复。

### 1. 什么是 Checkpoint？

Checkpoint 是在任务执行过程中保存的可恢复检查点。

例如：

~~~text
Checkpoint 1：
完成制度 A 审查

Checkpoint 2：
确认制度 B 已被修订

Checkpoint 3：
准备核对制度 C 的适用范围
~~~

当服务重启时，具备相应恢复协议的应用或 Runtime 可以根据检查点恢复对应状态。**但 Session 日志持久化、Runtime 内部持久化屏障和可从某个业务步骤继续运行的 Checkpoint 并不等价**；能恢复哪些内容，要看实际保存了什么，以及外部副作用是否得到处理。

### 2. 恢复后能不能直接重试？

不一定。

例如，Agent 已经成功向业务系统写入审查报告，但服务在记录成功状态之前崩溃。

如果恢复后直接重试，可能造成重复提交。

因此：

- 对于只读检索，通常较容易重试。
- 对于修改文件、更新数据库、发送邮件等有副作用的操作，需要确认此前是否已经执行。
- 必要时使用幂等控制或补偿机制，避免重复操作造成问题。

**Checkpoint 解决的是如何恢复任务进度；幂等和补偿机制解决的是如何安全处理已经发生的外部操作。**

## 六、Agent 可以自主执行任务，为什么还需要权限与安全控制？

Agent 可以根据任务目标选择工具，但不代表它可以随意使用所有工具。

假设制度审查系统提供：

~~~text
search_policy    检索制度
read_document    读取制度
write_report     生成报告
update_policy    修改正式制度
send_email       发送邮件
~~~

读取制度与修改正式制度显然具有不同风险。

即使模型认为应该调用 update_policy，**实际执行前也必须经过有效的权限判断与必要的人工审批**。这些控制可以由 Runtime 插件、业务系统或外部执行环境共同承担，不能假定任何默认 Profile 都自动具备完整授权机制。

~~~text
模型提出工具调用
        ↓
检查工具与参数
        ↓
检查用户权限
        ↓
必要时人工确认
        ↓
执行实际操作
        ↓
记录执行结果
~~~

对于文件系统、命令执行或网络访问，还可以使用沙箱限制 Agent 的活动范围。

同时，Agent 读取到的外部文件和工具结果只是任务数据，不能自动成为更高优先级的系统指令。

**让 Agent 具备自主行动能力，不等于把全部执行权限交给模型。**

**执行环境和授权机制必须确保行动发生在经过授权的范围之内。** Runtime 可以参与强制控制，但是否真正执行授权检查，取决于具体工具、插件、策略及外部业务系统的配置。

## 七、如何让 Agent 的结果更可靠？

第二章已经说明，复杂工作需要根据业务目标验证结果；但这类验证**不能仅凭 Agent Loop 正常结束来推定已经实现**。

在真实系统中，还需要进一步区分：

**工具执行成功，不等于业务任务成功。**

例如，报告生成工具返回：

~~~json
{
  "status": "success",
  "file": "review_report.docx"
}
~~~

这只能证明文件生成操作成功。

报告引用的制度是否有效、条款是否准确、结论是否成立，还需要进一步核实。

因此，可以组合不同层次的检查机制。

### 1. 确定性检查

例如：

- 报告文件是否生成；
- 引用的文件编号是否存在；
- 条款能否定位到原文；
- 报告是否符合规定格式。

这些检查适合由程序完成。

### 2. 语义判断

例如：

两项制度是否真正存在冲突，还是只是适用机构、业务范围或生效时间不同？

这可能需要模型进行进一步分析。

对于无法可靠自动判定的高风险结论，仍然需要人工复核。

### 3. 验证反馈

如果校验发现问题，可以将结果重新提供给 Agent，让它补充查证或修复报告。

这实际上是在 Agent Loop 中加入一项验证机制。

同时，Runtime 需要设置最大执行步数、超时、成本预算等边界，防止 Agent 因不断尝试修正而陷入无效循环。

无法确认的任务可以暂停或交由人工处理，不必强行要求模型给出确定结论。

## 八、什么时候应该使用 Agent？

理解 Agent 的能力之后，还需要判断哪些工作真正适合它。

### 1. 任务步骤完全确定：使用传统程序或工作流

例如：

~~~text
上传财务报表
    ↓
OCR 识别
    ↓
字段提取
    ↓
科目映射
    ↓
公式计算
    ↓
生成报告
~~~

如果步骤和处理规则已经明确，就没有必要让模型反复决定下一步。

其中仍然可以使用大模型，但总体流程由程序控制。

### 2. 一次检索即可回答：使用普通 RAG

例如，用户询问某项授信业务的审批权限。

系统检索制度条款，再让模型生成回答。

如果资料完整，这种固定检索与生成流程即可满足要求。

### 3. 需要动态追查资料：考虑使用 Agent

例如，检查制度冲突时，系统需要根据新发现的文件引用、修订记录和适用范围，动态决定下一步查询。

这种任务更适合让模型在执行过程中进行决策。

### 4. 能不能只在部分步骤使用 Agent？

可以。

例如：

~~~text
固定流程：确定审查范围
        ↓
Agent：动态追查制度关系
        ↓
固定流程：整理证据
        ↓
模型：分析制度冲突
        ↓
固定流程：校验并生成报告
        ↓
必要时人工复核
~~~

对于能够明确规定的步骤，继续使用传统程序。

对于需要根据新信息作出语义判断的步骤，再考虑引入 Agent。

**Agent 不是为了替代所有工作流，而是为了处理那些难以完全预先确定执行路径的工作。**

## 九、回到最初的问题

我们最开始希望做的，是让大语言模型不再局限于回答问题，而是能够完成一项真实工作任务。

从最小 Agent Loop 开始，系统需要让模型能够基于当前信息选择行动，让工具执行并把结果反馈给下一轮；模型也可以直接回答而不调用工具。

当任务变得复杂时，再按需增加显式计划、计划修订、业务结果验证、人工审核和任务恢复等能力。它们可以与 Agent Loop 配合，但**不应被理解为每个 Runtime 默认具备且每轮必经的五个步骤**。

而 Agent Runtime 负责组织这个循环，让模型决策、工具执行、执行反馈和任务状态更新真正发生。

随着任务执行时间增长，Runtime 又需要进一步处理上下文管理、状态持久化、中断恢复、权限控制和结果验证等问题。

因此，整个演进过程可以概括为：

**从回答问题到完成工作任务，我们引入 Agent；为了让 Agent 持续决策和行动，我们需要 Agent Loop；为了让这个循环真正运行起来，我们需要 Agent Runtime；为了让任务长期可靠执行，我们还需要上下文、状态、恢复、权限与验证等工程机制。**
