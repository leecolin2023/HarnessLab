# 什么是 Agent，为什么需要 Agent Runtime？

## 一、当任务的下一步无法预先确定

有一项任务：检查一批企业制度，找出与授信办理流程可能冲突的规定，并生成附有原文依据的审查报告。

如果只需根据固定关键词查询制度，程序可以按预设流程完成：检索 → 提取条款 → 汇总结果。但真正审查时，下一步可能取决于刚刚找到的证据。

例如，第一次检索发现制度 A 规定了某项审批要求，同时引用制度 B。打开 B 后，发现它已被制度 C 修订；进一步比较，又发现 C 只适用于部分机构。此时必须继续检查生效日期、适用范围和相关条款，才能判断是否真的存在冲突。

```text
目标：判断授信流程要求是否冲突
    ↓
检索制度 A → 发现引用 B
    ↓
读取 B → 发现可能存在修订版 C
    ↓
核对 C 的生效日期和适用范围
    ↓
证据足够？ ─ 否 → 补充检索或请求人工确认
    │
    是
    ↓
形成结论 → 核对引用依据 → 生成报告
```

这里需要动态决定的是**下一步查什么、用什么能力查、何时证据足够、发现矛盾后如何调整**。如果所有分支和判断规则都能事先写清楚，固定工作流即可完成；当新的环境反馈会改变任务路径时，把一部分决策权交给模型才有价值。

## 二、Agent 如何推进一个目标？

**Agent 是围绕目标，根据当前信息选择行动、获取环境反馈并调整后续行动的控制系统。**

一次任务由连续的决策与执行构成：

```text
任务目标
   ↓
观察已有信息与当前状态
   ↓
模型判断：下一步做什么？
   ↓
执行动作：检索、读文件、查询系统、修改文件……
   ↓
得到真实执行结果或错误
   ↓
更新信息与任务状态
   ├─ 目标未完成 → 再判断下一步
   ├─ 需要授权 → 等待人工确认
   └─ 结果已验证 → 结束任务
```

以制度审阅为例，模型先选择“检索制度 A”，随后根据实际检索结果决定打开 B，而不是在第一轮就固定完整的查询顺序。执行结果会改变下一轮模型能看到的证据，并影响它继续查证还是结束任务。

这涉及两个必须分配清楚的职责：

- **动态决策**：模型依据目标、约束和新观察，决定选哪个动作或是否继续。
- **确定性执行**：检索接口、数据库查询、文件写入和校验规则由程序执行，产生真实结果。

Agent 的动态决策权限可以限制在检索和分析环节；涉及修改审批状态、发送文件等高风险动作，仍由程序规则和人工授权控制。

## 三、为什么还需要 Agent Runtime？

当模型回答“我要打开制度 B”时，**它输出的是行动意图，制度文件还没有被读取**。

外部程序必须接收这项意图，找到相应工具，检查参数与权限，执行读取操作，然后把查到的内容或错误送回下一轮模型推理。模型才有条件决定下一步。

**Agent Runtime 就是持续组织模型决策、工具执行、环境观察与状态更新的运行层。**

同一项任务中的职责可以落到具体步骤：

| 运行环节 | Runtime 需要完成的事情 |
| --- | --- |
| 开始任务 | 保存目标、约束、可用工具与当前进度，组织本轮模型上下文 |
| 模型选择动作 | 接收结构化工具调用，确认工具存在且参数有效 |
| 执行动作 | 检查调用权限，交给实际工具或隔离环境执行 |
| 收到结果 | 记录成功、失败及输出，把必要观察提供给模型 |
| 继续或结束 | 更新任务状态，判断是否继续推理、暂停审批、终止或交付 |

```text
          Agent Runtime
┌───────────────────────────────────┐
│ 组织 Context → 调用模型 → 取得动作意图 │
│       ↑                      ↓     │
│ 更新 State ← Observation ← 工具执行  │
└───────────────────────────────────┘
                 ↓
       验证结果 / 继续 / 暂停 / 结束
```

最小的 Agent Runtime 可以只是模型调用与工具执行构成的一个循环。任务变长、执行环境变复杂后，才需要进一步处理会话持久化、恢复、并发、权限和可观测性。

### 从能执行到能可靠执行

**Context 与 State。** Context 是当前一次模型调用可见的信息；State 是外部保存的任务进度、已执行动作、证据、结果文件和人工确认。长任务不能只依赖模型的上下文窗口记住进度。

**Session 与恢复。** 如果审阅过程中服务重启，Runtime 需要知道已经查过哪些制度、保存了什么中间结果、下一步从哪里继续。恢复会话不等于可以重新执行全部工具：只读检索通常可以重试，而文件修改、系统提交等有副作用的操作必须先核实是否已执行，必要时使用幂等或补偿机制。

**权限与执行环境。** 同样是工具调用，读取制度和修改业务系统的风险不同。Runtime 必须依据调用者身份、授权范围和工具策略决定能否执行；需要时通过沙箱隔离文件、命令及网络访问。

**结果验证与反馈。** 检索接口返回成功，只能说明一次查询完成，不能证明制度依据已经找全；报告文件保存成功，也不能证明引用正确。Runtime 需要把校验结果重新纳入任务：发现遗漏就补查，发现生成错误就修复，无法核实时交由人工确认。

因此，**Agent 的智能体现在能根据反馈改变行动；Runtime 的工程价值体现在让这些行动真实发生，并使进度、权限、失败和结果可管理。**

## 四、什么时候该使用 Agent？

决定因素是**任务执行路径是否需要根据运行中出现的新信息作出语义判断，以及这些判断是否能够获得可靠反馈**。

| 任务 | 更合适的控制方式 |
| --- | --- |
| 根据确定公式计算财务指标 | 规则或程序直接执行 |
| 文档上传后按固定顺序做 OCR、字段校验、写库 | 固定工作流 |
| 按明确条件检索资料并生成一份标准答案 | 预设 RAG 流程 |
| 跨制度追查引用、修订和适用范围，证据不足时决定补检 | 在确定性工具和规则之间使用 Agent 动态决策 |
| 修改授信状态、发送重要文件 | 程序约束执行，并在必要节点加入人工审批 |

动态决策会带来更多模型调用、成本、不确定性和故障路径。对于固定、可验证的步骤，代码与工作流仍然是主要执行方式；Agent 应用于需要探索、补查或重规划的节点。

Coding Agent 较容易形成执行闭环，是因为代码仓库提供了可读写环境，编译、测试和 Git diff 能反馈修改结果。制度审阅要达到类似的可靠性，也需要可追溯的原文、受控的业务工具，以及能够验证引用与结论的机制。

## 五、Agent Runtime 与模型服务平台的分工

**模型服务平台**执行和治理单次模型推理请求：模型加载、推理调度、API、资源分配、访问控制与服务运行。

**Agent Runtime**负责把多次模型推理连接成一项真实任务：组织上下文、选择与执行工具、接收反馈、保存状态，并决定继续、暂停或完成。

```text
Agent Runtime：目标 → 模型判断 → 工具执行 → 观察结果 → 再判断
                         ↓ ↑
模型服务平台：       模型请求 → 推理执行 → 模型输出
```

模型完成一次推理，只产生了下一步决策所需的输出；Agent 完成任务，还需要外部动作真正执行、状态正确更新，以及最终结果通过验证。
