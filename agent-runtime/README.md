# 什么是 Agent，为什么需要 Agent Runtime？

## 一、为什么需要 Agent？

### 1. 大语言模型已经能够回答问题，为什么还需要 Agent？

假设我们正在开发一个银行制度审查工具。

用户提出一个问题：

> 授信业务的审批权限是如何规定的？

我们可以先从知识库检索相关制度，再把检索结果交给大语言模型，让它生成回答。

~~~text
用户提出问题
    ↓
检索相关制度
    ↓
大语言模型阅读资料
    ↓
生成回答
~~~

如果用户只是想了解某项制度，这样的系统可能已经足够。

但现在，用户提出了一个不同的要求：

> 检查现行授信管理制度，找出不同制度之间可能存在的规定冲突，并生成一份附有原文依据的审查报告。

这不再是一个简单的知识问答，而是一项需要实际完成的工作任务。

系统不仅要理解制度，还需要找到相关文件、检查修订关系、比较具体条款、核对依据，最后形成审查报告。

**用户希望获得的不再只是一段回答，而是一项工作已经完成的结果。**

### 2. 为什么不能直接让大模型一次完成这项任务？

最直接的办法，是把制度文件全部提供给大模型，让它一次性分析并生成报告。

如果资料数量少、证据齐全，任务又比较简单，这种方式可能奏效。

但真实的制度审查往往没有这么直接。

例如，模型阅读制度 A 后，发现它引用了制度 B；读取制度 B 后，又发现 B 已经由制度 C 修订。

此时，系统需要继续寻找制度 C，并检查其生效日期和适用范围。

问题在于，我们无法保证任务开始时就已经提供了全部必要资料，也不一定能够预先确定完整的执行步骤。

仅仅让模型生成一段文字，还不足以完成这些实际操作。

当然，传统程序也可以完成工作任务。如果检索、判断和处理规则都已经明确，固定工作流通常更合适。

但对于执行过程中需要不断理解新信息、判断下一步行动的任务，我们希望模型能够参与整个执行过程。

### 3. 我们真正希望 Agent 做到什么？

我们希望用户只需要提出目标：

> 检查授信制度冲突，并生成审查报告。

系统就能够围绕这个目标，开展必要的工作：

~~~text
用户提出工作目标
        ↓
理解需要完成什么
        ↓
开展实际工作
        ↓
根据结果继续推进
        ↓
完成任务并交付成果
~~~

这里最重要的变化是：

**从利用模型回答问题，扩展为利用模型推动一项真实工作任务的完成。**

模型不再仅仅负责生成最终答案，而是参与任务执行过程中的判断，并通过外部工具与真实环境交互。

这正是引入 Agent 的重要动机。

接下来要解决的问题是：为了让 Agent 真正完成一项工作，我们需要让它具备哪些能力？

---

## 二、为了完成工作任务，Agent 需要具备哪些能力？

继续使用授信制度审查的例子。

用户只提出最终目标，却没有规定具体的工作步骤。

为了让 Agent 完成任务，我们需要逐步解决几个问题。

### 1. 任务规划：只有工作目标，Agent 应该从哪里开始？

用户要求检查制度冲突，却没有告诉系统具体检查哪些文件、以什么顺序检查、怎样生成报告。

因此，Agent 首先需要理解目标，并规划完成任务的大致步骤。

例如：

~~~text
目标：完成授信制度冲突审查
    ↓
确定需要检查的制度范围
    ↓
收集相关制度文件
    ↓
检查引用和修订关系
    ↓
比较制度条款
    ↓
整理证据，生成报告
~~~

这里的计划只是初步的工作安排。

随着任务推进，Agent 可能发现新的制度文件，或需要增加新的查证步骤。

**任务规划让 Agent 能够从最终目标出发，推导出需要采取的行动，而不要求用户事先指定全部步骤。**

对于简单任务，规划可以非常简短，甚至直接表现为选择第一步行动。

### 2. 行动决策：面对当前情况，下一步具体做什么？

假设 Agent 已经找到制度 A，并发现其中引用了制度 B。

接下来应该读取制度 B。

如果已经知道文件编号，可以直接读取；如果只有文件名称，就需要先检索。

如果又发现 B 被制度 C 修订，那么下一步可能变成查询修订记录。

~~~text
检索制度 A
    ↓
发现引用制度 B
    ↓
读取制度 B
    ↓
发现制度 C 是修订版本
    ↓
查询制度 C
~~~

这些行动不是在任务开始时就全部确定的，而是由当前掌握的信息决定。

**行动决策让 Agent 根据任务目标和当前情况，选择下一步应该执行的操作。**

### 3. 工具执行：Agent 决定做什么之后，怎样真正完成操作？

模型可能判断：

> 下一步需要读取制度 B。

但这句话本身不会让制度 B 自动从知识库中被读取。

模型需要能够调用外部工具。

例如：

| 工具 | 具体用途 |
| --- | --- |
| search_policy | 检索相关制度 |
| read_document | 读取制度文件 |
| get_document_history | 查询制度修订记录 |
| check_effective_date | 核对制度有效期 |
| write_report | 生成报告文件 |

模型可以通过 Tool Calling 产生结构化的工具调用请求：

~~~json
{
  "name": "read_document",
  "arguments": {
    "document_id": "B"
  }
}
~~~

这个请求表达了模型的行动意图。

实际读取操作仍然需要程序或工具执行环境完成。

**模型负责决定调用什么工具，执行机制负责让操作真正发生。**

如果没有工具和实际执行环境，Agent 就只能提出工作建议，而无法直接完成需要外部操作的任务。

### 4. 反馈调整：执行结果与预期不同，Agent 应该怎么办？

假设 Agent 调用读取工具后，得到如下结果：

~~~json
{
  "status": "success",
  "document_id": "B",
  "content": "本办法已由制度 C 修订"
}
~~~

Agent 原本准备比较制度 A 和 B。

但是，工具返回的信息表明 B 已经被修订。

这时，原来的工作计划需要调整：先读取制度 C，再判断适用范围和条款差异。

另一种情况是读取失败：

~~~json
{
  "status": "error",
  "message": "document_not_found"
}
~~~

Agent 也可以根据错误信息，尝试用制度名称重新检索，或者查找历史归档文件。

**反馈调整让 Agent 知道刚才的行动实际产生了什么结果，并据此修正后续行动。**

这使它不再只能机械执行最初制定的计划。

### 5. 结果验证：怎样知道工作已经真正完成？

假设 Agent 最终生成了制度审查报告。

但报告生成成功，并不代表审查任务已经完成。

例如，报告可能引用了已经失效的制度，也可能遗漏关键的修订关系。

因此，在结束任务前，还需要检查结果是否满足最初的目标。

例如：

~~~text
生成审查报告
    ↓
核对引用依据
    ↓
发现部分依据已失效
    ↓
重新查询有效版本
    ↓
修正审查报告
    ↓
再次检查
    ↓
交付结果
~~~

这里有些验证可以通过程序完成，例如文件是否存在、引用编号是否有效。

有些验证则可能涉及语义判断，例如两项制度是否真的存在冲突。

**结果验证让 Agent 不只是执行了一系列动作，而是能够根据任务目标判断是否还需要继续工作。**

对于无法可靠验证的结论，应保留人工确认或明确说明证据不足，而不是让 Agent 无限循环。

### 6. 这些能力怎样组合起来？

现在，我们已经具备完成任务所需的主要能力：

- **任务规划**：根据工作目标，决定大致怎样完成。
- **行动决策**：根据当前信息，选择下一步操作。
- **工具执行**：通过外部工具，让操作实际发生。
- **反馈调整**：根据真实执行结果，改变后续行动。
- **结果验证**：检查是否满足目标，决定继续还是结束。

但这些能力不是各执行一次就结束。

例如，读取制度 B 后，需要重新决定下一步；读取制度 C 后，还要继续核对适用范围。

因此，它们需要组合成一个持续运行的循环。

这个循环就叫 **Agent Loop**。

~~~text
               用户工作目标
                    ↓
                 任务规划
                    ↓
               选择下一步行动
                    ↓
                 工具执行
                    ↓
                 获取反馈
                    ↓
             更新信息、调整计划
                    ↓
               验证任务结果
                 ↙       ↘
              未完成     已完成
                 ↓         ↓
             继续决策    交付成果
~~~

Agent Loop 的核心是：

**模型根据目标和当前信息决定行动，执行机制完成操作，再把真实结果反馈给模型，由模型继续判断，直到任务结束。**

规划不一定每一轮都重新进行，模型也不一定每一轮都必须调用工具。

关键在于：下一轮行动能够根据上一轮获得的新信息而改变。

到这里，我们可以理解什么是 Agent：

> Agent 是围绕目标，利用模型进行决策，通过工具与外部环境交互，并根据执行反馈持续调整行动，以推动任务完成的系统。

但是，模型、工具和这些能力不会自动连接成一个持续运行的程序。

于是又产生一个新的问题：**究竟是谁负责组织 Agent Loop，让 Agent 真正运行起来？**

## 三、什么是 Agent Runtime？

### 1. 为什么有了 Agent Loop，还需要 Runtime？

在刚才的 Agent Loop 中，我们已经看到：

模型需要被调用，工具调用请求需要被接收，工具需要真正执行，执行结果又需要交给下一轮模型。

那么：

谁负责调用模型？

谁负责接收和执行工具请求？

谁负责把执行结果送回模型？

谁负责判断是否继续运行？

这些工作需要一个实际的程序层进行组织。

这个程序层就是 Agent Runtime。

**Agent Runtime 是负责组织模型调用、工具执行、环境反馈和任务状态更新，使 Agent Loop 能够持续运行的执行层。**

### 2. Runtime 实际做了什么？

仍然以制度审查为例。

当模型决定读取制度 B 时，Runtime 需要：

1. 接收模型输出的 read_document 工具调用请求。
2. 检查工具是否存在、参数是否合法、当前操作是否获得授权。
3. 调用实际的文件读取工具。
4. 接收工具返回的文件内容或错误信息。
5. 更新任务记录，并为下一轮模型推理准备必要信息。
6. 继续调用模型，或者按照终止规则暂停、结束任务。

于是，模型和工具能够形成连续的执行过程。

最小的 Agent Runtime 可以只是一个循环：

~~~python
state = initialize_task(user_request)

while not state.finished:
    context = build_context(state)

    response = call_model(context, tools)

    if response.has_tool_calls:
        results = execute_authorized_tools(
            response.tool_calls
        )
        state = update_state(state, results)

    elif response.has_final_answer:
        state = handle_final_answer(state, response)
~~~

这是简化的伪代码，实际运行还需要处理执行失败、超时和终止条件。

它表达了 Runtime 的核心职责：

**负责让模型能够反复决策，让工具调用真正执行，让执行结果能够影响下一轮判断。**

### 3. Agent 与 Agent Runtime 有什么区别？

Agent 是由模型、工具和运行控制等机制共同构成的任务系统。

Agent Runtime 则强调使这个系统持续运行的执行机制。

模型可以负责理解目标、规划任务和选择行动。

工具负责与文件、数据库或业务系统交互。

Runtime 负责连接模型和工具，协调执行过程，并管理任务状态。

因此，Agent 和 Runtime 不一定是两个独立的软件服务。

最简单的 Agent 可以通过几十行循环代码运行；复杂的 Agent 则可能使用专门的 Runtime 框架。

## 四、为什么任务变长之后，还需要管理 Context 和 State？

前面介绍的最小 Agent Runtime 已经能够完成简单任务。

但如果制度审查涉及数百份文件、几十轮工具调用，就会遇到一个问题：

**每次调用模型，都需要把之前所有信息重新输入吗？**

### 1. 什么是 Context？

Context 是当前一次模型调用时，模型能够看到的信息。

例如：

~~~text
任务目标：
检查授信制度冲突。

当前进度：
已检查制度 A、B。

主要发现：
B 已由 C 修订。

下一步问题：
制度 C 是否适用于目标机构？
~~~

模型需要这些信息，才能判断下一步应该做什么。

但它不一定需要重新读取前面所有文件的完整内容。

如果每轮都带上全部历史，随着任务持续执行，上下文会越来越长，增加模型调用成本，并可能超过上下文窗口的限制。

因此，Runtime 需要为每轮模型调用组织必要的信息。

### 2. 什么是 State？

假设我们不再把所有信息放入当前 Context，那么之前的任务进度保存在哪里？

这就需要 State。

State 是系统维护的任务状态，例如：

~~~text
task_id: review_001

目标：
检查授信制度冲突

已检查：
- 制度 A
- 制度 B

待检查：
- 制度 C

已发现问题：
- 制度 B 已失效

任务状态：
running
~~~

State 可以保存已经完成的动作、待处理事项、收集到的证据及其存储位置等。

Runtime 根据 State 和外部资料，为当前模型调用组织 Context。

~~~text
            State
        （保存任务状态）
               ↓
       提取当前必要信息
               ↓
            Context
               ↓
           模型推理
               ↓
           工具执行
               ↓
          更新 State
~~~

可以简单理解为：

**State 保存任务进行到了哪里；Context 决定本轮模型需要看到什么。**

二者可能重叠，但并不相同。

### 3. Session 又是什么？

假设同一个用户同时发起两个审查任务：

一个检查授信审批制度，另一个检查贷后管理制度。

两项任务使用相同的模型和工具，但必须保留各自独立的历史与进度。

Session 通常用于组织一条连续交互的上下文。

不同框架还可能使用 Thread、Run、Task 等概念区分会话、任务和具体执行过程。

这些名称并不完全统一，重点是理解：Runtime 需要能够识别不同任务，并找到它们对应的状态与历史信息。

## 五、Agent 执行中断后，怎样继续工作？

假设 Agent 已经检查了 80 份制度，服务却突然重启。

如果进度只保存在程序内存中，就可能丢失此前完成的工作。

因此，长任务还需要考虑状态持久化与恢复。

### 1. 什么是 Checkpoint？

Checkpoint 是在任务执行过程中保存的可恢复检查点。

例如：

~~~text
Checkpoint 1：
完成制度 A 审查

Checkpoint 2：
确认制度 B 已被修订

Checkpoint 3：
准备核对制度 C 的适用范围
~~~

当服务重启时，Runtime 可以根据已保存的检查点恢复任务状态。

### 2. 恢复后能不能直接重试？

不一定。

例如，Agent 已经成功向业务系统写入审查报告，但服务在记录成功状态之前崩溃。

如果恢复后直接重试，可能造成重复提交。

因此：

- 对于只读检索，通常较容易重试。
- 对于修改文件、更新数据库、发送邮件等有副作用的操作，需要确认此前是否已经执行。
- 必要时使用幂等控制或补偿机制，避免重复操作造成问题。

**Checkpoint 解决的是如何恢复任务进度；幂等和补偿机制解决的是如何安全处理已经发生的外部操作。**

## 六、Agent 可以自主执行任务，为什么还需要权限与安全控制？

Agent 可以根据任务目标选择工具，但不代表它可以随意使用所有工具。

假设制度审查系统提供：

~~~text
search_policy    检索制度
read_document    读取制度
write_report     生成报告
update_policy    修改正式制度
send_email       发送邮件
~~~

读取制度与修改正式制度显然具有不同风险。

即使模型认为应该调用 update_policy，Runtime 也必须检查当前用户是否具有修改权限，以及该操作是否需要人工审批。

~~~text
模型提出工具调用
        ↓
检查工具与参数
        ↓
检查用户权限
        ↓
必要时人工确认
        ↓
执行实际操作
        ↓
记录执行结果
~~~

对于文件系统、命令执行或网络访问，还可以使用沙箱限制 Agent 的活动范围。

同时，Agent 读取到的外部文件和工具结果只是任务数据，不能自动成为更高优先级的系统指令。

**让 Agent 具备自主行动能力，不等于把全部执行权限交给模型。**

Runtime 必须确保行动发生在经过授权的范围之内。

## 七、如何让 Agent 的结果更可靠？

第二章已经说明，Agent 需要验证任务结果。

在真实系统中，还需要进一步区分：

**工具执行成功，不等于业务任务成功。**

例如，报告生成工具返回：

~~~json
{
  "status": "success",
  "file": "review_report.docx"
}
~~~

这只能证明文件生成操作成功。

报告引用的制度是否有效、条款是否准确、结论是否成立，还需要进一步核实。

因此，可以组合不同层次的检查机制。

### 1. 确定性检查

例如：

- 报告文件是否生成；
- 引用的文件编号是否存在；
- 条款能否定位到原文；
- 报告是否符合规定格式。

这些检查适合由程序完成。

### 2. 语义判断

例如：

两项制度是否真正存在冲突，还是只是适用机构、业务范围或生效时间不同？

这可能需要模型进行进一步分析。

对于无法可靠自动判定的高风险结论，仍然需要人工复核。

### 3. 验证反馈

如果校验发现问题，可以将结果重新提供给 Agent，让它补充查证或修复报告。

这实际上是在 Agent Loop 中加入一项验证机制。

同时，Runtime 需要设置最大执行步数、超时、成本预算等边界，防止 Agent 因不断尝试修正而陷入无效循环。

无法确认的任务可以暂停或交由人工处理，不必强行要求模型给出确定结论。

## 八、什么时候应该使用 Agent？

理解 Agent 的能力之后，还需要判断哪些工作真正适合它。

### 1. 任务步骤完全确定：使用传统程序或工作流

例如：

~~~text
上传财务报表
    ↓
OCR 识别
    ↓
字段提取
    ↓
科目映射
    ↓
公式计算
    ↓
生成报告
~~~

如果步骤和处理规则已经明确，就没有必要让模型反复决定下一步。

其中仍然可以使用大模型，但总体流程由程序控制。

### 2. 一次检索即可回答：使用普通 RAG

例如，用户询问某项授信业务的审批权限。

系统检索制度条款，再让模型生成回答。

如果资料完整，这种固定检索与生成流程即可满足要求。

### 3. 需要动态追查资料：考虑使用 Agent

例如，检查制度冲突时，系统需要根据新发现的文件引用、修订记录和适用范围，动态决定下一步查询。

这种任务更适合让模型在执行过程中进行决策。

### 4. 能不能只在部分步骤使用 Agent？

可以。

例如：

~~~text
固定流程：确定审查范围
        ↓
Agent：动态追查制度关系
        ↓
固定流程：整理证据
        ↓
模型：分析制度冲突
        ↓
固定流程：校验并生成报告
        ↓
必要时人工复核
~~~

对于能够明确规定的步骤，继续使用传统程序。

对于需要根据新信息作出语义判断的步骤，再考虑引入 Agent。

**Agent 不是为了替代所有工作流，而是为了处理那些难以完全预先确定执行路径的工作。**

---

## 九、回到最初的问题

我们最开始希望做的，是让大语言模型不再局限于回答问题，而是能够完成一项真实工作任务。

为了做到这一点，Agent 需要具备：

- 根据目标规划任务；
- 根据当前情况决定行动；
- 通过工具执行实际操作；
- 根据执行反馈调整计划；
- 验证任务结果并决定何时结束。

这些能力通过 Agent Loop 连接起来，使模型能够参与一个持续执行的工作过程。

而 Agent Runtime 负责组织这个循环，让模型决策、工具执行、执行反馈和任务状态更新真正发生。

随着任务执行时间增长，Runtime 又需要进一步处理上下文管理、状态持久化、中断恢复、权限控制和结果验证等问题。

因此，整个演进过程可以概括为：

**从回答问题到完成工作任务，我们引入 Agent；为了让 Agent 持续决策和行动，我们需要 Agent Loop；为了让这个循环真正运行起来，我们需要 Agent Runtime；为了让任务长期可靠执行，我们还需要上下文、状态、恢复、权限与验证等工程机制。**
