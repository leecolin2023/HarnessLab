# 什么是 Agent，为什么需要 Agent Runtime？

> HarnessLab / Agent Runtime · 定位初稿 V0.1 · 2026-10-21  
> 先解释 Agent 作为一种工作方式为何出现，再解释 Runtime 为什么是工程运行层；不以某个开源框架的 API 作为定义。

## 一、先看普通大模型做不到的一件事

假设用户问：“帮我审阅这一批制度，查出与授信流程可能冲突的要求，并生成一份可复核的报告。”

一次普通 LLM 对话可以根据用户直接给它的材料提出分析，但问题是：制度可能有几百份；有的条款互相引用，有的已被替代；检索结果可能不全；必要时还要读取其他文件、查询系统、校验分析并生成文档。

真正的困难不是“模型不会写报告”，而是**它开始工作前还不知道所有信息，也不知道每一步究竟会遇到什么**：

- 检索到一个条款后，发现它引用了另一份制度，是否继续查？
- 新旧制度要求冲突，是否需要检查生效日期或适用范围？
- 查询结果不足以支撑结论，是否补检、标记证据不足或请求人工判断？
- 报告已生成，但文件结构、引用和事实是否验证通过？

如果每一步都由用户重新提问，模型只是会聊天的助手；如果把全部分支都预先写死，又难覆盖复杂真实环境。这之间出现了 Agent 的需求。

## 二、Agent 到底是什么？

Agent 不只是“在 LLM 外面接几个 Tool”，也不等于一套叫 Agent 的开发框架。

**Agent 是一种围绕目标持续决定下一步行动、在环境中执行、观察结果、更新状态并继续推进的智能控制系统。** 核心不在于回答的文本有多像人，而在于它能否依据新的真实反馈改变后续行动。

最小事件链：

`用户目标 → 理解当前状态 → 决定下一步 → 选择能力 → 执行动作 → 观察环境反馈 → 更新状态 → 继续 / 重试 / 改计划 / 人工介入 → 完成`

这条链里，模型通常负责理解、判断与生成行动意图；工具或执行环境负责真正读取和修改外部世界；运行系统则负责连接、约束和记录这些动作。

所谓“自主”，也只是**在授权范围内的一部分动态决策权**，不是可以绕过系统权限或替用户作出所有重要决定。

## 三、Chatbot、RAG、Workflow 与 Agent 的真正边界

| 方式 | 谁决定下一步？ | 适合解决什么 |
| --- | --- | --- |
| Chatbot / Generator | 用户发起每轮问题，模型主要生成回复 | 解释、总结、起草、简单问答 |
| RAG | 检索提供外部材料，回答通常仍由固定问答流程控制 | 知识补充、基于证据回答 |
| 固定 Workflow / 规则系统 | 代码或流程图预先规定步骤和条件 | 步骤清楚、规则稳定、可确定性执行的任务 |
| Agent | 模型在受限执行循环内，依据新观察动态选择部分动作 | 路径难提前穷举、需要探索、补检、纠错或重规划的任务 |

这些不是四种互斥产品。RAG 可成为 Agent 的检索能力；固定 Workflow 可以包围一个需要动态判断的 Agent 节点；Agent 可以选择调用确定性的工具和规则引擎。

真正的问题是：**这件事情的下一步，能否在运行前完整规定？**

- 能规定，且用规则/代码更可靠：优先代码与 Workflow。
- 无法完全规定，但可通过工具探索并获得反馈：考虑 Agent。
- 决策后果高风险、无法由机器独立核验：设置审批或人工介入。

## 四、为什么 Coding Agent 比“万能数字员工”更容易成立？

Coding Agent 的优势，不只是模型擅长写代码，而是它身处一个容易形成闭环的环境：

| 必要条件 | Coding Agent 的现成基础 |
| --- | --- |
| Context：知道当前对象 | 源代码、Issue、Git diff、日志 |
| Action：可以采取行动 | 编辑文件、运行 Shell、提交代码 |
| Feedback：环境告诉它发生什么 | 测试结果、编译错误、Lint |
| State：进度有地方保存 | 文件系统、Git、会话与任务记录 |
| Verification：可判断结果 | 测试、静态检查、人工 Review |

例如修复一个并发写入问题：Agent 先读代码与测试，提出修改，执行测试，依据失败信息再次修改。测试和 Review 是外部反馈，不是模型自己声称“已经修复”。

将场景换成银行制度审查或合同核验，通常会发现难点不只是 Prompt：证据是否齐全、业务系统有没有可调用的 Action、能否核对原文、是否拥有可验证的结果，以及哪些判断必须经人工复核。

因此，Agent 落地程度往往取决于 **Context、Action、Feedback、State、Verification 是否足够成熟**；不是采用越复杂的 Multi-Agent 架构，就越能完成工作。

## 五、什么是 Agent Runtime，为什么 Agent 还需要它？

上面的“观察 → 决策 → 执行 → 再观察”不是模型本身完成的。模型通常只对单次请求给出文本、结构化内容或工具调用意图。

**Agent Runtime 是让这个闭环真正运行起来的执行与控制层**。它至少需要回答以下六个问题：

1. **循环与控制权**：收到模型的工具调用意图后，谁执行？返回结果后谁决定是否再发起一轮？如何终止或取消？
2. **上下文（Context）**：这轮模型看到哪些用户要求、制度证据、历史消息和工具结果？内容过长后如何压缩？
3. **工具与环境（Tool / Environment）**：有哪些能力可用？参数怎样校验？到底在宿主机、容器还是受限环境里执行？
4. **状态（State / Session）**：任务完成了什么、有哪些产物和待处理问题？怎样在多轮甚至进程重启后继续？
5. **权限与人为控制**：读取、修改、发送、删除等动作由谁授权？哪些动作需要先暂停审批？
6. **反馈与质量（Trace / Verification）**：工具运行成功能否证明业务目标完成？失败如何记录、重试、复盘与回归？

一条简化的 Runtime 执行链：

```text
用户目标
   ↓
Session / 当前任务状态 + Context 组装
   ↓
模型推理（提出回答或工具调用）
   ↓
Runtime 校验参数、权限与执行环境
   ↓
工具执行 → Observation / 错误
   ↓
记录事件、更新 State 与 Context、验证结果
   ├─ 未完成 → 再次调用模型
   ├─ 高风险 → 人工审批 / 暂停
   └─ 已完成 → 输出可核验成果
```

不是每个 Agent 都要持久化、多 Agent 或复杂 Planner，但只要它要**持续采取行动**，就必须存在某种循环控制与实际执行机制；生产级任务才逐步增加持久状态、治理与恢复等要求。

## 六、几个尤其容易混淆的概念

**Model ≠ Agent ≠ Runtime/Harness。** 模型负责产生智能判断；Agent 是目标驱动的控制闭环；Runtime/Harness 是让闭环运行、连接工具与环境、执行权限和状态管理的工程机制。Harness 常包含 Runtime，也可能包含 UI、插件、Skills、模型适配等更多能力，二者并非严格同义。

**Context ≠ State。** Context 是这一轮发给模型的可见信息；State 是外部系统保存的真实任务进度、执行记录、产物、人工确认结果。摘要或压缩 Context 不代表事实状态也完成了持久化。

**Tool ≠ Skill。** Tool 是可执行能力接口；Skill 更多是“如何完成某类任务”的知识、策略与流程组织。Skill 可以指导调用若干 Tool，但不能代替真实系统执行。

**Session 恢复 ≠ 外部动作可靠恢复。** 对话回来了，不意味着之前的转账、文件写入、邮件发送或系统提交可以盲目重新执行。需要依据已发生副作用的确认结果，设置幂等键、去重、补偿或人工复核。

**提示词约束 ≠ 安全边界。** 对重要文件、Shell、内网系统和敏感数据，必须依赖真实权限、沙箱和服务端策略，而不能仅以“模型不会这样做”作为保证。

## 七、为什么不把所有业务流程都改成 Agent？

Agent 的动态适应能力，天然带来输出不确定、调用轮次增多、成本更高及结果难以验证等问题。

一个确定的财务指标计算公式，应该由代码执行，而不是让 Agent 每次自己算。一条“审批后同步状态”的确定业务链，也应由事务和工作流保证；在“材料异常后该追加查什么证据”这类不确定节点，才可能引入 Agent。

更稳健的工程分工：

- **确定的事情** → 规则、代码、Workflow；
- **不确定但可探索的事情** → Agent 动态判断；
- **可以机器核实的结果** → 自动反馈与验证；
- **无法可靠核实的高风险动作** → 人工介入。

Agent 的价值不是取代所有确定性软件，而是把过去需要人来不断判断“下一步做什么”的一部分工作，变成受约束、可观察、可验证的执行过程。

## 八、HarnessLab 为什么要单独研究 Agent Runtime？

我们要能解释的不仅是“如何用 LangGraph、Deep Agents、Pi 或 DeepSeek Harness 写出一个 Agent”，更是：

- 同一个模型、同一个任务，为什么换一套 Harness 会表现不同？
- Context 是如何装配、裁剪、压缩和恢复的？为什么工具结果会改变下一步？
- 任务取消、审批、断电、工具超时后，真实执行状态发生了什么？
- 为什么“工具调用成功”不等于“最终任务成功”？
- 一个成熟 Harness 应该直接复用到什么程度，哪些企业能力需要单独建设？

本目录后续先研究最小 Agent Loop 与一条真实 Trace，再逐步进入上下文、工具、Session、恢复与权限；不提前自研通用 Kernel，也不把某个框架名称当成原理。
