# Harness 中的上下文管理：哪些信息值得反复交给模型？

## 一、为什么模型已经支持长上下文，Harness 还要管理上下文？

假设我们正在使用一个编程 Agent 排查生产故障。

业务人员报告：“Qwen 昨天还能正常调用，今天突然不可用了。”

Agent 开始工作。它先检查服务状态，再读取网关日志，接着查看模型实例、路由配置和监控指标。

在这个过程中，模型可能先后读取：

- 200 行应用报错日志；
- 3000 行网关运行日志；
- 模型实例的启动配置；
- 10 次接口调用的返回结果；
- 几份模型服务部署文档。

这些信息在排查过程中都有价值。但是，当 Agent 已经发现“网关返回 upstream unavailable，而后端模型直连正常”时，之前读取的几千行日志还需要全部留在上下文里吗？

显然不一定。

下一步最需要知道的是：故障发生在哪一层、已经确认了什么、哪些假设被排除、还需要检查什么。

但这里马上出现一个难题：

**我们怎么知道哪些信息以后还会有用？**

某段日志现在看来无关，下一轮可能恰好成为关键证据。某个部署约束虽然是很早以前提供的，却可能在整个排障过程中始终有效。

这就是 Harness 上下文管理要解决的问题。

它不是简单地缩短聊天记录，而是决定：**每次模型需要行动时，怎样让它获得足够完成当前任务的信息，同时避免被无关历史淹没。**

## 二、先理解一件事：模型为什么需要反复接收历史？

我们平常使用 ChatGPT，很容易产生一种印象：模型知道我们之前聊过什么，所以它应该一直记得。

但从基本的模型推理机制来看，模型并不会因为回答过一次问题，就自动把这段经历写入自身参数。

对于通常的语言模型调用，它是在给定输入上下文的条件下生成下一段内容。

如果下一次调用只发送：

> 接着刚才的问题，下一步怎么办？

而没有提供刚才讨论的内容或其他可延续的状态，模型就缺少理解“刚才”所需要的依据。

因此，最简单的多轮对话程序会采用一种办法：**把之前的消息重新放进下一次请求。**

例如：

```text
第一次请求：
用户：帮我检查 Qwen 服务状态。

第二次请求：
用户：帮我检查 Qwen 服务状态。
助手：服务进程正常。
用户：那为什么网关调用失败？

第三次请求：
用户：帮我检查 Qwen 服务状态。
助手：服务进程正常。
用户：那为什么网关调用失败？
助手：需要继续检查路由和健康状态。
用户：现在已经确认后端直连正常，下一步呢？
```

实际系统还可能需要传递工具调用、工具结果，以及推理模型的特定状态项目，因此并不总是简单的文本拼接。

OpenAI Responses API 提供 `previous_response_id` 和 Conversation 等方式，让服务端管理这种延续状态，不要求应用每次手动重新上传完整消息列表。

但无论是客户端管理历史，还是服务端管理历史，模型下一轮能够利用的信息都需要有来源。

**保存对话历史、把历史交给模型、让模型真正利用这些历史，是三件不同的事情。**

这一区分非常重要。它也是理解后面所有机制的基础。

## 三、为什么不能把所有历史一直交给模型？

最初的问题确实是上下文窗口太小。

早期模型只有几千 Token 的上下文容量。历史消息积累到一定程度，就可能超过模型能够接收的范围。

后来，模型逐渐支持数万、十几万乃至百万级 Token。容量限制得到大幅缓解，但三个问题仍然存在。

### 1. 输入越多，调用成本通常越高

假设每轮都重新携带大量历史内容，后续调用就会越来越大。

即使提供商采用缓存机制，重复输入可以获得一定的成本和延迟优化，整个上下文仍然有容量限制。

而且，Agent 在一个任务中可能调用模型几十次，甚至上百次。单次冗余不大，累积起来也可能很可观。

### 2. 信息越多，模型不一定越容易做出正确判断

想象一下，你正在调查网关故障。

一份报告只有以下几项信息：

> 目标模型：Qwen  
> 网关：返回 upstream unavailable  
> 后端：直连接口成功  
> 其他模型：网关访问正常  
> 待确认：目标模型的路由映射、服务发现和健康状态

另一份报告有几千行日志、十几轮猜测以及各种已经排除的方案。

哪一份更容易帮助你决定下一步？

在这个场景里，第一份很可能更有效。

大模型也存在类似问题。长上下文研究发现，在某些模型和任务中，随着无关内容增加，模型对关键事实的利用可能下降。

因此，**上下文容量足够，不代表应该把所有信息都放进去。**

### 3. 历史中可能存在过时信息

Agent 排查故障时，第一轮可能猜测 GPU 显存不足。

第二轮查到 GPU 正常。

第三轮又发现后端直连接口成功。

如果模型继续看到第一轮的所有猜测，却没有明确区分哪些已被推翻，就可能重复考虑早已排除的方向。

所以真正的问题变成：

**下一次调用时，模型需要的不是完整经历，而是能够支持下一步判断的有效状态。**

这促使 Harness 从单纯保存历史，发展到主动管理上下文。

## 四、一次模型调用的上下文，到底由什么组成？

理解 Harness 上下文管理，首先要知道模型每次实际接收什么。

通常可以分成几类：

| 上下文内容 | 作用 | 是否必须每轮完整携带 |
|---|---|---|
| 系统指令、开发者指令 | 规定 Agent 的角色、约束和行为 | 有效约束需要持续生效 |
| 当前用户目标 | 告诉模型现在要完成什么 | 通常需要 |
| 最近对话 | 保留当前讨论进展 | 视任务需要 |
| 工具定义 | 告诉模型能够调用什么工具 | 根据模型接口和工具管理方式 |
| 工具执行结果 | 提供文件、日志、数据库等外部信息 | 不一定 |
| 已确认的任务状态 | 告诉模型已经做了什么、下一步是什么 | 通常很重要 |
| 历史资料与长期记忆 | 提供跨任务的信息 | 按需加载 |

在具体系统中，这些内容的排列、格式和管理方式可能不同。

但 Harness 需要完成一项共同的工作：

**在模型开始推理之前，把当前任务需要的信息组装成可用的上下文。**

这叫 Context Assembly，即上下文组装。

它不同于 Prompt Engineering。

Prompt Engineering 主要关注指令如何表达；Context Engineering 则进一步关注：到底有哪些信息应该进入模型、什么时候进入、从哪里获取、什么时候不再携带。

这就是为什么我们不能把上下文管理简单理解成“写一个更好的系统提示词”。

## 五、第一个自然想到的办法：只保留最近几轮消息，行不行？

假设 Agent 已经执行了 50 轮对话。

我们可以规定：永远只保留最近 10 轮。

这就是一种简单的历史截断（Trimming）。

优点很明显：容易实现，不需要再调用模型生成摘要，也能直接限制历史长度。

但它依赖一个隐含假设：

**越近的信息越重要。**

这个假设并不总是成立。

例如，用户在第 1 轮提出：

> 不允许修改生产配置，只能读取日志和检查状态。

这个限制即使过了 50 轮，也不应该因为太早而被忘记。

相反，第 48 轮返回的两千行日志，如果已经被分析并记录了结论，可能就不需要继续携带。

因此，单纯按时间删除历史，无法区分长期有效的约束和短暂有用的观察。

我们需要一种更聪明的方法。

## 六、第二个办法：把旧历史总结成一份摘要

既然不能直接删除，那能不能先总结？

例如，原始历史是：

> 先检查 GPU，没有异常。  
> 再检查推理进程，服务正常。  
> 网关调用返回 503。  
> 其他模型从同一网关可以访问。  
> 直接调用目标后端成功。  
> 初步怀疑目标模型路由或健康状态异常。

可以压缩成：

> Qwen 网关调用异常。GPU 和推理进程暂未发现故障；后端直连成功，其他模型通过网关访问正常。下一步优先排查目标模型的网关路由、服务发现及健康状态，不应直接认定具体根因。

两段历史不同，但第二段保留了继续排查所需要的大部分信息。

这就是最常见的 **Compaction（上下文压缩）** 思路。

在早期 Agent 中，Compaction 往往由模型生成文字摘要，再把原有历史替换为摘要。

到了 2026 年，OpenAI 的 Responses API 已经提供原生 Compaction，可以通过指定阈值自动压缩，或者显式调用压缩接口。压缩结果还可能包含不供人直接阅读的状态项目，不一定是一段普通文字。

Anthropic 也提供相应的压缩和上下文编辑机制。

但需要注意：

**Compaction 的目标不是生成一篇好读的文章，而是让后续模型调用尽可能继续完成任务。**

这与我们熟悉的 Deep Read 是有区别的。

### 那么，一份好的 Agent 压缩摘要应该保留什么？

对于前面的 Qwen 故障，至少需要关注四类信息：

1. **当前目标**：要解决什么问题，怎样才算完成。
2. **已确认状态**：哪些事实已由日志、接口或工具结果支持。
3. **重要约束**：哪些操作禁止执行，哪些条件必须遵守。
4. **未完成事项**：还不知道什么，下一步应该检查哪里。

其中一个尤其容易犯的错误，是把**假设压缩成事实**。

例如：

> 初步怀疑网关健康检查异常。

不能在压缩后变成：

> 已确认网关健康检查异常。

否则压缩不仅减少了 Token，还改变了任务状态。

## 七、为什么已经有 Compaction，仍然需要清理工具结果？

因为 Agent 上下文中存在大量不需要模型重新总结的信息。

假设 Agent 通过 `grep` 搜索网关日志，返回 2000 行记录。

模型已经从中提取出三个重要时间点和一类错误信息。

此时有两种办法。

第一种是把这 2000 行日志交给模型再次摘要。

第二种是把日志保存在外部文件，只在上下文里保留结论和文件位置，然后清除旧的工具结果。

第二种方法在许多情况下更经济，因为它甚至不需要额外调用模型进行总结。

这就是 **Tool Result Clearing（工具结果清理）**。

Claude 的 Context Editing 支持清理较早的工具结果，保留必要的调用结构，让旧输出不再持续占用活动上下文。

这里就形成了一项重要区别：

- Compaction：提炼历史中的重要状态，通常需要某种模型驱动的压缩。
- Tool Result Clearing：移除已经不需要继续携带的工具输出，通常可以采用机械规则。

当然，只有在结果已被处理、可以重新获取，或者已经有可靠结论时，清理才更安全。

如果工具返回的是一次性结果、不可重放的数据，或尚未保存的重要证据，直接清理就可能导致永久信息损失。

## 八、但我们怎么知道一条旧日志以后还会不会有用？

这是上下文压缩无法完全解决的问题。

某一刻不重要的信息，之后可能变得重要。

例如 Agent 最初发现网关返回 503，把日志摘要成“upstream unavailable”。

后来又发现只有指定业务空间的请求失败。

此时，早期日志中被省略的路由标识、请求头或时间信息可能突然变得关键。

如果原始日志已经彻底删除，模型只能依靠之前的摘要。

而摘要未必保留了这些细节。

因此，较好的上下文管理不应只考虑“怎么压缩”，还要考虑：

**如果以后发现压缩错了，怎样取回原始信息？**

这就引出了按需检索（Just-in-Time Retrieval）。

## 九、按需检索：不在上下文里，不等于信息已经丢失

设想 Agent 完成了一轮网关日志分析。

它不再每次携带两千行日志，而是记录：

```text
已确认事实：
- 网关返回 upstream unavailable
- 后端直连正常
- 同一网关上的其他模型正常

原始资料：
- gateway-error.log
- backend-health.json
- routing-config.yaml

下一步：
- 检查目标模型的路由和健康状态
```

这些路径只是教学示例，不代表真实生产系统中的文件。

当下一步不需要原始日志时，模型依靠简短状态即可继续。

当模型需要核对具体错误时间或路由标识时，再使用文件读取或检索工具访问原始材料。

这就是：

**活动上下文保留当前必要信息，外部资料保存可以重新获取的细节。**

它不仅适用于日志，也适用于大型代码仓库、企业知识库和长篇研究资料。

例如一个编程 Agent 不需要每轮携带整个仓库的全部代码，只需要知道当前相关模块，必要时再次读取具体文件。

Anthropic 在 Context Engineering 中介绍了这种 Just-in-Time Context 的思想：通过文件路径、链接、查询等轻量线索，让 Agent 在运行过程中逐步获取所需资料。

这里还有一个边界：**按需读取能减少预先输入的无关资料，但也会增加工具调用和检索时间。**

因此，它与提前加载全文并非绝对的优劣关系。

对于短小、稳定、必需的内容，直接放进上下文可能更简单；对于大量、动态、只有部分相关的资料，按需读取更有优势。

## 十、为什么 Compaction 和按需检索仍然不能替代 Checkpoint？

我们继续观察这个 Qwen 故障排查任务。

假设 Agent 已经完成十几轮调查，接下来准备修改测试环境的路由配置。

就在此时，Agent 进程异常退出。

第二天重新启动时，即使它能够重新读取聊天摘要，也还有几个问题：

任务执行到哪一步了？

哪些工具操作已经完成？

哪些状态已经写入外部系统？

是否有一项操作执行成功，但工具返回之前超时了？

单纯的自然语言摘要不一定能可靠回答这些问题。

于是我们需要 **Checkpoint（状态检查点）**。

以 LangGraph 为例，Checkpoint 保存的是执行图在某一时刻的 State（状态）快照，而不只是人类可读的对话摘要。它可以支持线程恢复、中断后继续和故障处理。

可以把区别理解成：

| 机制 | 主要解决的问题 |
|---|---|
| Compaction | 历史太多，怎样缩小后续模型上下文 |
| Checkpoint | 执行中断后，怎样恢复任务状态 |
| Tool Result Clearing | 旧工具输出不再需要时，怎样移出活动上下文 |
| Retrieval | 需要细节时，怎样重新找到外部资料 |

四者可以组合使用。

例如，Checkpoint 保存“现在执行到路由检查步骤”；Compaction 保存“此前已排除哪些故障”；外部文件保存原始日志；Retrieval 负责需要时读取具体记录。

特别要注意：**保存了 Checkpoint，不代表所有 Checkpoint 内容都应该自动注入下一次模型请求。**

状态持久化与上下文选择仍然是两个不同问题。

而且，恢复了 Agent 的执行状态，也不意味着外部业务操作天然具备幂等性。对于修改配置、写入数据库等可能产生副作用的操作，还必须单独设计操作确认和重试机制。

## 十一、短期状态和长期记忆，有什么不同？

现在又出现一个新问题。

如果这个 Agent 不仅要排查今天的 Qwen 故障，以后还要处理很多其他问题，那么哪些内容值得跨任务长期保留？

例如：

> 当前 Qwen 网关发生 503 故障。

这属于当前任务状态。故障解决后，它不应该永远作为一个仍在发生的问题影响后续工作。

但下面的信息可能长期有效：

> 这个环境使用某种模型网关架构，模型服务通过指定方式注册和路由。

如果经过确认且仍然有效，它可以成为以后排障的基础知识。

这就涉及 **Long-Term Memory（长期记忆）**。

LangGraph 区分两类持久化：

**Checkpointer** 面向一个执行线程，保存任务运行状态。

**Store** 面向跨线程的数据，保存可在其他会话中重新使用的信息。

因此，可以建立一个简单区分：

- **当前任务状态**：这次故障排查到了哪里？
- **长期知识或记忆**：以后遇到类似任务，哪些稳定事实与经验值得再次使用？

长期记忆也不等于把所有旧任务的摘要堆起来。

如果记忆里充满过期配置、临时猜测和已经失效的环境信息，Agent 反而可能做出错误判断。

所以长期记忆需要考虑信息的有效期、来源、更新和适用范围。

## 十二、Prompt Caching 又是什么？它与上下文压缩有何关系？

这里还有一个非常容易混淆的概念：Prompt Caching。

假设 Agent 的系统指令、工具定义和部分历史记录在连续多次请求中完全相同。

如果底层服务可以复用之前对这段输入所做的部分计算，就可以降低重复处理的成本和延迟。

这就是 Prompt Caching 所要解决的问题。

但它并没有直接解决“哪些内容应该输入模型”。

即使某段历史命中了缓存，它通常仍然属于这次调用的有效上下文，仍占用上下文窗口中的位置。

而 Compaction 是用更短的表示替代部分历史。

二者解决的主要问题不同：

| 技术 | 减少上下文内容 | 减少重复计算 |
|---|---|---|
| Prompt Caching | 通常不减少 | 是 |
| Compaction | 是 | 不一定 |
| Tool Result Clearing | 是 | 不必依靠模型计算 |
| 按需检索 | 减少预先加载的内容 | 可能增加工具调用 |

而且还有一个有趣的权衡：

如果每一轮都随意重写前面的消息，可能降低提示缓存命中率。

如果进行了大规模 Compaction，原来可以复用的长前缀也可能发生变化。

所以，**最低 Token 数量不一定直接等于最低实际成本。**

真正设计 Harness 时，要同时观察模型效果、输入量、缓存命中、延迟和外部工具成本。

## 十三、将这些机制放在一起，一次 Agent 任务究竟怎样运行？

现在我们终于可以把完整过程串起来。

仍以 Qwen 网关异常为例。

**第一步：接收任务。**

Harness 取得用户目标、必要指令、当前任务状态和可用工具，然后调用模型。

模型判断应该先确认异常现象，而不是直接修改配置。

**第二步：执行工具。**

Harness 调用日志查询工具，得到大量运行日志，并将必要结果提供给模型。

模型发现网关出现 upstream unavailable，但还无法确定原因。

**第三步：继续调查。**

Harness 再执行后端直连测试和其他模型调用对照。

模型据此缩小排查范围，优先关注路由与健康状态。

**第四步：缩减不再需要的上下文。**

一些已经分析完毕的原始工具结果，可以在保留外部记录和重要结论后，从活动上下文移除。

**第五步：保存任务状态。**

Harness 把当前步骤、已确认事实、未完成事项等写入任务状态或 Checkpoint。

**第六步：必要时进行 Compaction。**

如果历史已经很长，就把过去的推理与执行记录压缩成能够支持后续任务的状态表示。

此处的核心不是保留所有过程，而是让 Agent 继续排查时不丢失关键依据。

**第七步：下一轮重新组装上下文。**

Harness 根据当前目标、持久状态、必要历史和外部资料引用，构造新的模型输入。

如果模型需要核对以前的一段日志，再调用工具取回。

**第八步：完成任务并更新长期信息。**

任务结束后，当前故障状态关闭；其中经过确认、对未来仍有价值的稳定知识，可按应用的记忆策略保存。

这条执行链说明：

**Harness 不需要把所有历史永久放在模型面前，而是持续在当前任务状态、历史摘要和外部可回取资料之间组织信息。**

不同 Harness 的实现可能很不一样，有些机制由 API 提供，有些由 SDK 提供，有些由应用开发者自行实现。但整体问题是相通的。

## 十四、Harness 究竟应该依据什么判断“信息值不值得继续携带”？

走到这里，我们可以建立一个实用的判断方法。

不要先问“这段信息是不是重要”。

应该先问：

**如果下一次模型调用没有这段信息，会不会明显影响它完成当前任务？**

然后区分三种情况。

### 情况一：缺少它就容易做错下一步

例如，用户禁止修改生产配置；或者已经确认后端直连成功。

这些内容应继续作为模型当前决策的依据。

### 情况二：当前不需要，但未来可能要核对细节

例如，网关日志全文、某份部署配置、某个源码文件。

可以保存到外部，携带来源位置，必要时重新读取。

### 情况三：已经失去作用，而且不需要恢复

例如，重复出现的相同报错、已被确凿证据排除的旧猜测、无意义的重复工具输出。

这些内容可以清理。

这不是一套可以永远准确预测信息价值的算法。

真正的难点在于：**信息对未来任务的价值，可能要到未来才知道。**

因此，较好的设计不是要求模型一次就无误地预测全部未来需求，而是尽量让压缩具有可恢复性。

能安全回查的信息，就不必长期占据活动上下文。

不能安全回查、但对任务关键的信息，就应更加慎重地保存。

## 十五、怎么判断我们的上下文管理设计是否有效？

最后不能只评估压缩比例。

假设两个 Harness 都能把 100K Token 的历史压缩为 10K Token。

其中一个忘记了用户不允许修改生产环境的约束，另一个没有忘记。

即使压缩率完全相同，它们的实际质量也不同。

因此，上下文管理至少要从三个方向评估。

**第一，后续任务有没有做对。**

压缩前后，模型是否还能定位故障、遵守约束、正确选择工具和完成下一步？

**第二，重要状态有没有被扭曲。**

例如，“怀疑路由异常”是否被错误升级成“确认路由异常”？已经完成的操作是否被忘记并重复执行？

**第三，是否真的减少了成本与复杂度。**

上下文 Token 有没有下降？是否因此增加过多的检索调用？压缩带来的缓存损失是否抵消了收益？

为了识别 Compaction 本身的价值，可以固定同一份 Agent 历史，比较完整历史与压缩历史在后续任务中的表现。

如果完整历史能完成任务、压缩历史却失败，就进一步定位丢失了哪项必要信息。

这比要求压缩模型永远遵守几十条保留规则更有针对性。

## 十六、回到最初的问题：哪些信息值得反复输入？

现在可以给出一个更准确的答案：

**值得反复输入的，不一定是历史中最重要、最新或篇幅最多的信息，而是当前这一步真正需要、且不能安全地通过其他方式获取的信息。**

Harness 的上下文管理，就是围绕这个原则持续做出选择。

当模型窗口很小时，主要挑战是如何把历史压缩到能放进去。

当模型窗口越来越大时，主要挑战逐渐转变为怎样控制无关信息、延续正确状态、利用缓存，并让必要细节能够随时恢复。

所以 Harness 上下文管理并不是一个独立的摘要功能，而是一组相互协作的机制：

**上下文组装决定这轮看什么；Compaction 保留长期任务的连续性；工具结果清理移除过时负担；Checkpoint 支持执行恢复；长期记忆保存跨任务知识；按需检索让信息不必永久占据当前窗口。**

理解这组关系，才真正理解了为什么今天的大模型即使拥有很长的上下文窗口，Agent Harness 仍然需要专门的上下文管理。
