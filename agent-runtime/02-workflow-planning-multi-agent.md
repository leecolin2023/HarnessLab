# 02 · Workflow、Planning 与 Multi-Agent：复杂任务应该由谁决定下一步？

> **学习目标**：理解固定工作流与模型动态决策怎样配合；明确什么情况下需要显式规划、独立检查或多个 Agent。
>
> **贯穿任务**：统计岗位职责或任职要求中出现 RAG 的岗位，分析相关技术要求，区分必备与优先条件，并生成可回查职位 ID 与原文依据的报告。
>
> 本篇承接 [01 · Agent Loop 的运行机制](./01-agent-loop-execution-mechanism.md)。01 讨论“模型的一次工具请求如何变成执行、反馈与下一步”；02 研究更上层的问题：**一整项工作应该按什么顺序推进，每一步由程序决定还是由模型决定？**
>
> **实现状态**：HarnessLab 目前的 [SDK Minimal Phase 0](./labs/sdk-minimal-phase0/README.md) 只运行隔离目录的 Bash 演示并统计 Session 事件，尚未实现本文的 JD Workflow、Planner、Checker 或多 Agent。下文的示例流程和代码均为教学设计，不是已完成的实验结果。

## 一、Agent 已经能自己调用工具，为什么还要设计工作流程？

现在我们希望 Agent 完成一项比执行 `pwd` 复杂得多的工作：

> 在一批完整招聘 JD 中，找出岗位职责或任职要求出现 RAG 的岗位，统计相关技术要求，区分必备与加分项，最后生成有职位证据的报告。

如果只向一个有 Shell 工具的 Agent 发送这句话，模型可以自己决定先读哪个文件、怎样分析、何时生成报告。

但是，一个看起来合理的报告仍可能存在几个问题。

例如：岗位 A 和岗位 B 实际具有相同的职位 ID，却被算了两次；模型把“优先熟悉 Milvus”统计为“必须掌握 Milvus”；报告声称筛查了 500 条 JD，实际上只读取了前 50 条；甚至报告引用的职位 ID 无法找到原文。

这些错误有一个共同点：**模型完成了某些操作，却不能保证它按业务口径完成了整项工作。**

解决办法不一定是增加一个更聪明的 Planner，更不一定是马上拆成多个 Agent。我们应该先判断：

**这项工作里，哪些步骤本来就是确定的，哪些步骤才真正需要模型临场决策？**

以当前任务为例，可以先把必要工作拆开：

| 需要做什么 | 为什么需要 | 谁更适合控制 |
| --- | --- | --- |
| 固定数据快照和统计范围 | 避免不同时间读取不同版本 | 程序 |
| 选取符合 RAG 出现条件的 JD | 必须遵守明确字段和匹配口径 | 规则程序，边界样本单独处理 |
| 按稳定职位 ID 去重 | 防止重复计数 | 程序 |
| 从 JD 识别 Python、Milvus、Reranker 等技术及其要求性质 | 需要理解语言、条件和上下文 | 模型或规则与模型组合 |
| 对缺失信息、冲突表述作进一步查证 | 下一步可能取决于当前发现 | 受约束的 Agent |
| 汇总统计、核对分母、检查引用 ID | 能形成明确的校验条件 | 程序 |
| 判断语义证据不足的结论是否需要复核 | 不能仅靠简单公式检查 | 模型辅助或人工 |
| 输出最终报告 | 有固定结构和必要字段 | 程序组织，模型负责适合生成的解释 |

**工作步骤不是因为用了模型就必须交给模型控制。** 对确定性操作，程序可以提供更明确的执行范围、稳定性和可复核性。

接下来先看最简单的做法。

## 二、如果步骤已经确定，为什么不直接使用 Workflow？

### 1. Workflow 究竟是什么？

在这里，**Workflow（工作流）** 指应用事先规定任务的步骤、依赖和分支：即使某一步调用了模型，也由程序决定下一阶段如何衔接。

例如，第一版 JD 分析可以采用：

~~~text
读取固定的脱敏 JD 快照
            ↓
选出符合统计口径的岗位
            ↓
按 job_id 去重
            ↓
逐条提取技术要求及证据
            ↓
核查提取结果
            ↓
汇总频次、计算分母
            ↓
生成 report.md
~~~

其中“逐条提取技术要求”可以使用大模型，但进入这一阶段的时机、输入数据结构、结果必须包含哪些字段，都由应用规定。

例如，一个**教学伪代码**可以是：

~~~python
snapshot = load_approved_snapshot()
jobs = deduplicate(
    select_jobs_by_defined_rag_rule(snapshot),
    key="job_id",
)

extractions = [
    extract_requirements_with_model(job)
    for job in jobs
]
checked = validate_extractions(extractions, jobs)
statistics = aggregate(checked)
report = render_report(statistics, checked)
save_report(report)
~~~

这不是 HarnessLab 当前可直接运行的代码。它用于说明：即使某一阶段使用模型，**外层执行顺序仍然可以由 Python 程序掌握**。

### 2. 固定步骤为什么反而有价值？

假设每次让模型自由决定是否去重。它可能做，也可能忘记。

改成 Workflow 后，程序保证在统计之前执行去重；不需要浪费模型推理来决定“是否遵守必需的统计口径”。

固定控制还能让失败范围更清晰。例如，报告分母不对时，可以先检查筛选和去重阶段，而不必从一段冗长的模型对话中猜测它漏了什么。

这种结构的优势不是“完全不使用 AI”，而是**让 AI 集中处理需要理解和判断的部分**。

### 3. Workflow 一定只能是一条直线吗？

不一定。固定工作流同样可以包含条件判断、循环、并行与失败分支。

例如：

~~~text
模型提取一条 JD 的技术要求
               ↓
程序检查职位 ID、证据和结果结构
          ↙             ↘
        通过             不通过
          ↓                ↓
       进入汇总         返回错误原因
                           ↓
                     有限次数修正
                           ↓
                     通过或终止
~~~

这里虽然出现循环，但**循环是否继续由程序按照预设规则判断**；它与 01 中“模型每轮可以自主选择下一次工具调用”的 Agent Loop 不是同一个控制层次。

同样，Workflow 可以通过模型输出决定进入哪个预定义分支，但**可走的路径集合与分支处理规则**仍由应用设计。

这也是 Workflow 与 Agent 的关键分界：不是有没有模型、有没有循环，而是**谁掌握下一步行动的控制权**。

## 三、什么时候固定 Workflow 不够，需要 Agent 动态决定下一步？

考虑一条具体 JD：

> 岗位职责涉及 RAG 知识检索；具备向量数据库实践经验者优先；熟悉 Milvus 或 FAISS 可加分。

对于这类描述，我们可以要求模型抽取技术名和条件性质，再按照固定规则统计。

但假设我们又发现一条记录：

> 岗位职责写有 RAG 系统维护，任职要求没有列出具体技术，详情页引用了一份补充说明。

系统原本只读取当前 JD 的步骤，可能无法回答“相关技术要求到底有哪些”。

此时有两种做法：

**做法 A：扩展固定 Workflow。** 规定遇到“引用补充说明”时，查询补充文件；找不到则标记信息不足。若这种情况规则明确、出现频繁，固定分支通常足够。

**做法 B：允许模型在限定工具中选择下一步。** 如果补充资料关系复杂、需要根据每次查到的内容决定继续查什么，就可以让 Agent 动态检索与追查，直到得到足够证据或达到限制。

~~~text
读取 JD
   ↓
发现“详见补充说明”
   ↓
Agent 决定查询对应文件
   ↓
工具返回：补充说明引用了新版要求
   ↓
Agent 决定继续读取新版要求
   ↓
获得证据或明确无法确认
   ↓
回到统一的统计与校验环节
~~~

这是一条**条件性的教学示例**，不代表目前 JD 数据中已存在这条引用链，也不代表项目已实现该工具。

真正让 Agent 有价值的，不是“它会做多步任务”，而是**执行过程中出现了新信息，下一步无法完全依靠事先写好的路径确定**。

因此，可以用一个判断顺序：

1. 规则能够覆盖这类情况吗？能覆盖就优先写成程序。
2. 若规则难以覆盖，模型能否在有限的只读工具中作出可回查的行动决策？
3. 即使允许动态决策，数据范围、权限和最终验收是否仍然可以由程序控制？

如果第三个问题没有答案，增加自主性通常只会让失误更难定位。

## 四、既然 Agent 会决定下一步，为什么还需要 Planning？

在 01 中，我们看到模型可以在每轮工具执行后重新选择行动。那为什么还要专门研究 **Planning（规划）**？

因为“知道下一步做什么”和“知道整项工作还差哪些部分”是两个不同的问题。

对 `pwd`、`ls` 这类简单任务，模型不必先生成正式计划；直接判断下一次工具调用即可。

但对数百份 JD 的研究任务，模型可能先花大量时间分析技术名称，最后才发现还没明确分母、重复记录和证据范围。此时即使单次工具调用都成功，整体工作仍可能返工。

### 1. 显式计划需要解决什么？

它应该把任务目标转化为一份**可检查、可更新的工作安排**。

例如：

~~~yaml
goal: 统计指定 JD 快照中的 RAG 岗位技术要求

scope:
  source: 固定脱敏快照
  fields: 岗位职责、任职要求
  dedupe_key: job_id

steps:
  - name: 确认 RAG 匹配与排除口径
    status: pending
  - name: 筛选并去重候选岗位
    status: pending
  - name: 提取技术要求及原文证据
    status: pending
  - name: 区分 required / preferred / unspecified
    status: pending
  - name: 检查分母和引用完整性
    status: pending
  - name: 生成报告
    status: pending

open_questions:
  - 出现 RAGFlow 是否按 RAG 命中？
  - 否定或排除性描述是否计入？
~~~

这里是用于理解的**示意计划**，并非某个 SDK 的默认计划格式，也未经过用户对统计口径的确认。

这份计划有三个用途：

- **明确完成条件**：不能只因为报告文件生成，就跳过证据检查。
- **暴露未知项**：例如 RAGFlow 是否计入、否定句如何处理，必须在统计前确定。
- **跟踪偏差**：如果新证据推翻了原先的提取结论，应能指出需要重做哪一步。

### 2. Planning 与 Workflow 怎样区分？

- **Workflow** 规定工作由哪些阶段组成、阶段如何衔接和哪些边界不能突破。
- **Planning** 决定这一次任务打算如何推进，包括具体子任务、所需资料、先后顺序和待解决问题。
- **Agent Loop** 执行一个又一个模型—工具步骤，接收反馈并继续。

三者可以组合，也可以只使用其中一部分。

例如，应用可以固定“筛选 → 分析 → 校验 → 报告”的大流程，在“分析”阶段让 Agent 临时制定对可疑 JD 的查证计划，再用 Agent Loop 执行。

### 3. 谁生成计划？计划是否必须一直遵守？

计划可以由程序模板生成，也可以由模型提出，还可以由人先确定目标和边界。

关键不在于格式是不是 YAML，而在于**哪些内容允许调整**。

例如，模型发现需要额外检查某条 JD 的补充说明，可以增加一个查证步骤；但不能擅自把“只统计岗位职责和任职要求”改成“统计招聘网站所有文本”，更不能在没有说明的情况下改变统计分母。

因此：

**计划是帮助推进工作的中间产物，而不是高于任务目标和数据口径的命令。** 

计划可能需要随证据修订，但对统计规则、权限范围等约束的修改，应遵循预先确定的授权方式。

### 4. 什么时候不值得显式规划？

如果任务只有“读取一条记录 → 提取三个字段 → 输出 JSON”，先调用一次模型生成计划，可能只增加延迟和 Token 成本。

只有任务包含较长的依赖链、容易遗漏必要工作、多个未知条件或明确的执行审查要求时，才更值得引入显式计划。

**不是所有 Agent 都需要一个独立的 Planner。**

## 五、怎样把 Workflow 与 Agent 组合，而不是让模型控制全部工作？

现在可以为 JD 研究任务设计一个更实用的组合方案：

~~~text
               用户任务
                  ↓
       固定统计范围与数据快照
                  ↓
          程序筛选、去重
                  ↓
        批量模型提取技术要求
                  ↓
      程序检查结构、证据与口径
           ↙             ↘
        可确认            需补充查证
           ↓                 ↓
        进入汇总      Agent 在限定工具内追查
           ↑                 ↓
           └──── 有证据的补充结果
                  ↓
         程序汇总与生成报告
                  ↓
         最终校验与交付
~~~

这个方案的核心不是“固定流程和 Agent 各占一半”，而是根据可控性分配职责：

- **数据范围、去重、统计分母**：能确定的就由程序完成。
- **技术要求理解、条件性质判断**：由模型承担语义分析。
- **需要依据新证据不断查证的例外**：在权限和步数限制下由 Agent 决定行动。
- **报告是否符合结构要求、职位 ID 能否回查**：由程序验证。
- **仍存在无法裁决的语义争议**：保留不确定性或转人工复核。

这与直接“让 Agent 随意读文件、最后写报告”最大的区别是：**变化发生在局部，关键业务约束仍然稳定。**

### Checker 应该放在哪里？

例如，模型返回：

~~~json
{
  "job_id": "J001",
  "technology": "Milvus",
  "requirement": "required",
  "evidence": "熟悉 Milvus 者优先"
}
~~~

代码可以检查字段完整性、`job_id` 是否存在、证据文本能否在原 JD 中定位。

但是这里还有一个语义问题：**“优先”与 `required` 不一致。**

可以进一步设计：

1. **确定性 Checker**：检查 Schema、职位 ID、重复记录、证据定位和计数口径。
2. **语义 Checker**：对模型提取的技术和“必备/优先”判断进行复核。
3. **有限修正**：把明确错误及原文证据反馈给提取步骤，最多修正预设次数。
4. **无法解决**：标记待复核，不强行输出确定结论。

这里的 Checker 可以是普通 Python 函数，也可以是一次单独的模型调用。**增加一个 Checker 阶段，不等于必须增加一个 Checker Agent。**

### 两种循环为什么不能混为一谈？

本篇实际上涉及两种不同层次的循环：

- **内部 Agent Loop**：模型请求工具、工具返回、模型继续判断；由 Agent Runtime 组织。
- **外部业务修正循环**：应用检查结果是否符合任务标准，决定是否重做某个阶段；由 Workflow 或业务控制器组织。

内部 Loop 结束，只说明这一次模型—工具处理走到了终点；外部 Checker 不通过，仍可能需要新的处理阶段。

这个区别有助于避免把“多次模型调用”误认为“系统已经具备业务自我验证能力”。

## 六、Planner、Researcher、Writer、Checker 一定要拆成四个 Agent 吗？

现在我们有了规划、查证、生成和验证这些环节。一个很自然的想法是：

> 给每个环节起一个角色名称，再创建四个 Agent，是不是就更专业、更可靠？

未必。

**功能分工不等于执行主体必须拆分。**

同一个 Agent 可以在不同阶段承担分析和写作，也可以由 Python 程序顺序调用两次不同 Prompt；这些方案都不必创建四个独立 Agent。

### 1. 什么情况下单 Agent 更合适？

如果任务数据不大、所需工具相近、没有严格的权限隔离，且单个 Agent 能稳定完成动态查证，那么保留单 Agent 通常更简单。

可以让应用固定必要阶段，让一个 Agent 负责阶段中的不确定行动，再由程序校验。

这样不需要在多个 Agent 间同步上下文，也不需要处理它们的重复检索、相互矛盾和结果合并。

### 2. 什么情况下值得引入多个 Agent？

关键看拆分是否解决了真实问题。

例如：

- **独立权限或环境**：负责读取数据的 Agent 只能访问只读工具；负责交付成果的执行主体只允许写指定目录。
- **任务能够独立并行**：互不依赖的资料查证可以并发执行，然后统一合并与核查。
- **上下文确实需要隔离**：某个长期子任务有自己的大量材料与工作历史，放在主 Agent 中会干扰主任务。
- **职责需要独立治理**：不同子任务需要独立的超时、预算、日志和失败处理。

即使符合这些条件，也需要考虑通信、上下文传递、结果冲突、调试成本和延迟是否抵消了收益。

### 3. Multi-Agent 怎样协调？

假设真的需要拆成两个独立研究子任务：

~~~text
                    主任务
                      ↓
              确定数据与约束
                      ↓
             Orchestrator（协调）
                ↙           ↘
      Agent A：查证术语    Agent B：查证岗位证据
                ↘           ↙
                 汇总子任务结果
                      ↓
              统一核验与报告
~~~

这里至少需要明确四件事：

- **分派**：每个子 Agent 负责哪些任务、可使用哪些工具。
- **结果契约**：各自必须返回职位 ID、证据及状态，而不只是自然语言结论。
- **失败与冲突**：其中一个子任务失败或者结论不一致，谁负责处理。
- **最终责任**：由谁决定整个工作是否已经完成。

多 Agent 的好处不是“出现更多模型”，而是**把确实需要独立执行和独立管理的工作拆开，同时保留整体协调机制**。

### 4. Multi-Agent 一定比单 Agent 准确吗？

没有这样的保证。

比如把相同的 JD 和相同的任务同时发给三个 Agent，再投票，可能增加开销，却不一定消除相同来源的误解。不同 Agent 之间如果共享了错误的前提，还可能一起给出错误结论。

因此，比较的重点应是同一个样本范围和任务标准下的：**可回查错误数、遗漏率、实际调用次数、延迟、成本与失败定位难度**，而不是 Agent 数量。

## 七、DeepSeek Harness 已经有什么？新 Agent 又需要自己实现什么？

到这里可以回到实际工程：上面的 Workflow、规划、Checker、多 Agent，是不是已经包含在我们正在使用的 DeepSeek Harness 中？

要分清**框架存在相应能力**、**当前 Profile 实际加载了什么**、**应用是否真的实现业务逻辑**。

| 能力 | DeepSeek Harness 框架层 | 当前 HarnessLab Phase 0 | 下一阶段需要做什么 |
| --- | --- | --- | --- |
| 模型—工具循环 | 已有 Agent Loop、模型接口与工具执行机制 | 通过 `sdk-minimal` 使用该基础能力 | 不重复实现内部 Loop |
| Bash 与 Session | Profile 可提供 Shell、Session 记录 | 已有 SDK 入口、隔离配置、日志统计代码 | 获取真实运行轨迹以完成验证 |
| 固定 JD Workflow | 可由应用代码编排；框架另有工作流相关扩展 | **尚未实现 JD 业务流程** | 在应用层明确筛选、分析、校验、汇总阶段 |
| 显式 Planning | 框架有可选的 Plan Mode 等机制 | **未启用业务规划阶段** | 先设计计划结构和何时需要规划 |
| 业务 Checker | 可利用模型与工具机制实现 | **尚无 JD 语义与证据校验** | 先做确定性检查，再按需补语义检查 |
| Subagent / Multi-Agent | 框架另有子 Agent 能力家族及相关插件 | **`sdk-minimal` 默认不含 Subagent** | 只有证明确有必要时再配置并验证 |
| 最终业务验收 | Runtime 正常完成不是业务成功 | Phase 0 不产出 JD 业务报告 | 检查报告、统计分母及引用证据 |

这也解释了一个容易误解的地方：

Google ADK 中有 `SequentialAgent`、`ParallelAgent` 和 `LoopAgent` 等工作流类，但**不能据此推断当前 DeepSeek Harness 的 Python SDK 存在同名类或自动具备同样的编排方式**。

DeepSeek Harness 的 [Workflow 能力家族](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/workflow/README.zh.md)、[Plan Mode](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/plan/plan-mode/README.zh.md) 与 [Subagent 能力家族](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/subagent/README.zh.md) 确实存在，但它们的职责和装配条件各不相同。尤其官方的 [`sdk-minimal` Profile](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/bundle/sdk-minimal/README.zh.md) 明确没有默认包含 Subagent。

所以，按照 [学习路线阶段 3](./LEARNING_PATH.md)，更合理的起步方式是：

**先在应用层使用 Python 控制器串联必要步骤，用 Harness 处理模型与工具循环；观察到动态规划或多 Agent 的实际收益，再选择是否接入对应扩展。**

这里讨论的是设计与后续验证路径，并没有声称仓库当前已实现 Planner、Checker 或 Multi-Agent。

## 八、怎样判断下一阶段应该增加哪种机制？

不要一次性同时增加规划器、子 Agent、复杂工作流和多个检查器，否则结果变好或变差时，很难知道原因。

可以在**同一份固定、脱敏、带有预期答案的完整 JD 样本**上比较几种方案。

| 方案 | 增加了什么 | 主要观察什么 |
| --- | --- | --- |
| A：固定 Workflow | 程序控制筛选、去重、提取、汇总 | 基础正确性与可复现性 |
| B：Workflow + Checker | 显式的结构、证据和语义核查 | 是否减少真实错误，是否产生额外误判 |
| C：Workflow + 局部 Agent | 对有疑问的记录动态查证 | 是否补足证据，增加多少调用成本 |
| D：再按需添加 Planning | 对长任务形成可更新工作安排 | 是否减少遗漏与返工 |
| E：仅在有必要时 Multi-Agent | 独立执行上下文或任务并行 | 是否得到足以抵消协调开销的收益 |

这里并不是要求把 A—E 全部开发一遍。应根据上一阶段真正暴露的问题，选择**最小的下一项改造**。

### 为什么验证不能只看最终报告写得好不好？

还是以那条“熟悉 Milvus 者优先”为例。

如果报告把 Milvus 归类为必备，那么即使文案通顺、格式漂亮，核心判断也是错的。

因此，至少要让评估能够观察：

- **数据范围**：候选岗位数、去重后分母是否正确。
- **字段语义**：技术要求的 `required`、`preferred`、`unspecified` 等归类是否符合原文。
- **证据完整性**：职位 ID 和对应原文是否能够回查。
- **行为过程**：哪些模型调用或工具操作真正改变了结果。
- **执行代价**：额外的模型请求、耗时与错误恢复。

若 Checker 只是把错误从一种类型换成另一种类型，或多 Agent 显著增加成本却没有改善可复核结果，就没有充分理由增加复杂性。

这也是整个学习路径里“先实现—观察—解释—改进”的意义：**先知道是哪一步不够好，再选择能改变这一问题的机制。**

## 九、这篇文章应该留下怎样的认识？

从固定 JD 统计任务出发，我们得到了四个不同的工程对象：

- **Workflow**：应用规定任务的阶段、依赖和可走的分支，适合控制确定性流程。
- **Planning**：为具体任务组织可检查、可更新的工作安排，适合步骤依赖多、容易遗漏或需要审查的任务。
- **Agent Loop**：模型结合执行反馈持续选择下一步行动，适合局部执行路径难以预先穷尽的工作。
- **Multi-Agent**：在确有独立权限、并行性、上下文或治理需求时，把任务拆给不同执行主体。

它们不是四种必须依次升级的技术等级，而是解决**不同控制问题**的手段。

对于当前 JD Research Agent，优先建设的是一个可靠的 **“固定工作流 + 必要的模型判断 + 明确的结果校验”**。只有当真实样本表明需要动态查证、显式计划或独立子任务时，再按问题添加 Agent 或 Multi-Agent 机制。

**真正要学会的不是“怎么搭四个 Agent”，而是面对一项任务，能解释为什么这一步由程序控制、那一步交给模型决策，以及何时值得引入新的执行主体。**
