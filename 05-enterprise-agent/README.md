# 05 · 企业 Agent 场景与需求规格

**定位：** 明确企业 Agent 的业务目标与技术环境约束，沉淀不绑定具体开发框架的需求合同，并提供各框架的实现设计入口。

## 研究场景

- [离线部署](./offline-deployment/)：无公网环境、安装升级、数据隔离、依赖治理。
- [Office 能力](./office-capabilities/)：文件读取/定位/修改、格式保真、验证与交付。
- [银行 Skills](./banking-skills/)：金融业务规则、证据溯源、权限、审查与可复核性。

这些目录是**场景探索与能力研究**，不是正式的产品需求基线。

## 正式工程产物

| 目录 | 定位 | 不应包含 |
| --- | --- | --- |
| [specifications](./specifications/) | **框架无关的产品需求规格书 SRS**、需求索引和验收标准 | 针对某个框架的类名、插件 API、模块文件路径 |
| [implementation-profiles](./implementation-profiles/) | **框架相关的实现设计**，把同一个需求映射到 DSH、LangGraph 等 | 反向更改业务目标而不更新 SRS |
| [../06-engineering-decisions](../06-engineering-decisions/) | 决策记录：采用哪条路径，为什么，怎样追踪到产品落地 | 把单一技术偏好写成已批准需求 |

## 基本流转

企业场景与需求证据 → SRS（需求 ID、验收标准）→ 各框架实现方案 → 实验验证 → 工程决策 → 产品仓库实施。

**重要：** 不强制该流程瀑布化。研发实验可能导致需求澄清，但 SRS 与实现方案的职责应保持分离。
