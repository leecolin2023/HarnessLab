# SenseWright Learning｜把一个 OCR 模型变成企业级模型服务

> 学习问题：**模型能够识别文字，为什么还需要模型服务平台？服务化到底增添了哪些机制？**
>
> 材料：当前 HarnessLab EXP-MS-001 中的 `app/main.py`、`app/provider.py`、`Dockerfile`、`compose.yaml`，以及 PaddleOCR 3.7.0 / PP-OCRv6 官方文档。
>
> 方法：依照 SenseWright Learning V0.6.2 的“问题 → 必要机制 → 代码与证据 → 区分性挑战”重建认识。当前宿主没有独立 D/R 模型调用的可核查 Trace，本文件不宣称已经验证 D/R 运行时隔离；服务器实验未执行，不将预期写成实测。

## 一个先要区分的对象

直接运行 `PaddleOCR(...).predict(image)` 是**模型调用**，解决“这张图有哪些文字”。提供 `POST /v1/ocr` 是**模型服务**，还要解决“谁能调用、以什么协议、何时可用、资源不足怎么办、返回什么稳定格式、故障怎样被发现”。

它们使用的是同一个 OCR 引擎，但各自负责不同的结果。**模型管理**（选哪个模型/版本、资源、发布）又不同于**模型推理**（执行图像的检测和识别）。一个企业采购的产品可以同时提供这些功能，逻辑边界仍然存在。

| 整理结果 | [provider.py:7–36](./app/provider.py#L7-L36) | 将原生输出规范化为文本、识别置信度与坐标列表 |

输入在推理侧的主要路径：**上传字节 → Pillow 图片对象 → NumPy RGB 数组 → PP-OCRv6 检测文字区域 → 按区域识别文字 → 标准化记录**。

注意：PP-OCRv6 检测与识别只是输出**候选文字、位置和得分**，并没有完成借款合同字段语义抽取，也没有保证财报科目匹配正确。“OCR 置信度”和“业务字段识别准确率”是不同指标。

## 核心机制一：控制面和数据面为何分离？

- **控制面（模型交付）**负责模型选择/版本、资源配额、发布和配置；在实验中由环境变量、`compose.yaml`、Docker 镜像及人工发布流程承接。这还**不是**一套完整的模型注册与管理平台。
- **数据面（请求执行）**负责接收图片、鉴权、解码、推理、结果返回；由 Uvicorn/FastAPI + PaddleOCR Provider 承接。
- **资源边界**：Compose 给容器设置 CPU 和内存上限；Python 的 CPU 线程数控制引擎并行粒度；进程信号量控制应用层同时发起的推理次数。这三者**不是同一个并发参数**。

为什么要分开？升级一个模型版本，不应迫使每个业务系统重新实现图片上传、凭证验证和数据解析；调整 NPU/CPU 配额，不应改变业务 API 的含义。

## 核心机制二：SK 鉴权到底保护了什么？

当前 `verify_key()` 能确保错误 SK 无法执行模型推理。但有一个容易误读的细节：

FastAPI 对 `UploadFile = File(...)` 的请求一般会在执行路由函数**之前完成 multipart 解析**。因此，代码中“先 `verify_key` 再 `file.read`”不意味着未经认证的客户端不用上传或不会消耗解析资源。

- 实验能够证明的是 **错误 SK 不会进入 Provider 的预测调用**（需通过控制流检查和错误请求测试）。
- 它**不能**证明：网关级认证、租户权限隔离、SK 轮换、速率限制、防止恶意请求上传。
- 企业正式入口通常需要复用前置代理/网关的认证与限流，并按应用分配权限和调用额度。

**对照思考**：如果在鉴权错误时仍观察到请求解析开销，并不推翻 SK 生效，只说明保护发生的层次不同。

## 核心机制三：限制并发≠模型只能并发一次

当前固定 `asyncio.Semaphore(1)`，单实例一次只向 OCR 引擎送一张图片；超过等待阈值返回 429。

这能验证**应用层过载保护**，却不能据此推断 PP-OCRv6 的 CPU 极限并发就是 1。真实并发还受模型线程、CPU 配额、模型大小、输入大小、实例数和队列策略影响。

有区分力的两个问题：

1. 并发从 1 增加到 4，429 增多，但成功请求耗时不变：说明什么？——可能是应用层限流在保护推理，不是模型性能退化。
2. 顺序请求也很慢，CPU 始终接近上限：说明什么？——更有理由调查 CPU 推理与预处理瓶颈，而不是单纯调高允许并发数。

这个实验可实测成功 QPS、P50/P95、429 比例；**它不能在现有单实例/拒绝策略下直接测得模型最大物理并行能力**。做平台容量规划必须把入口拒绝策略和引擎能力拆开。

## 核心机制四：部署成功、模型就绪和服务可靠是三件事

- **Docker 构建成功**只能说明依赖镜像构建完成，不证明模型能正确装载。
- **`/health/ready` 成功**说明 Provider 初始化完成，不证明识别结果正确。
- **一张样例图识别成功**说明最小链路打通，不证明长时间运行稳定、不同图片有效或业务准确率。
- **固定负载压测通过**才支持“在这个版本/硬件/数据负载下，达到了观察到的性能”。

当前模型在 FastAPI `lifespan` 中同步初始化（经线程池）。启动期间 API 通常尚未接受请求；`/health/live` 和 `/health/ready` **并不能在启动未完成时分别提供可用状态**。如果要求生产可观测启动阶段，需要另行设计，而非因为写了两个 endpoint 就声称已经做到。

Docker 的 `./models:/models` 和 `PADDLEX_HOME=/models` 旨在复用模型缓存，但是否全部模型文件与相关下载缓存都落在该路径，必须通过首次加载和重启观察确认。

## 重建理解：如何迁移到 NPU 模型、LLM 和轻量 VLM？

如果下次把 PP-OCRv6_small 换成某个 LLM 或 VLM：

- **稳定不变：** 身份、权限、服务端点、版本、容量、日志、故障、上线回归的责任。
- **需要改变：** 推理引擎、模型输入/输出协议、资源模型、吞吐指标以及业务质量评测。
- **不能硬统一：** OCR 的“上传图片→文本与坐标”与 LLM 的“消息→Token 流/工具调用”不是同一种输出契约，不应简单用一个 `/v1/ocr` 伪装成所有模型的通用接口。

**本轮最重要的可迁移认识：** 企业真正要稳定交付的不是某个模型文件，而是具备明确协议、资源边界、运行状态和责任归属的**模型服务契约**。
