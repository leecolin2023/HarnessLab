# SenseWright Learning｜从一次财报识别理解“模型服务”

> **这次只解决一个问题：为什么已经能运行的 PaddleOCR，还需要被纳入企业统一管理，有时还要作为独立服务交付？**
>
> 学习顺序：真实问题 → 最简单的做法 → 遇到的困难 → 增加的工程机制 → 当前源码怎样实现。**先不需要执行任何命令。**

## 一、先想象一个你已经熟悉的业务场景

银行的财务报表智能分析工具中，客户经理上传一份财报。工具需要知道图片里写了什么，例如：

> 营业收入 12,000 万元

PaddleOCR 的工作，就是尝试从图片中找出这些文字，并告诉调用者它们大概在图片的哪个位置。

**如果只有财报工具一个程序要用 OCR，最简单的办法是什么？**

把 PaddleOCR 安装到财报程序的运行环境里，由它自己加载模型、读取图片、直接识别。**在资源足够、负载简单、无需统一治理的情况下，这完全可能是合适的做法。**

**但现在换一个条件：银行的 NPU 算力池有限。**

尽管只有财报工具需要 OCR，同一个算力池可能还运行着其他大模型。财报月底集中上传时，OCR 应该占用多少算力？是否挤占其他模型？闲时能否释放资源？升级模型时如何验证容量仍然足够？

这些问题与“有几个 OCR 使用方”无关；即使只有**一个** OCR 应用，也需要有人统一管理算力、分配资源、监控占用和负责模型交付。

再换一个条件：合同审核、影像归档、材料校验也都需要 OCR。如果每个业务程序自己安装、加载和升级同一个模型，会额外产生重复部署、重复占用和接口不一致的问题。此时把模型作为公共服务提供出来，更容易统一维护。

**所以要区分两个决定，而不是把它们混成一个：**

- **是否纳入统一资源与生命周期管理？** 算力昂贵、有限、需跨模型协调或有严格安全要求时，即使只有一个应用，也可能需要。
- **是否拆成独立的网络服务，让业务系统通过 API 调用？** 当算力需要集中部署、模型与业务应用分别运维、多个应用需要复用时，通常更有价值；但并非唯一方案。

本实验选择“**统一配置与资源约束 + 独立 OCR HTTP 服务**”来观察机制。它**不是**在证明：只要算力有限，就必须为每个模型单独建设一个 HTTP 服务。

注意：当前实验的接口只接受**单张图片**。真实业务上传 PDF 时，需要在其他环节把 PDF 页转换成图片；本轮不学习 PDF 解析。

## 二、一次识别到底发生什么？

先认识三个角色，不引入任何框架名称：

- **业务系统**：有图片、需要文字，例如财报工具。
- **模型服务**：长期运行，负责接收请求、保护模型、交还结果。
- **OCR 模型**：真正分析图片内容、给出文字和位置的计算程序。

现在看一次完整请求。

### 识别之前：服务需要先准备好

想象 OCR 模型像一台扫描设备，不能每有一张图片才现场组装一遍。

在我们的实验中，服务器启动时就准备 Python 运行环境、加载识别模型，让这个程序一直等待请求。

这里加载的主要是两个环节：

1. **文字检测**：先找出图片中哪些位置可能有文字。
2. **文字识别**：再判断这些区域里究竟写了什么。

它们共同完成“图片 → 文字及位置”。此时还没有判断“这是不是营业收入科目”，那属于更上层的业务处理。

### 先解释一个新问题：为什么请求要带 SK？普通 API 不需要吗？

**普通 API 也可能需要身份验证，但不一定叫 SK。** 请求发往另一套程序时，服务需要判断“谁在请求、能否使用”；不过并不是所有 API 都需要单独携带密钥。例如公开查询接口可能允许匿名访问，内部接口也可能已经由登录系统或网关统一校验。

先比较两个你熟悉的场景：

**过去：对公信贷系统的普通业务接口。** 用户登录系统后，浏览器可能自动携带登录后的 Cookie 或访问令牌；也可能由统一网关或内部服务间机制处理身份。业务开发人员只负责后面的业务逻辑，所以并不一定在每个接口里亲自写密钥验证。具体使用哪种方式，仍须以实际系统架构为准。

**现在：财报工具调用独立的 OCR 服务。** 调用方通常不是一个正在浏览器里操作的员工，而是财报工具这套**程序**。模型平台需要知道是哪套程序在使用模型，并决定是否允许它调用、如何记录用量与控制资源。因此，“给应用颁发一份凭证，再由服务验证”是常见做法，API Key 就是其中一种。

这里容易混淆三个名称：

| 名称 | 先理解成什么 | 是否大模型专有 |
| --- | --- | --- |
| **API Key** | 颁发给调用程序的一段秘密字符串，相当于一张调用凭证 | 否 |
| **SK / `sk-`** | `SK` 常写作 Secret Key；`sk-` 是部分厂商密钥的命名前缀，**不是统一协议** | 否 |
| **`Authorization: Bearer ...`** | HTTP 请求头里传递凭证的一种写法；`Bearer` 表示持有该凭证即可出示它 | 否 |

于是一个示意请求可能是：

```http
POST /v1/ocr HTTP/1.1
Authorization: Bearer <这里放应用自己的密钥>
Content-Type: multipart/form-data; boundary=...
```

**注意：上面仅为示意，不是真实密钥。** 也有平台使用 `X-API-Key` 或 `api-key` 请求头，不能把某一个格式当成所有模型 API 的标准。

为什么你到了大模型平台才频繁看见 SK？除了独立服务间调用，大模型推理还常伴随**算力成本、共享资源、按应用用量统计、调用额度与访问范围**等管理需求，API Key 因而成为比较直观的调用凭证。但它不是唯一方案：有些企业会改用短期令牌、服务身份或双向证书；一个长期共享的 API Key 也不能单独替代完整的身份与授权体系。

**现有实验到底做到了什么？** [main.py 中的 `verify_key`](./app/main.py#L53-L57) 把请求头里的 Bearer 凭证同环境变量 `MODEL_API_KEY` 对比；吻合就允许继续，不吻合就返回 401。它目前只有**一把共用密钥**，还不能识别究竟是哪一个业务应用，也没有独立的权限、额度和轮换管理。代码采用普通随机字符串，**并不要求以 `sk-` 开头**。

把这个区分记住：**身份认证问“凭证是否有效”，访问授权问“这个调用方能使用什么”，用量治理问“它可以消耗多少资源”。** 这三个问题可以由同一个平台管理，但不是一件事。

更进一步，API Key 应放在受控的服务端配置中，不应嵌入浏览器代码、提交到 GitHub 或出现在日志中；通过网络调用时应采用 TLS 等安全传输措施。

参考：[微软 API 鉴权综述](https://learn.microsoft.com/en-us/azure/api-management/authentication-authorization-overview)、[Azure AI API Key 使用方式](https://learn.microsoft.com/en-us/azure/api-management/api-management-authenticate-authorize-ai-apis)、[AWS API Key 与使用计划的适用边界](https://docs.aws.amazon.com/apigateway/latest/developerguide/api-gateway-api-usage-plans.html)。

### 请求到来：按顺序走一遍

**第 1 步：业务系统发送图片。** 它访问模型服务提供的地址，并带上一段身份凭证（SK）。这里的“接口”，你先把它理解为业务系统约定好的请求入口。

**第 2 步：模型服务验证能不能使用。** 在本实验里，服务检查请求中的 Bearer 凭证是否与预设 API Key 一致；不一致就拒绝执行 OCR。企业生产平台还可能进一步检查调用应用的具体权限。

**第 3 步：服务检查图片。** 它确认文件类型、体积和像素数量是否在限制内，并把图片变成模型能处理的图像数据。没有限制的话，异常大的文件可能大量占用服务器资源。

**第 4 步：服务判断现在是否有处理位置。** 当前实验设定为一次只让一张图片进入推理。如果已在处理其他图片，新请求可能收到 429，意思是“当前太忙，请稍后再试”。

**第 5 步：OCR 真正开始识别。** 检测模型找文字区域，识别模型把它们读成文字，得到对应位置和置信度。

**第 6 步：服务把结果交还给业务系统。** 返回识别到的文字、位置、得分，以及所用的模型名称和本次推理耗时。业务系统随后才进行科目匹配、财务规则校验等处理。

示意返回结果（**只是帮助理解，不是服务器实测**）：

```json
{
  "model": "PP-OCRv6_small",
  "lines": [
    {"text": "营业收入", "score": 0.96, "box": [10, 20, 125, 48]}
  ]
}
```

至此，整条链路是：

**业务系统给图片 → 服务检查请求 → OCR 模型识别 → 服务交还结果。**

这才是接下来读代码时应当在脑中保持的完整故事。

## 三、为什么这中间多了一个“服务”？真正增加了什么工作？

### 1. 谁能够使用它？

如果模型完全由一个程序在自己进程内调用，通常不需要额外验证远程 API 调用方。但只要通过独立服务向业务程序提供能力，即使只有一个调用方，也需要明确谁能访问、怎样认证以及是否允许使用。

当前代码只使用一把 API Key 判断凭证是否有效。**它还没有真正实现按应用或部门分配权限、调用额度或密钥轮换。** 在企业中，这些功能往往可以复用已有网关产品。

还要注意一个区别：虽然程序的路由函数先检查 SK，再读图片内容，但服务器框架通常已经先解析了上传请求。所以，这个检查能拦住**模型推理**，却不意味着能拦住未授权上传造成的全部资源消耗。

### 2. 同时有十张图片怎么办？

即使只有财报工具一个业务系统，也可能在集中上传时同时发来十张图片。服务器不一定能同时处理十次识别。

当前实验选择一种最容易解释的策略：**每次只执行一次识别；过载时拒绝，而不是让请求无限排队。**

这样能防止服务被堆积请求拖垮，但不能证明 PaddleOCR 本身最多只能并发处理一张图。这里的“一张”是我们的服务程序**人为设定的保护规则**。

以后要做容量评估，需要分别研究：模型自身速度、服务器 CPU/内存、服务允许的并发，以及拒绝请求的策略。

### 3. 怎么知道它已经能用了？

“服务器进程启动了”与“模型加载好了”不是同一件事。

假设 Python 程序正在启动，但模型文件还没有加载完成，此时图片请求可能无法正常识别。服务因此需要提供一个让管理人员或其他程序查询的状态入口。

当前实验有两个地址：

- `/health/live`：回答“程序是否还在响应”。
- `/health/ready`：回答“模型是否完成初始化”。

但当前程序在正式开始提供 HTTP 请求之前加载模型，因此**这两个地址并不能完整展示模型加载过程中的所有状态**。这属于以后需要优化的生产可观测性问题。

### 4. 模型升级以后怎么办？

假设 OCR 模型从 small 换成 medium，业务系统最好仍能使用相同的请求地址和返回结构，而不需要各自重写接口。

所以模型服务需要明确：现在使用哪个模型版本、升级前后是否兼容、异常时怎样恢复旧版本。

当前实验提供了模型选择的配置，但**没有自动灰度发布或一键回滚平台**。不要把“知道版本管理需要什么”与“已经实现完整版本管理”混为一谈。

## 四、现在再解释两个之前突然冒出来的术语

前面我们已经认识两类工作：

- 有人决定部署哪个 OCR 模型、给它多少内存、什么时候升级。**这是管理和准备服务的工作。**
- 图片实际到达以后，程序验凭证、交给模型计算、把结果返回。**这是处理每一次请求的工作。**

在某些技术架构文档里，前者叫 **控制面（Control Plane）**，后者叫 **数据面（Data Plane）**。

先记住实际含义即可：**一个是管理模型服务，一个是执行模型请求。**

它们是认识职责的两种角度，不代表必须自建两套系统。当前实验也没有分出两套独立的控制面和数据面产品。

## 五、理解之后，再对应源码

现在有了完整故事，下面的文件才有具体意义。

| 你刚理解的事情 | 对应文件 | 看什么 |
| --- | --- | --- |
| 服务启动时准备好 OCR | [main.py:29–38](./app/main.py#L29-L38) | 模型在服务启动时初始化 |
| 具体使用哪个检测/识别模型 | [provider.py:39–55](./app/provider.py#L39-L55) | 配置 small 与 CPU |
| 业务系统把图片发过来 | [main.py:71–82](./app/main.py#L71-L82) | 接收图片、SK、检查输入 |
| 服务器忙时拒绝请求 | [main.py:83–87](./app/main.py#L83-L87) | 一次只放一个推理任务 |
| 真正执行识别并交还结果 | [main.py:88–98](./app/main.py#L88-L98) | 调用模型、组织回应 |
| 把模型结果转换成统一格式 | [provider.py:7–36](./app/provider.py#L7-L36) | 文字、位置、得分 |
| 限制服务所用计算资源 | [compose.yaml](./compose.yaml) | 为容器设置 CPU、内存上限 |

其中 FastAPI 是帮我们接收 HTTP 请求的 Python 框架；Docker 是让这个服务带着运行环境一起部署的工具。**它们不是 OCR 识别算法，也不会使识别精度天然提高。**

## 六、哪些知识不需要你跑命令？哪些必须实测？

通过现有代码，已经可以理解“请求走了哪些步骤、SK 在哪里验证、并发规则由谁制定、模型在什么时候加载”。

但**源码不能证明计划中的部署已经成功**，也不能告诉我们在 4 核 16 GiB 云服务器上实际能跑多快。

因此，只把下面几个结论留给实测：依赖与权重是否能正常加载；一张图片是否返回正确结果；服务重启后是否可恢复；给定负载下真实响应时间、成功率和资源占用是多少。

这些实测可以用 [实验 README](./README.md) 中的单次验证脚本收集。执行它是**为了检验尚未知晓的事实**，不是为了通过输入命令学习概念。

## 最终应该建立的认识

**PaddleOCR 解决“图片里是什么文字”；企业模型平台解决“如何在有限资源与安全约束下管理、交付并保障这项模型能力”；独立模型服务则是一种常见的交付方式。**

这也解释了为什么广州银行的模型平台团队要负责 OCR 部署、NPU 资源、SK 鉴权和压测：即使只有财报工具需要 OCR，这些责任也可能存在，而不需要亲自研发新的 OCR 算法。

以后换成大语言模型、轻量视觉模型，识别或生成算法会变，但“模型服务怎么提供给全行系统”这一类工程问题仍然存在。
