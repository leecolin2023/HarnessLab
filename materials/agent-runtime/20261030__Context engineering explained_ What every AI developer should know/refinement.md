## [00:00 更长的提示词解决不了糟糕的 AI 回答](https://www.youtube.com/watch?v=BBPQYtR7oUk&t=0s)

很多人遇到 AI 回答不理想，第一反应就是把提示词写得更长。这个方向不对。如果你一直在把提示词写得像作文一样长，试图让模型回答得更好，接下来的内容会介绍一种更直接的方法：利用上下文工程，让 AI 系统更聪明、更可靠。

看完这期视频，你会了解什么是上下文工程，它与单纯编写提示词有何不同，以及如何在实际项目中一步步运用。我们会用一个小型但贴近现实的 Agent 来演示，看看上下文通常会在哪些地方出问题，并介绍快速排查的方法。

## [00:47 什么是上下文工程？](https://www.youtube.com/watch?v=BBPQYtR7oUk&t=47s)

上下文工程，就是决定**模型在每一步应该看到什么，以及不应该看到什么**。这里的内容包括系统消息、工具、检索得到的事实、短期笔记、长期记忆、格式要求，以及最近的对话历史。

如果说提示词工程关注的是“如何措辞来提出要求”，那么上下文工程关注的是“为了完成当前工作，究竟向模型提供哪些信息”。

行业中的 AI 团队正在发生一个重要转变：不再只追求完美的提示词，而是精心选择数量尽可能少、信号尽可能强的 Token，引导模型采取正确行动。对于需要连续运行多轮、不断使用工具的 Agent，这一点尤其重要。

## [01:39 为什么上下文窗口越大，并不一定越好？](https://www.youtube.com/watch?v=BBPQYtR7oUk&t=99s)

现在，上下文越来越被视为一种稀缺的工作记忆资源，AI 开发者也开始以不同的方式看待它。

虽然模型的上下文窗口越来越大，但更长不等于效果必然更好。窗口被大量信息填满后，准确性可能下降：错误信息混入其中，模型被陈旧或不相关的文字分散注意力，或者两份信息悄悄相互矛盾。

Agent 的问题更加明显，因为对话记录和工具输出会随着任务推进不断累积。实际使用中，常见四种失败模式。

## [02:18 四种失败模式：污染、分心、混淆与冲突](https://www.youtube.com/watch?v=BBPQYtR7oUk&t=138s)

第一种是**污染（Poisoning）**：某个模型编造的事实进入上下文，随后被反复引用。

第二种是**分心（Distraction）**：模型过度关注庞大的历史记录，而不是根据当前情况制定新计划。

第三种是**混淆（Confusion）**：额外的无关细节把模型引向错误答案。

第四种是**冲突（Clash）**：两个信息来源互相矛盾，模型却选错了依据。

理解这四种问题的名称和表现，有助于定位故障。接下来，需要进一步区分上下文工程和提示词工程。

## [02:58 上下文工程与提示词工程有什么区别？](https://www.youtube.com/watch?v=BBPQYtR7oUk&t=178s)

提示词工程研究如何编写和组织指令、示例与约束，它仍然有用。上下文工程则研究如何在**运行时**组装模型即将看到的全部信息：恰当的工具、相关事实、必要的历史和要求的输出格式。它是动态过程，可以发生在每次模型调用之前。

可以把模型想象成只有有限短期记忆的大脑。开发者的任务是在有限空间内放入下一步真正需要的东西。

对于视频中介绍的常见模型应用，上下文栈可分为七部分：

1. **指令**：系统提示词和安全约束，尽量使用清晰、直接的语言。
2. **用户输入**：用户当前提出的要求。
3. **检索事实**：少量与当前任务最相关的材料片段。
4. **工具**：模型可以调用的函数及其说明；这些描述本身也占用上下文。
5. **短期笔记**：对最近执行步骤的概括，让模型记住刚刚发生的变化。
6. **长期记忆**：按需选取的用户或项目稳定信息。
7. **输出格式**：用 Schema 或示例限定结果的结构。

接下来用一个具体例子说明如何组织这些内容。

## [04:16 上下文栈的七个组成部分](https://www.youtube.com/watch?v=BBPQYtR7oUk&t=256s)

我们构建一个名为 **LogLook** 的简单 Agent。它负责对出现的安全告警进行初步分诊，生成一段告警摘要，并给出严重程度评分。

如果采用普通聊天机器人的方式，只告诉它“分析今天的日志，看看哪里出了问题”，它可能只能随意猜测。上下文工程的做法，是先为 LogLook 准备一份内容明确、经过筛选的输入。

## [05:02 用 LogLook 演示真实的 Agent 场景](https://www.youtube.com/watch?v=BBPQYtR7oUk&t=302s)

首先，提供系统指令：把事件总结成一段文字，并给出 **0～4 分**的严重程度评分；只能使用已提供的上下文；如果缺少数据，明确请求具体文件路径。

其次，列出它完成任务所需的工具，例如读取文件、使用 `grep` 搜索，以及查询已知误报。

第三，提供检索到的事实，但不要把全天所有日志都塞进去。只选择当天的相关日志片段，并把过去一小时内标记为 `error` 或 `critical` 的行交给 Agent。同时，提供团队记录的常见噪声告警、误报清单。

第四，提供短期笔记，例如：“已经检查过这个文件，下一步扫描另一份日志。”

最后，明确输出格式，例如要求按 JSON 结构输入和输出。

模型还是同一个模型，但上下文质量明显不同。讲者随后把上下文工程归纳为四个步骤：**Write（写入）、Select（选择）、Compress（压缩）和 Isolate（隔离）**。

## [07:00 上下文工程的四个步骤](https://www.youtube.com/watch?v=BBPQYtR7oUk&t=420s)

这四个步骤在优秀的 Agent 系统中很常见，而且容易记忆。第一步 Write，是把笔记保存到上下文窗口之外，让 Agent 可以维护一个外部工作记录，保存计划、中间结果和待解决的问题。

这样做不必每次都把所有信息重新塞进下一轮模型调用，而是在相关时再取回。

## [07:08 第一步：Write，写入外部记录](https://www.youtube.com/watch?v=BBPQYtR7oUk&t=428s)

把必要信息放在外部记录中，既能保持工作上下文简洁，又不至于丢失信息。对于 LogLook，可以维护一份“调查步骤”清单，以条目记录已经检查过的内容。

第二步 **Select（选择）**，是在当前时刻只取回真正相关的信息。可以通过检索获取本轮需要的日志片段和制度条款。在杂乱的日志场景中，结合关键词与语义的混合检索，往往比只使用 Embedding 搜索更合适。关键是筛选，而不是囤积。

## [07:50 第二步：Select，选择当前需要的信息](https://www.youtube.com/watch?v=BBPQYtR7oUk&t=470s)

例如，LogLook 只选择排名靠前的 N 组错误集中爆发记录，以及操作手册中与严重程度评分相关的章节。

第三步 **Compress（压缩）**，是保留重要信号，舍弃其他部分。可以定期把很长的对话历史概括为较短、尽量减少关键信息损失的笔记，再从较清爽的上下文继续任务。

这种方法可以保留最近几条原始记录作为核查依据，同时避免每次调用都携带庞大的完整历史。对于 LogLook，讲者建议保留最近五项发现，更早的内容归纳成三行回顾。

## [08:34 第三步：Compress，压缩历史](https://www.youtube.com/watch?v=BBPQYtR7oUk&t=514s)

第四步 **Isolate（隔离）**，是隔离不同的信息来源，减少相互干扰。大型任务可以拆成不同阶段或子 Agent，让它们分别在自己的上下文中工作，再向协调者返回简短结果。

这样可以降低工具之间的信息串扰，避免某个噪声很大的来源影响其他部分。例如，LogLook 可以由一个阅读子 Agent 提取事实、一个评分 Agent 按规则给出严重程度、一个写作 Agent 根据它们的摘要生成最终报告。

## [09:14 第四步：Isolate，隔离上下文](https://www.youtube.com/watch?v=BBPQYtR7oUk&t=554s)

如果只记住一个原则，那就是：**精心组织上下文，而不是把大量内容一股脑塞给模型。**

上下文工程不只是流行术语，它也是提示词工程向更完整的系统工程演进的自然结果。它有助于构建更稳健、可靠和实用的应用。

## [09:50 精选上下文，而不是堆积提示词](https://www.youtube.com/watch?v=BBPQYtR7oUk&t=590s)

通过管理模型每一步看到的内容，我们才能从简单聊天机器人走向能够协同工作的复杂 AI Agent。希望这期视频帮助你理解了上下文工程的运行方式，以及它与提示词工程的区别。
